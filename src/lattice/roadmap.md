# Orleans.Lattice Roadmap

Potential improvements and new features.

---

## ✅ Completed

### API

- [x] **F-001 — Range Delete (`DeleteRangeAsync`)**: Delete all keys within a lexicographic range (`startInclusive`, `endExclusive`) in a single call by walking the leaf chain and tombstoning matching entries in bulk.
- [x] **F-002 — `CountAsync` / `CountPerShardAsync`**: Return the number of live keys without streaming them across the wire. A per-shard variant aids diagnostics and load-balancing analysis.
- [x] **F-003 — `GetOrSetAsync` (conditional write)**: Set a key only if it does not already exist, avoiding a read-then-write roundtrip. The leaf grain short-circuits when a live value is present.
- [x] **F-004 — Typed value helpers**: A thin generic wrapper `ILattice<T>` and extension methods that accept serializer/deserializer delegates (or default to `System.Text.Json`) to eliminate per-caller `byte[]` boilerplate.
- [x] **F-005 — `EntriesAsync` (key + value scan)**: Stream `KeyValuePair<string, byte[]>` in sorted order, complementing the existing `KeysAsync`. Useful for exports, migrations, and analytics without a separate `GetAsync` per key.
- [x] **F-016 — TTL on `SetAsync`**: New `ILattice.SetAsync(string key, byte[] value, TimeSpan ttl, CancellationToken)` overload (with matching typed `SetAsync<T>` overloads on `TypedLatticeExtensions`) writes an entry that expires after `ttl`. `LwwValue<T>` gains an `[Id(3)] ExpiresAtTicks` field (defaults to `0` — no expiry; wire-compatible with existing persisted state) and an `IsExpired(long nowUtcTicks)` helper. The TTL is resolved to an absolute UTC `DateTimeOffset.UtcNow.Add(ttl).UtcTicks` on the silo handling the call, so per-entry lifetimes are not shifted by client-clock skew. Expired entries are hidden from every read path — `GetAsync`, `GetWithVersionAsync`, `ExistsAsync`, `GetManyAsync`, `GetOrSetAsync`, `SetIfVersionAsync`, `CountAsync`, `KeysAsync`, `EntriesAsync`, `GetLiveEntriesAsync`, and `DeleteRangeAsync` — and reaped by the existing `CompactTombstonesAsync` alongside tombstones past the configured `LatticeOptions.TombstoneGracePeriod`. The grace retention protects against a stale-clock peer resurrecting an expired entry via CRDT merge: replication paths (`GetDeltaSinceAsync`, `MergeEntriesAsync`, `MergeManyAsync`) deliberately keep expired entries visible so they propagate correctly and win LWW by timestamp. `LeafCacheGrain` also filters expired on read. `SetAsync` throws `ArgumentOutOfRangeException` when `ttl <= TimeSpan.Zero`. **TTL metadata is preserved end-to-end across every lifecycle path**: shard-split shadow-forwards (`ForwardLocalWriteToShadowIfNeededAsync` reads the raw `LwwValue` including `ExpiresAtTicks` before merging into the target shard); saga compensation rollback (`AtomicWriteGrain.PrepareAsync` resolves routing via the public-internal `ILattice.GetRoutingAsync` hook and then captures the pre-saga `LwwValue` by calling `IShardRootGrain.GetRawEntryAsync` directly on the guarded internal interface — the raw `LwwEntry` DTO never crosses the public `ILattice` surface — and `CompensatePhaseAsync` restores TTL'd entries through the TTL-aware `SetAsync(key, value, TimeSpan)` overload with `ttl = expiresAtTicks - now`; past-due entries are equivalent to "absent" and are tombstoned); and tree snapshot / restore (`TreeSnapshotGrain.CopyShardAsync` drains via a new raw `IBPlusLeafGrain.GetLiveRawEntriesAsync` and bulk-loads via `IShardRootGrain.BulkLoadRawAsync`, both of which carry the source HLC and `ExpiresAtTicks` through verbatim). The raw / bulk-load paths exchange a new `LwwEntry` DTO (alias `ol.lwe`, `[EditorBrowsable(Never)]`) that lives exclusively on guarded internal grain interfaces (`IBPlusLeafGrain`, `IShardRootGrain`) — it is never exposed on `ILattice`. Its fields are stored flat rather than embedding `LwwValue<byte[]>` as a property, because the Orleans type-alias encoder has a codec-generation race with `Task<LwwValue<byte[]>?>` grain signatures that produces malformed alias strings under concurrent cold activation.
- [x] **F-017 — Compare-and-swap (CAS)**: Optimistic concurrency via `SetIfVersionAsync(key, value, expectedVersion)` — the write succeeds only if the current entry's HLC matches, enabling safe read-modify-write patterns without distributed locks.
- [x] **F-026 — Operation status queries**: Expose `IsMergeCompleteAsync()`, `IsSnapshotCompleteAsync()`, and `IsResizeCompleteAsync()` on `ILattice` so callers can poll long-running maintenance operations without reaching into coordination grains. Returns `true` vacuously when no operation has ever been initiated; uses existing reminder-based crash recovery for fire-and-forget completion.

### Performance & Scalability

- [x] **F-006 — Leaf-side continuation filtering for `EntriesAsync`**: Pass the continuation token down to the leaf grain as an `afterExclusive` parameter so it filters entries at the source, avoiding unnecessary `byte[]` serialization across the grain boundary during forward pagination.
- [x] **F-007 — Leaf-side continuation filtering for `KeysAsync`**: Apply the same `afterExclusive` leaf-side filtering to `GetSortedKeysBatchAsync`, eliminating shard-level skip loops for key-only scans.
- [x] **F-008 — Reverse-scan leaf-side filtering**: Add a `beforeExclusive` parameter to leaf `GetKeysAsync` / `GetEntriesAsync` so reverse pagination also filters at the leaf, avoiding unnecessary serialization in `GetSortedKeysBatchReverseAsync` / `GetSortedEntriesBatchReverseAsync`.
- [x] **F-009 — Parallel shard pre-fetch for `KeysAsync`**: Double-buffer the k-way merge by pre-fetching the next page from each shard in parallel, hiding per-shard latency during ordered key scans. Controlled via `LatticeOptions.PrefetchKeysScan` or the per-call `prefetch` parameter.
- [x] **F-024 — Parallel shard pre-fetch for `EntriesAsync`** *(required F-009 ✓)*: Extends the F-009 double-buffering strategy to `EntriesAsync`, hiding per-shard grain-call latency during ordered entry scans. Controlled via `LatticeOptions.PrefetchEntriesScan` (new, default `false`) or an optional `prefetch` parameter on `ILattice.EntriesAsync` (and the typed `EntriesAsync<T>` extensions). Gated separately from `PrefetchKeysScan` because entry pages carry `byte[]` values and increase in-flight memory by `shardCount × KeysPageSize × avgValueSize` — callers opt in only when the memory trade-off is acceptable. Ordering, completeness, and scan-reconciliation semantics are unchanged; the prefetch kick-off mirrors `ShardCursor.MoveNextAsync` so `MovedAwaySlots` observed on a pre-fetched page are still consumed on the next loop iteration before any further dequeue. Regression tests: 8 `EntriesPrefetchTests` integration cases (sorted, reverse, range, reverse range, forced pagination, `prefetch: false` override, empty tree, prefetch-vs-non-prefetch parity) and one typed-extension forwarding test.
- [x] **F-013 — Internal shard hotness counters**: Volatile in-memory counters (`reads`, `writes`, `countersSince`) on `ShardRootGrain`, incremented at zero persistence cost. Exposed via `GetHotnessAsync()` returning a `ShardHotness` struct so coordinators can poll all shards in parallel. Counters reset on grain deactivation.
- [x] **F-028 — Shard map indirection**: Replaced fixed `XxHash32 % shardCount` routing with a persistent `ShardMap` mapping virtual shard indices to physical `ShardRootGrain` identities over a large fixed virtual slot space (4 096 slots). `LatticeGrain` caches the map in memory and invalidates on topology changes.
- [x] **F-030 — Route `BulkLoadAsync` through the shard map**: The streaming `BulkLoadAsync` overload resolves the per-tree `ShardMap` up-front via `ILattice.GetRoutingAsync()` and routes each entry through `ShardMap.Resolve`. The legacy `int shardCount` overload is preserved but marked `[Obsolete]`.
- [x] **F-011 — Adaptive shard splitting** *(required F-013 ✓, F-028 ✓, F-030 ✓)*: Fully-online shadow-write split: source shard continues serving reads/writes; concurrent writes to migrating slots are mirrored via `MergeManyAsync`; after a background drain, the `ShardMap` is swapped and the source enters a reject phase emitting `StaleShardRoutingException`. `HotShardMonitorGrain` triggers splits autonomically when ops/sec exceeds `HotShardOpsPerSecondThreshold` (default 200 ops/s). Because `HotShardMonitorGrain` is keyed per-tree, `MaxConcurrentAutoSplits` (default 2) bounds concurrent splits **per tree**; in a multi-tree cluster each tree has its own independent cap. Scans use per-slot reconciliation with a `HashSet<string>` deduplicator, bounded by `LatticeOptions.MaxScanRetries` (default 3), so the complete live key set is returned with no missing or phantom entries. Strict lexicographic ordering of `KeysAsync` / `EntriesAsync` output is preserved across mid-scan splits via **F-032** (in-line reconciliation-cursor injection into the k-way merge).
- [x] **F-032 — Scan ordering preservation under topology change** *(required F-011 ✓)*: `KeysAsync` and `EntriesAsync` preserve strict lexicographic (or reverse) output ordering even when a shard split commits mid-scan. Before each priority-queue dequeue, the orchestrator checks whether any live shard cursor has reported new `MovedAwaySlots` since the last reconciliation step; if so, it drains the affected virtual slots from their current owners into an in-memory buffer, sorts it with the same comparer, and injects it as an additional cursor into the same k-way merge priority queue. A post-drain final-stability check handles splits that commit after all live cursors have finished. Reconciliation is bounded by `LatticeOptions.MaxScanRetries` (default 3); the per-call `HashSet<string>` continues to suppress duplicates across pre- and post-swap views. `CountAsync` is unaffected (it reduces rather than streams). A complete stateful-cursor design for long-running exports remains tracked by F-033.
- [x] **F-027 — Leaf-grouped merge routing**: `ShardRootGrain.MergeManyAsync` groups entries by target leaf before issuing grain calls, reducing tree traversals from O(entries) to O(leaves) and collapsing multiple `WriteStateAsync` calls per leaf into one. Root-is-leaf trees fast-path the whole batch through a single grain call. Per-group re-traversal preserves correctness under mid-batch splits — distinct groups target distinct leaves, so a split produced by one group cannot re-route another group's keys (internal splits create sibling internsals but preserve child `GrainId`s; leaf splits only affect the one leaf being written to). Per-group retry on transient `OrleansException` / `TimeoutException` / `IOException` is retained; the leaf's `MergeManyAsync` is LWW-idempotent so replay is safe. No interface or wire-format changes — every caller (`ShardRootGrain`, `TreeMergeGrain`, `TreeShardSplitGrain` shadow-forward and drain, continuous merge) benefits transparently. Regression tests: `ShardRootGrainMergeManyTests` covering empty batch, root-is-leaf fast path, multi-leaf grouping, single-leaf fan-in, transient-exception retry, and non-transient propagation.

### Reliability

- [x] **F-020 — Merge trees (`MergeAsync`)**: Merge all entries from a source tree into the current tree using LWW semantics. Useful for combining snapshots, migrating data, or rejoining forked datasets.
- [x] **F-031 — Atomic multi-key writes (saga)** *(covers audit #6 — `SetMany` atomicity)*: `ILattice.SetManyAtomicAsync` routes a batch of key-value pairs through a dedicated `IAtomicWriteGrain` saga coordinator (keyed per `{treeId}/{operationId}`). The saga reads pre-saga values, applies writes sequentially, and — on any failure — compensates already-committed entries by rewriting their pre-saga values (or tombstoning previously-absent keys) with fresh HLC ticks, relying on LWW to win over the partial write. A keepalive reminder registered at saga start drives reminder-based crash recovery: on reactivation the grain consults its persisted phase (`Prepare` / `Execute` / `Compensate` / `Completed`) and resumes. Duplicate keys and null values fail fast with `ArgumentException`; post-compensation failures surface as `InvalidOperationException` with the original failure's message preserved. `SetManyAsync` (the non-atomic, parallel fan-out path) is retained and now documents its non-atomicity. Readers may observe a partial-visibility window between the first and last committed write — inherent to the saga pattern and documented in `docs/api.md`.
- [x] **F-033 — Stateful cursor / iterator grain** *(covers audit #10 `DeleteRange` pagination and #15 scan fallback; completes scan liveness story started by F-032)*: `ILatticeCursorGrain` checkpoints scan progress server-side after every page so multi-minute exports and resumable range deletes survive silo failover, client restarts, and topology changes. Exposed via `ILattice.OpenKeyCursorAsync` / `OpenEntryCursorAsync` / `OpenDeleteRangeCursorAsync` / `NextKeysAsync` / `NextEntriesAsync` / `DeleteRangeStepAsync` / `CloseCursorAsync`; the cursor grain is keyed `{treeId}/{cursorId}` and persists `LastYieldedKey` plus phase so a new activation resumes exactly where it left off. Each step is routed through the normal `ILattice.KeysAsync` / `EntriesAsync` / `DeleteRangeAsync` path, inheriting F-032 ordering preservation under concurrent shard splits. **Self-cleaning:** the grain registers a sliding idle-TTL reminder (`cursor-ttl`) refreshed on every call; if it fires without activity, the grain clears state, unregisters the reminder, and deactivates. Interval is configured by `LatticeOptions.CursorIdleTtl` (default 48h, clamped to a 1-minute floor, disabled with `Timeout.InfiniteTimeSpan`). The same retention-reminder pattern was layered onto `AtomicWriteGrain` (F-031) via `LatticeOptions.AtomicWriteRetention` (default 48h) so completed saga state does not leak indefinitely. Public DTOs (`LatticeCursorSpec`, `LatticeCursorKeysPage`, `LatticeCursorEntriesPage`, `LatticeCursorDeleteProgress`, `LatticeCursorKind`) are visible to IntelliSense as first-class public API; only the internal `ILatticeCursorGrain` is marked `[EditorBrowsable(Never)]`. Stateless `KeysAsync` / `EntriesAsync` / `DeleteRangeAsync` overloads are retained for short scans.
- [x] **F-034 — Resilient client-side scan iterators** *(complements F-033 for in-process scans)*: `ScanKeysAsync` and `ScanEntriesAsync` extension methods on `ILattice` (plus the typed `ScanEntriesAsync<T>` overloads on `TypedLatticeExtensions`) transparently recover from `Orleans.Runtime.EnumerationAbortedException` when the `LatticeGrain` enumerator is reclaimed mid-scan (idle expiry, cold start, silo failover, scale-down). The wrapper tracks the last yielded key and deterministically resumes by tightening the range bound — forward scans reopen with `startInclusive = lastKey + "\u0000"`, reverse scans reopen with `endExclusive = lastKey` — so callers see a single uninterrupted `IAsyncEnumerable<T>` with no duplicates, no gaps, and original `CancellationToken` semantics preserved. Retry budget is configurable via `LatticeOptions.ScanReconnectAttempts` (default 8) with bounded linear backoff; exhaustion rethrows the last `EnumerationAbortedException` verbatim. Callers hardening multi-minute exports against *client restart* continue to use F-033's stateful `ILatticeCursorGrain`; F-034 covers the far more common case of a single in-process scan that outlives one grain activation. Interacts cleanly with F-032's in-flight reconciliation cursors: the reopened enumerator inherits the current `ShardMap`, so a mid-scan shard split that commits during a reconnect is picked up on the next attempt without special casing. The HelloWorld sample and the chaos integration suites (`ChaosIntegrationTests`, `ChaosReshardIntegrationTests`, `ChaosResizeIntegrationTests`, `ChaosWithFaultsIntegrationTests`) all consume the resilient wrappers instead of hand-rolled retry loops. Regression tests: 13 `ResilientScanExtensionsTests` covering single-abort resume, multi-abort resume without duplicates, budget exhaustion, reverse resume, non-abort exception propagation, cancellation, null-argument guards, typed deserializer round-trip, and default-serializer forwarding. Documented in [`docs/api.md`](../../docs/lattice/api.md#scan-reliability).
- [x] **F-019 — Online (non-blocking) resize** *(required F-028 ✓)*: Fully online structural reshaping of a live tree with no read/write downtime. Delivered as three composed PRs that together form a cohesive capability — grow the physical shard count, re-tune the B+ fan-out, and lock the structural parameters into a drift-proof source of truth:

  - **F-019a — Online grow-only reshard** ([#61](https://github.com/NSTA1/Orleans.Lattice/pull/61)). `ILattice.ReshardAsync(int newShardCount, CancellationToken)` grows a tree's physical shard count online via `ITreeReshardGrain`, dispatching up to `LatticeOptions.MaxConcurrentMigrations` concurrent per-shard splits (each using its own shadow-write + swap + reject phases). Grow-only; idempotent on same target; crash-safe via reminder-anchored coordinator. Progress via `IsReshardCompleteAsync`. Interlocked against `HotShardMonitorGrain`.

  - **F-019b — Online `ResizeAsync` via shadow-forwarding** ([#62](https://github.com/NSTA1/Orleans.Lattice/pull/62)). `ILattice.ResizeAsync(int newMaxLeafKeys, int newMaxInternalChildren)` runs online. A new `ShardRootGrain` shadow-forwarding primitive (`BeginShadowForwardAsync` / `MarkDrainedAsync` / `EnterRejectingAsync` / `ClearShadowForwardAsync`, LWW-commutative by construction) lets `TreeSnapshotGrain` run a strictly-consistent `SnapshotMode.Online` drain while live traffic is mirrored to the destination physical tree. The drain merges via `IShardRootGrain.MergeManyAsync` on the destination so concurrent shadow-forward writes converge with the drain batch under LWW. `TreeResizeGrain` adds a `ResizePhase.Reject` transition, a phase-aware dual-window `UndoResizeAsync` (drain-window gated on `Phase == Snapshot`; all later phases route through after-swap recovery), and threads a `logicalTreeId` through `SnapshotWithOperationIdAsync` so the transient per-shard `StaleTreeRoutingException` at swap carries the caller's logical name. `HotShardMonitorGrain` polls `ITreeResizeGrain.IsCompleteAsync`; `ReshardAsync` rejects while a resize is running. Verified end-to-end by `ChaosResizeIntegrationTests.Chaos_resize_under_concurrent_load_preserves_all_data`. See [Tree Sizing](../../docs/lattice/tree-sizing.md#resizing-an_existing_tree).

  - **F-019c — Registry-authoritative structural sizing** ([#63](https://github.com/NSTA1/Orleans.Lattice/pull/63)). Removes the `MaxLeafKeys`, `MaxInternalChildren`, `ShardCount`, and `VirtualShardCount` knobs from `LatticeOptions` entirely so they can never silently diverge from the layout a tree was built with. Canonical defaults live in `LatticeConstants` (`DefaultMaxLeafKeys = 128`, `DefaultMaxInternalChildren = 128`, `DefaultShardCount = 64`, `DefaultVirtualShardCount = 4096`) and the per-tree values are seeded into `TreeRegistryEntry` on first tree use via `LatticeRegistryGrain.RegisterAsync` (idempotent). After seeding, the registry is the only source of structural truth: `ShardRootGrain`, `BPlusLeafGrain`, and `BPlusInternalGrain` all read through the new `LatticeOptionsResolver`, which lazy-seeds on a missing pin and otherwise returns the per-tree values verbatim. `ResizeAsync` and `ReshardAsync` remain the only mutation paths for the pinned fields, and both ship with an empty-tree fast-path that atomically updates the registry pin without activating the coordinator machinery; `ReshardAsync`'s grow-only restriction is relaxed when the tree is empty so callers who want non-default sizing (including test fixtures) simply call `ResizeAsync` and/or `ReshardAsync` on the freshly-created tree — or pre-register the pin via `ILatticeRegistry.RegisterAsync` (a new `FourShardClusterFixture.CreateTreeAsync` helper encapsulates this for integration tests). `VirtualShardCount` is now an immovable library constant because changing it would invalidate every persisted `ShardMap`. System trees (e.g. `_lattice_trees`) resolve directly from `LatticeConstants` without consulting the registry, closing the system-tree corruption surface that FX-013's monitor-fallback design left open. Pre-production breaking change: callers that previously set the removed `LatticeOptions` properties must migrate to `ResizeAsync` / `ReshardAsync` on the new tree or pre-register through the registry; FX-013's registry-first resolver, drift-throw, and "pin wins over monitor" rules are now moot.

  **Explicit boundaries (by design, not gaps).** `ReshardAsync` is grow-only on non-empty trees — shrink would require live-merging shards and is out of scope. `ResizeAsync` fan-out changes are bidirectional (grow or shrink) because the snapshot + alias-swap path rebuilds the tree regardless of direction. Split concurrency is bounded per-tree via `MaxConcurrentAutoSplits` and `MaxConcurrentMigrations`; cluster-wide aggregate admission control is tracked separately as **G-008**.
- [x] **G-011 — Caller-supplied idempotency key for `SetManyAtomicAsync`** *(pre-v3.0.0 API lock-in)*: A new `ILattice.SetManyAtomicAsync(entries, operationId)` overload (plus two matching typed overloads on `TypedLatticeExtensions`) accepts a stable caller-supplied idempotency key. The saga grain is keyed `{treeId}/{operationId}` as before, so re-submitting with the same `operationId` re-attaches to the original saga: if it has completed, the second call observes the terminal outcome (or rethrows the original compensation-surrogate `InvalidOperationException`); if it is still in flight, the call awaits the terminal state. This turns a transport-level failure (silo crash mid-call, client-side timeout) into a safe client retry. `operationId` validation rejects null / empty / whitespace and any value containing `'/'` (reserved as the grain-key separator) with `ArgumentException`. Key-set stability is enforced via a SHA-256 fingerprint over the sorted key set, persisted on first `Prepare` as `[Id(7)] AtomicWriteState.KeyFingerprint` (wire-compatible: missing field on legacy state decodes to `null` and skips the check). Re-submissions whose key set differs (added, removed, or renamed keys) throw `InvalidOperationException`; reordering keys and changing values is allowed. The default `SetManyAtomicAsync(entries)` overload is unchanged and continues to generate a fresh `Guid`. Retention semantics are unchanged: completed saga state lives for `LatticeOptions.AtomicWriteRetention` (default 48h) and is then purged, after which the same `operationId` becomes eligible for a fresh saga. Regression tests: 7 unit tests on `AtomicWriteGrain` (fingerprint stability, mismatch detection, legacy-state compatibility) and 6 integration tests on `AtomicWriteIntegrationTests` (idempotent replay, mismatched-key-set rejection, invalid-operationId rejection, typed overload). Documented in [`docs/atomic-writes.md`](../../docs/lattice/atomic-writes.md#caller-supplied-idempotency-keys) and [`docs/api.md`](../../docs/lattice/api.md).

### Observability

- [x] **F-014 — Per-shard health / diagnostics**: New `ILattice.DiagnoseAsync(bool deep = false, CancellationToken)` method returns a `TreeDiagnosticReport` with per-shard depth, live key count, tombstone count (deep mode only), hotness (ops/sec, reads, writes, window), split-in-progress and bulk-operation-pending flags, plus a bounded 32-entry ring buffer of recent adaptive-split events. Aggregation runs through a new internal, single-activation `ILatticeStats` grain keyed by logical tree id: `LatticeGrain.DiagnoseAsync` forwards to it, it fans out to every physical `IShardRootGrain.GetDiagnosticsAsync(deep)`, and coalesces repeat callers through a dual-mode (shallow/deep) cache bounded by `LatticeOptions.DiagnosticsCacheTtl` (default 5 s, `TimeSpan.Zero` disables). Shard-level depth is computed by walking `RootNodeId` via `IBPlusInternalGrain.GetLeftmostChildWithMetadataAsync`; deep tombstone counts walk the leaf chain via `IBPlusLeafGrain.GetStatsAsync`. `TreeShardSplitGrain.FinaliseAsync` pushes a best-effort `RecordSplitAsync(shardIndex, utcNow)` to the diagnostics grain as a fire-and-forget notification that also invalidates the cache, guaranteeing the next call after a topology change returns a fresh report. Per-shard RPC failures surface as empty shard entries rather than failing the whole report, so `DiagnoseAsync` is safe to call during an ongoing resize or reshard. Public DTOs (`TreeDiagnosticReport`, `ShardDiagnosticReport`, `RecentSplit`) are `readonly record struct`, `[GenerateSerializer][Immutable]`, and aliased in `TypeAliases`. Regression tests: 10 unit tests on `LatticeStatsGrainTests` (shallow/deep aggregation, dual-mode cache independence, ring-buffer capacity, cache invalidation on split, pre-cancelled token, shard-index stamping) and 7 integration tests on `DiagnosticsIntegrationTests` (empty tree, populated vs `CountAsync`, deep tombstones, depth growth after splits, cancellation fail-fast, hotness counters, cache-within-TTL identical `SampledAt`). Documented in [`docs/diagnostics.md`](../../docs/lattice/diagnostics.md) and [`docs/api.md`](../../docs/lattice/api.md).

- [x] **F-015 — Tree events (Orleans Streams)**: Metadata-only event publication on a per-tree Orleans stream, opt-in via `LatticeOptions.PublishEvents` (default `false`) and configurable via `LatticeOptions.EventStreamProviderName` (default `"Default"`). Stream namespace `"orleans.lattice.events"`, stream id = logical tree id, payload `LatticeTreeEvent` (`readonly record struct`, alias `ol.lte`) with `Kind`, `TreeId`, `Key`, `ShardIndex`, `OperationId`, `AtUtc`. Twelve kinds (`LatticeTreeEventKind`, alias `ol.ltk`): `Set`, `Delete`, `DeleteRange`, `AtomicWriteCompleted`, `SplitCommitted`, `CompactionCompleted`, `SnapshotCompleted`, `ResizeCompleted`, `ReshardCompleted`, `TreeDeleted`, `TreeRecovered`, `TreePurged`. Producers: `LatticeGrain` (per-key write events, with conditional emission on `SetIfVersion` / `GetOrSet`; `DeleteRange` collapsed to a single `{start}..{end}` event when anything was deleted), `AtomicWriteGrain` (stamps the saga's `operationId` into `RequestContext` on every phase so downstream per-key `Set` events carry the correlation id, plus a terminal `AtomicWriteCompleted`), and the four coordinator grains (`TreeShardSplitGrain`, `TombstoneCompactionGrain`, `TreeSnapshotGrain`, `TreeResizeGrain`, `TreeReshardGrain`) plus `TreeDeletionGrain` for the three tree-lifecycle kinds. Publication is fire-and-forget with log-and-swallow semantics: missing provider, serialization failures, and downstream queue exceptions never propagate to the write path. Subscribers consume via `LatticeExtensions.SubscribeToEventsAsync(ILattice, IClusterClient, Func<LatticeTreeEvent, Task>, string providerName = "Default", CancellationToken)` which returns a `StreamSubscriptionHandle<LatticeTreeEvent>` and throws `InvalidOperationException` with an actionable remediation message when the client-side provider is missing. Lattice does not register a stream provider on your behalf — opt in on both silo and client (e.g. `AddMemoryStreams("Default")` + `AddMemoryGrainStorage("PubSubStore")`). Regression tests: 4 unit tests on `LatticeEventPublisherTests` (gating, missing-provider no-throw, `OperationId` round-trip through `RequestContext`) and 5 integration tests on `EventStreamIntegrationTests` (per-key `Set`, `Delete`, `DeleteRange`, `SetManyAtomicAsync` with correlated `OperationId`, `SetIfVersionAsync` conditional emission). Documented in [`docs/events.md`](../../docs/lattice/events.md), [`docs/api.md`](../../docs/lattice/api.md), and [`docs/configuration.md`](../../docs/lattice/configuration.md).
- [x] **F-029 — External metrics / telemetry export** *(required F-013 ✓)*: Orleans.Lattice publishes `System.Diagnostics.Metrics` instruments on a single static `Meter` named `orleans.lattice` (pinned by FX-008's regression test), exposed via `Orleans.Lattice.LatticeMetrics` so OpenTelemetry pipelines subscribe once with `.AddMeter("orleans.lattice")` and receive every instrument. Eighteen instruments across five tiers: **shard-level** counters (`orleans.lattice.shard.reads`, `orleans.lattice.shard.writes`, `orleans.lattice.shard.splits_committed`) emitted from `ShardRootGrain.RecordRead` / `RecordWrite` and `TreeShardSplitGrain.FinaliseAsync` respectively; **leaf-level** histograms and counters (`orleans.lattice.leaf.write.duration`, `orleans.lattice.leaf.scan.duration` tagged `operation=keys|entries`, `orleans.lattice.leaf.compaction.duration`, `orleans.lattice.leaf.tombstones.created`, `orleans.lattice.leaf.tombstones.reaped`, `orleans.lattice.leaf.tombstones.expired`, `orleans.lattice.leaf.splits`) emitted from `BPlusLeafGrain` — a new `PersistAsync()` helper (partial file `BPlusLeafGrain.Metrics.cs`) wraps every `state.WriteStateAsync()` call with `Stopwatch.GetTimestamp()` deltas so the write histogram captures storage-provider latency from the grain boundary where I/O actually occurs, scan durations are timed around the synchronous loop body in `GetKeysAsync` / `GetEntriesAsync`, and `CompactTombstonesAsync` counts explicit-delete tombstones and TTL-expired entries into separate counters so operators can distinguish delete throughput from TTL churn; **cache** counters (`orleans.lattice.cache.hits`, `orleans.lattice.cache.misses`) emitted from `LeafCacheGrain.GetAsync` / `ExistsAsync` / `GetManyAsync`; **saga / coordinator / lifecycle** counters (`orleans.lattice.atomic_write.completed` tagged `outcome=committed|compensated|failed` from `AtomicWriteGrain.CompleteSagaAsync`; `orleans.lattice.coordinator.completed` tagged `kind=snapshot|resize|reshard|merge|compaction` from the five coordinator completion paths; `orleans.lattice.tree.lifecycle` tagged `kind=deleted|recovered|purged` emitted **unconditionally** from `TreeDeletionGrain.PublishTreeLifecycleEventAsync` so lifecycle visibility does not depend on the event stream being enabled); - [ ] **F-042 — Cluster-internal queue abstraction (`ILatticeQueue<T>`)** *(prerequisite for any future replication FIFO-queue generalisation)*: New public `ILatticeQueue<T>` primitive — a typed, **single-cluster, FIFO** queue backed by a reserved system tree under a new `LatticeConstants.QueueTreePrefix` (e.g. `_lattice_queue_`), one logical queue per coordinator grain. Surface: `EnqueueAsync(item, ct)` returning a monotonic `long` entry id; `TryDequeueAsync(ct)` returning `QueueItem<T>?`; `PeekAsync(ct)` non-destructive head read; `CountAsync(ct)` cached count; `ListAsync(ct)` ascending-id snapshot for diagnostics. Bounded variant exposes a `QueueCapacity` option with FIFO eviction on overflow (the same shape the DLQ inlines today ضد `_lattice_replog_dlq_{treeId}`). Per-item payload is `(EntryId, T)` serialised through an injectable `ILatticeSerializer<T>` (default: the same `JsonLatticeSerializer<T>.Default` the F-038 CRDT accessors use).

  **Backing model.** Each queue is one coordinator grain (`ILatticeQueueGrain<T>`, internal) over one `ISystemLattice` system tree, with rows keyed `e/{19-padded-id}` so lexicographic order matches insertion order byte-for-byte. The grain bulk-loads on activation, serves reads from an in-memory cache, and writes through to the system tree on every mutation. `_nextEntryId` is recomputed on activation as `max(stored entry-id) + 1` so monotonicity survives silo restart. Big-O: enqueue is one leaf write (O(log n) via the shard map), dequeue is one leaf read + delete (O(log n)); the cache makes `Count` / `Peek` / `List` O(1) / O(1) / O(N).

  **Known performance hazard.** Lexicographic monotonic ids concentrate every enqueue / dequeue on the head and tail leaves of a single shard, so a sustained high-throughput queue does not get the load-balancing benefit of the rest of the tree. Mitigations available out of the box: a head-cursor row that lets a steady-state dequeue reuse a single leaf rather than re-walking from the root; batched range-delete-on-rotation so trimmed ids are reaped in chunks rather than one tombstone per dequeue; documented operator guidance to scope queue throughput to "diagnostic / control-plane" rather than "primary data-plane" workloads. A non-monotonic key hash (which would spread writes across the tree but lose FIFO ordering on read) is explicitly **not** offered — FIFO is the contract, and a queue without it would be `IReadOnlyDictionary<long, T>` plus a counter.

  **Strict cluster-internal scope.** `ILatticeQueue<T>` is **not** a CRDT-replicated primitive and **never** ships an associated `LatticeMergeMode`. Two reasons: (1) destructive dequeue is fundamentally non-monotonic — under the CALM theorem any coordination-free distributed FIFO requires consensus, which is outside the library's CRDT-merge model; (2) concurrent enqueues across replicas would have to agree on offset assignments to preserve FIFO, and offset assignment does not commute even though increment of a tail counter does (a PN-counter for the tail does not solve the problem because two replicas can claim the same offset). A replicated cross-cluster log primitive — per-cluster append lanes plus an OR-set of consumed offsets, providing **at-least-once** consumption with idempotent consumers rather than exactly-once destructive FIFO — is a separate, much larger design tracked under `G-014` framing if it is ever pursued; it would more honestly be named `ILatticeReplicatedLog<T>` or `ILatticeEventStream<T>` to avoid implying destructive-dequeue semantics that CRDTs cannot deliver.

  **Existing inline implementations to consolidate.** Today the replication DLQ (`IReplicationDeadLetterGrain`, see [`docs/lattice.replication/dead-letter-queue.md`](../../docs/lattice.replication/dead-letter-queue.md)) inlines exactly this pattern — bounded FIFO over a reserved system tree with capacity-driven eviction and a `dead_letter.removed{reason=evicted}` metric on overflow. The replication WAL pending-batch shape (R-071) is a related but distinct queue-of-batches structure. F-042 promotes the DLQ's inline buffer to the typed primitive, the DLQ becomes a thin specialisation (parked-entry payload, eviction-reason tagging), and any future FIFO-shaped replication staging area builds on the same abstraction rather than introducing a third inline copy.

  **Sequencing.** Land F-042 **before** any replication-side item that would generalise the DLQ's inline FIFO behaviour (or introduce a new FIFO-shaped buffer) — the replication package then consumes `ILatticeQueue<T>` rather than re-implementing the system-tree-backed buffer. Tracked as a forward dependency in [`../lattice.replication/roadmap.md`](../lattice.replication/roadmap.md).

### Replication enablers — WAL-as-commit-point promotion (v2 commit path)

The items below promote the replication package's per-shard WAL (`IWalShardGrain`, replication R-011) to the **sole durable commit point** for the core library, with the leaf grain reduced to a materialised projection rebuilt from the WAL on activation. Together they retire the dual-write cost of "leaf `WriteStateAsync` + WAL append" that exists today (every committed mutation hits storage twice) and unlock several second-order wins: faster recovery (rebuild the projection from the trimmed WAL tail rather than scanning the leaf state), cheaper structural rewrites (resize / rebalance / compaction become deterministic log entries that every silo replays identically rather than coordinated rewrites against persisted leaf state), and a single source of truth for replication and local apply (the v2 local materialiser is just another `IChangeFeed` subscriber, indistinguishable from a remote peer modulo target).

The model has shipped under F-047 → F-052 (and F-049a–d) and is documented from the runtime perspective in [`docs/lattice/wal.md`](../../docs/lattice/wal.md). The items below are the landable work that converted the original design into shipped reality. The promotion itself (F-049) shipped in three phases: F-049b introduced the dual-durability commit on `BPlusLeafGrain` with the legacy state row still written behind a feature flag for reversible rollback; F-049d flipped the default and removed the shadow-write code path entirely in v3.4.0.

#### Design points worth pinning before implementation

- **The WAL is already the canonical mutation record.** Replication R-080 (causal+ schema) deliberately captures `OriginClusterId` (F-036), `VectorClock` (F-043), `MutationCategory` (F-045), and `TransactionId` (F-044) on every WAL entry — exactly the metadata a local materialiser needs to rebuild the leaf projection deterministically. The work below leverages those slots; it does not extend them.
- **Two HWM tables, distinct shapes.** The cross-cluster per-origin HWM (replication R-023, key `(tree, originClusterId) → HLC`) tracks remote-peer apply progress. The intra-cluster materialiser HWM (F-051) tracks local-projection apply progress per `(tree, shardIndex) → offset`. Both are first-class consumers of the WAL via `ILatticeReplicationCursorRegistry`, but they key differently because their dedupe semantics differ: cross-cluster dedupe is by `(origin, hlc)` and is necessarily HLC-shaped because remote peers do not share offset spaces; intra-cluster dedupe is by `(shard, offset)` and is necessarily offset-shaped because the materialiser walks one WAL shard at a time and offsets are dense and monotonic. The two tables coexist; neither subsumes the other. Documented up-front so a future reader does not "simplify" them into one and break either correctness invariant.
- **Structural ops stay on `WriteStateAsync()` for now.** The original design committed resize / rebalance / compaction to the WAL as `MutationCategory.Maintenance` entries that every silo replays identically. Under decision C of the F-049 design review this is **deferred** — the WAL-as-sole-commit-point flip is scoped to **leaf data only** (`BPlusLeafGrain`), and `BPlusInternalGrain` / `ShardRootGrain` / every coordinator grain keeps its existing `IPersistentState<T>` commit path. The retraction is on risk grounds, not value grounds: encoding structural rewrites as deterministic log entries requires a determinism contract enforcement surface (likely a Roslyn analyser) and a wire-format growth on `MutationKind` that would coordinate with the replication package's `LatticeMergeMode` enum, neither of which is justified before the leaf-only flip has accumulated operational evidence. Tracked as **G-015** for revisit once F-049 has shipped without incident.
- **Pre-merge delta capture, not post-merge state.** Every replication-side delta type (R-030: `LwwRegisterDelta`, `OrSetDelta`, `PnCounterDelta`, `VersionVectorDelta`) is shaped against the **author's intent** at the call site, not the post-merge state of the value. F-038's typed accessors and F-039 / F-040 / F-041 are explicitly designed this way. Carrying that discipline into the WAL means a v2 leaf projection rebuild applies the same deltas the producer authored — convergence is guaranteed by the CRDT merge function, not by replay order. F-047 lays the producer-side groundwork.
- **No new wire format.** Every item below is internal to the core library or strictly additive on existing slots. The replication wire format (R-041, alias `olr.be`, wire version 1) is unchanged.

**Recommended implementation order:** F-047 ✓ → F-048 ✓ → F-051 ✓ → F-050 ✓ → F-049a ✓ → F-049b ✓ → F-049c ✓ → F-049c.2 ✓ → F-049d ✓ → F-052. F-049 itself is split into five sequential sub-items (see entry below): F-049a lands the dormant commit-log adapter seams, F-049b introduces the dual-durability commit on `BPlusLeafGrain` with `LeafShadowWrites = true` so the legacy state row continues to be written, F-049c lands the per-shard replay coordinator + fall-off-log recovery + the F-052 digest API (which ships alongside F-049c so cross-silo divergence can be detected the moment WAL becomes the rebuild source), F-049c.2 promotes `IWalStorageProvider` from the replication package to `Orleans.Lattice` so single-cluster deployments under F-049d's flip do not need a hard reference on the replication package, and F-049d flips the `LeafShadowWrites` default to `false` and removes the legacy state row one minor later. F-047 / F-048 / F-051 / F-050 each ship dormant or behind a feature flag and are individually reversible; F-049b is the first step that observably changes commit behaviour, but `LeafShadowWrites = true` keeps it reversible until F-049d. F-052's `RebuildLeafProjectionAsync` and `GetMaterialiserLagAsync` (the rebuild and lag halves) ship as a follow-up because they only matter once the WAL is the durable source of truth.

An eagerly-registered cursor at offset `0` would pin the WAL at offset `0` indefinitely and block all GC — exactly the failure mode the registry is designed to *prevent*. The fix is **lazy registration**: the leaf calls `RegisterCursorAsync` only on the first checkpoint persist whose offset is strictly greater than `0`, and `AdvanceCursorAsync` on every subsequent flush. Pre-F-049, the projection-checkpoint persist seam (`FlushPendingCheckpointAsync`) is never driven on the foreground write path, so the cursor-report helper is unreachable and no leaf is ever registered; the WAL GC behaves exactly as it does today. (Foreground writes _do_ tick the leaf HLC for LWW timestamps, but the cursor report is gated on the projection-seam call site, not on HLC progression — the lazy `Clock > Zero` check inside the helper is defence-in-depth, not the primary protection.) Post-F-049, the first foreground-driven `Apply` advances the projection past `0`, F-051 persists the new checkpoint, and F-050 registers the cursor on that same flush. Symmetrically, a leaf grain that deactivates does **not** deregister — silo failover and idle deactivation are routine, and a deregister-on-deactivate would let the WAL GC the entries the next activation needs to replay. Cursor cardinality is bounded by the existing leaf activation density and is the same order of magnitude as the leaf grain count — well within the registry's design envelope. The per-shard WAL trim point is the `min` over every leaf cursor whose shard the registry maps to, computed by the registry's GC predicate (replication R-083).     **Incremental projection hash — O(1) digest reads, no leaf rehashing.** The original F-049c spec computed `GetLeafProjectionDigestAsync` as an on-demand XxHash128 walk over every entry in the leaf's `Entries` dictionary on every call. That cost is unacceptable for the digest's primary use case (steady-state cross-silo divergence detection under WAL-as-truth post-F-049d): a whole-tree poll would activate every leaf in every shard and rehash every entry on every call, defeating Orleans' idle deactivation and warming the entire tree on a timer. F-049c instead maintains the digest **incrementally** on the leaf state. A new `[Id(12)] byte[]? ProjectionHash` slot on `LeafNodeState` (default `null`, treated as 16-byte zero, wire-compatible with legacy state) carries an XOR fold over per-key XxHash128 contributions `H(key, hlc, isTombstone, expiresAtTicks, originClusterId, vc-fingerprint, value-or-empty)`. XOR-of-per-key-hashes is commutative and self-inverse, and XxHash128 outputs are uniformly distributed, so a single-key mutation updates the projection hash in O(1) regardless of leaf size: insert is `hash ^= H(K, V_new)`, update is `hash ^= H(K, V_old) ^ H(K, V_new)` (the V_old contribution cancels), live-to-tombstone re-stamps the same key under its new tuple. Because the contribution is a function of the **post-merge** `LwwValue`, an idempotent re-application of the same mutation is a no-op on the hash (XOR of the same value twice cancels), matching the LWW idempotence `Apply` already provides; reordered application of two commutative LWW writes converges on the same final hash because XOR is associative and commutative. The hash is persisted alongside the rest of `LeafNodeState` on every `PersistAsync()`, so a silo restart resumes from the persisted value without rebuilding it. `BPlusLeafGrain.SetCoreAsync` / `DeleteAsync` / `DeleteRangeAsync` and `ILeafProjection.Apply` all maintain the fold through a shared internal `UpdateProjectionHash(in LwwValue<byte[]>? oldValue, in LwwValue<byte[]>? newValue)` helper, so the digest is meaningful in both the foreground-commit world (today) and the WAL-replay world (post-F-049d).

    **Public surface unchanged, cost inverted.** `ILattice.GetLeafProjectionDigestAsync(shardIndex, ct)` still walks the shard's leaf chain and chains per-leaf hashes through a shard-level XxHash128, but **no leaf is rehashed** — each leaf returns its persisted `ProjectionHash` field directly. Per-leaf grain-call cost: one field read, no `Entries` enumeration, no hashing work on the leaf side. Whole-tree poll cost is `O(shardCount × leafCount)` grain calls of microsecond-scale work each, and crucially the call no longer activates cold leaves to rehash them — the digest visits exactly the leaves a normal scan would visit anyway. A future optimisation can chain leaf hashes through `IBPlusInternalGrain` so each shard returns one hash without touching leaves at all; that's an internal change behind the existing public surface. Documentation framing in `docs/lattice/projection-rebuild.md` shifts from "diagnostic only, runs on demand" to "cheap enough for steady-state monitoring, including periodic cross-silo equality canaries".

    **Determinism oracle.** A walk-the-state XxHash128 is retained **as a regression-test oracle only** (`BPlusLeafGrainTests.Projection.IncrementalHash_matches_walk_state_hash`): after random Set / Delete / Set-with-TTL / DeleteRange sequences — including pairs of operations that converge on the same final state through different intermediate orderings — the test computes a one-shot hash over the leaf's sorted entry tuples and asserts equality with the persisted `ProjectionHash`. The walk path is never invoked in production code; it exists solely to catch "running hash got out of sync" bugs in the incremental fold, providing the structural-determinism enforcement F-048 deferred without requiring a Roslyn analyser.

Incremental, ongoing merge from one or more source trees using `VersionVector` to track a per-source high-water mark, so each cycle transfers only entries newer than the last. Requires a delta-aware leaf scan (`GetEntriesNewerThanAsync(HybridLogicalClock threshold)`) and a merge-state tracking grain to persist the vector per source tree. Should replace the current full-shard drain in `TreeMergeGrain.MergeShardAsync` with a chunked or cursor-based leaf-chain iteration.

**Shared primitive with replication.** The `GetEntriesNewerThanAsync(HybridLogicalClock threshold)` leaf scan introduced by F-025 is the same primitive required by the replication package's `ISnapshotProvider` (R-050 in [`../lattice.replication/roadmap.md`](../lattice.replication/roadmap.md)) — both need a streaming, HLC-threshold-filtered scan of the primary tree. Whichever lands first, the other consumes it verbatim; do not introduce a second, parallel scan API. F-025 and replication remain otherwise orthogonal — F-025 is in-cluster tree-to-tree merge on a scheduled pull cycle, replication is cross-cluster push of a single tree to peer clusters via a commit-time WAL (R-010 / R-011). The per-source-tree HWM table introduced by F-025 is structurally compatible with replication's per-origin-cluster HWM table (R-023), differing only in key shape.

### 5 · F-055 ✅ shipped
**Reliability / high impact (delivers universal cross-leaf, cross-shard, cross-cluster atomic-batch reader isolation)**

Reader isolation during in-flight sagas. Today the consistency contract documented in [`docs/lattice/consistency.md`](../../docs/lattice/consistency.md) ("What Lattice does **not** guarantee" — *Reader isolation during in-flight sagas or range deletes*) explicitly warns that readers concurrent with `SetManyAtomicAsync` may observe a partial view of the mutation, and recommends version-guarded reads (`GetWithVersionAsync` + `SetIfVersionAsync`) as the user-side workaround. F-055 closes the carve-out with a WAL-metadata primitive that delivers cross-leaf, cross-shard, and cross-cluster strict reader isolation by construction, with no per-tree opt-in, zero leaf-state I/O on the saga prepare path, and **zero grain hops on the read path**.

**Design.** Saga prepare routes every per-key write through `BPlusLeafGrain.SetCoreAsync` / `DeleteAsync` with the mutation carrying a new `[Id(14)] bool IsPrepared` slot (default `false`, wire-compatible) and the saga's `TransactionId`. The `IsPrepared` flag is threaded into the leaf via the existing `LatticeTransactionContext` ambient (extended with an `isPrepared` field alongside `TransactionId`) so saga prepare and saga commit/abort phases reach the leaf through the same call shape as every other write — no new public method, no new grain interface parameter on the per-key write path. The leaf's existing F-049b commit pipeline appends to the per-shard WAL via `ICommitLogWriter` exactly once, then `((ILeafProjection)this).Apply` branches on `IsPrepared`: prepared mutations route into a per-leaf in-memory `Dictionary<Guid, PendingTxEntries>` rather than `Entries`. No new direct-WAL call site exists — every saga write goes through the same grain entry point as a non-saga write, so the existing F-019 shadow-forward integration applies for free during topology changes (see "Shadow-forward and topology-change integration" below). Saga commit and abort go through a new `IShardRootGrain.AppendTxTerminalAsync(Guid txid, bool committed, CancellationToken)` per touched shard — one terminal append per WAL shard the saga touched, never per-key. For a typical 16-key batch hitting 1–4 shards this is 1–4 terminal appends after N parallel prepare writes; `AtomicWriteGrain` resolves the touched-shard set up-front via `LatticeGrain.GetRoutingAsync()` and retries each terminal append on `StaleShardRoutingException` and `StaleTreeRoutingException` (matching every other public-API write — the latter covers the resize / reshard alias-swap window) so a slot that migrated between prepare and commit, or a tree alias swap that committed mid-saga, lands the terminal mark on the new owner.

**Reads do not consult any ledger grain.** Each `BPlusLeafGrain` carries the in-memory pending-tx map populated as `IsPrepared=true` mutations replay through F-049c's per-shard replay coordinator. `GetAsync` / `GetWithVersionAsync` / `ExistsAsync` / `GetManyAsync` / `KeysAsync` / `EntriesAsync` / `CountAsync` filter pending entries out of the visible projection via a local hash lookup on the read path — zero RPC, zero allocation beyond what the v3.4.0 read path already does. When the per-shard replay coordinator surfaces a `TxCommit` mutation, the leaves on that shard flip every matching pending entry into `Entries` via the existing `LwwValue<byte[]>.Merge` path; on `TxAbort`, matching pending entries are dropped. The terminal mutation is the **single linearization point for the whole batch on its WAL shard** — every leaf on that shard observes either pre-saga state for every key the saga touched on that shard, or post-saga state for every such key, never a split. Because the saga broadcasts the same terminal mark to every WAL shard it touched, the cross-shard reader observes the same atomicity property tree-wide. There is no `ITxCommitLedgerGrain` and no per-tree linearization grain on the read path.

**Shadow-forward and topology-change integration.** Both halves of the saga compose with the existing shadow-forward machinery (shard split F-011, online resize F-019b, online reshard F-019a) without any new code path:

- *Prepare during a migration window.* `BPlusLeafGrain.SetCoreAsync` is reached via the standard `ShardRootGrain.SetCoreAsync` entry, which already invokes `ForwardLocalWriteToShadowIfNeededAsync` to mirror every write to the target shard's leaf. The forward replays the mutation under its `TransactionId` and `IsPrepared=true` flag — so the target leaf appends the same prepared entry to its own WAL, runs the same `Apply`, and adds the same entry to its own pending-tx map. Source and target leaves converge on identical pending-tx state for every saga in flight during the migration window.
- *Terminal mark during a migration window.* `IShardRootGrain.AppendTxTerminalAsync` is wrapped in the same `ForwardLocalWriteToShadowIfNeededAsync` integration as `SetCoreAsync` — when the source shard is shadow-forwarding, the terminal mark also forwards to the target shard, which appends it to its own WAL. Each shard's F-049c replay coordinator independently surfaces the terminal mark to its leaves, which flip pending entries identically. Post-swap, the saga's retry-on-`StaleShardRoutingException` loop on `AtomicWriteGrain` lands any straggler terminal appends on the new owner; LWW idempotence + the leaf-side terminal-set dedup makes double-delivery a no-op.
- *Online resize and reshard.* These compose: resize wraps the entire physical-tree replacement in a shadow-forward window, and reshard composes per-shard splits with their own windows. Saga writes in flight inherit the two compositions above through every layer, so destination leaves see the same `Prepared`-then-terminal sequence and converge identically. After alias swap or shard-map swap, the destination is authoritative and the saga's continuing terminal broadcast retries onto the new owner. `ResizeAsync` and `ReshardAsync` do not need to wait for in-flight sagas to drain — atomicity holds across the boundary by construction.

**Surface and crash recovery.** No public method signature changes. Internal additions: `MutationKind.TxCommit` and `MutationKind.TxAbort` marker variants; a new `[Id(14)] bool IsPrepared` slot on `LatticeMutation` (default `false`, wire-compatible) so existing `Set` / `Delete` mutation kinds carry the prepared/committed phase without enum proliferation; `IShardRootGrain.AppendTxTerminalAsync(Guid txid, bool committed, CancellationToken)` integrated with the shadow-forward tracker; a per-leaf in-memory `Dictionary<Guid, Dictionary<string, PendingEntry>>` (txid -> key -> entry) that is **not** persisted on `LeafNodeState` — under F-049d the WAL is the sole durable record and the pending map is rebuilt deterministically by F-049c's per-shard replay coordinator on activation, alongside `Entries`. To keep the WAL retention bounded by the slowest in-flight saga rather than the F-051 checkpoint cadence, projection-checkpoint advance is gated on prepare resolution: each leaf advances `ProjectionCheckpointOffset` only up to `min(highest contiguous Apply'd offset, (min unresolved prepare offset) - 1)`, and the F-050 cursor-registry hook publishes that bounded offset to `ILatticeReplicationCursorRegistry.AdvanceCursorAsync` so the WAL GC predicate (R-083) naturally retains every prepared entry whose terminal mark has not yet replayed. A small "recently terminal" `HashSet<Guid>` on each leaf, also in-memory, is populated as `TxCommit` / `TxAbort` mutations replay and GC'd as pending entries clear under each txid; it survives only as long as the activation. Worst-case crash-recovery replay distance is bounded by the existing `LatticeOptions.MaxLeafReplayEntries` budget (default 10 000) and `LatticeOptions.AtomicWriteRetention` saga-state lifetime (default 48h) — beyond those bounds, the F-049c snapshot-then-WAL recovery path takes over. Crash recovery is anchored on `AtomicWriteGrain`'s existing persisted `AtomicWriteState`: a saga whose phase is `Prepare` or `Execute` on reactivation re-runs the commit (or compensate) broadcast — both are LWW-idempotent (re-appending the same `TxCommit` to a shard that has already seen one is a no-op via the dedup in the leaf-side terminal set). On leaf activation the F-049c replay coordinator surfaces both prepared and terminal mutations from the persisted checkpoint forward, so a fresh leaf converges to the same pending-and-terminal state every other leaf has.

**Replication interaction (universal — atomic batch ships are entirely deleted).** Prepared and terminal mutations ride the standard WAL → replication transport (R-080 / R-081 already preserve `MutationKind`, and the new `IsPrepared` slot is a strictly-additive field on `LatticeMutation` flowing through verbatim). Receiver-side leaves consume prepared and terminal mutations through the standard projection path, populate their own pending-tx map, and flip pending entries via the same local hash lookup the source-cluster leaves use. **No receiver-side coordinator grain, no staging buffer, no per-tree opt-in, no atomic-batch detection on the wire.** Cross-cluster atomic visibility is the only behaviour. Every one of the following surfaces is **deleted from the replication package in the same change set** — not deprecated, not behind a flag, not retained for backwards compatibility:

- `LatticeReplicationOptions.AtomicBatchDelivery` (the property, its default-value comment, every test that toggles it, every doc paragraph that mentions it).
- The per-tree `IReplicationTxBufferGrain` staging-buffer interface, its `ReplicationTxBufferGrain` implementation, its alias entry in `TypeAliases`, its DI registration in `AddLatticeReplication`, and every `[Id]`'d state DTO it owned.
- `IReplicationApplyGrain.ApplyManyAtomicAsync` (the receiver-side apply-mode saga that F-054 wired up) and its `AtomicApplyEntry` / `AtomicApplyResult` DTOs (`ol.aae` / `ol.aar` aliases). The point-apply seam (`ApplySetAsync` / `ApplyDeleteAsync` / `ApplyDeleteRangeAsync`) is unchanged — F-046 / R-091 still apply for non-saga writes — but the atomic-saga apply seam is removed because every prepared mutation now flows through the same point-apply path with `IsPrepared=true`.
- The bootstrap saga-blacklist set on the replication apply state, the blocked-floor HLC machinery, the `SnapshotSagaQuiesceTimeout` configuration knob, and every guard that rejected snapshot bootstrap when an atomic batch was in flight.
- Every `apply.batch.*` metric tied to the staging buffer (counters and histograms covering buffer depth, batch-flush latency, atomic-apply outcomes); the `orleans.lattice.replication` meter retains only the per-mutation counters that survive the change.
- The receiver-side atomic-batch encoder/decoder paths in `ReplicationApplier.Batch.cs` that detected `TransactionId`-grouped batches and packed them into a single `ReplicationBatchEnvelope` field. (No corresponding gRPC ship-side surface exists today — atomic-batch detection was confined to the apply-side staging buffer — so this deletion is scoped to the apply-side encoder/decoder.) The transport ships `LatticeMutation` envelopes one-by-one as before; atomic ordering is enforced at the receiver leaf via the WAL's mutation order, not by the wire framing.

After F-055 ships, `ILattice.SetManyAtomicAsync` "just works" on every tree — local single-cluster, replicated source-cluster, and replicated receiver-cluster — through the single WAL-metadata primitive, with no caller-visible flag, no opt-in, and no replication-side detection of "is this batch atomic". The R-103 chaos fixture is correspondingly tightened to the originally-spec'd "continuous reader observes either zero or all keys at every poll" invariant, asserted universally with no bounded-window caveat.

### ✅ FX-012 — `CountAsync` over-counts during concurrent shard splits *(discovered by chaos test — reliability / high, correctness)*
Fixed in two passes. **v1** added a shard-map version stability check after the `CountWithMovedAwayAsync` fan-out but still relied on each source shard filtering moved-slot keys via its persisted `SplitInProgress.Phase`. That left a race window: the split coordinator publishes the new `ShardMap` (including the target shard) before advancing the source's phase to `Reject`, so a count arriving in the window saw slot-S keys on both the source (not yet filtering) and the target (already drained) while the map version was already at its new value — the stability check passed and the over-count was returned. **v2** (this fix) routes counts through the authoritative `ShardMap` directly: `LatticeGrain.CountAsyncCore` and `CountPerShardAsyncCore` partition virtual slots by current owner via `BuildOwnedSlotMap(map)` and ask each physical shard to count only its owned slots via `IShardRootGrain.CountForSlotsAsync(sortedSlots, virtualShardCount)`. Every virtual slot is counted exactly once, against whichever shard the map identifies as its owner, independent of the source shard's per-split phase. The version stability check is retained to guard against splits committing mid-fan-out and is bounded by `LatticeOptions.MaxScanRetries`. Regression tests: `CountAsyncSplitRegressionTests.CountAsync_matches_true_live_count_after_split`, `CountPerShardAsync_matches_true_live_count_after_split`, `CountAsync_never_overcounts_during_concurrent_split`, `CountPerShardAsync_never_overcounts_during_concurrent_split` (the last two spin the public counter while driving `SplitAsync` + `RunSplitPassAsync` so every observation inside the phase-machine window is checked), plus the `Chaos_concurrent_reads_writes_scans_counts_and_splits_preserve_invariants` and `CountAsync_returns_exact_count_during_active_split` integration tests that caught the v1 gap in CI.

### ✅ FX-013 — Observe shadow-forward tasks in `ShardRootGrain` mutation paths *(reliability / low — follow-up from F-019 review)*
`ShardRootGrain` now routes every `ForwardShadowAsync` dispatch through a new `TrackShadowForward` helper (partial file `ShardRootGrain.ShadowForwardTracking.cs`) that attaches an `OnlyOnFaulted` continuation accessing `Task.Exception` — so a retry-loop iteration that abandons its forward task can never fault silently via `TaskScheduler.UnobservedTaskException`. `SetManyAsync` was reshaped from `try { local } finally { await forwardTask; }` to a local-exception-preserving pattern using `ExceptionDispatchInfo`, so a local failure is no longer masked by a concurrent forward failure. `MergeManyAsync`'s grouped path now awaits `forwardTask` at the end (previously it fell off the end of the method, leaving the forward unobserved by the caller). `ShardRootGrain` gains an `ILogger<ShardRootGrain>` primary-constructor parameter; the fault-logger continuation emits one warning per abandoned faulted forward. No public API change. Regression tests: `ShardRootGrainFx013Tests` — `SetManyAsync_surfaces_local_exception_when_both_local_and_forward_fail`, `SetManyAsync_surfaces_forward_exception_when_only_forward_fails`, `SetAsync_happy_path_awaits_forward_before_returning`, `TrackShadowForward_logs_warning_when_abandoned_forward_faults`.

### ✅ FX-014 — Rejecting precedence over IsDeleted on shard preamble *(reliability / medium, found by chaos test)*
After an online resize commits, the OLD physical tree's shards transition Reject (sets ShadowForward.Phase = Rejecting) → Cleanup (calls ITreeDeletionGrain.DeleteTreeAsync, which sets IsDeleted = true). A stale in-flight scan iterator that was routed against the old physical tree before the alias swap now correctly surfaces as StaleTreeRoutingException so the calling LatticeGrain refreshes its alias and retries against the new physical tree, rather than as the terminal InvalidOperationException("This tree has been deleted and is no longer accessible."). Fix: swapped the order of ThrowIfTreeRejecting() and ThrowIfDeleted() in ShardRootGrain.PrepareForOperationAsync. A user-initiated DeleteTreeAsync never touches ShadowForward, so for that case ThrowIfTreeRejecting is a no-op and ThrowIfDeleted still fires correctly. Surfaced by Chaos_resize_under_concurrent_load_preserves_all_data in CI: a scanner concurrent with a fast resize-driver loop landed its next page after the source shard's Cleanup phase committed, and the deleted-flavoured exception escaped both LatticeGrain.KeysAsyncCore's StaleTreeRoutingException retry and ScanKeysAsync's EnumerationAbortedException catch. Regression tests: 4 ShardRootGrainShadowForwardTests partials (Get_throws_StaleTreeRoutingException_when_rejecting_and_deleted, Set_throws_StaleTreeRoutingException_when_rejecting_and_deleted, Get_throws_InvalidOperationException_when_deleted_without_rejecting, Set_throws_InvalidOperationException_when_deleted_without_rejecting).

### ✅ G-012 — `CoordinatorGrain<TSelf>` base class + `IsIdleAsync` rename *(refactor / hygiene — no behaviour change)*
The reminder-anchored work-pump pattern shared by `TreeSnapshotGrain`, `TreeResizeGrain`, `TreeShardSplitGrain`, and `TreeReshardGrain` is now factored into a new `internal abstract class CoordinatorGrain<TSelf>(IGrainContext, IReminderRegistry, ILogger<TSelf>) : IRemindable, IGrainBase`. Derived grains supply three abstracts (`KeepaliveReminderName`, `InProgress`, `ProcessNextPhaseAsync()`) and call two helpers (`StartCoordinatorAsync()` after persisting intent; `CompleteCoordinatorAsync()` after persisting terminal state); the base class owns the 1-minute keepalive reminder, the 2-second phase grain timer (idempotent re-arm via `??=`), the reminder handler that re-arms the timer on silo reactivation or unregisters when idle, and a defensive `UnregisterKeepaliveAsync` that swallows transient storage failures on shutdown. Per-tick exceptions are logged-and-swallowed at the base so a single failed tick does not stop the pump. The signature was narrowed from the original `CoordinatorGrain<TSelf, TState>` shape in the proposal to just `CoordinatorGrain<TSelf>` because derived grains already hold their own `IPersistentState<T>` and a generic `TState` parameter would force the base to mediate persistence without adding leverage. `TombstoneCompactionGrain` was out of scope — its reminder semantics are compaction-trigger rather than keepalive and would distort the base contract. The rename `IsCompleteAsync` → `IsIdleAsync` lands on the same four internal coordinator interfaces (`ITreeSnapshotGrain`, `ITreeResizeGrain`, `ITreeShardSplitGrain`, `ITreeReshardGrain`); `IAtomicWriteGrain` and `ITreeMergeGrain` retain `IsCompleteAsync` because their semantics genuinely are per-operation completion. Breaking change at the Orleans wire level on those four internal interfaces; all callsites in `LatticeGrain.BulkLoad` / `LatticeGrain.Reshard` / `HotShardMonitorGrain` and every test harness were updated. Net ~300 lines of duplicated boilerplate removed across four grains with zero behaviour change; no public API change. The full non-chaos suite (1086 tests) remains green.

## 🔍 Gaps & Potential Additions

The following areas are not currently on the roadmap but represent meaningful opportunities, particularly as the library moves toward production adoption.

### G-001 — Leaf-level write batching (investigate before committing)
Sharding and adaptive splitting (F-011) already distribute write load across leaf grains, progressively undermining the need for in-grain write coalescing. The changes required for safe batching — `[Reentrant]` leaf grains, a `FlushAsync` drain contract for split/merge/snapshot coordinators, and an explicit `WriteMode` API to surface the weakened durability guarantee — touch almost every major system component. The failure modes (silent data loss on crash, stale state seeded into a new shard post-split) are hard to detect in tests and severe in production. Before pursuing, profile under realistic write-skew conditions with adaptive splitting active and confirm that leaf-level hotness persists after splits have stabilized. If poor key entropy is the root cause, key-design guidance is a lower-risk remedy. Only implement if profiling proves the leaf grain itself is the bottleneck.

### G-002 — Compaction policy controls
F-016 (TTL) assumes that "existing compaction infrastructure" handles expired-key reaping, but there is no roadmap item covering compaction itself as a configurable feature. Operators have no way to tune tombstone reaping thresholds, set compaction schedules, or observe space amplification (beyond the tombstone ratio in F-014). Compaction policy controls — minimum tombstone ratio before reaping, maximum leaf size before forced compaction, and a compaction telemetry hook for F-029 — warrant a dedicated item.

### G-003 — Per-key change subscriptions
F-015 targets tree-level events. Reactive patterns (e.g. cache invalidation, real-time leaderboard updates) need per-key or prefix-scoped subscriptions — closer to Redis `SUBSCRIBE` or Cosmos DB change feed. This could be layered on top of F-015 with a filter registry grain, but the routing and fan-out semantics need explicit design.

### G-004 — Value compression / encryption
There is no transparent per-tree compression or encryption of stored `byte[]` values. For storage-cost-sensitive workloads (large values, many tombstones) or compliance-sensitive data, a pluggable `IValueTransformer` pipeline applied before `WriteStateAsync` and after read would address both concerns without changing the public API surface.

### G-005 — Quota / admission control per tree
Multi-tenant deployments need a way to cap a single tree's live key count or total estimated storage size and reject writes once the cap is breached. Without this, a misbehaving tenant can starve storage for all other trees in the cluster. A `MaxLiveKeys` or `MaxEstimatedBytes` option on `LatticeOptions`, enforced at the shard level via the hotness counters already present in F-013, would be low-friction to implement.

### G-006 — Admin CLI / `dotnet` tool
All management operations (run diagnostics, inspect shard map, trigger snapshot) require in-process code or test harnesses. A `dotnet tool` wrapping the `ILatticeAdmin` surface (once F-014 lands) would lower the operational bar significantly — particularly for diagnosing concurrent split activity or stale cache behaviour described in F-022. Shard splits remain an autonomic concern — `ITreeShardSplitGrain` is guarded and not part of any planned public surface.

### G-007 — Shard-affine grain placement
Each `ShardRootGrain` is currently placed by Orleans' default random placement director. Because `LatticeGrain` is a `[StatelessWorker]` that activates on every silo, every shard call that lands on a silo that does not host the target shard's activation pays a cross-silo round-trip. A custom `IPlacementDirector` that deterministically maps each `ShardRootGrain` (by shard index) to a specific silo — stable hash of shard index across the current membership ring — would co-locate the router and the shard on the same silo for the majority of requests. Realising the full benefit also requires `LatticeGrain` to forward each fan-out leg to the shard's home silo rather than executing the grain call from the local activation. The benefit is **limited to point operations** (`GetAsync`, `SetAsync`, `DeleteAsync`, `SetIfVersionAsync`, etc.) — scans fan out to all shards by definition and pay cross-silo hops regardless of placement. The magnitude of the gain is storage-latency-dependent: against a slow backend (Azure Table Storage, Cosmos DB) the cross-silo hop is noise; against a fast local backend it can be a meaningful fraction of total round-trip time. F-029 telemetry should land first so profiling can confirm whether the hop is actually showing up before committing to the placement director design. The main implementation complication is adaptive splitting (F-011): a `ShardMap` swap changes which shard indices exist, so the placement director must either re-evaluate home-silo assignments after each swap or accept degraded affinity until shard grains naturally migrate. `[PreferLocal]` is not sufficient — it only biases initial activation and has no effect once a grain is already activated on another silo.

### G-008 — Cluster-wide split concurrency control
`MaxConcurrentAutoSplits` is enforced per-tree: because `HotShardMonitorGrain` is keyed by tree ID, each tree independently counts its own in-flight splits. In a cluster hosting many trees simultaneously, aggregate storage I/O from drain phases across all trees is unbounded — a large number of concurrent trees each with 2 in-flight splits can saturate the storage provider or silo thread pool just as effectively as a single tree with a high limit. A cluster-level admission gate (e.g. a singleton `IClusterSplitConcurrencyGrain` tracking cluster-wide in-flight count, checked by each `HotShardMonitorGrain` before triggering) would cap aggregate drain I/O independently of tree count. Low priority in single-tree or low-tree-count deployments; becomes relevant in multi-tenant or many-tree scenarios.

### G-009 — `AtomicWriteGrain` generalization to non-tree mutations
The `IAtomicWriteGrain` interface and `AtomicWriteGrain` implementation are currently tied to per-tree mutation sagas. Generalize to a lightweight `IAtomicActionGrain` that just executes a body of code atomically with respect to other grains, not necessarily tied to a tree or a saga. The caller supplies a delegate or expression tree; execution faults or retries surface as `OrleansException` or `TimeoutException` on the grain call. Supports low-infra-cost distributed locks (inherently FIFO by design) and fine-grained multi-key updates without overwriting or reading stale values. Built on lightweight grain interfaces, no new public surface on `ILattice`. Lowers the latency of F-035 (replication grain-side observer) and unblocks G-013 (observer latency telemetry).

### G-010 — Repository of point-in-time tree snapshots
Materialize and commit the in-memory tree state at a given UTC point as a persistent snapshot (folder with tree-id blob + one blob per shard). Snapshots are read-only and directly usable by `ILattice` readers (get/state/exist) at the snapshot UTC or later. New shadow-forwards and stale reads fail with `StaleTreeRoutingException` until the observation period expires (default 5 minutes); triggers an immediate `RecordSplitAsync` if a split is in progress. `TTL` and selective pruning (by shard or globally) via `ILattice.DeleteRangeAsync`, callers opt in to snapshotting via a `WithSnapshot` extension on `ILattice`, diagnostics via `SnapshotDiagnostics` in `ILatticeStats`.
`IGrainSnapshot` for low-cost materialization of arbitrary grain states (partial or full).

### G-011 — Configurable mutation semantics per tree
The current all-or-nothing mutation model (single `TreeId` + `OperationId` per `IAtomicWriteGrain`) limits flexibility. Introduce `IMutationBufferGrain` (backed by a new `MutationBufferGrain` implementation) that receives a batch of operations with per-key lock/retry/commit semantics — individual key mutations can succeed or fail independently. The buffer grain itself can be replicated or sharded as desired. Initial use case: replication staging area for F-035 observer payloads before fan-out to avoid overloading transient message queues with large bursts. Bonus: non-replicated grains (e.g. `TreeSnapshotGrain`) can use it to stage writes from in-memory to persistent without an intervening mutable grain activation.

### G-012 — Time-based lease grants for admin operations
Long-running admin operations (resize, snapshot, reconfig) risk conflicting with normal traffic (reads/writes/scans) or with themselves (concurrent admin operations) if retry loops do not observe `IsIdleAsync`. Augment `IClusterClient` with a `RequestLeaseAsync` / `ReleaseLeaseAsync` pair to control access to a named logical resource (tree id, operation id, etc.) across the cluster; the lease is granted to the first request and times out after a preset interval (default 5 minutes). Every admin operation acquires a lease at the start and releases it on completion or error, prolonging on retry. Lowers the PCI surface of F-027 (grouped merge routing) and F-031 (atomic writes) by moving the admission check to the client side.

### G-013 — Observer-latency telemetry
`IMutationObserver` (F-035) runs inline on the grain write path and is documented with prominent pitfall guidance, but operators have no direct visibility into how much latency each observer is actually contributing. Add an `orleans.lattice.observer.duration` histogram (milliseconds) to the `orleans.lattice` meter, tagged `observer=<typename>` and `tree=<treeId>`, timed inside `MutationObserverDispatcher.PublishAsync` around the per-observer `await`. Keep the existing "zero-cost when no observer is registered" guarantee by checking `HasObservers` before starting the stopwatch; the measurement callback is further elided by `Meter` when no listener is attached, so the instrument is free on the hot path for callers who do not opt in. Surfaces misbehaving observers (synchronous I/O, blocking calls) on the same OpenTelemetry pipeline as the traffic they slow down. Complements F-029's existing instrument catalog without changing its public surface. Implement alongside or after the first replication consumer (R-010) lands, so the instrument ships with a real-world validation workload.

### G-014 — WAL-as-sole-commit-point promotion (substantially shipped via F-047 → F-052) ✅
Tracked as concrete work under the **Replication enablers — WAL-as-commit-point promotion (v2 commit path)** sub-section above and substantially shipped in v3.4.0. Pre-merge delta capture landed as F-047, the leaf-projection rebuild seam as F-048, the WAL-as-sole-commit-point flip as F-049 (with the shadow-write rollback path retired by F-049d's default flip and removal in v3.4.0), the background materialiser as F-050, the materialiser-side offset-keyed HWM as F-051, and the operator surface (rebuild / digest / lag) as F-052. The shipped runtime model is documented in [`docs/lattice/wal.md`](../../docs/lattice/wal.md). The consumer-side concerns (auditing the change feed and HWM surfaces for "remote peer" assumptions, widening R-061 / R-083's GC predicates to include the local materialiser, suppressing the redundant WAL append in `ReplicationMutationObserver` when the commit-log adapter is the source) were folded into the replication package's initial release shape rather than tracked as a separate follow-on.

### G-015 — Structural ops as WAL-replayable deterministic log entries
F-049 (decision C from its design review) deliberately scopes the WAL-as-sole-commit-point flip to **leaf data only**: `BPlusLeafGrain` flips, while `BPlusInternalGrain`, `ShardRootGrain`, `LatticeRegistryGrain`, and the nine coordinator grains (`AtomicWriteGrain`, `LatticeCursorGrain`, `HotShardMonitorGrain`, `TombstoneCompactionGrain`, `TreeDeletionGrain`, `TreeMergeGrain`, `TreeReshardGrain`, `TreeResizeGrain`, `TreeShardSplitGrain`, `TreeSnapshotGrain`) keep their existing `IPersistentState<T>` commit path. The original F-048 acceptance criterion — "a manufactured leaf split is committed to the WAL and replayed across three silos with bit-identical post-state" — is **retracted** under that decision. G-015 captures the deferred work to encode structural rewrites (leaf split, internal-node rebalance, tombstone compaction, online resize, online reshard, shard-split shadow-forward) as deterministic `MutationCategory.Maintenance` WAL entries that every silo replays identically. Two prerequisites must land before G-015 becomes implementable: (1) every structural op must be **purely deterministic** (no `DateTime.UtcNow`, no random shard placement, no non-deterministic iteration order over `Dictionary<,>`); under decision C this is not enforced today because structural ops continue to commit through `WriteStateAsync()` and the silo whose foreground path runs the op publishes the post-rewrite state. (2) The `MutationKind` enum must grow at least three new shapes (`StructuralLeafSplit`, `StructuralInternalRewrite`, `StructuralCompaction`) plus a stable serialisation envelope for the per-shape payload (split key, sibling node id, parent linkage, etc.) — this is a wire-format change to `LatticeMutation` and would coordinate with the replication package's `LatticeMergeMode` enum (R-030 / R-032). The benefit of pursuing G-015 is symmetry between leaf data and structural metadata under WAL-as-truth: a silo that boots with a stale internal-tree state replays structural ops alongside data ops and converges. The cost is the wire-format growth and the determinism contract enforcement (likely a Roslyn analyser flagging non-deterministic primitives inside any method tagged `[StructuralOp]`). Defer until F-049 is in production for at least one minor version and the WAL-as-leaf-truth path has accumulated operational evidence — the decision to retract structural-op WAL replay was made on risk grounds, not value grounds, and G-015 should be revisited once the leaf-only flip has shipped without incident.

### G-016 — Operator dashboards package (`Orleans.Lattice.Dashboards`) ✅ Shipped
Operators today wire `.AddMeter("orleans.lattice")` into an OpenTelemetry pipeline and assemble Grafana panels by hand against the F-029 / F-049b / F-049c instrument catalog. That is friction at every new deployment and a drift surface — a panel hand-authored against a metric name that later gets renamed silently goes blank. Ship a new optional sibling package `Orleans.Lattice.Dashboards` at `src/lattice.dashboards/` (mirroring the `src/lattice.replication.grpc/` layout precedent) that bundles three Grafana JSON dashboards as embedded resources covering every instrument in the `orleans.lattice` meter (and, when the replication package is registered, every instrument in `orleans.lattice.replication`): an **Overview** dashboard (per-tree throughput, p50/p99 of `leaf.write.duration`, cache hit-rate, tombstone churn split by `reaped` vs `expired`, splits committed, atomic-write outcomes, coordinator completions, tree-lifecycle, event publish / drop, config changes); a **Commit Path** dashboard targeting the F-049 WAL-only commit path (`leaf.commit.duration` broken out by `step={wal|apply|observer}`, `leaf.replay.duration` tagged by recovery outcome, `leaf.replay.entries` split `applied|skipped`, projection-digest panels — the visual evidence harness for the F-049d default-flip-and-removal release and ongoing rebuild-on-activation health); and a **Replication** dashboard (ship / apply / lag durations, WAL append vs trim throughput, dead-letter queue churn, apply-FIFO violations, causal-wait histograms, fall-off-log events, peer cursor lag). Public surface: `LatticeDashboards.GetGrafanaDashboardJson(LatticeDashboardKind kind)` returning the embedded JSON as a string, plus a `LatticeDashboardKind { Overview, CommitPath, Replication }` enum. No grain, no DI registration, no runtime cost — the package is pure JSON-and-string-helper. The package ships with Grafana provisioning yaml templates (`Provisioning/datasources.yaml`, `Provisioning/dashboards.yaml`) so a host can drop the dashboards into a Grafana sidecar without hand-editing UIDs. **Drift guard.** A regression suite in `test/lattice.dashboards/` parses every embedded dashboard JSON, extracts every metric name referenced in panel `expr` strings (Prometheus PromQL), and asserts each name resolves to a live instrument on `LatticeMetrics.Meter` (and, for the Replication dashboard, `LatticeReplicationMetrics.Meter`) via a `MeterListener` snapshot — so a future rename in the core or replication package fails CI before the dashboard ships stale. Asymmetric coupling: `Orleans.Lattice.Dashboards` consumes the meter (hard reference), the meter does not depend on dashboards. v0.1.0 takes a direct project reference on `Orleans.Lattice.Replication` so the Replication dashboard always resolves; splitting that into an optional reference (so a local-only deployment can skip the replication meter entirely) is planned for a follow-up once both packages are published to NuGet. Strictly additive, non-breaking, optional package — users who want hand-rolled dashboards keep them.
