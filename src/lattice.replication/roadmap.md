# Orleans.Lattice.Replication Roadmap

Feature plan for the `Orleans.Lattice.Replication` package - a cross-cluster replication library layered on top of `Orleans.Lattice`. See the [package overview](../../docs/lattice.replication/replication.md) for the user-facing description. The `MultiSiteManufacturing` sample's pull-over-HTTP / gRPC-push pipeline is treated as the reference "what to promote, what to fix" artifact.

> **Feature IDs.** Items are numbered `R-XXX` to avoid collision with the core library's `F-XXX` space (tracked in [`../lattice/roadmap.md`](../lattice/roadmap.md)).
>
> **Package boundary.** Everything here ships in a new `Orleans.Lattice.Replication` assembly. Public API lives under `Orleans.Lattice.Replication`; internal grains/types under `Orleans.Lattice.Replication.{Area}`. The package has a single upstream dependency: `Orleans.Lattice`.
>
> **Non-goals for the initial release.** Cross-cluster Orleans cluster membership, multi-region storage provisioning, conflict UIs, user-facing admin tooling. This package is the on-the-wire replication engine only.
>
> **Scoped sub-roadmaps.** Larger work items that span multiple feature ids
> are tracked in their own scoped roadmap files alongside this one and
> graduate back into this canonical roadmap when they ship:
>
> - [`roadmap-cross-cluster-bootstrap.md`](./roadmap-cross-cluster-bootstrap.md)
>   - closes the cross-cluster bootstrap-snapshot gap (`R-150`-`R-157`):
>   ships a remote-snapshot transport seam, a gRPC binding, and the
>   receiver-side wiring needed to make the auto-bootstrap path actually
>   deliver entries across clusters.

## Compatibility with the core WAL-only commit model

The core library's WAL-only commit model shipped under **Core F-049** in v3.4.0: the WAL is the sole foreground-commit durability boundary, and the in-memory leaf projection is rebuilt from it on activation. See [`../../docs/lattice/wal.md`](../../docs/lattice/wal.md) for the core-library commit-pipeline view.

Several items on this roadmap were implemented as direct building blocks for that model. Three constraints applied across every item below, and continue to apply to net-new work:

1. **The WAL entry schema is the canonical mutation record**, not a replication-only side-car. `WalRecord` carries the operation, key, value-or-delta, HLC and origin cluster id - the same shape the core-library local-apply pipeline consumes.
2. **`IChangeFeed` (R-013) treats the outbound replication ship loop as one consumer among many.** The core-library local materialiser, secondary indexes, or projection rebuilders subscribe at the same seam without replication being installed.
3. **Per-origin HWM (R-023) is keyed `(tree, originClusterId)`, but the shape generalises to local apply.** A `null`/local origin is a valid key; the log-replay-on-activation path uses the same table without schema changes.

Where a phase item made a design choice that affects this compatibility, it is annotated *Future-compat:* below. The annotations are retained as evidence that the choice preserved compatibility with the now-shipped Core F-049 model.

## Guiding principles

Each phase below has an explicit "what the sample gets wrong" entry from the design doc it is fixing. Don't carry forward the sample's shortcuts:

- **No thread-local cycle-break.** `RequestContext["lattice.replay"]` is fragile across async boundaries - origin is durable metadata, not ambient state.
- **No ship-time value read.** Capture the mutation at commit time; readers of a replog entry never re-read the primary.
- **No post-merge LWW-by-bytes.** The wire carries CRDT deltas for recognised primitives; opaque bytes are the fallback, not the default.
- **No host-level outgoing-call filter.** Replication is produced by the grain at commit time, so value capture is atomic with the write.
- **No reminder-cadence pull for hot paths.** Push transport with backoff is the baseline; HTTP pull is retained only for bootstrap / low-frequency paths.

Preserve what the sample got right (design doc §8): per-peer HLC cursor, advance-strictly-on-ack, don't-replicate-the-replog, per-tree opt-in + per-key filter, janitor as a separate grain.

### Pre Initial Release

The replication library is functionally complete for an initial NuGet release - Phases 0 through 8 are shipped end-to-end. This section captures the release-readiness gates and known-limitation items operators should be aware of before the first published package.

**Release-blocking for GA**:

1. **R-046 ✓ shipped - Standard transport security** `[deps: R-042 ✓]`
   Shipped as a secure-by-default shared-secret authenticator. The replication package owns the transport-agnostic secret-source seam (`ILatticeReplicationSecretSource`, default env-var source, caching provider, startup hostile-config validator) and the gRPC package layers an `LatticeReplicationGrpcAuthInterceptor` + sender-side `CallCredentials` on top, refusing non-`https://` peers unless `GrpcPushTransportOptions.AllowPlaintextEndpoints` is explicitly set. mTLS remains plug-in-able via `ConfigureChannel(...)` which now runs after the package's hardened defaults so hosts can replace the credentials chain when they need stricter posture.

2. **R-073 ✓ - Azure Table Storage `IWalStorageProvider`** `[deps: R-070 ✓, R-071 ✓]`
   The only durable provider shipped today is `InMemoryWalStorageProvider`. R-070 / R-071 ship the seam, but a GA tag without at least one batteries-included durable backend forces every adopter to write their own. The Azure Table Storage layout is already pinned by the WAL design doc and exactly matches the 100-entity / 4 MB transactional-batch defaults R-071 chose. Recommend shipping as a sibling package (`Orleans.Lattice.Replication.AzureTableStorage`) so the core replication library does not pull in an Azure dependency.

**Strongly recommended for GA** (operational polish - non-blocking, but materially improves operability):

3. **R-065 ✓ shipped - Back-pressure `IHealthCheck`** `[deps: R-064 ✓]`
   First-class Kubernetes / ASP.NET Core probe target. Cheap to land; large operational payoff once a fleet is live.

4. **R-066 ✓ shipped - Observable topology** `[deps: none]`
   Today peer endpoints are read once at silo startup; runtime peer add / remove requires a host restart. Real multi-cluster operations hit this within weeks of deployment.

5. **R-062 ✓ shipped - Receiver-side flow control** `[deps: R-042 ✓]`
   Sender currently always ships `ShipBatchSize` regardless of receiver state. A struggling receiver times out instead of throttling - recovery shape is "operator restarts the silo" rather than "the system breathes".

6. **R-077 - Trim-aware `GetEntryCountAsync`** `[deps: R-070 ✓]`
   Latent dashboard / `IHealthCheck` divergence: `GetEntryCountAsync` returns `_nextOffset`, which silently inflates monitoring once R-061's GC begins trimming in production. Cheap fix; pair with R-065 so health signals stay honest.

**Known limitations to surface in the pre-GA release notes** - these are *not* gates, but users with the matching exposure should know:

- **Causal+ scope.** R-080 → R-088 deliver causal+ for the point-write, single-shard-per-mutation path. The full completeness wave (R-089 atomic multi-key writes, R-090 maintenance rewrites, R-091 shard-split / merge / saga shadow-forwards, R-092 tree-global producer VC, R-093 intra-cluster snapshot/restore) has shipped end-to-end alongside the matching core enablers (Core F-043 / F-044 / F-045 / F-046).
- **Cross-cluster atomic visibility.** Replicated atomic batches authored via `SetManyAtomicAsync` arrive on every receiver as a unit when the per-tree `LatticeReplicationOptions.AtomicBatchDelivery` opt-in is enabled (default `false`) - the receiver buffers every key of the enclosing transaction until the whole batch is in hand and applies them under one saga, advancing the per-origin high-water-mark once at completion. Phase 9 (R-094 → R-104) is shipped end-to-end alongside the matching core enabler (Core F-054 `ApplyManyAtomicAsync`). With the opt-in off, causal+ remains *strictly weaker than atomic visibility*: a remote reader concurrent with replication of a `SetManyAtomicAsync` may observe a partial view until the batch finishes converging on that peer. **Residual carve-out:** real-time receiver-side reader isolation inside the saga commit window - where a reader concurrent with the per-key sequential commit may observe a partial view - remains tracked as **core F-055**.
- **Extended CRDT modes.** Of the three follow-on dispatch items, **R-034 (MV-Register) is shipped** on top of the already-shipped Core F-039, and **Core F-040 (OR-Map) is shipped** so **R-035** is unblocked and tracked under Phase 3 below. **R-036 (RGA sequence)** is unblocked now that Core F-041 has shipped.
- **Performance follow-ons.** R-047 / R-043 / R-044 / R-045 / R-074 / R-075 / R-076 / R-078 / R-114 ✓ / R-115 ✓ / R-116 ✓ / R-117 ✓ close perf gaps documented in the WAL design doc's deferred-acceptance rows. None affect correctness; all are scheduled post-GA.

### Production hardening (must-have before any real deployment)

9. **R-060 ✓ shipped - Poison-entry DLQ**
   Closed the "first exception stalls the stream forever" hazard. Public `DeadLetterEntry` (alias `olr.dl`) + `ILatticeReplicationDeadLetters` seam (`ListAsync` / `CountAsync` / `DiscardAsync` / `ReplayAsync`); internal `IReplicationDeadLetterGrain` (alias `olr.gd`) per tree backed by reserved system tree `_lattice_replog_dlq_{treeId}` via `ISystemLattice`; `DeadLetterTrackingReplicationApplier` decorator parks the offending entry and advances the per-origin HWM past it after `MaxApplyRetries` consecutive failures on the same `(treeId, originClusterId, timestamp, key, op)` tuple. Replay path bypasses the decorator to avoid infinite re-park loops. New options `MaxApplyRetries` (default 5) and `DeadLetterQueueCapacity` (default 1000); new metrics `dead_letter.enqueued` / `dead_letter.removed` tagged `tree` + `reason`. Documented in `docs/lattice.replication/dead-letter-queue.md`. See the detailed entry under Phase 6 for full implementation notes including the forward-dependency on core `F-042` for any future FIFO generalisation.

   *Forward dependency:* the DLQ ships today with an **inline** bounded-FIFO buffer over a reserved system tree (`_lattice_replog_dlq_{treeId}`). Any later replication item that generalises this FIFO behaviour into a shared primitive - or introduces a second FIFO-shaped staging buffer alongside the DLQ - must wait for **core `F-042` (`ILatticeQueue<T>`)** to land in `Orleans.Lattice` first, then refactor the DLQ to consume it instead of re-implementing the buffer. F-042 captures the cluster-internal queue contract, the system-tree backing model, the head/tail hot-leaf hazards, and the explicit "not a CRDT-replicated primitive" scope; see [`../lattice/roadmap.md`](../lattice/roadmap.md#replication-enablers) for the full design notes. Until F-042 lands, the DLQ's inline implementation is the canonical reference and must not be duplicated elsewhere in the package.

10. **R-061 ✓ shipped - GC by min-acked cursor**
    Closed the "WAL grows unboundedly" hazard by replacing the never-implemented wall-clock-TTL janitor with a min-acked-cursor GC predicate. Public `ILatticeReplicationCursorRegistry` seam (process-local `InMemoryReplicationCursorRegistry` default) lets every change-feed consumer publish its acked HLC; public `ILatticeReplicationGc.RunOnceAsync(treeName)` walks each WAL shard for the named tree, finds the largest contiguous prefix whose entries satisfy the predicate, and asks the configured `IWalStorageProvider` to trim through that offset. Predicate is the OR of two clauses - `entry.Timestamp <= minCursor` (gated on `minCursor > HybridLogicalClock.Zero` so range-delete entries with `Zero` HLC are not flushed under an unset cursor) and `entry.Timestamp <= ttlCeiling` synthesised from the new `LatticeReplicationOptions.WalRetention` (`TimeSpan?`, default `null`, validator rejects `<= TimeSpan.Zero` when set). The scan is conservative - first non-eligible entry per shard stops the walk for that shard - because WAL offsets are dense and append-only but HLC `WallClockTicks` is mostly-monotonic-with-skew, so a stop-at-first-miss walk preserves correctness while subsequent passes pick up entries skipped this round. Per-tree `WalStorageProvider` override is honoured; falls back to the DI-registered singleton. New `WalEntriesTrimmed` counter on the `orleans.lattice.replication` meter tagged `tree`, incremented only when the pass trimmed at least one entry. New public `ReplicationCursorSnapshot` (`ConsumerId`, `Cursor`, `LastReportedAtTicks`) and `ReplicationGcReport` (`TreeName`, `MinCursor?`, `TtlCeilingHlc?`, `ShardsScanned`, `EntriesTrimmed`) record structs as diagnostic returns. Both seams registered via `TryAddSingleton` so a host can pre-register durable replacements (cross-restart cursor persistence, custom GC scheduler) before calling `AddLatticeReplication`. The library deliberately does **not** install a background timer - `RunOnceAsync` is single-pass; the host owns the cadence. Documented in `docs/lattice/wal.md`. Forward-compat: predicate is `min(cursor across IChangeFeed subscribers)` rather than `min(cursor across remote peers)`, so a future v2 local materialiser is just another consumer that pins the log under its own `consumerId`. Test coverage: 20 `InMemoryReplicationCursorRegistryTests` (Report/Get/Snapshot/Unregister, monotonic coalescing, per-tree isolation, null/whitespace/zero-cursor/cancellation guards), 12 `LatticeReplicationGcTests` (no-consumer-no-ttl no-op, trim-by-cursor, slowest-consumer-pins, multi-shard, TTL ceiling, conservative scan, empty WAL, multi-page (>256 entries), report fields, per-tree provider override, null/cancellation guards), 6 DI tests (registry + GC default registration / singleton / no-overwrite each), 4 `WalRetention` validator tests, 2 `WalRetention` options-default tests, 2 `WalEntriesTrimmed` metric tests. Full suite green: 522/522 replication tests (non-Chaos).

28. **R-047 - Typed-envelope `IReplicationTransport` shape** `[deps: R-042 ✓]`
    Eliminates the sender-side decode-then-re-encode round-trip the gRPC push transport currently pays. Today `IReplicationTransport.SendAsync` takes `ReplicationBatch` whose `Payload` is `ReadOnlyMemory<byte>`, so `GrpcPushTransport.BuildEnvelope` calls `IReplicationBatchEncoder.Decode(batch.Payload)` purely to satisfy the gRPC marshaller, which then re-encodes via `Encode(envelope, IBufferWriter<byte>)`. The decode allocates one `WalRecord` per WAL row in the batch on every send. Widen the transport seam to carry the typed `ReplicationBatchEnvelope` directly - either by adding a typed overload (`SendAsync(ReplicationBatchEnvelope envelope, string targetClusterId, CancellationToken ct)`) or by reshaping `ReplicationBatch` to carry the envelope alongside (or instead of) the byte[] payload, with a backwards-compat fallback for transports that only support bytes. After this change the gRPC hot path is genuinely zero-allocation beyond the gRPC box wrapper. LoopbackTransport / NoOpTransport are unaffected because they never re-encode.

### WAL hardening (post-critical-path)

These five items close the WAL design doc's deferred acceptance rows from R-070 / R-071. R-074 / R-075 / R-077 are independent and parallelisable; R-076 sequences after R-075; R-078 sequences after R-047 and R-076.

29. **R-074 ✓ shipped - Multi-batch in-flight flush concurrency** `[deps: R-071 ✓]`
    Closes WAL design §9.1.4. Lifts the hard-coded single-in-flight flush to `WalMaxPendingBatches` while preserving dense offsets via grain-turn-serialised offset assignment.

    - **R-079 ✓ shipped - Per-batch Azure Table partition keys with manifest-driven reads** `[deps: R-074 ✓]`
      Removes the head-pointer clobber race that R-074 documents against Azure Tables when `WalMaxPendingBatches > 1`, and lifts the per-shard write quota by spreading concurrent batches across Azure Tables partition servers. Storage layout change: each batch lands in its own Azure Tables partition keyed by `treeId|shardIndex|S{startOffset:D19}`; a per-shard manifest partition records committed batches and exposes a monotonic tail pointer. Append becomes a two-phase commit (batch transaction → manifest transaction, the latter serialised per shard); read becomes manifest-driven multi-partition fetch; reconciliation on activation closes the crash window between phases. Sequenced after R-074 so the writer-side concurrency and the storage-side parallelism land separately with clean perf attribution.

30. **R-075 ✓ shipped - Exact byte accounting in pending-batch sizing** `[deps: R-071 ✓]`
    Closes WAL design §9.1.3. Replaces the heuristic batch sizer with an allocation-free `IReplicationBatchEncoder.Measure(...)` so a 4 MB batch never overshoots the Azure Table Storage transactional-batch ceiling.

31. **R-076 ✓ shipped - `ArraySegment<byte>` provider contract for zero-copy hand-off** `[deps: R-070 ✓, R-075 ✓]`

### Causal+ completeness - full coverage of structural & atomic write paths

The R-080 → R-088 wave delivers causal+ for the point-write, single-tree, single-shard-per-mutation path. The five items below extend that guarantee to every write path the core library exposes (`SetManyAtomic`, resize, reshard / shadow-forward, snapshot/restore) so a host that enables any one of those features still gets full causal+ semantics. Each pairs with a core-side dependency (F-043–F-046) and the core change + replication consumer must land in a single feature cycle. Cross-tree causality is intentionally out of scope.

42. **R-089 ✓ shipped - Atomic multi-key VC capture point** `[deps: R-080 ✓, R-081 ✓, Core F-044 ✓]`
    Closes per-key VC drift in `SetManyAtomic`: the local vector-clock frontier is captured **once** at the start of the atomic transaction and stamped onto every emitted `LatticeMutation.VectorClock` (and through to the resulting `WalRecord.VectorClock`) in the batch with the identical frontier so a remote peer never sees a partial-set state where the writer's frontier said all N should be visible together. Receiver: no change - entries with identical VCs unblock together when their shared frontier is satisfied. Implementation: a new `[Id(11)] AtomicWriteState.VectorClock` slot persists the captured frontier on the saga's first `Prepare` (capture-once, mirroring the `KeyFingerprint` / `TransactionId` / `DeltaKind` precedent - wire-compatible: missing field on legacy persisted state decodes to `null`); a new private `StampVectorClockContext` helper on `AtomicWriteGrain` (alongside `StampOperationIdContext` / `StampTransactionIdContext` / `StampDeltaContext`) writes the persisted value back to `LatticeVectorClockContext.Current` at the head of every `RunSagaAsync` so every per-key `SetAsync` the saga issues during `Execute` reads the identical ambient and the leaf grain stamps it onto the freshly-constructed `LwwValue`. The saga-wide stamp survives crash recovery because the persisted slot is the single source of truth. Compensation rolls override the saga-wide stamp per-key with each `AtomicPreValue.VectorClock` via `LatticeVectorClockContext.With` and the saga-wide stamp is restored when each rollback's scope disposes. Regression tests: 5 `AtomicWriteGrainTests` partials (capture-once, null-default, per-key restamp, crash-replay re-stamp, no-overwrite-on-replay) and 3 `MutationObserverIntegrationTests.SagaVectorClock` end-to-end through the real cluster fixture (null when caller unset, identical VC on every per-key emit alongside identical TransactionId, no leak across calls).

43. **R-090 ✓ shipped - `MutationCategory` classification + maintenance skip** `[deps: R-080 ✓, Core F-045 ✓]`
    Resize / rebalance / compaction emits structural rewrites that are not user-authored causal events. Reading them as causal would inflate every replicated tree's VC under maintenance pressure and pollute the dependency graph. R-090 reads the `[Id(11)] Category` slot Core F-045 added to `LatticeMutation` inside `ReplicationMutationObserver` and skips the WAL append for any emit stamped `MutationCategory.Maintenance` - gate runs before mode resolution and per-key filter compilation. Independent of `OriginClusterId`.

44. **R-091 ✓ shipped - Shadow-forward VC preservation** `[deps: R-080 ✓, R-081 ✓, R-022 ✓, Core F-046 ✓]`
    Shard-split / merge / saga-compensate shadow-forward a user write into a different shard. Today F-036's `LatticeOriginContext` carries `OriginClusterId` through these rewrites; R-091 extends the same end-to-end discipline to `VectorClock`. The replication observer never re-captures a VC for any emit whose ambient context already supplies one. Receiver-side: a small `RecentApplyCache<(origin, hlc, key, op)>` LRU (default `4096`, new `ShadowForwardDedupeCacheSize` option) drops the duplicate emit pair shadow-forward generates so the receiver applies the shadow-forwarded write exactly once.

45. **R-092 ✓ shipped - Tree-global producer VC at commit time** `[deps: R-080 ✓, R-081 ✓]`
    R-080 captures VC at the per-grain commit-time observer site, but a single user write touching multiple shards (range delete, multi-leaf saga) emits from multiple grains in close succession; if each grain reads its own diagonal-only HWM the resulting per-emit VCs disagree on cross-shard origins. R-092 introduces a per-`(silo, tree)` in-memory `LocalVectorClock` cache populated from `IReplicationHighWaterMarkGrain.GetVectorAsync` on cold start, advanced on every WAL append (local origin) and every inbound apply (foreign origin). Producer reads from the cache; cost is one grain call per (silo, tree, restart). The cache is the producer-side counterpart to R-081's receiver-side `LocalVectorClock`.

46. **R-093 ✓ shipped - Snapshot/restore VC reconstruction** `[deps: R-080 ✓, R-081 ✓, Core F-043 ✓]`
    Closes the intra-cluster snapshot-as-a-tool gap: when an operator snapshots a tree and restores it (same cluster, possibly different timestamp) the live HWM table is wiped but the values still carry their commit-time VC slot (Core F-043). R-093 introduces an `IReplicationLocalVcSeeder.SeedFromTreeAsync(treeName)` that walks the restored values' VC slots and seeds `LocalVectorClock` to per-origin pointwise max. Without this, a restore-then-replicate cycle would replay every restored entry against a zeroed VC and either re-park or re-merge them. Cross-cluster bootstrap (R-050 / R-084) is unaffected - that path pins the snapshot's `causalStableFrontier` directly via `PinSnapshotAsync`.

### Atomic visibility cross-cluster - closing the carve-out R-089 deferred

The R-080 → R-093 wave delivers causal+ for every write path the core library exposes. Causal+ pins the dependency graph, but it is **strictly weaker than atomic visibility**: a remote reader concurrent with replication of a `SetManyAtomicAsync` may observe a partial view (some keys arrived and applied, others have not) until every entry in the batch finishes converging on that peer. R-089's retrospective explicitly flagged this as a follow-on. The eleven items below close it via a receiver-side staging buffer that holds every key in an in-flight atomic batch until the whole batch is in hand and then applies them under a single saga that preserves source-side metadata verbatim. Per-tree opt-in via `AtomicBatchDelivery` (default `false`); operators trade extra latency and a partially-buffered batch's GC pin against the stronger visibility guarantee. Cross-tree atomicity is intentionally out of scope (one batch is one tree).

### Automatic Merkle-based drift remediation (additive on top of the digest chain)

Today digests are an **observability surface** - a `digest_mismatch` alert tells an operator that two clusters diverged but provides no automatic repair path. The core library ships an additive Merkle-style chained digest (shard → internal nodes → leaves, each with a versioned `LeafProjectionDigest`), so cross-cluster reconciliation can localise drift to a small key range without scanning the entire keyspace. The opt-out latch on the core side guarantees that once digest maintenance has been disabled on a tree, the persisted aggregate cannot silently be trusted by a future remediation pass - the tree must be opted back in via a deliberate rebuild before any of the items below engage with it. The work is **purely additive**: no public surface area on the core library changes, no wire-format bump on the replication channel, and every step degrades to "do nothing" when either side advertises an incompatible `LeafProjectionDigest.Version`.

58. **R-105 - Peer digest probe RPC + scheduler** `[deps: R-042 ✓, R-066 ✓, Core F-053 ✓]`
    A low-frequency (default: 5 min, jittered) per-peer scheduler that calls `ILattice.GetLeafProjectionDigestAsync(shardIndex)` on the local cluster and over the existing push transport on each remote peer, for each replicated tree. Emits `replication.digest_probe.mismatch{tree,shard,peer}` and `replication.digest_probe.compared{tree,shard,peer,outcome}` counters. Respects the core opt-out: trees with `MaintainProjectionDigest = false` (including the system-tree default) are skipped; trees whose registry latch is set are skipped permanently. Version-skew (`local.Version != remote.Version`) records `outcome=version_skew` and does not raise a mismatch.

59. **R-106 - Merkle-walk drift localisation** `[deps: R-105]`
    When R-105 reports a shard-level mismatch, walk the internal-node tree top-down using `IBPlusInternalGrain.GetChildDigestSnapshotAsync` (already wire-stable from the digest chain) to localise the divergence to a single leaf or small set of leaves. Caps recursion depth and total bytes inspected per probe to avoid pathological cases; emits `replication.merkle_walk.localised{tree,depth}` and `replication.merkle_walk.aborted{reason}` counters. Strictly read-only - no repair attempt at this stage.

60. **R-107 - Targeted leaf re-replay from WAL** `[deps: R-106, R-082 ✓, R-097 ✓]`
    For each divergent leaf identified by R-106, ship the relevant key range from the local WAL to the remote peer using the existing causal+ apply pipeline (R-082 / R-097), so the repair travels through the same TX-aware causal-stable apply path as ordinary replication and respects atomic-batch boundaries. Producer-side selection uses the per-leaf `[FirstKey, LastKey)` covering range plus the diverged peer's HLC cursor to bound what gets re-sent. Falls back to "operator-only alert" if the WAL has been GC'd past the divergence point - a follow-up bootstrap-snapshot remediation belongs in R-109.

61. **R-108 - Rate-limit, circuit breaker, and operator override** `[deps: R-107]`
    Per-tree and per-peer caps on remediation traffic (default: 1 % of `ShipBatchSize` budget). Circuit breaker that disables automatic remediation for a tree after N consecutive failures and surfaces a `digest_remediation.disabled{tree,peer,reason}` gauge. Operator opt-in flag (`ReplicationOptions.AutoRemediateOnDigestMismatch`, default false for the first release) so the feature ships dark and is opted in per-deployment after operators have observed the probe signals from R-105.

62. **R-109 - Bootstrap-snapshot fallback for GC'd divergence** `[deps: R-107, R-050 ✓, R-051 ✓]`
    When R-107 can't reach the divergence point because the WAL has been trimmed, fall back to a scoped bootstrap snapshot of only the divergent leaf range using R-050 / R-051's existing snapshot machinery. Snapshot scope is bounded to the leaves identified by R-106 to keep the repair cost proportional to the drift, not to the tree.

63. **R-110 - End-to-end remediation chaos test** `[Category("Chaos")]` `[deps: R-105, R-106, R-107, R-108, R-109]`
    Three-node cluster with controlled drift injection (skipped writes, corrupted apply, partition-then-heal). Asserts that probes detect the mismatch within 2 × scheduler interval, Merkle walk localises within depth ≤ `log_k(N)` for fan-out `k`, and remediation closes the gap within the configured budget. Verifies the system-tree default-off and registry-latch paths short-circuit cleanly with zero remediation traffic.

64. **R-111 - Documentation + operator playbook** `[deps: R-110]`
    New `docs/lattice.replication/automatic-drift-remediation.md` covering the feature stack, default-off posture, opt-in path, metrics surface, and the failure-mode matrix (version skew, WAL-trimmed divergence, circuit-breaker tripped). Updates `docs/lattice/projection-rebuild.md` to cross-link from the digest opt-out section so an operator who disables digest maintenance is told what they lose.

  Per-shard write-ahead log (`IWalShardGrain` keyed by `{treeId}/{shardIndex}`) is the single source of truth for replication. Mutations append-then-apply (not apply-then-best-effort-append); the WAL-append is the commit point. `WalRecord` carries op + full value *or* typed delta. Removes the sample's read-amplification (`primary.GetAsync(origKey)` in `ShipOneBatchAsync`) and the "writes coalesced between append and ship collapse silently" / "false-delete on intervening delete" data-loss bugs.
  *Future-compat:* the grain shape, dense sequence numbers, and `WalShardSequencedEntry` envelope are reusable as the v2 commit-point WAL (future C-020/C-030). The leaf grain still persists today; promoting the WAL to *the* commit point is a future change to the core lib's commit path, not a wire format change here.

- [x] **R-012 - Per-tree opt-in and per-key filter**
  `LatticeReplicationOptions.ReplicatedTrees` (names) + `LatticeReplicationOptions.KeyFilter` (`Func<string, bool>` or declarative prefix set) - parity with the sample's `mfg-part-crdt` label-only split. The filter runs on the *producer* side so non-replicated mutations never touch the WAL. Filters are precompiled per tree id and cached on the `IMutationObserver` (`ConcurrentDictionary<string, CompiledFilter>` invalidated via `IOptionsMonitor.OnChange`) so the commit-time hot path is a dictionary lookup, a single bool, and at most one delegate plus a linear prefix scan.
  *Future-compat:* in the v2 WAL-only model the WAL must capture every mutation regardless of replication scope (because storage materialisation reads it too). Implement the filter as a *replication consumer* predicate, not a producer-side gate, so a future local materialiser sees every entry. The current "non-replicated mutations never touch the WAL" wording stays accurate for today; it becomes "non-replicated mutations are not shipped" under v2.

- [x] **R-013 - `IChangeFeed` public surface**
  Subscriber API for in-process consumers (tests, bridges, custom transports): `IChangeFeed.Subscribe(treeName, cursorHlc)` returning `IAsyncEnumerable<WalRecord>`. The outbound ship loop in later phases is one consumer among many.
  *Future-compat:* this is the seam future C-050 (background materialiser) subscribes to. Keep the contract pure-pull, cursor-driven, and free of replication-specific assumptions (no peer id, no transport-shaped acks). A `Subscribe` parameter for "include locally-originated entries" must default to `true` - the materialiser needs them.

- [x] **R-014 - Strict-only commit semantics**
  WAL failures propagate. A failure inside `IReplogSink.WriteAsync` flows back out of the commit-time observer and surfaces to the caller of `ILattice.SetAsync` / `DeleteAsync` / `DeleteRangeAsync` as the same exception the underlying storage provider threw - guaranteeing every committed mutation is also captured for replication. There is intentionally no opt-in "best-effort" mode that would let the primary write report success while silently dropping the change-feed record; silent change-feed drops are exactly the hazard commit-time capture exists to remove. A host that needs different semantics for a specific tree should compose its own `IMutationObserver` rather than configure correctness away.
  *Future-compat:* this matches the v2 commit semantics (C-030: WAL append = commit) - no behaviour change required when the WAL becomes the sole durability mechanism.

## 🔲 Phase 2 - Origin-stamped HLC + idempotent apply *(design §1b, §2, §5)*

Makes cycle-break durable, enables exactly-once apply, unlocks transitive topologies (A → B → C).

- [x] **R-020 - Origin cluster id in mutation metadata**
  New `[Id]` slot on `LwwValue` / `LwwEntry` for `OriginClusterId` (string, default `LatticeReplicationOptions.ClusterId`). Wire-compatible: missing field on legacy state decodes to `null` and is treated as "local". The field is authored once at commit time (R-010) and propagates through every merge / drain / snapshot path. Delivered through two co-ordinated layers: the core library's F-036 added the `[Id(4)]` slot on `LwwValue<T>`, the `[Id(5)]` slot on `LwwEntry`, the `[Id(8)]` slot on `LatticeMutation`, and the public `LatticeOriginContext` ambient (`Current` getter/setter + scoped `With(string?)`) that grain write paths read at the HLC-tick site to stamp the field via `with { OriginClusterId = ... }` - preserved end-to-end through shard-split shadow-forward, saga prepare/compensate, tree snapshot/restore, bulk-load, merge, and tombstone compaction. The replication package's `ReplicationMutationObserver` substitutes the validated local `LatticeReplicationOptions.ClusterId` whenever the incoming `LatticeMutation.OriginClusterId` is `null` (local-origin) and forwards the existing origin verbatim otherwise (remote replays), so every emitted `WalRecord.OriginClusterId` is non-`null` for replicated mutations and remote-origin writes never loop back stamped as local. Regression tests covering R-020 specifically: 3 `ChangeCaptureIntegrationTests` additions exercising `SetAsync` / `DeleteAsync` / `DeleteRangeAsync` under `LatticeOriginContext.With(remoteId)` and asserting the resulting `WalRecord.OriginClusterId` is the remote id, not the local cluster id - the cross-package end-to-end cycle-break check that closes the loop on F-036's per-grain stamping and the observer's preserve-or-substitute branch.

- [x] **R-021 - Durable origin-based cycle-break**
  Outbound ship filters WAL entries where `OriginClusterId == self`. Replaces the sample's `RequestContext["lattice.replay"]` thread-local. Robust across async boundaries, streams, saga compensations, and any apply path that doesn't originate from the inbound call chain. **Implemented:** `ChangeFeed.ReadSinceAsync` accepts `includeLocalOrigin: false` (the default), filtering entries whose `OriginClusterId` equals the local cluster id before they are shipped. Covered by `ChangeCaptureIntegrationTests` (cycle-break end-to-end) and `ChangeFeedTests` (filter unit tests).

- [x] **R-022 - Preserve source HLC on apply**
  Receiver stores `SourceHlc` (not a locally-stamped fresh HLC) in the entry's metadata. Enables transitive replication - B → C can propagate an A-origin write with A's HLC intact - and deterministic resolution for any vector-clock-based conflict scheme. **Implemented:** new internal `IReplicationApplyGrain` (core lib) routes `ApplySetAsync` / `ApplyDeleteAsync` through `IShardRootGrain.MergeManyAsync`, persisting the `LwwValue<byte[]>` with the caller-supplied HLC and origin cluster id verbatim. `ApplyDeleteRangeAsync` wraps the per-shard fan-out in a `LatticeOriginContext.With(originClusterId)` scope so range observers publish the remote origin and the outbound filter excludes the resulting WAL rows. Receiver-side `IReplicationApplier` (replication package) is the public seam the transport layer calls. Covered by `LatticeGrainReplicationApplyTests`, `ReplicationApplierTests`, and `ReplicationApplyIntegrationTests` (HLC round-trip, origin round-trip, cycle-break cross-package).

- [x] **R-023 - Per-origin high-water-mark table**
  Receiver-side `{(tree, originClusterId) → lastAppliedHlc}` persistent map. Inbound apply checks HWM before merging; re-delivery of `(origin, hlc)` is a no-op. Turns at-least-once delivery into at-most-once apply - required for correctness under typed CRDT counters/sets (phase 3).
  *Future-compat:* the `(tree, origin)` key shape generalises to v2 C-040: a local-origin row tracks the materialiser's apply progress and a remote-origin row tracks each peer. Keep the table and its grain interface neutral about who writes which row; do not assume `originClusterId != self`. **Implemented:** new internal `IReplicationHighWaterMarkGrain` keyed `{treeId}/{originClusterId}` with `GetAsync` / `TryAdvanceAsync(candidate)` (monotonic) / `PinSnapshotAsync(value)` (unconditional). `ReplicationApplier` consults `GetAsync` before every Set/Delete apply and short-circuits (`Applied=false`) when `entry.Timestamp <= hwm`; advances via `TryAdvanceAsync` after a successful apply. Range deletes bypass the HWM (idempotent at the leaf layer because they carry `HybridLogicalClock.Zero`). Covered by `ReplicationHighWaterMarkGrainTests`, `ReplicationApplierTests` (dedupe), and `ReplicationApplyIntegrationTests` (per-tree / per-origin isolation).

- [x] **R-024 - HWM-driven snapshot integration point**
  The HWM table is the handoff contract for the bootstrap protocol (phase 5): a newly-bootstrapped peer starts incremental replication from `hwm[(tree, origin)]` and the HWM guarantees the handoff is exactly-once across the snapshot/incremental boundary. **Implemented:** the `PinSnapshotAsync(HybridLogicalClock)` operation on `IReplicationHighWaterMarkGrain` is the explicit handoff seam - phase 5 bootstrap will pin the snapshot frontier (which may be lower than the current HWM if a remote peer rewinds to a snapshot) and then resume incremental replication from that pinned frontier. Unconditional overwrite is intentional: the snapshot defines the apply point, not the receiver's prior progress. Covered by `ReplicationHighWaterMarkGrainTests` (`PinSnapshotAsync_overwrites_unconditionally`, `PinSnapshotAsync_can_lower_high_water_mark`) and `ReplicationApplyIntegrationTests` (`HighWaterMarkGrain_pin_snapshot_overwrites_unconditionally`).

## 🔲 Phase 3 - Typed CRDT deltas *(design §1a)*

The real CRDT payoff - active-active convergence for the primitives the library ships, rather than cross-cluster LWW-on-bytes that silently loses concurrent set adds / counter increments.

This phase deliberately reorders the two items below from the design doc's narrative order. The original sequencing assumed the producer could *infer* a delta type from the value; in this codebase every value is an opaque `byte[]` (the core lib ships no typed CRDT value surface), so inference is impossible. The mode is declared, not detected - and that declaration has to land *before* the dispatch wired on top of it. R-032 therefore becomes the gate; R-031 plugs into it.

- [x] **R-030 - Delta contract for core primitives**
  Typed delta records for each replicable primitive the core library ships: `LwwRegisterDelta` (value + HLC + origin), `OrSetDelta` (adds + removes with dot context), `PnCounterDelta` (per-replica +/- increments), `VersionVectorDelta` (vector merge). Each is `readonly record struct`, `[GenerateSerializer][Immutable]` with a stable `[Alias]` constant in a new `ReplicationTypeAliases` class.
  *Future-compat:* these delta types are the v2 commit payload (C-010). The contract - produced by the core lib, consumed by replication - is identical in v1 and v2; the only change in v2 is that the local apply path also consumes them rather than writing through the leaf state directly.

- [x] **R-032 - Mandatory replication-mode declaration *(no implicit opaque-bytes)***
  Replicated trees must declare a `LatticeMergeMode` at configuration time; there is no implicit fallback that silently picks LWW-on-bytes for an undeclared tree. The declaration converts the previously-implicit "what convergence rule applies here?" question into a config-time decision the validator surfaces, eliminating the silent-data-loss footgun where two clusters could concurrently update the same opaque-byte key and one side's update vanished without an error, log line, or metric. **Implemented:** new public `LatticeMergeMode` enum (`LwwRegister`/`OrSet`/`PnCounter`/`VersionVector`, full set reserved up-front for wire-format stability); `LatticeReplicationOptions.ReplicatedTrees` reshaped from `IReadOnlyCollection<string>?` to `IReadOnlyDictionary<string, LatticeMergeMode>?` (`null` and empty both mean "no trees replicate" - the previous "`null` ⇒ everything" default is removed); new public `ILatticeMergeModeResolver` seam with the default options-backed `ConfiguredLatticeMergeModeResolver` cached per tree id and invalidated on `IOptionsMonitor.OnChange`; new `[Id(9)] WalRecord.Mode` slot stamped by the commit-time observer (default `LwwRegister` so legacy persisted state decodes safely); `LatticeReplicationOptionsValidator` rejects null-or-empty keys in the `ReplicatedTrees` map and rejects every declared mode other than `LwwRegister` (with a "typed-primitive surface lands in F-038/R-031" error message); `ReplicationMutationObserver` routes every mutation through the resolver and short-circuits before the sink when the resolver returns `null`. The `Orleans.Lattice.Replication` and `Orleans.Lattice.Replication.Tests` projects build with zero warnings; 302/303 replication tests pass (the one failure is a pre-existing `wal-design.md` hygiene check unrelated to this feature) and all 1432 core tests pass. Covered by `ReplicationModeTests` (wire-stable underlying values), `ReplicationModeResolverTests` (cache, options-change invalidation, null-tree-id guard, dispose), the migrated `ReplicationMutationObserverTests` (mode-resolver gate, `Mode` stamping on every emitted entry, replaces the old "tree allowlist" branch), and `LatticeReplicationOptionsValidatorTests` (null/whitespace key rejection + non-`LwwRegister` mode rejection per enum value).

  **Public surface:**
  - `LatticeMergeMode` enum with members `LwwRegister`, `OrSet`, `PnCounter`, `VersionVector`. The full set is reserved up-front so adding a typed-primitive mode in a later phase is not a wire-format break.
  - `LatticeReplicationOptions.ReplicatedTrees` is reshaped from `IReadOnlyCollection<string>?` to `IReadOnlyDictionary<string, LatticeMergeMode>?`. Membership and mode are co-declared - there is no second "modes" dictionary that can drift out of sync with the membership set. `null` and empty both mean "no trees replicate" (the previous "`null` ⇒ everything replicates" default is removed because it is itself a footgun: misconfiguring a host accidentally replicates every tree it owns).
  - `ILatticeMergeModeResolver` (public, silo-side service) - returns the resolved `LatticeMergeMode` for a given `treeId`, or `null` when the tree is not configured for replication. Cached per tree id; invalidated on `IOptionsMonitor<LatticeReplicationOptions>.OnChange`.
  - `WalRecord.Mode` (new `[Id(9)]` slot) - the wire-side dispatch tag that R-031 reads on the receiver. Stamped at commit time from the resolved mode so transitive paths (A → B → C) preserve the originating mode end-to-end. Default value is `LwwRegister` so legacy persisted state without the field decodes safely.

  **Validator gate:**
  - Reject any null-or-empty key in the `ReplicatedTrees` map.
  - Reject every declared mode other than `LwwRegister` in this phase, with a clear "the typed-primitive value surface lands in F-038 / R-031" error message. Reserving the enum members early means R-031 just relaxes this rule - no wire-format or option-shape change.
  - Continue rejecting empty `ClusterId` and non-positive `ReplogPartitions` (existing rules).

  **Producer behaviour:**
  - The commit-time observer resolves the mode via `ILatticeMergeModeResolver` for the mutation's tree; an undeclared tree is skipped (same shape as the previous "tree not in allowlist" branch). A mutation against a declared tree whose mode resolves to `LwwRegister` continues to emit today's `byte[]`-based `WalRecord` shape, now stamped with `Mode = LwwRegister`. Other modes are unreachable until the validator relaxation in R-031 + F-038 ships the typed primitive surface that makes the other modes reachable from user code.

  **`LwwRegister` mode framing:**
  - `LwwRegister` is the explicit, opt-in successor to the old implicit opaque-bytes path. Its convergence semantics ("two clusters concurrently updating the same key resolve to the higher `(HLC, originClusterId)` pair; the loser's update is silently dropped") are documented prominently in both the XML doc and the validator error path so any user picking it sees the trade. The mode is correct under single-writer-per-key discipline (the dominant Lattice usage) and is genuinely the right answer for keys with overwrite-with-latest semantics; what it is *not* is a silent default a user can land on without choosing it.

  *Future-compat:* in v2 the local materialiser also dispatches on `Mode`, so adding the field here keeps the WAL entry schema canonical for both today's replication consumer and tomorrow's local-apply consumer. The resolver's `(treeId) → mode?` shape generalises to the local-origin row that v2 needs.

  **Shipper grain (`IReplicationShipperGrain`, key `{treeName}/{peerClusterId}`).** Cluster-singleton; hybrid `IRemindable` (90 s liveness backstop) + `IGrainTimer` (200 ms steady-state pulse) + writer-side doorbell from `ShardedReplogSink.WriteAsync`. The pump loop drains `IChangeFeed.Subscribe(treeName, cursor, includeLocalOrigin: true)`, applies the producer-side filter chain (`KeyFilter`, `KeyPrefixes`, and the durable origin-based cycle-break that skips entries whose `OriginClusterId` matches the peer's own cluster id), encodes the batch via `IReplicationBatchEncoder` into an activation-scoped `ArrayBufferWriter<byte>`, calls `IReplicationTransport.SendAsync`, and on positive ack advances the durable cursor to `min(ack.HighestAppliedHlc, lastShippedHlc)` and reports the new cursor through the `ILatticeReplicationCursorRegistry`. Transient failures (drain throw, transport throw, ack rejected) feed an exponential backoff sized by `ShipBackoffInitial` (default 100 ms) doubling up to `ShipBackoffMax` (default 30 s) with `ShipBackoffJitter` (default 0.2) symmetric multiplier; `ConsecutiveFailures` resets on the first successful round-trip. Permanent encode failures (`ArgumentException` / `InvalidOperationException` from the encoder - schema-shape errors the bytes can never recover from in their current form) park every entry in the offending batch on the per-tree `IReplicationDeadLetterGrain` tagged `LatticeReplicationMetrics.ReasonSchema`, then advance the cursor past the batch so a single poison entry never stalls the stream forever. The DLQ enqueue is best-effort; a deterministically-failing DLQ does not pin the ship loop because the WAL retains the originals until the GC pass trims them.

  **Maintenance grain (`IReplicationMaintenanceGrain`, key `{treeName}`).** Cluster-singleton; hybrid `IRemindable` (60 s) + `IGrainTimer` (5 s). Two scheduled passes on independent cadences with their own last-run timestamps in persistent state: GC every `MaintenanceGcInterval` (default 5 s) calling `ILatticeReplicationGc.RunOnceAsync(treeName)`; fall-off-the-log probe every `MaintenanceFallOffCheckInterval` (default 30 s) iterating `ReplicationPeers` and calling `ILatticeFallOffLogDetector.CheckAndTriggerAsync(treeName, peer, oldestHlc)` where `oldestHlc` comes from `ILatticeWalIntrospection.GetOldestAvailableHlcAsync`. The cadence stamp advances **only on a successful pass** so a thrown `RunOnceAsync` or probe pass is logged as a warning and retried on the next phase tick rather than waiting a full cadence interval; the keepalive reminder is the backstop against a deterministically-failing pass. The detector itself drives the bootstrap kickoff via `ILatticeBootstrapCoordinator.BootstrapAsync` so this grain stays a pure scheduler.

  **Activation service (`ReplicationDriverActivationService`, `BackgroundService`).** Calls `EnsureActiveAsync` on every replicated tree's shipper-per-peer + maintenance-per-tree singleton on host startup. The activation loop is retry-with-backoff: starts at 250 ms inter-attempt, doubles on each consecutive miss up to 30 s, resets on first success. Loop only exits when the pending set is empty or the host's `stoppingToken` is cancelled. Decoupled from Orleans' own `IHostedService` ordering so a fast-silo restart does not race the runtime.

  **Doorbell wiring.** `ShardedReplogSink.WriteAsync` rings a per-`(tree, peer)` doorbell after a successful WAL append; the shipper's `OnDoorbellAsync` short-circuits the timer wait and pumps immediately when there's actually new data so steady-state ship latency is sub-second rather than waiting for the next 200 ms tick. The fan-out is bounded (one no-op grain call per active peer per WAL append) and best-effort; a missed doorbell only delays the next ship by one timer tick.

  **Buffer reuse on the ship hot path.** The shipper maintains two activation-scoped buffers reused across pump ticks: `_drainBuffer` (`List<WalRecord>`) cleared in place at the start of every `PumpOnceAsync`, and `_writeBuffer` (`ArrayBufferWriter<byte>`) reset via `ResetWrittenCount()` between ticks (keeps the underlying array, rewinds write index to 0). A one-time spike that grows the buffer at-or-past the 4 MB soft cap recreates the writer so a single outlier batch does not pin a multi-MB array on the heap forever. Net effect: zero per-tick heap allocation on the steady-state path beyond Orleans-internal serializer wrappers.

  **New options.** `ShipBatchSize` (default `256`, validator `>= 1`), `ShipMaxInFlight` (default `1`, validator `>= 1` - declared and validated but **v1-inert**: the shipper hard-codes strict serial sends per `(tree, peer)`; multi-batch pipelining is gated on the typed-envelope transport seam and multi-batch in-flight WAL flush landing first), `ShipBackoffInitial` (default `100 ms`, validator `> TimeSpan.Zero`), `ShipBackoffMax` (default `30 s`, validator `>= ShipBackoffInitial`), `ShipBackoffJitter` (default `0.2`, validator `[0.0, 1.0]`), `MaintenanceGcInterval` (default `5 s`, validator `> TimeSpan.Zero`), `MaintenanceFallOffCheckInterval` (default `30 s`, validator `> TimeSpan.Zero`), `ShipDoorbellEnabled` (default `true`). All resolved via `IOptionsMonitor<LatticeReplicationOptions>.Get(treeName)`.

  **Why grain-native, not `IHostedService`.** An `IHostedService` runs once per silo, so a 3-silo cluster would issue duplicate sends and require manual leader election; an Orleans grain activation is cluster-wide, so silo loss triggers automatic migration with no extra coordination. Per-peer isolation (a slow peer must not block other peers) falls out of "one activation per `(tree, peer)`" naturally; with `IHostedService` it would require a custom per-peer task pool. The codebase pattern is already grain-based - `IReplicationDeadLetterGrain`, `LatticeBootstrapCoordinatorGrain`, `IReplicationHighWaterMarkGrain` all use the same shape - so a non-grain background pump would be the outlier.

  **Metric activation surface.** Today `wal.entries_appended` and `dead_letter.*` fire from existing wire-up; everything else was dormant pending a caller. After this change: `ship.duration` and `wal.entries_shipped` fire from the shipper's `SendAsync` call; `wal.entries_trimmed` fires from the maintenance grain's GC pass; `peer.fell_off_log` fires from the maintenance grain's fall-off probe; `apply.*` (lag / fifo violations / buffered entries / buffer bytes / dependency wait / causal violations blocked) all fire transitively because the peer end now has real inbound traffic to apply.

  *Future-compat:* the shipper grain is the canonical scheduler shape for the local-apply materialiser shipped under Core F-049. A future materialiser is just another `IChangeFeed` consumer with its own cursor; replacing the `IReplicationTransport.SendAsync` call with a local `IReplicationApplier.ApplyAsync` call (or the commit-log apply seam) reuses the entire scheduling skeleton verbatim. The maintenance grain similarly is the natural home for any future per-tree background pass (compaction, snapshot pruning, projection rebuild) without inventing a third scheduler shape.

## 🔲 Phase 5 - Snapshot / bootstrap protocol *(design §4)*

Required before any production deployment. Without it, a peer whose cursor falls behind the oldest replog entry can never catch up.

- [x] **R-050 - `ISnapshotProvider` abstraction**
  Sender-side: streaming `as-of` HLC range scan over the primary tree (not the replog). Backed by the core library's stateful cursor grain (`F-033` from the core roadmap) so snapshots are resumable on silo failover. Chunked by key range so snapshot streams don't monopolise a single shard.
  *Future-compat:* the same interface satisfies v2 C-060 (snapshot + WAL-tail restore for fast local recovery). Today it scans the primary tree and is consumed by the bootstrap protocol; in v2 it scans the materialised projection and is consumed by both bootstrap and crash recovery. Avoid hard-coding "remote peer" in the API surface - keep it `ISnapshotProvider.ExportAsync(treeName, asOfHlc, ct)` and let the consumer decide what to do with the stream.

- [x] **R-051 ✓ shipped - Receiver-side bootstrap state machine**
  States: `RequestingSnapshot` → `ApplyingSnapshot` → `IncrementalHandoff` → `LiveIncremental`. On snapshot completion the receiver pins the snapshot's as-of HLC `h` and causal-stable frontier on its per-tree `IReplicationHighWaterMarkGrain` via `PinSnapshotAsync(asOfHlc, frontier, ct)` (R-081-widened) and switches to incremental from `h`. The HWM dedupe in R-023 makes the handoff exactly-once regardless of snapshot/incremental overlap. **Implemented:** new public `LatticeBootstrapState` enum (`Idle` / `RequestingSnapshot` / `ApplyingSnapshot` / `IncrementalHandoff` / `LiveIncremental` / `Failed`) and public `ILatticeBootstrapCoordinator` seam (`GetStateAsync(treeName, ct)` + `BootstrapAsync(treeName, sourceClusterId, ct)`); the public surface is a thin façade - internal sealed `LatticeBootstrapCoordinator` registered via `TryAddSingleton` in `AddLatticeReplication` - that forwards every call to a per-tree internal `ILatticeBootstrapCoordinatorGrain` (alias `olr.gb`) keyed by tree name. Hosting the state machine inside an Orleans grain whose single activation is cluster-wide makes concurrent bootstraps mutually exclusive across silos at zero coordination cost: two silos that both call `BootstrapAsync` for the same tree route to one activation. The grain inherits the same `CoordinatorGrain<TSelf>` reminder + phase-timer pattern used by the core tree-resize coordinator (1-minute keepalive reminder + 2-second phase grain timer): `BootstrapAsync` is an **idempotent kickoff** - it persists the bootstrap intent (phase, source cluster id, operation id, `LastAppliedHlc` cursor) to the `LatticeOptions.StorageProviderName` storage provider via `IPersistentState<BootstrapCoordinatorState>` (alias `olr.bs`), schedules the phase pump, and returns; callers poll `GetStateAsync` for progress. This avoids the 30-second Orleans RPC timeout on long snapshot drains and decouples caller liveness from the workflow. A concurrent kickoff from the same source cluster is a no-op (idempotent retry); a concurrent kickoff from a different source cluster throws `InvalidOperationException`. The phase pump drives the four-state cycle: `RequestingSnapshot` issues `ISnapshotProvider.ExportAsync(treeName, state.LastAppliedHlc, ct)` against whichever provider is registered in DI - using the persisted cursor (not `HybridLogicalClock.Zero`) so a silo crash mid-drain resumes from where it left off rather than re-fetching the entire snapshot; `ApplyingSnapshot` drains `SnapshotStream.Entries` through `IReplicationApplyGrain.ApplySetAsync` so each entry is persisted with its commit-time HLC and the supplied `sourceClusterId` as origin (transitive replication paths preserve the originating HLC), updating `LastAppliedHlc` per entry and persisting the cursor every 100 entries; `IncrementalHandoff` calls `IReplicationHighWaterMarkGrain.PinSnapshotAsync(snapshot.AsOfHlc, snapshot.CausalStableFrontier, ct)` so the first incremental entry runs through both the per-origin HWM dedupe (R-023) and the causal-plus dependency check (R-082) from a non-empty frontier; `LiveIncremental` is terminal. State is **durable and crash-resumable**: after a silo crash, Orleans reactivates the grain on a surviving silo within the keepalive period and the phase pump resumes from the persisted phase and `LastAppliedHlc`. Worst-case waste on crash is bounded re-application of ~100 entries, which the per-origin HWM dedupe makes a correctness no-op (cost is bandwidth, not correctness). Different trees bootstrap on different activations and run in parallel. Each phase wraps its work in try/catch that persists `Phase = Failed` and `InProgress = false`, tears down the keepalive reminder + phase timer, and rethrows; a subsequent `BootstrapAsync` call restarts the cycle from `RequestingSnapshot`, making `Failed` an idempotent restart point. Restart after `LiveIncremental` likewise begins a fresh cycle. Snapshot entries with a null `Value` are skipped (the default provider does not emit them, but a host-supplied `ISnapshotProvider` could). Documented in [`docs/lattice.replication/snapshot-bootstrap.md`](../../docs/lattice.replication/snapshot-bootstrap.md) under the `Receiver-side bootstrap state machine` section. Test coverage: state-machine behaviour pinned by ~30 unit tests in `LatticeBootstrapCoordinatorGrainTests` directly against the grain - ctor null guards, `GetStateAsync` (idle default + reflects-persisted-phase + cancellation), `BootstrapAsync` arg/CT guards, `TryInitiateBootstrapAsync` persistence shape + idempotent same-source + throws-different-source + arg guards, and 11 `ProcessNextPhaseAsync` tests (idle no-op, `RequestingSnapshot` → `IncrementalHandoff` full drain, in-order multi-entry application, null-value skip, **resume-from-persisted-LastAppliedHlc-after-crash**, `IncrementalHandoff` pin+complete, 3 `Failed` transitions for export/apply/pin throws, two-tick full cycle, restart-after-`LiveIncremental`, restart-after-`Failed`). Forwarding contract pinned by 12 unit tests in `LatticeBootstrapCoordinatorTests`. Plus 3 DI tests in `LatticeReplicationServiceCollectionExtensionsTests`. Full suite green: 726/726 replication + 1583/1583 core (non-Chaos), 0 errors / 0 warnings.

- [x] **R-052 ✓ shipped - Auto-bootstrap trigger**
  Fires when the inbound apply path detects the sender's cursor is older than the sender's oldest WAL entry ("fall-off-the-log"). **Implemented:** new public `ILatticeFallOffLogDetector` seam (`CheckAndTriggerAsync(treeName, sourceClusterId, senderOldestAvailableHlc, ct)`) returning a `FallOffLogDecision` record struct (`FellOffLog`, `LocalHighWaterMark`, `BootstrapTriggered`); the detector resolves the per-tree `IReplicationHighWaterMarkGrain`, calls `GetAsync(sourceClusterId)`, and applies a strict `localHwm < senderOldestAvailableHlc` predicate (boundary equality is *not* fall-off - the sender still has the entry the receiver is asking for). ## 🔲 Phase 6 - GC, DLQ, back-pressure, observability *(design §4–§6)*

Ops polish and production-grade reliability. Within this phase, **R-060 (DLQ) is the highest priority** because a single poison entry in the current sample stalls the pipeline forever.

- [x] **R-060 - Poison-entry DLQ**
  After `K` consecutive apply retries on the same `(origin, hlc)` tuple, the receiver moves the entry to a bounded DLQ (new grain `IReplicationDeadLetterGrain`) and advances past it. Configurable via `LatticeReplicationOptions.MaxApplyRetries` (default `5`). Operators inspect the DLQ via a read-only query API and can replay or discard individual entries. Removes the sample's "first exception stalls the stream forever" hazard. **Implemented:** new public `DeadLetterEntry` (record struct, alias `olr.dl`) and `ILatticeReplicationDeadLetters` seam (`ListAsync` / `CountAsync` / `DiscardAsync` / `ReplayAsync`) in `Orleans.Lattice.Replication`; internal `IReplicationDeadLetterGrain` (alias `olr.gd`) per tree, backed by a reserved system tree `_lattice_replog_dlq_{treeId}` (resolved through `ISystemLattice`) so parked entries inherit the scaling, sharding, and persistence of the core B+ tree rather than living inside one grain's persistent-state row. Each parked row is keyed `e/{19-padded-id}` and holds an Orleans-binary-serialised `DeadLetterEntry`. The grain bulk-loads its rows on activation into an in-memory cache and writes through on every mutation; FIFO eviction keeps the cache at or below `LatticeReplicationOptions.DeadLetterQueueCapacity` (default `1000`, validator `>= 1`). New internal `DeadLetterTrackingReplicationApplier` decorator wraps the canonical `ReplicationApplier`, tracks consecutive failures per `(treeId, originClusterId, timestamp, key, op)` tuple in a `ConcurrentDictionary`, and on the `MaxApplyRetries`-th failure parks the entry, advances the per-origin HWM past it (point ops only - `DeleteRange` skips HWM advance because the canonical applier doesn't consult the HWM for ranges), clears the counter, and returns `Applied=false`. Successful apply (or filtered re-delivery) clears the counter for that tuple. The decorator is wired via DI factory in `AddLatticeReplication` so the canonical `ReplicationApplier` is registered as a concrete singleton (reused by the `ILatticeReplicationDeadLetters` replay path to bypass the decorator and avoid an infinite re-park loop on a deterministically-failing parked entry) while the public `IReplicationApplier` resolves to the decorator. `ReplayAsync` removes the parked entry on any non-throwing return - including HWM-filtered re-delivery - so a `Replay` after parking is terminal-for-cleanup. New DLQ metrics on the `orleans.lattice.replication` meter: `dead_letter.enqueued` and `dead_letter.removed` counters, both tagged `tree` and `reason`; reason values `discarded` / `replayed` / `evicted` / `unknown` are exposed as `LatticeReplicationMetrics.Reason*` constants. - [x] **R-061 - GC by min-acked cursor**
  Replace the sample's wall-clock TTL janitor with a GC predicate of `entry.hlc < min(ackedCursor_peer_i)` across all subscribed peers. Trims aggressively while guaranteeing every subscribed peer can always resume without a snapshot. A lagging peer pins the log - coupled with a "lag alert" metric (R-064) operators notice before it becomes a bootstrap scenario. TTL remains as a hard ceiling (configurable) to bound worst-case disk usage.
  *Future-compat:* the GC predicate must consult **every** consumer's cursor, not just remote peers. - [x] **R-079 - Per-batch Azure Table partition keys with manifest-driven reads** *(closes head-pointer clobber race exposed by R-074 against Azure Tables; lifts per-shard write quota)* `[deps: R-074 ✓]` ✓ shipped
  R-074 lifts the writer-side single-in-flight cap inside the WAL grain, but the Azure Table Storage backend (R-073) still serialises every concurrent batch through one partition `treeId|shardIndex`. Two costs result. (1) Throughput: Azure Tables enforces a per-partition write quota (~500 transactions/sec, ~2,000 entities/sec) regardless of how many flushes the grain has in flight, so `WalMaxPendingBatches > 1` against Azure Tables buys only RPC pipelining, not partition-server parallelism. (2) Correctness window: the per-batch transaction upserts a shared `(PK = treeId|shardIndex, RK = HEAD)` sentinel with the batch's max offset, and concurrent batches can race the upsert so a smaller-offset batch's `HEAD = endOffset_small` lands after a larger-offset batch's `HEAD = endOffset_large`, briefly reporting a stale tail from `GetHighestOffsetAsync`. R-074 documents this as a bounded, opt-in hazard; R-079 eliminates it.

  Approach: each batch lands in its own Azure Tables partition keyed by `treeId|shardIndex|S{startOffset:D19}` (`S` so it sorts after the manifest's `M…` rows lexicographically). A separate per-shard **manifest partition** keyed by `treeId|shardIndex|MANIFEST` carries one row per committed batch (`RK = M{startOffset:D19}`, payload = `(startOffset, endOffsetInclusive)`) plus a single tail-pointer row (`RK = TAIL`, payload = max committed `endOffsetInclusive`). Append becomes a **two-phase commit**: phase 1 commits the entry rows + per-batch head sentinel atomically within the batch partition (true parallelism across batches because every batch hits a distinct partition); phase 2 commits the manifest row + tail-pointer upsert atomically within the manifest partition (serialised per shard inside the grain to keep the tail pointer monotonic). The grain gates phase 2 with a per-shard ordered queue so phase-2 transactions commit in offset order regardless of phase-1 completion order.

  Read paths rewrite around the manifest. `GetHighestOffsetAsync` is one point read on `(MANIFEST, TAIL)` - O(1), same cost as today. `ReadAsync(fromOffsetExclusive, maxEntries)` first range-queries the manifest partition for batches that overlap the requested window, then fetches each batch partition's entries in parallel and yields them in offset order. Net cost is `1 + ceil(window / batchSize)` RPCs; mitigated by an in-memory manifest cache invalidated only when the tail pointer advances. `TrimAsync(throughOffsetInclusive)` reads the manifest, deletes the whole partition for each fully-trimmable batch (faster than the per-row delete today), pages the boundary batch as today, then deletes the corresponding manifest rows.

  Reliability hardening: phase-1 commit without phase-2 commit (transient failure or process crash between phases) leaves orphan batch partitions invisible to the tail pointer. Two complementary recovery mechanisms close the window: (a) **idempotent retry** - the grain retains the phase-2 transaction payload until it commits, retrying on transient phase-2 failures with bounded exponential backoff before failing the writer's TCS; (b) **activation reconciliation** - a new `IWalStorageProvider.ReconcileAsync(treeId, shardIndex)` method is called from `OnActivateAsync` after `GetHighestOffsetAsync`, scans the table's `treeId|shardIndex|S` partition prefix (one-shot cross-partition query bounded by a "manifest-consistent-through" sentinel), and either commits the missing manifest rows for orphan batches with offsets at or below the consistent-through watermark or rolls them back. The watermark is advanced after every successful manifest commit so the reconciliation scan stays O(orphans) rather than O(all batches).

  Implementation notes: the head-pointer entity type stays as today (per-batch `HEAD` rows are point-readable for diagnostics); a new `ManifestEntity` and the `TAIL` pointer use the same `AzureTableWalEntity` row schema with `Payload = null` and the offset packed into the existing `Offset` column. `BuildPartitionKey` gains an overload for the batch and manifest variants. The new `ReconcileAsync` method on `IWalStorageProvider` defaults to a no-op (the in-memory provider has no orphan state to reconcile because phase 1 and phase 2 are folded back into the existing single-transaction in-memory commit).

  Acceptance: with `WalMaxPendingBatches = 4` against the Azure Tables emulator, a 1024-entry burst spread across 8 shards shows throughput-uplift over today's path proportional to partition-server count, measured by the optimisation agent protocol; `GetHighestOffsetAsync` reports a strictly monotonic sequence across concurrent appends (no clobber); fault-injection harness that kills the grain process between phase 1 and phase 2 for N=1000 random failure points leaves zero data-loss and zero double-apply after reconciliation; `ReadAsync` tail-replay of K batches completes in `ceil(window / batchSize) + 1` RPCs and yields entries in strict offset order; `TrimAsync` of K fully-trimmable batches completes in K full-partition delete transactions plus K manifest-row deletes; existing single-partition WAL data is rejected at activation with a descriptive error rather than silent migration (one-way storage break documented in CHANGELOG and migration guide).

    1. **Commit** (`ILattice.SetAsync` -> publish helper) - constructs a `LatticeMutation` value. **No encode** (struct construction; the historical "encode #1" claim in the prior R-078 wording was wrong).
    2. **WAL append** (`WalShardGrain.AppendAsync`) - `WalRecordConverter.FromWalRecord(entry)` builds a `LatticeMutation`, then `IWalMutationEncoder.Encode(in mutation, writer)` writes it into a `PooledByteBufferWriter`.     3. **Shipper drain** (`ReplicationShipperGrain.DrainAsync` -> `IWalShardGrain.ReadAsync`) - the WAL grain returns a `WalShardPage` whose `Entries` are already-deserialised `WalRecord` objects. Surfaced as `ReplicationBatch.Payload`. **Dead on the gRPC fast path** post R-047 because `GrpcPushTransport.BuildEnvelope` prefers `batch.Envelope`.
    5. **gRPC marshaller** (`LatticeReplicationGrpcMarshallers.CreateEnvelopeMarshaller`'s serializer delegate) - `encoder.Encode(box.Value, context.GetBufferWriter())` writes the same envelope into the gRPC stream's buffer. **One encode.**

   Result: **two `Encode(ReplicationBatchEnvelope)` calls on every ship tick post R-047** (step 4 + step 5), one of which is unconditionally discarded by the only production transport that consumes it.

  **Acceptance.**
  1. **No regression in non-gRPC transport behaviour.** `LoopbackTransport`, `NoOpReplicationTransport`, and any third-party `IReplicationTransport` that *does* consume `ReplicationBatch.Payload` continues to receive bytes-shaped payloads. The seam must therefore live on `IReplicationTransport` (e.g. a `bool ConsumesPayloadBytes` capability property, or a typed `IReplicationTransport.SendAsync(ReplicationBatchEnvelope, ...)` overload that the shipper prefers when present) and not as a host-level opt-in flag.
  2. **`ReplicationBatch.Payload` retains its bytes contract.** Existing public-API contract tests (`PublicReplicationApiContractTests.IReplicationTransport_send_emits_replication_batch_with_routing_metadata` asserts `Payload.IsEmpty` is false) continue to pass against the loopback transport. The bytes-shaped seam must not silently turn into an empty buffer for typed-envelope transports either - the test fixture's transport is bytes-consuming, and that must stay observably true.
  3. **Allocation count drops.** A `BenchmarkDotNet` of a 1024-entry ship through `GrpcPushTransport` shows the `_writeBuffer` encode and its underlying `ArrayBufferWriter<byte>.WrittenMemory` allocation go to zero on the typed-envelope fast path (the `ArrayBufferWriter<byte>` field itself stays, but its capacity-growth churn flatlines to one initial growth at activation rather than per-tick growth on a previously-recycled buffer). Same benchmark on a loopback-only configuration shows no change vs today.
  4. **Bytes / typed-slot round-trip equivalence.** A `Theory`-style test feeds the same drain buffer through both paths in turn (encode-then-`Decode` vs. typed-envelope direct) and asserts the resulting `ReplicationBatchEnvelope` values are equal field-for-field, so the elimination of step 4 cannot mask a divergence between the encoded bytes and the in-memory envelope.

  **Out of scope (explicitly).** Collapsing the WAL append's per-entry `LatticeMutation` bytes into the replication wire is **not** in scope - the two formats serialise different types under different encoders. That collapse would be a separate, larger item (likely "R-079 - harmonise WAL and replication wire shapes") and would itself require either reshaping the WAL to store `WalRecord` bytes (breaking change on R-076's provider contract and on every shipped Azure Table row) or reshaping the replication envelope to embed `LatticeMutation` per entry (breaking change on `ReplicationBatchEnvelope.WireVersion`). The "1 encode end-to-end" target the prior R-078 wording promised is **not achievable** without that harmonisation, so this revised entry sets the target at "1 encode at WAL append + 1 encode at gRPC marshaller (down from 2 + 1 today)" and parks the larger collapse behind a separate roadmap entry.

The shipper's `PumpOnceAsync` populates whichever slot the transport prefers: gRPC consumes `EncodedEnvelope`, loopback / no-op consumes `Envelope`, third-party bytes-consuming transports continue to read `Payload` (the encoder still emits framed bytes for that path, but framing is now a constant-size header plus the pre-encoded entry segments concatenated, not a re-encode of `WalRecord[]`). `IReplicationBatchEncoder` gains a framing-only method `void EncodeFraming(in EncodedBatchHeader header, ReadOnlyMemory<ArraySegment<byte>> entries, IBufferWriter<byte> writer)` and a matching `bool TryDecodeFraming(ReadOnlyMemory<byte> bytes, out EncodedBatchHeader header, out ReadOnlyMemory<ArraySegment<byte>> entries)`; the existing typed `Encode(envelope, writer)` is preserved (loopback still uses it). `ReplicationBatchEnvelope.WireVersion` bumps to `2.0` (major, signalling the framing-only consumer is now canonical); legacy peers running `1.x` are rejected at the receiver with a descriptive error referencing the migration guide. Aliases `olr.bee` and the new `IWalRecordEncoder` are added to `TypeAliases.cs`; alias-hygiene tests pin them.

  **Sequencing inside the migration.** Five stages, each independently buildable and shippable behind a feature flag (`LatticeReplicationOptions.OneEncodeFastPath`, default `false` until stage 5 lands and flips the default):

  - **Stage 1 - encoder rename and wire baseline flip.** `IWalMutationEncoder` is renamed to `IWalRecordEncoder`; the encode/decode methods' subject type flips from `LatticeMutation` to `WalRecord`. `WalShardGrain.AppendAsync` continues to construct a `WalRecord` via `WalRecordConverter.ToWalRecord(...)` from the incoming `LatticeMutation` argument so the observer-site change is deferred to stage 5; only the byte representation written to storage changes here. The wire bytes are **not** preserved (Orleans serialization is type-keyed; `Serializer<WalRecord>` and `Serializer<LatticeMutation>` emit different headers and field tags), so this stage carries the wire-version break. `OrleansBinaryWalMutationEncoderTests` is renamed to `OrleansBinaryWalRecordEncoderTests` and re-pinned against `Serializer<WalRecord>`. Legacy on-disk WAL data from before R-114 is **not** supported on a silo built against the new encoder; operators are expected to migrate clusters on quiesced WALs (the operational contract that already applied to every prior wire-breaking roadmap item that did not ship a detection probe). No allocation change on the hot path yet (one encode per append, same as today); the value of stage 1 is locking in the encoder identity for stages 2-5. The append-path round-trip `WalRecordConverter.FromWalRecord(...)` -> `encoder.Encode(in LatticeMutation, ...)` collapses to a direct `encoder.Encode(in record, ...)` since `WalShardGrain` already has the `WalRecord` in hand from the producer-side `ToWalRecord` projection; the converter's reverse projection survives only on the read seam where the provider-boundary `WalEntry.Mutation` (`LatticeMutation`-shaped) is reconstructed from the decoded `WalRecord`.

  - **Stage 2 - provider read seam.** `IWalStorageProvider.ReadEncodedAsync` ships with the decode-then-re-encode default body; in-memory provider override returns the bytes from R-076's segment pool directly; Azure Table provider override projects rows to byte segments without rehydrating the strongly-typed `WalRecord`. Shipper continues to use `ReadAsync` (apply path also uses it, unchanged). Allocation change: zero on the shipper path (it isn't on the new seam yet), but the seam is now in place. Tests: 1024-entry round-trip equivalence between `ReadAsync` and `ReadEncodedAsync` on every provider (in-memory, Azure Table, default-fallback third-party stub).

  - **Stage 3 - framing-only encoder seam.** `IReplicationBatchEncoder.EncodeFraming` / `TryDecodeFraming` ship. Default implementations on `OrleansBinaryReplicationBatchEncoder` write a fixed 32-byte header (`MagicNumber`, `WireVersion`, `ClusterId hash`, `EntryCount`, `BatchSequence`, `AtomicBatchSpanCount`) followed by 4-byte length-prefixed entry segments. `ReplicationBatch.EncodedEnvelope` slot ships, populated to `null` by default; the existing `Envelope` and `Payload` slots are unchanged. `GrpcPushTransport.BuildEnvelope` learns to prefer `batch.EncodedEnvelope` when present (short-circuiting both the typed-envelope decode path and the legacy bytes decode path). Behaviour change: none yet because the shipper does not populate `EncodedEnvelope` yet. Tests: framing round-trip equivalence (header round-trips bit-identically; entry byte segments round-trip verbatim); legacy `WireVersion = 1.x` payloads still decode through the typed seam.

  - **Stage 4 - shipper one-encode fast path.** When `LatticeReplicationOptions.OneEncodeFastPath` is `true`, `ReplicationShipperGrain.PumpOnceAsync` calls `IWalShardGrain.ReadEncodedAsync` instead of `ReadAsync`, builds an `EncodedBatchHeader` directly from the page's metadata, and populates `ReplicationBatch.EncodedEnvelope`. The grain-internal `_writeBuffer` encode at the shipper is skipped entirely on the fast path (no `Envelope` -> bytes round-trip; the framing encoder writes the header + segments straight into `_writeBuffer`, but no `WalRecord` is ever materialised on the shipper side). Allocation drops from one-`Encode(WalRecord)`-per-entry on the existing path to one-fixed-size-header-write per batch on the fast path. Benchmark: 1024-entry ship through `GrpcPushTransport` with `OneEncodeFastPath = true` shows zero `WalRecord` allocations on the shipper path and one `EncodedBatchHeader` value-type write per batch; same benchmark on a `LoopbackTransport` is unchanged (loopback still consumes `Envelope`).

  - **Stage 5 - WAL append constructs `WalRecord` directly at the observer site, and the legacy typed-envelope sender path is deleted (folds in R-115).** The historical `WalShardGrain.AppendAsync(WalRecord entry, ...)` -> `WalRecordConverter.FromWalRecord(entry)` -> encode path is replaced with the observer constructing the `WalRecord` directly (folding HLC stamping, origin stamping, mode resolution, and vector clock capture at the same site that today produces a `LatticeMutation`). Allocation drops from one-`LatticeMutation`-plus-one-`WalRecord`-per-append to one-`WalRecord`-per-append on the WAL append path. **The `OneEncodeFastPath` flag is deleted entirely** (not flipped to `true` as originally planned): the framing-only ship path becomes unconditional, the legacy `DrainBatchAsync` branch in `ReplicationShipperGrain` is removed, the `ITypedReplicationTransport` capability surface is deleted (no remaining consumers once the typed-envelope shipper branch is gone), and `GrpcPushTransport` collapses to the framing path plus a `Payload`-decoding fallback for non-shipper consumers. `ReplicationBatch.Envelope` is preserved as a slot for in-process loopback transports that already hold a typed envelope, but the shipper no longer populates it on the steady-state ship path. This collapses R-115 into stage 5 rather than deferring it across a release window: the documented soak-window contract was never entered (the option's default has only ever shipped at `false`, so no released version of `Orleans.Lattice.Replication` has ever taken the typed sender path off in production), and a runtime flag would not have helped anyway because the only failure mode the framing path could exhibit is a wire-encoding defect that requires a code fix, not a configuration toggle. `LatticeMutation` remains the public mutation-observer surface (`IMutationObserver.OnMutated(in LatticeMutation, ...)`); the WAL-internal converter is retired in favour of a new internal `WalRecordBuilder` value type that owns the field-stamping logic for both surfaces (the observer continues to receive a `LatticeMutation` synthesised from the `WalRecord` so the public observer contract is unchanged).

- [x] **R-116 - Strip context-redundant `TreeId` from per-entry WAL bytes** *(performance follow-on to R-114 ✓; medium blast radius)* `[deps: R-114 ✓]`

  Today every `WalRecord` on the wire and on disk carries `[Id(0)] TreeId` as its first slot. The R-114 ship-path A/B microbench in `benchmark/host/Bench.Microbench/r114-ship-bench-results.md` measured ~14-22 B per entry of pure duplication on bench-name strings (`"ship-bench"`); production tree names like `"orders/eu-west-1/v3"` push the per-entry overhead to ~25-35 B. The duplication is provable: every `IWalStorageProvider` entry point (`AppendBatchAsync`, `ReadAsync`, `ReadEncodedAsync`, `GetHighestOffsetAsync`, `TrimAsync`, `ReconcileDestructivelyAsync`) takes `(string treeId, int shardIndex, ...)` as method arguments, so the partition key always supplies the tree id. The replication shipper drains a single `(treeId, shardIndex)` partition per batch, so the framing tail (R-114 stage 5's variable-length `treeName` after the fixed header) supplies the tree id at the receiver as well. R-116 elides the slot at the producer's commit-time encode and reconstructs it at every decode site from the surrounding context.

  **Expected outcome.** Per-entry on-disk and on-the-wire bytes shrink by the UTF-8 length of the tree name plus Orleans' 1-byte field tag and 1-2 byte length prefix. On a 256-entry × 1 KiB batch with a 20-character tree name, that is ~5.4 KB amortised on top of the framing path's existing 39% reduction; on a 1024-entry batch with the same tree name, ~21 KB. The hot-path allocation profile is unchanged on the ship path (the framing seam still copies opaque segment bytes verbatim - no extra serializer call).

  **Wire and storage break.** The on-disk WAL byte layout changes: legacy on-disk WAL data persisted before R-116 is **not** decodable by a silo built against the new encoder. Operators are expected to migrate clusters on quiesced WALs, the same operational contract that already governed R-114's stage-1 encoder rename. On the wire, peers running pre-R-116 receivers cannot decode R-116-shaped framing entries because the per-entry Orleans field tag for `[Id(0)]` will be absent and `WalRecord.TreeId` will deserialize as the empty string. The framing header's `WireVersion` is bumped from `3` to `4`; receivers running v3 reject v4 (existing strictly-greater-than rejection in `IReplicationBatchEncoder.TryDecodeFraming`); a v4 sender to a v3 receiver fails the gRPC handshake and surfaces a `NotSupportedException` to the shipper's transient-backoff loop (no rollback fallback exists post-R-115; the typed-envelope sender path is retired and the framing path is unconditional). The receiver-version skew window is the operational rollout-coordination concern that already governed R-042 / R-114, not a code-side seam.

  **Implementation surface (sized).**
  1. **`OrleansBinaryWalRecordEncoder`** (`src/lattice/OrleansBinaryWalRecordEncoder.cs`) gains a sibling `Encode(in WalRecord, IBufferWriter<byte>)` overload that projects the record to a clone with `TreeId = ""` before handing it to `Serializer<WalRecord>.Serialize`, plus a sibling `Decode(ReadOnlySpan<byte>, string treeId)` overload that re-stamps `TreeId` on the deserialized record.   2. **`IWalStorageProvider` (in-memory + Azure Table)** is unchanged at the interface level; `InMemoryWalStorageProvider`'s `ReadAsync` and `ReadEncodedAsync` already hold `treeId` as a method parameter and pass it through `WalRecordConverter.FromWalRecord` (which is the existing `WalRecord -> LatticeMutation` projection at the read seam). The fan-out is: every read seam that today calls `encoder.Decode(span)` is rewritten to call `encoder.Decode(span, treeId)`. The producer's `Encode` site - `WalCommitLogWriter.AppendBatchAsync` - is rewritten to call the strip variant.
  3. **WAL replay on activation** (`BPlusLeafGrain` activation flush, `ShardRootGrain` recovery, R-061 GC scan, R-082 causal applier) consumes `IWalStorageProvider.ReadAsync`, which already receives the tree id from its caller; no new plumbing required.
  4. **Replication-apply seam** (`gRPC marshaller`, `LatticeReplicationGrpcMarshallers.cs:200-220`) currently runs `walRecordEncoder.Decode(seg.AsSpan())` after the framing header has already supplied `treeName`. Rewritten to `walRecordEncoder.Decode(seg.AsSpan(), treeName)`. The `ReplicationShipperGrain.DrainBatchShippingAsync` decode at line ~1096 is rewritten the same way, sourcing the tree id from the shipper's owning grain key.
  5. **Tests.** `OrleansBinaryWalRecordEncoderTests` add a strip-roundtrip pair (encode-then-decode-with-treeId returns the original record; encode-then-decode-without-treeId returns a record with `TreeId == ""`). `InMemoryWalStorageProviderTests` and `AzureTableWalStorageProviderTests` get an "appended record's `TreeId` field is recoverable from the partition key on read" assertion. - [x] **R-117 ✓ shipped - Move per-entry `Mode` slot into the framing header** *(performance follow-on to R-114 ✓; low blast radius, byte-cheap)* `[deps: R-114 ✓, R-116 ✓]`

  The `WalRecord.Mode` slot (`[Id(9)]`, the per-tree `LatticeMergeMode`) is uniformly constant within a single shipped batch: it is resolved once at append time from the tree's configured `ILatticeMergeModeResolver` and stamped on every entry of every batch from that tree. R-117 hoists it into the `EncodedBatchHeader`'s trailing packed slot (which already has 8 unused bits between `AtomicBatchSpanCount` and `Compression`) and elides it from the per-entry encoded bytes. The saving per entry is small - one Orleans field-tag byte plus one varint byte for the enum value, ~2 B/entry - but it is additive on top of R-116's ~20 B/entry (TreeId strip), and the receiver's apply hot path picks up `Mode` from the header once per batch instead of once per entry.

  **Scope note: `ShardIndex` is intentionally excluded.** A first-pass design hoisted `WalRecord.ShardIndex` into the header alongside `Mode`, on the premise that the shipper drains a single `(treeId, shardIndex)` partition per batch. That premise is wrong: `ReplicationShipperGrain.DrainBatchAsync` performs a k-way merge across `LatticeReplicationOptions.ReplogPartitions` partitions and the per-entry `WalRecord.ShardIndex` reflects the *leaf's chain-shard index* (set in `BPlusLeafGrain.MutationObserver`) rather than the WAL partition index, so a single shipped batch can legitimately interleave entries from multiple chain-shards. Hoisting `ShardIndex` would either require a producer-side invariant that does not hold today or would force a sender-side regrouping pass that does not pay for itself. The Mode-only hoist captures the real wire-format simplification without making a structural-invariant claim the ship path cannot back up.

  **Expected outcome.** ~2 B per entry of additional reduction on top of R-116. On the bench's 1024-entry corners, ~2 KB amortised per batch; on a typical 64-entry batch, ~128 B. The framing header grows by zero bytes (re-uses the packed slot's reserved bits, so `WireSize` stays at 32). `EncodedBatchHeader.AtomicBatchSpanCount` is tightened from a 24-bit cap (~16 M) to a 16-bit cap (65 535) - still vastly larger than any realised batch entry count - to free 8 bits for `Mode`.

  **Replication-wire-only break.** Unlike R-116, `Mode` cannot be stripped on the storage path (`IWalStorageProvider.AppendEncodedBatchAsync` and `ReadEncodedAsync` have no batch-level header to restore Mode from, and the round-trip-through-`LatticeMutation` default fallback also cannot carry it). R-117's strip therefore applies only to the framing-encoded replication wire: the WAL grain's storage append continues to write Mode-bearing bytes, and the encoder's `Encode(in WalRecord, IBufferWriter<byte>)` strip is gated to the framing path. The framing header `WireVersion` is bumped from `4` to `5`; peers running pre-R-117 receivers reject v5 framing payloads with the existing `NotSupportedException` shape. On-disk WAL bytes are unchanged.

  **Implementation surface (sized).**
  1. **`EncodedBatchHeader`** (`src/lattice.replication/EncodedBatchHeader.cs`) repacks the trailing 32-bit slot from `(spanCount:24 | compression:8)` to `(spanCount:16 | mode:8 | compression:8)`. `WireSize` stays at 32 bytes; `CurrentWireVersion` increments from 4 to 5; `AtomicBatchSpanCount`'s validated cap tightens to `0xFFFF`. `WriteTo` / `ReadFrom` carry the new `Mode` field.
  2. **`OrleansBinaryWalRecordEncoder.Encode`** strips `Mode` (in addition to R-116's `TreeId` strip) before serialisation, and gains a `Decode(ReadOnlySpan<byte>, string treeId, LatticeMergeMode mode)` overload that re-stamps both `TreeId` and `Mode` on the deserialised record. The 2-arg `Decode(span, treeId)` overload remains for the shipper-side code path that does not consume `Mode`.
  3. **`ReplicationShipperGrain`** stamps `header.Mode` on the framing-only envelope at build time, sourcing it from the activation-cached `ILatticeMergeModeResolver.Resolve(_treeName)` (defaults to `LwwRegister` when the tree is non-replicated, matching the existing producer-side WAL-writer stamp).
  4. **Replication-apply seam** (`LatticeReplicationGrpcMarshallers.DecodeEnvelopeFromMemory`, `LoopbackDeliveringTransport`, `ReplicationShipperGrainTests.PartitionResume`) calls `walRecordEncoder.Decode(seg, treeName, header.Mode)` so the apply path sees the producer-side mode without consulting the receiver-side resolver. The in-memory `WalRecord.Mode` slot continues to be the single source of truth on the apply path; only the bytes shrink.

  **Acceptance criteria.**
  1. The R-114 ship-path microbench shows a **per-entry absolute allocation saving** that is additive on top of R-116's measured ~20 B/entry baseline, at every corner where `entryCount >= 64`. The structural projection is ~2 B/entry; at the 1024-entry corners that materialises as ~2 KB amortised per batch on top of R-116's ~20 KB.
  2. `EncodedBatchHeader.WireSize` remains 32; `EncodedBatchHeader.CurrentWireVersion` is 5; both are pinned by the existing wire-shape regression tests. `AtomicBatchSpanCount` validated cap tightens to `0xFFFF` and is pinned by a unit test.

  **R-116 bench signal (resolved).** R-116's measured per-entry saving on `Ship_FramingOnly` is ~20 B at the bench's 10-byte tree name and projects to ~30 B for production-shaped names like `"orders/eu-west-1/v3"`. This is a go-signal for R-117 even at the smaller ~2 B/entry projection: the per-entry constant is real, the strip mechanism scales linearly with `entryCount`, and the operational cost (one wire-version bump) is identical whether one slot or two are stripped, so the marginal cost of shipping the Mode-only hoist alongside R-116's TreeId hoist is the entry's own implementation effort. The k-way-merge ship path forecloses the `ShardIndex` half of the original two-slot design; that constraint is documented in the scope note above and the slot remains per-entry.

  **Phase 7 implementation pivot (post-ship).** The originally-shipped implementation hoisted `Mode` into the framing header *and* added an encoder-side strip (`OrleansBinaryWalRecordEncoder.Encode` rewrote the `Mode` slot to its enum default before calling `Serializer<WalRecord>.Serialize`). Phase 7 benchmarking with a direct-serializer probe revealed that the strip yielded **zero on-the-wire saving**: the Orleans codec's per-property tagging makes a default-valued enum field cost the same on the wire as a non-default one. The fix was to remove the property's `[Id(9)]` attribute entirely and mark the backing field `[field: NonSerialized]`, so the canonical codec never writes the slot in the first place. The in-memory `WalRecord.Mode` shape is unchanged - the property still exists, it is still read by every existing apply-path call site, the receiver-side `Decode(span, treeId, mode)` overload still re-stamps it from the framing header - only the wire encoding changed. The previous wire id `[Id(9)]` is permanently reserved on `WalRecord` and must never be reused for a different field, because legacy WAL bytes authored before R-117 still carry it and Orleans silently drops unknown ids on decode (forward-only upgrade is therefore correct: a post-R-117 silo reading legacy bytes observes `Mode = LwwRegister`, the enum default, and the receiver-side apply seam re-stamps it from `header.Mode` per the existing 3-arg overload). The bench signal post-pivot is exactly **2 B/entry on the wire**, deterministic across every payload size and entry count we measured (the field tag byte plus the enum-zero value byte); the BenchmarkDotNet allocation-counter figure shows ~4 B/entry at batch sizes of 256+ because the 2-byte cut trims both the per-entry serialiser buffer and the framing concatenation buffer.

- [x] **R-118 - Elide `WalRecord.ShardIndex` from on-wire bytes** *(closed: not viable as scoped; see Phase 1 postscript below)* `[deps: R-117 ✓]`

  `WalRecord.ShardIndex` is currently stamped per-entry on every WAL append (sourced from the leaf's chain-shard index in `BPlusLeafGrain.MutationObserver`) and serialised on every encoded entry. R-117's scope analysis confirmed that the slot is **not constant within a shipped batch** (the shipper k-way-merges across `ReplogPartitions` and may interleave entries from multiple chain-shards), so the framing-header hoist used for `TreeId` (R-116) and `Mode` (R-117) is structurally not available. R-118 explored a different strip strategy: elide the slot from the encoded bytes entirely on the replication wire, accepting that the receiver's apply path either does not need it or can reconstruct it from context.

  **Receiver-side observation.** A repository-wide read-site audit at R-117 ship time found exactly one consumer of `entry.ShardIndex` on the receiver: `ReplicationApplier` (`src/lattice.replication/ReplicationApplier.cs:666`) reads `entry.ShardIndex` as a hint for shard routing, falling back to parsing the leaf grain key when the slot is zero / absent. That fallback is the seam R-118 would lean on: if every receiver-side read site has a context-recovery fallback, the slot can be elided from the wire and reconstructed on demand.

  **Why a simple "zero before encode" projection does not save bytes.** Orleans's `[Id(N)]` field encoding writes a field-tag byte plus the value's varint encoding for every present field, regardless of value. A zeroed `int` still costs the field-tag byte plus the varint zero (~2 B), so projecting `record with { ShardIndex = 0 }` before `Encode` is a no-op on the wire. To genuinely elide the slot the producer must either:
  1. Make `ShardIndex` nullable (`int?`) on `WalRecord` and project to `null` before encode (Orleans omits the field tag entirely for null values), or
  2. Have the encoder skip the slot via a custom serialiser that owns its own framing.

  Option (1) is a breaking change to the in-memory `WalRecord` shape: every read site that does `entry.ShardIndex > 0` gains a null-check and a fallback decision, and the on-disk WAL bytes change shape (existing entries decode the present-and-zero shape, but new writes never carry it - so any storage-layer tooling that assumed the slot was always present must learn to handle the absent case). Option (2) keeps the in-memory shape but adds a second WAL-encoder code path with its own version skew story.

  **Cost of the strip on the hot path.** The shipper's pre-encode loop emits each `WalRecord` directly from the WAL grain's `ReadEncodedAsync` page, so a strip-time projection (`record with { ShardIndex = null }`) introduces a record-copy allocation per entry on the hottest path in the system. The optimisation is genuinely additive over R-117 only if the strip is done either (a) at append time on the WAL writer side (so the in-memory record is already stripped before it reaches the shipper - viable if every read site of `WalRecord.ShardIndex` outside the apply path is audited and migrated to the leaf-key parse fallback), or (b) inside the encoder itself via a serialiser-level field skip that does not require a record-with projection.

  **Scope (provisional, subject to design pass).**
  1. Audit every read site of `WalRecord.ShardIndex` and `LatticeMutation.ShardIndex` in the repo. Classify each as (i) producer-side stamping, (ii) receiver-side apply-path consumer, (iii) replay/forensic consumer. Confirm that every consumer has a leaf-key parse fallback or can be migrated to one.
  2. Decide between strategy (1) nullable-slot, (2) encoder-level skip, or a hybrid (e.g. strip on the framing path only, keep the slot on the storage path - matching R-117's wire-only break).
  3. If the encoded saving is genuinely ~2 B/entry on top of R-117 and the audit clears, ship behind a wire-version bump and document the storage-path compatibility story.

  **Why this is a separate ticket and not folded into R-117.** R-117's blast radius is `EncodedBatchHeader`, the encoder pair, and the apply seam - one wire-version bump, no in-memory shape changes, no read-site audit. R-118 needs at minimum a cross-repo read-site audit and a serialiser-level decision; the implementation surfaces are disjoint and the operational risks compound.

  **Expected saving.** ~2 B/entry on top of R-117's ~2 B/entry and R-116's ~20-30 B/entry. At 1024-entry batches, ~2 KB amortised per batch.

  **Phase 1 postscript (closed: not viable as scoped).** A code-level audit and a wire-byte probe ruled out every strip strategy considered above. The findings are recorded here so a future re-investigation does not repeat the same dead-ends.

  *Probe results (canonical Orleans codec, `Serializer<WalRecord>`-shaped DTO, 64 B payload).* The roadmap's option (1) hypothesis ("Orleans omits the field tag entirely for null values") is **empirically false** for `int?` slots: an `int? = null` encodes to the same byte count as `int? = 7`, which equals the byte count of `int = 7`. Orleans writes the field-tag byte plus a null marker for null `int?`, identical in width to tag + varint(value). Wire delta from option (1): **0 B/entry**. The only mechanism that actually elides the slot from the canonical codec is the per-batch Mode hoist's mechanism: drop the `[Id]` attribute and mark the backing field `[field: NonSerialized]`. Probe delta from that mechanism applied to `ShardIndex` in isolation: **3 B/entry** (130 B baseline - 127 B stripped), so ~3 KB on a 1024-entry batch on both the wire and the on-disk WAL.

  *The activation-replay blocker that ruled out the viable mechanism.* `BPlusLeafGrain.Activation.ShouldApplyDuringReplay` filters WAL entries by both a shard axis (`mutation.ShardIndex == leafShardIndex`) and a range axis (`key in [low, high)`). The natural assumption that the range axis subsumes the shard axis is **wrong for the initial leaf in any chain-shard**: `ShardRootGrain.EnsureRootAsync` seeds the initial leaf with `SetTreeIdAsync` and `SetShardIndexAsync` but no `SetKeyRangeAsync`, so its persisted state has both range bounds null until the first split. The activation-time replay always reads from `ReplayWalPartition = 0` (a single partition shared across every chain-shard), so an initial leaf in chain-shard `N > 0` reads commits authored by every chain-shard. With both range bounds null, the range axis lets every record through; the shard axis is the only filter that keeps sibling-chain-shard records out of the leaf's projection. A `[field: NonSerialized]` strip would silently break the projection for every initial leaf in a multi-shard topology. Self-stamping `ShardIndex` from the leaf's own `state.State.ShardIndex` on disk-read is no rescue either: it makes the shard axis trivially pass, removing the discrimination that keeps cross-shard records out.

  *The receiver-side fallback assumption was incomplete.* The roadmap's "exactly one consumer of `entry.ShardIndex` on the receiver" finding is correct for the replication wire path (`ReplicationApplier`'s key-parse fallback at line 666 still works under the strip), but missed the on-disk-WAL-replay consumer at activation time. R-117's analogous "re-stamp from a deterministic, side-effect-free source" pattern (the per-tree `ILatticeMergeModeResolver`) does not generalise: there is no equivalent deterministic recovery for `ShardIndex` short of a `(treeId, key) -> shardIndex` routing-table lookup invoked once per replayed entry, which couples the WAL read path to the routing layer and is a multi-week implementation surface, not a strip follow-on.

  *Re-open trigger.* This ticket becomes viable iff one of (a) `ReplayWalPartition` becomes per-chain-shard so the activation-replay filter no longer needs a shard axis at all, or (b) the seed path (`ShardRootGrain.EnsureRootAsync`) starts stamping at least one open-ended range bound on the initial leaf, in which case the range axis becomes authoritative and the shard axis can be removed without contamination risk. Both are larger surface-area changes than R-118 itself was scoped for.

  *Probe disposition.* The wire-byte probe and projection-allocation probe used to produce the numbers above were transient measurement scaffolding. They are not retained in the repository because the postscript records the per-mechanism deltas inline, so a future re-investigation has the numbers without needing to re-execute. Re-creating the probe is straightforward: build two sibling DTOs that mirror the production `WalRecord` `[Id]` surface and differ only in the slot under test, drive each through `Serializer<T>.SerializeToArray` for the same key/payload, and read off the `Length` delta.

  *Net.* R-117's mechanism saves bytes (~2 B/entry on Mode); R-118 cannot ship the same mechanism on `ShardIndex` without breaking a real activation-replay invariant, and the alternative mechanisms either save zero bytes (option (1)) or require disjoint, larger work (option (2), routing-table self-stamp, multi-partition fan-out). Closed.

## 🔲 Phase 8 - Causal+ consistency *(design [`docs/lattice/wal-causal-plus.md`](../../docs/lattice/wal-causal-plus.md))*

Extends today's per-origin LWW + HWM convergence to causal+ consistency: writers that read-then-write across keys see their dependencies preserved on every peer, under arbitrary partition and re-delivery, without changing the WAL's commit point or ordering semantics. Every item is purely additive on the wire and off the commit path - append-then-apply, monotonic offsets, and origin stamping are unchanged.

  Receiver-side dependency check + bounded per-tree FIFO buffer added to the canonical `ReplicationApplier`. **Implemented:** new internal `CausalApplyBuffer` (per-tree, owned by the singleton applier; `LinkedList<BufferedEntry>` + `Dictionary<EntryKey, node>` index for O(1) duplicate detection and O(1) random-remove FIFO under a private lock) parks entries whose declared `entry.VectorClock` is not yet dominated by the local vector clock. `ApplyAsync` runs the HWM check first (unchanged - preserves the O(1) duplicate fast path), then - only when the entry actually carries a non-empty `VectorClock` - fetches the local vector via `IReplicationHighWaterMarkGrain.GetVectorAsync` and runs `CausalApplyBuffer.DependenciesSatisfied`. ### Causal+ completeness - full coverage of structural & atomic write paths

The R-080 → R-088 wave delivers causal+ for the point-write, single-tree, single-shard-per-mutation path. The five items below extend that guarantee to every write path the core library exposes. Each pairs with a core-side dependency (F-043–F-046) so the core change and the replication consumer land in a single feature cycle - building either side in isolation freezes a contract before its consumer validates it. Cross-tree causality is intentionally out of scope.

- [x] **R-089 ✓ shipped - Atomic multi-key VC capture point** *(depends on R-080 ✓, R-081 ✓, Core F-044 ✓)*
  Closes the per-key VC drift that breaks `SetManyAtomic` cross-replica. F-035's mutation hook fires once per `LatticeMutation`, so an atomic N-key set produces N observer calls; if R-080 captures VC at each call site, each emitted entry stamps a slightly different frontier (the local VC advances between calls) and a remote peer can park entry K waiting for entry K-1 - observable as a transient inter-key gap that no local reader could see. Causal+ does not promise atomic visibility, but it does promise the dependency graph reflects the writer's actual causal history; per-key drift fabricates a graph the writer never authored.

  **Fix:** capture the cluster's local VC **once** at the start of the atomic transaction and stamp every emitted entry within that transaction with the identical frontier. Requires Core F-044 (a `TransactionId` field on `LatticeMutation`, or an explicit `BeginTransaction` / `EndTransaction` lifecycle on the observer hook) so `ReplicationMutationObserver` can recognise the boundary. The observer reads the tree-global VC once on transaction start, retains it as immutable shard-local state for the duration of the batch, and stamps every `WalRecord.VectorClock` from that snapshot. Intra-transaction self-edges (writer reading post-write state of key 1 before writing key 2) are *not* external causal edges and are deliberately not captured - that's the point of single-capture-per-transaction.

  **Receiver:** no change to R-082's dep-check; entries with identical VCs unblock together when their shared frontier is satisfied.

  **Atomic visibility note:** all-or-none cross-replica visibility is strictly stronger than causal+. R-089 does not deliver it on its own - it ships the producer-side capture seam that the cross-cluster atomic-batch delivery wave (Phase 9, R-094 → R-104) builds on. Phase 9 ships the receiver-side staging buffer (LatticeReplicationOptions.AtomicBatchDelivery, default alse) that consumes the size / index slots stamped here and applies every batch under one saga. ## 🔲 Phase 9 - Atomic visibility cross-cluster *(closes the carve-out R-089 deferred)*

Causal+ pins the dependency graph but is **strictly weaker than atomic visibility**: a remote reader concurrent with replication of a `SetManyAtomicAsync` may observe a partial view (some keys arrived and applied, others have not) until every entry in the batch finishes converging on that peer. R-089's retrospective explicitly flagged this as a follow-on. Phase 9 closes it via a receiver-side staging buffer that holds every key in an in-flight atomic batch until the whole batch is in hand and then applies them under a single saga that preserves source-side metadata verbatim. Per-tree opt-in via `LatticeReplicationOptions.AtomicBatchDelivery` (default `false`); operators trade extra latency and a partially-buffered batch's GC pin against the stronger visibility guarantee. Cross-tree atomicity is intentionally out of scope (one batch is one tree) - that broader primitive would require multi-tree saga coordination that the core library does not expose.

The phase is a tightly-coupled wave: R-094 / R-095 ship the producer-side metadata; R-096 ships the per-tree opt-in; R-097 ships the receiver-side staging buffer; R-098 ships the atomic apply on completion via Core F-054; R-099 / R-100 close the producer-side GC and orphan-recovery hazards the buffer introduces; R-101 ships observability; R-102 closes the bootstrap interaction; R-103 ships the chaos verification; R-104 ships the operator playbook. Build sequentially - each item directly depends on the prior one and several depend on outstanding core enablers (F-054 most prominently).

- [x] **R-098 ✓ shipped - Atomic apply on completion via Core F-054** *(depends on R-097 ✓, Core F-054 ✓)*
  On batch completion (every `Size` entries for a `(originClusterId, transactionId)` key are buffered), the receiver dequeues the batch under one saga via `IReplicationApplyGrain.ApplyManyAtomicAsync(entries, transactionId, originClusterId, sourceVectorClock, ct)` (Core F-054).   Per-origin HWM advance: on apply completion, the receiver advances the per-origin HWM **once** to the maximum HLC across the batch (not per-entry), and **only if** the apply succeeded all-or-nothing. A failed apply leaves the HWM unchanged so the producer re-ships the batch on the next pump cycle. This is the critical invariant that delivers atomic visibility cross-cluster: a concurrent reader observing the per-origin HWM never sees an intermediate value where some-but-not-all keys have been applied.

  Idempotency: F-054's `ApplyManyAtomicAsync` is itself idempotent on `transactionId` (the underlying `AtomicWriteGrain` is keyed by `(treeId, transactionId)` and replays its persisted saga state on re-entry), so a producer that re-ships the same batch after a transient receiver failure observes the same terminal outcome on the second attempt.

  Per-entry observability still fires: R-064's `apply.lag` and R-068's `apply.duration` continue to record per-entry inside the saga, so existing dashboards do not lose granularity. R-101 adds the new transaction-scoped instruments alongside.

### ✅ FX-015 ✓ shipped - Per-partition resume cursor on outbound shipper *(reliability / high - ship-throughput collapse under sustained writes)*
The outbound shipper grain drains its per-`(tree, peer)` batch via `IChangeFeed.Subscribe(treeName, hlcCursor)`, which walks **every** WAL partition from sequence `0` on every pump tick and filters in-app by `entry.Timestamp > cursor`. At sustained-write benchmark rates (1188/s WAL appends, single peer, single partition) the rescan dominates the pump's work budget and the ship rate caps at ~10/s - three orders of magnitude below the WAL append rate. Steady-state `apply.lag` p99 pegs the 10000 ms top bucket; the WAL grows unboundedly until the GC catches up after the load eases. Independently, the per-tick allocation profile is dominated by `IAsyncEnumerator` state-machine boxes and `List<WalRecord>` fill/sort pairs inside `ChangeFeed`. The fix is to give the shipper its own durable per-partition resume cursor (sequence-based, not HLC-based) and bypass `IChangeFeed` in the steady-state hot path: each pump tick reads the next page from each partition starting at the saved sequence, then merges by `entry.Timestamp` (HLC ascending) via a heap-free O(P) linear scan-for-min over partition-page heads - collapsing to O(1) for the default `ReplogPartitions=1` case. The merge runs against activation-scoped scratch arrays sized lazily on first activation, so steady-state pump ticks allocate nothing beyond the page DTOs the shard grain returns. `IChangeFeed` is retained verbatim for bootstrap, test, and future-materialiser consumers that have no notion of partition routing - its docstring already anticipates this divergence. The HLC `state.Cursor` is preserved unchanged because the GC consumes it via `ILatticeReplicationCursorRegistry.ReportCursorAsync` - partition cursors are private shipper state and never surface to the GC predicate. New public option `LatticeReplicationOptions.ShipPartitionPageSize` (default `256`, validator `>= 1`) caps the per-partition page size; distinct from `ShipBatchSize` which caps the merged output batch. Wire-compat additive change: new `[Id(2)] PartitionCursors` slot on `ReplicationShipperState` decodes as the empty map for legacy persisted state (cold-start equivalent). Persistence is amortized: new public option `LatticeReplicationOptions.ShipCursorWriteInterval` (default `16`, validator `>= 1`) writes the cursor state once per N successful acks instead of once per ack - receiver-side apply is HLC-monotonic and dedupes on `(originClusterId, originHlc)`, so a silo crash inside the deferred-persist window costs at most `N × ShipBatchSize` entries of wasteful re-shipping (the receiver no-ops the duplicates) but no data loss. Load-bearing invariant: `ILatticeReplicationCursorRegistry.ReportCursorAsync` is called strictly after `WriteStateAsync` completes, so the WAL GC trim frontier never exceeds the durably-recoverable cursor; this is a tightening of today's already-correct ordering and is preserved across the deferred-persist change. Setting `ShipCursorWriteInterval=1` recovers the current persist-every-ack behavior.

### ✅ FX-016 ✓ shipped - Tag `apply.duration` and inbound apply counters with the source peer *(observability / high - per-peer inbound attribution silently broken)*
The `ApplyDuration` histogram (and the `ApplyLag` / receiver-side throughput counters that pair with it) documents a `peer` tag in both its XML doc (`Tagged by TagTree, TagPeer, and TagOutcome`) and its OTel `description` string (`tagged by tree, peer and outcome`), but the actual `Record(...)` call site in `ReplicationApplier.RecordApplyDuration` emits only `tree` and `outcome` - the applier's `IReplicationApplier.ApplyBatchAsync(entries, ct)` signature is peer-agnostic and never threads the origin through. The `LatticePushService.Push` gRPC server method validates `request.OriginClusterId` and surfaces it in error logs but does not feed it back into the metric path either. The result is a docstring/implementation drift that operators cannot detect without tracing meter callbacks: dashboards built against the documented schema render an unattributed time-series, log-based correlation is the only way to break inbound apply latency or rate down by source peer, and any consumer that filters Prometheus / OTel queries by `peer="..."` silently gets the empty set. The fix is to thread the origin through the apply path: every `WalRecord` already carries `OriginClusterId` (populated by the ship side and round-tripped through the envelope), so `RecordApplyDuration` can tag with `peer = entry.OriginClusterId` per-entry without an interface change; the aggregate `ApplyBatchAsync` shape needs the same treatment so multi-origin batches don't lose signal (record one sample per origin, or tag with the dominant origin). Per-entry path (`ReplicationApplier.ApplyAsync`): the `RecordApplyDuration` helper gains a `peerOriginClusterId` parameter threaded from the caller; `ApplyAsync`'s `finally` passes `entry.OriginClusterId ?? string.Empty` so an empty value (e.g. when the upstream origin guard threw before any apply work happened) is emitted verbatim rather than skipped - keeping per-tree cardinality stable across failure outcomes. `RecordApplyLag` reads `entry.OriginClusterId` directly inside its own scope and emits the `peer` tag alongside `tree`.
