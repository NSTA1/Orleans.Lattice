# Changelog

All notable changes to the Orleans.Lattice package family are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

This changelog covers the **package family**: `Orleans.Lattice`, `Orleans.Lattice.Replication`, `Orleans.Lattice.Replication.Grpc`, `Orleans.Lattice.Storage.AzureTable`, `Orleans.Lattice.Dashboards`, `Orleans.Lattice.Api.State`, and `Orleans.Lattice.Api.State.Grpc`. Packages ship in lockstep on the major and minor digits; patch digits may advance per-package.

### Added

- **F-110 - Orleans.Lattice.Api.State: read-only cluster-state introspection surface.** A new optional package-family member exposes a cluster's tree state and metadata over a transport-agnostic read facade, with no write, delete, or reconfigure verb. `ISiloBuilder.AddLatticeStateApi(...)` (called after `AddLattice`) registers the facade and a shared metrics sampler in-process; the companion `Orleans.Lattice.Api.State.Grpc` package binds it over a code-first gRPC service (`AddLatticeStateApiGrpc` + `MapLatticeStateApiGrpc`) consumed by the public `LatticeStateApiGrpcClient`. The surface covers tree / view discovery with per-tree lifecycle state and effective config (catalog), a paged depth-limited tree-structure snapshot backed by pushed-up O(shards) topology metadata, snapshot-isolated predicate-capable entry / key-range inspection and single-key fetch, a resumable server-streaming change-observation feed that stays off the write hot path, and a coalesced live metrics / topology-delta stream for dashboard gauges. The gRPC binding fails closed: with authorization required and no authorizer registered, the default `DenyAllStateApiAuthorizer` rejects every call, and the authorization seam carries the requested operation and target tree id. Many subscribers to one metrics request share a single reference-counted sampling loop, and registering nothing adds zero overhead. The facade is built to be reused in-process by a later MCP bridge. New packages `Orleans.Lattice.Api.State` and `Orleans.Lattice.Api.State.Grpc`; see [`docs/lattice.api.state/README.md`](docs/lattice.api.state/README.md) (#836).

- **F-139 - State API entries now carry the CRDT shape.** `EntryRecord.CrdtShape` (returned by `ILatticeStateQuery.ScanEntriesAsync` / `GetEntryAsync` and across the gRPC binding) is no longer always `null`: it now reports the name of the tree's declared CRDT merge mode (for example `"OrSet"`) for a typed-CRDT tree, and stays `null` for an opaque last-writer-wins tree. The shape is sourced from the per-tree merge mode the system already tracks, so a consumer - the Explorer Data tab or any external dashboard - can tell a CRDT entry apart from raw bytes without decoding the value. No new wire field or alias; the existing `CrdtShape` slot is simply populated. See [`docs/lattice.api.state/surfaces.md`](docs/lattice.api.state/surfaces.md) (#951).

- **F-143 - State API: read a key's change history through `GetEntryHistoryAsync`.** A new read-only State API endpoint `ILatticeStateQuery.GetEntryHistoryAsync(EntryHistoryRequest, ct)` - sibling to `GetEntryAsync`, bound over the gRPC service and the `LatticeStateApiGrpcClient` and explorer client - returns a single key's change-history timeline as a continuation-paged list of revision records. Each `EntryRevisionRecord` carries the revision's hybrid-logical-clock, kind (set / delete / CRDT delta / range tombstone), origin cluster id, mutation category, and a value-or-metadata view bounded by the tree's retention mode (a size-bounded value / delta preview with full length when values are retained; a content hash and length only under metadata-only retention). A CRDT revision whose bytes were retained in full also carries the decoded element-level member changes (added / removed element, replica, causal ordinal) via the F-142 provenance decoders. Every revision carries a per-row `RevisionRetention` descriptor (the retention mode applied when the row was written, and whether its value bytes were retained) so a consumer can detect a retention-config transition by diffing adjacent revisions, and the response's top-level `EntryHistoryBound` reports whether the timeline is durable-bounded-by-age (the F-141 history view), truncated (the bounded write-ahead-log fallback, with the earliest still-readable clock), or a write-ahead-log-window fallback when no history view is enabled. The read is backed by `ILattice.ScanEntryHistoryAsync`; an optional `Reverse` flag orders revisions newest-first within each page. New public types `EntryHistoryRequest`, `EntryRevisionRecord`, `RevisionRetention`, and `EntryHistoryBound` (in `Orleans.Lattice.Api.State`), `EntryHistoryResponse` (in `Orleans.Lattice.Api.State.Grpc`), and a new `LatticeStateApiOperation.GetEntryHistory`; new serializer aliases `ola.ehq` / `ola.erev` / `ola.rret` / `ola.ehb` / `olag.ehresp`. See [`docs/lattice.api.state/surfaces.md`](docs/lattice.api.state/surfaces.md) (#955).

- **F-144 - Orleans.Lattice.Explorer: History tab (per-key revision timeline, retention-mode aware).** A new History tab in the explorer detail panel renders a selected key's change-history timeline over the F-143 `GetEntryHistoryAsync` State API endpoint, for both CRDT and plain last-writer-wins keys. It reuses the Data tab's key selection (drill into a key in the Data tab, then switch to History, or type a key directly) and shows the active retention mode for the key as a badge. Each revision row carries its relative and absolute hybrid-logical-clock timestamp, originating replica / cluster id, and operation kind (set / delete / crdt-merge / range-delete), and renders adaptively to the per-row retention shape: a full-value (or value-retaining hybrid) LWW revision shows the JSON-aware value preview plus a line diff against the previous retained value; a metadata-only revision shows the value hash and length with an explicit "values not retained - metadata only" affordance and no diff; a CRDT revision shows decoded element-level member add / remove events with their originating replica rather than a raw blob. An inline divider marks a retention-configuration transition between adjacent revisions (for example `retention changed: full-value -> metadata-only`), derived purely from the per-row retention descriptors with no extra backend call. The page surfaces a prominent "history truncated by retention" banner only for the trimmed write-ahead-log fallback, a subtler bounded-by-age hint for the durable history view, and a WAL-window-fallback hint when no history view is enabled; a newest-first toggle and a "load more revisions" continuation page the timeline. New explorer types `IHistoryReader` / `HistoryReader`, `HistoryTimeline`, `HistoryPage`, `HistoryRevisionRow`, `HistoryMemberChange`, `HistoryValueDiff`, `HistoryDiffLine`, `RetentionTransition`, and the render-branch enums `HistoryRowRenderMode` / `HistoryDiffLineKind`, plus the `History` detail tab and the `AddExplorerHistory` registration (#956).

- **F-145 - Orleans.Lattice.Explorer: live follow mode for the History tab.** With a key open, the History tab now keeps its timeline live: it subscribes to the forward change feed (`ObserveChangesAsync`) scoped to the tree, filters client-side to the followed key, and appends each new mutation to the timeline in real time without a manual refresh, so the user watches history grow. A visible "Live" indicator with a pause / resume control sits above the timeline; while paused, incoming changes are buffered (and shown as a count) and flushed on resume so none is lost. A live-appended row is a lightweight metadata-only marker - it carries only the notification's kind, hybrid-logical-clock timestamp, and origin, with no value preview, line diff, or CRDT member list - clearly flagged as the live tail pending a durable backfill; the timeline never re-fetches per notification. Rows are de-duplicated against the already-loaded page by hybrid-logical-clock (the identifier both a loaded revision and a live notification carry), so the retrospective page and the live tail never double-count where they overlap. The subscription is torn down on key change and tab dispose (no leaked stream or background task). The live feed only carries changes emitted while the tab is open: it extends the timeline forward from "now" and is not a substitute for durable history retention of past changes. New explorer types `IHistoryLiveFollower` / `HistoryLiveFollower` and `HistoryLiveTail`, plus the `HistoryRowRenderMode.LiveTail` render branch and the live follow wiring on the `History` detail tab (#957).

- **F-146 - Change-history sample + docs showcase.** The change-history epic is now discoverable and demonstrable end to end. On startup the `MultiSiteManufacturing` sample enables a durable per-key history view, with value-retaining (`FullValue`) retention, over two CRDT trees - so the timeline survives source write-ahead-log garbage collection rather than depending on the transient WAL-window fallback - and then seeds a multi-revision timeline into them: a sequence of operator handoffs on the `mfg-part-operator` last-writer-wins register and interleaved label add / remove operations on the `mfg-part-labels` OR-Set, both for part `HPT-BLD-S1-2028-00002`, so the Explorer's History tab shows a non-trivial timeline (successive values plus diffs, and decoded element-level member changes) the moment the sample runs; the sample README documents the run-and-inspect flow against `run-explorer.ps1`. A new [`docs/lattice/change-history.md`](docs/lattice/change-history.md) page documents the capability end to end - the durable history view vs retained-WAL-window fallback vs live-feed distinction, the value-retention modes (metadata-only / full-value / hybrid) and bounded-by-age vs truncated caveats, the State API `GetEntryHistoryAsync` endpoint, and the Explorer History tab with live-follow - and is linked from the README documentation table. Docs and sample only; no public-API or wire-format change (#958).

- **Orleans.Lattice.Explorer: the Data tab's selected-entry detail now updates live.** With a key selected in the Explorer **Data** tab, its value / decoded CRDT current-state panel now refreshes automatically as the underlying entry is mutated, instead of staying frozen at the value read when the key was first opened. The detail subscribes to the forward state-API change feed (`ObserveChangesAsync`) scoped to the tree, filters client-side to the selected key (an exact match, or a range delete whose swept range covers it), and on a match debounces a silent re-read (`GetEntryAsync`) that swaps the displayed value and decoded CRDT members with no spinner - so a CRDT key's members appear and disappear in step with the writes. A connection-state-mirrored "Live" indicator sits in the detail header and a non-fatal "Live updates stopped" note surfaces a dropped subscription, mirroring the History tab. The subscription is torn down on key change and tab dispose (no leaked stream or refresh loop), and the live wiring degrades gracefully when the change-feed services are not registered. The live feed only carries changes emitted while the tab is open. New explorer types `IEntryLiveFollower` / `EntryLiveFollower` and the `EntryChangeSignal` value type (#1018).

- **Orleans.Lattice.Explorer: the Data tab renders a CRDT key's live current state.** Inspecting a key on a typed-CRDT tree in the Explorer **Data** tab now shows the decoded **current, complete, live state** of the value - only the members presently in the set / map / register / sequence, the net counter total, or the current flag state - rendered as element-level rows, instead of the raw serialized blob. Crucially, a removed OR-Set element no longer appears: the rendering is a value-level projection of the folded CRDT, not a provenance timeline, so an element whose add dots have all been tombstoned is correctly absent. The projection is computed server-side via a new `ICrdtProvenanceDecoder.DecodeCurrentValue(state)` method (implemented by every shape decoder) and surfaced on the `EntryRecord.CurrentMembers` field - now a list of the new `CrdtMemberValue` (live member: element bytes, contributing replica, causal ordinal) rather than the add/remove `CrdtMemberChange` provenance projection - across both the single-key detail (`GetEntryAsync`) and the entry list (`ScanEntriesAsync`), so an external consumer gets the live members in both paths. Materialised **views** and **tag-index** trees now reuse the same rendering: a predicate / key-preserving view mirrors its source tree's CRDT shape and decodes the same live members instead of rendering raw hex, a flag-membership tag index renders its current boolean state, while an aggregation view, a history view, and an opaque last-writer-wins value all correctly stay blobs. Detection degrades gracefully when the view / CRDT services are not registered. New public type `CrdtMemberValue` (serializer alias `ol.cmv`); the Data tab's removed-member rendering path is gone. See [`docs/lattice.api.state/surfaces.md`](docs/lattice.api.state/surfaces.md) (#1013).

- **Orleans.Lattice.Explorer: history views guide to the History tab instead of rendering hex.** Selecting a change-history (accumulative) view in the Explorer **Data** tab no longer dumps the serialized history-record bytes as raw hex. The tab now detects a history view and shows a guidance panel that names the view's source table and routes the operator to its per-entry History (open a key in the source table's Data tab, then choose History), with a "Go to source table" action that selects the source tree via the shared explorer selection (switching the navigation list to its **Trees** toggle so the source tree is listed and highlighted). The value scan and the live-entry follow loop are skipped entirely for a history view, and history views carry a small `history` badge in the navigation view list. Backing this, the State API's `ViewStateSummary` gains an additive `[Id(6)] IsHistory` flag (populated from the view registration's accumulative nature) so a consumer can tell a history view apart from a value / aggregation view; `ListViews` still enumerates every view so metrics rollups keep their observability. See [`docs/lattice.api.state/surfaces.md`](docs/lattice.api.state/surfaces.md) (#1019).

### Fixed

- **FX-068 - Opening a snapshot-isolated cursor no longer wedges an entire sharded tree while it captures its baseline.** Opening a point-in-time (snapshot) cursor freezes a per-shard baseline on every physical shard root, and each capture walks that shard's whole leaf chain and materialises its rows on the shard root's non-reentrant turn. The open previously fanned that capture out to every shard root at once (an unbounded `Task.WhenAll`), so on a wide tree a single snapshot open - for example a State-API / Explorer `ScanEntries` over a 64-shard tree - blocked every shard root simultaneously, starving the cross-cluster replication applies and reads queued on those same roots (a peer stalling mid-backfill, a dashboard reading empty, and the tree tripping write throttle), and a client timeout-and-retry sustained the storm. The fan-out is now bounded by a new `LatticeOptions.MaxConcurrentSnapshotCaptures` knob (default 4): at most that many shard roots are blocked on their baseline capture at a time, so the rest of the tree stays free to serve replication and reads while the open proceeds in waves. The captured baseline and its point-in-time consistency are unchanged - only the dispatch schedule is bounded; a value below 1 is clamped to 1 at the open site. See [`docs/lattice/configuration.md`](docs/lattice/configuration.md) (#1054).

- **FX-069 - A snapshot-cursor open is now shed fast when the tree is saturated, instead of piling its baseline capture onto collapsing shard roots.** Completes the snapshot-scan-storm series (after FX-068 bounded the fan-out). Opening a point-in-time cursor is heavier than a write - it freezes and materialises every shard's leaf chain on the non-reentrant shard roots. When a tree is already WAL-saturated (writes are being back-pressured), admitting one still fed that work onto roots that were collapsing, prolonging the starvation of replication applies and reads and feeding a client-retry storm on the resulting timeout - exactly the Explorer-driven regime that motivated the series. `OpenSnapshot*CursorAsync` now checks the per-silo WAL saturation signal at admission and, when the tree reports `Saturated`, sheds the open before any capture is fanned out by throwing a retryable `LatticeSaturatedException` carrying the tree id. Only `Saturated` sheds; a `Throttled` tree is unaffected and stays browsable, mirroring the atomic-write saga's quiesce gate. Gated by a new `LatticeOptions.ShedSnapshotOpensWhenSaturated` knob (default `true`; set `false` to restore the prior always-open behaviour). Over the read-only state API the refusal maps to gRPC `ResourceExhausted`, and the Explorer catches it to keep the connection usable, skip the storm-amplifying auto-retry, and show a plain non-expert "this table is very busy, try again" notice with a Try again action. No wire-format change. See [`docs/lattice/snapshot-cursors.md`](docs/lattice/snapshot-cursors.md) and [`docs/lattice/configuration.md`](docs/lattice/configuration.md) (#1053).

- **FX-070 - The live metrics tab no longer walks every shard twice, and steps aside entirely for a saturated tree.** Completes the snapshot-scan-storm series (after FX-068 bounded the snapshot fan-out and FX-069 shed saturated opens) by giving the metrics surface the same restraint. A per-tree metrics sample previously issued two full per-shard diagnostics fan-outs on a cold or post-cache-expiry load: one for the tile aggregates (live keys, tombstones, depth, splitting shards) and, when per-shard hotness was requested, a second, redundant walk for the hotness rows - each fanning a leaf-chain walk out to every non-reentrant shard root. Both projections are now derived from a single deep per-shard walk, so requesting hotness adds no extra fan-out. In addition, the sampler now consults the per-silo WAL saturation signal per tree: when a tree reports `Saturated`, it skips the fresh per-shard walk entirely and serves a degraded snapshot built from a single fan-out-free routing read - lifecycle and shard count (and any requested view lag) remain, while the live counts and hotness are paused - so the metrics tab never piles read load onto shard roots that are already collapsing under a write backlog. Only `Saturated` pauses detail; a `Throttled` tree still samples fully, mirroring the rest of the series. The new `TreeMetrics.DetailPaused` flag (serialized additively, no new alias) reports the paused state to a consumer; the Explorer metrics tab renders the paused tiles and a plain non-expert "live counts and per-shard hotness paused - tree is busy" note that clears automatically once the tree settles. See [`docs/lattice.api.state/surfaces.md`](docs/lattice.api.state/surfaces.md) and [`docs/lattice.api.state/efficiency.md`](docs/lattice.api.state/efficiency.md) (#1058).

- **FX-071 - A write burst no longer floods the replication shipper with a doorbell per commit.** The commit-time replication sink rings a per-`(tree, peer)` shipper's doorbell after every committed write to wake its background ship loop for low-latency shipping. Under a sustained write burst that fired one doorbell per commit per peer, and because the shipper activation is non-reentrant, its turn queue grew without bound (observed in the thousands): fresh doorbell messages were dropped as expired before they ran, and the keepalive reminder that actually drives shipping was starved behind the backlog - so shipping stalled and the peer fell behind exactly when it had the most to ship. A doorbell is an idempotent, edge-triggered "there is work" signal, so the sink now coalesces at the source: it collapses a burst of ring requests for the same `(tree, peer)` into at most one in-flight ring plus one pending follow-up. A request that arrives while a ring is already in flight sets a single pending flag instead of dispatching its own `OnDoorbellAsync` grain call, and the in-flight ring loop fires exactly one trailing ring once it drains - so the last write in a burst still wakes the shipper (no missed wake), while the doorbell message rate the shipper sees is bounded to a small constant regardless of write throughput. Shipping latency and the base phase-timer / keepalive-reminder safety net are unchanged. Two new metrics on the `orleans.lattice.replication` meter - `orleans.lattice.replication.doorbell.rung` (rings dispatched) and `orleans.lattice.replication.doorbell.coalesced` (rings elided), both tagged by tree and peer - expose the coalescing ratio. No wire-format or public-API change. See [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md) and [`docs/lattice.replication/replication-drivers.md`](docs/lattice.replication/replication-drivers.md) (#1061).

- **FX-067 - Cross-cluster replication no longer wedges permanently when an apply batch repeatedly exceeds the receiver's phase-2 commit timeout.** Sender-side adaptive batch sizing (`LatticeReplicationOptions.AdaptiveBatchSizingEnabled`) now **defaults to `true`** (was `false`). Previously, an oversized apply batch that deterministically exceeded the receiver's `PhaseTwoCommitTimeout` during the manifest-commit phase (for example a few-hundred-entry batch into a large WAL partition under a burst seed, with a slow storage backend) was abandoned and dead-lettered, the receiving partition cursor never advanced, and the shipper backed off and re-fetched the *identical* oversized batch on every retry - so the same commit re-timed-out forever and the peer fell permanently behind with the receiver silo reporting WAL saturation. With adaptive sizing on by default, the shipper's AIMD controller treats the repeated send failure as a multiplicative-decrease signal and halves the effective per-tick batch size on each failure (down to a floor of one entry), so the batch shrinks until a single manifest commit fits inside the timeout budget and the stream resumes; the additive increase then rebuilds the batch toward `ShipBatchSize` once the link is healthy. A healthy link whose window-mean ack latency stays at or below `AdaptiveBatchLatencyThreshold` (default 50 ms) stays pinned at the configured `ShipBatchSize` ceiling, so steady-state behaviour is unchanged; set `AdaptiveBatchSizingEnabled = false` to restore the static-sizing path. No wire, serialization, or public-API change - only the default value of an existing flag. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#sender-side-adaptive-batch-sizing) (#1047).

- **FX-066 - Paged range scans no longer read to the end of the tree on a sparse range.** `ShardRootGrain`'s forward / reverse sorted key- and entry-batch readers (and their slot-filtered variants) terminated the leaf sibling walk only on a full page or end-of-tree, never when the walk passed `endExclusive`: a sparse half-open scan (for example a single-serial prefix scan over a many-serial tree) whose in-range matches were fewer than the page size therefore kept fetching the next sibling and reading every remaining leaf to the end of the tree - an O(tree size) grain-call fan-out for an O(range size) query, and the per-scan amplifier behind the MultiSiteManufacturing dashboard scan-storm. The coordinator now consults each leaf's persisted owned-key-range bounds via the new `IBPlusLeafGrain.GetKeyRangeAsync` (returning `LeafKeyRange`) and stops the forward walk once a leaf's `HighKeyExclusive` reaches `endExclusive`, and the reverse walk once its `LowKeyInclusive` reaches `startInclusive`. The signal is range-based rather than emptiness-based, so a scan whose predicate filters every in-range row on a leaf still terminates correctly, and a null bound (the outermost leaf, or legacy leaf state predating the slot) falls back to the prior end-of-tree behaviour. Scan results, ordering, and `HasMore` pagination semantics are unchanged; new public type `LeafKeyRange` (serializer alias `ol.lkr`) and the `GetKeyRangeAsync` leaf accessor (#1046).

- **FX-065 - WAL leaf-materialiser drain path no longer wedges a cluster under a modest write burst.** A burst of only a few hundred writes into a freshly-seeded tree could saturate every silo and drop a co-hosted dashboard / Explorer connection, and a `docker restart` re-wedged because the pressure was durable. Root cause: every active leaf mirrored its per-WAL-partition checkpoint frontier into a single per-tree durable pin grain with an awaited `WriteStateAsync` per advancing report, so a leaf-birth / split storm funnelled `O(leaves x partitions)` serialized durable writes through one activation, and no signal observed materialiser drain lag so the existing write-admission and replication back-pressure never engaged. The fix (a) coalesces durable pin writes behind a debounced grain-timer flush and batches the birth seed into a single through-write, collapsing a report burst to one durable write per shard per window; (b) re-keys the durable pin store across `WalMaterialiserPinShards` shard activations (the WAL GC dual-reads every shard plus the legacy key during the migration so no trim floor is lost); (c) measures leaf-materialiser drain lag on every saturation-sampler tick (default 200 ms) directly from in-memory state - the WAL head wall-clock minus the slowest in-memory materialiser cursor frontier (so an idle, caught-up tree reads zero and never trips) - so the back-pressure engages immediately on a write spike rather than waiting for a WAL GC pass; when the lag stays above `WalSaturationMaterialiserLagThreshold` (enabled by default at 30s) for `WalSaturationMaterialiserLagSampleWindows` consecutive sampler windows it holds the tree at Throttled - a pure back-off that slows callers without ever faulting them - and the local WAL writer obeys the signal by pacing each admission by `WalThrottledAdmissionPace` (default 25ms) so the single-silo write path slows even when no remote replication sender exists to drip-feed, while the replication receiver flow control throttles the upstream sender when one does (this is what protects a downstream cluster); (d) caps concurrent activation-time leaf replays per silo at `WalMaterialiserMaxConcurrentReplays` (default `Environment.ProcessorCount`) and yields cooperatively every `WalReplayMaxRecordsPerTurn` records so a reactivation storm queues instead of stampeding the scheduler; and (e) adds durable-pin-write, drain-lag, activation-replay, and cursor-publish-failure metrics (with a rate-limited activation-failure warning) plus two CommitPath dashboard panels. New public options `WalMaterialiserPinShards`, `WalMaterialiserPinFlushIntervalMs`, `WalSaturationMaterialiserLagThreshold`, `WalSaturationMaterialiserLagSampleWindows`, `WalThrottledAdmissionPace`, `WalMaterialiserMaxConcurrentReplays`, and `WalReplayMaxRecordsPerTurn`; new serializer alias `ol.wpr` (`MaterialiserPinReport`). The durable pin store re-keys forward-compatibly; the drain-lag back-pressure (30s threshold) and local pacing (25ms) are enabled by default so the wedge is prevented without configuration, and the only change to retained WAL is the new coalescing window (always GC-safe). `AddLattice` now always registers both the in-memory `IWalCursorRegistry` and a lightweight in-memory `ILeafCursorReporter`, so every leaf publishes its applied checkpoint frontier into the registry and the sampler's drain-lag back-pressure is live for every write workload out of the box rather than only on hosts that opt into the materialiser / replication stack. A host that trims the WAL still opts into the durable cross-restart pin backstop via `AddWalCursorRegistry`, which upgrades the lightweight reporter to the durable-pin-aware `LeafCursorReporter`; a host-supplied custom registry or reporter is always preserved. See [`docs/lattice/configuration.md`](docs/lattice/configuration.md) (#1030).

- **FX-063 - A CRDT anti-entropy / bootstrap resync row now renders in history as a member snapshot, not a raw blob.** Follow-up to FX-062. A single CRDT change appeared on the receiving cluster as a `CrdtDelta` member diff, but a later anti-entropy / committed-projection resync still shipped a full-state row (`Set`, value = whole serialized OR-Set/PN-counter/OR-Map, no delta) that recorded as a full-value set and rendered as a raw blob tripping the explorer's value-preview cap - confusing duplicate-looking noise on CRDT trees. The history row already carries the source merge mode, so the explorer now classifies a CRDT-mode `Set` as a membership snapshot (decoded members, visually distinct from an LWW overwrite) rather than a last-writer-wins value diff; LWW sets still render as value diffs. Replication apply correctness and wire format are unchanged - bootstrap full-state stays a correct full-state merge, it just renders nicely. Presentation/classification fix in `Orleans.Lattice.Explorer`; no public-API or wire-format change (#1010).

- **Explorer can now inspect a view's Data, Topology, and History tabs.** Selecting a view under the Explorer "Views" catalog no longer reports "The requested tree or entry was not found." A materialised view is a read-only tree (its physical id is `view-<name>`), and the Explorer now queries that physical id while still showing the bare view name in the list and detail header. The read-only state API inspection endpoints (`GetTreeStructureAsync`, `ScanEntriesAsync`, `GetEntryAsync`, `GetEntryHistoryAsync`) now admit `view-*` trees read-only under an authorised view-read scope, exposing the view's active generation, while system (`_lattice_*`) trees stay hidden and view writes stay rejected (#1009).

- **Orleans.Lattice.Explorer web head now enforces antiforgery on the sign-in / sign-out endpoints (login / logout CSRF hardening).** The web head's `/auth/login` and `/auth/logout` form-post endpoints previously called `.DisableAntiforgery()`, justified by `SameSite=Strict` on the credential cookie - but that cookie is not presented on the login POST itself, so it gave no CSRF protection. A cross-site form post could drive a victim's browser to authenticate (or sign out) the Explorer with attacker-chosen credentials, and because the auth session is a process-global singleton this flipped the shared connection's credential for the whole process. Both endpoints now validate a `RequestVerificationToken` (the login and logout forms embed `<AntiforgeryToken />`) and reject a tokenless or mismatched post with `400 Bad Request` before touching the auth session. Explorer-only change; no public-API or wire-format change to the package family. (#966)

- **Atomic-write saga no longer fails when Orleans' reminder service is still initialising.** A `SetManyAtomicAsync` saga that starts inside the reminder service's asynchronous startup window - or just after a partition / restart - registered its crash-recovery keepalive reminder via `RegisterOrUpdateReminder` before the service was ready and surfaced the transient `OrleansException: "Reminder Service is still initializing..."` (inner `TimeoutException`), failing the whole atomic write (observed as a flake in the cross-cluster atomic-visibility chaos suite). Unlike the best-effort first-write bootstraps that defer the same transient and re-attempt on a later write, the saga keepalive is essential and has no later-write seam, so it now waits the startup window out with a bounded retry (`ReminderServiceReadiness.RetryWhileInitializingAsync`) and only surfaces a genuinely stuck reminder service once the retry budget is exhausted. Core `Orleans.Lattice` robustness fix; no public-API or wire-format change (#1029).

- **Replication chaos suite: the LWW convergence test no longer flakes under CI CPU starvation.** `Concurrent_writes_across_three_sites_under_partition_pick_lexicographic_max` polls every site for a converged last-writer-wins value within a fixed budget after the delivery pump drains. On a heavily CPU-starved CI runner that 30s budget could elapse before the background gossip pumps finished re-emission, surfacing as a spurious value-divergence failure - even though the merge is deterministic on the original `(HLC, origin)` and the never-partitioned site pair cannot drop a delivery, so a genuine permanent divergence is not possible in this scenario. The post-drain convergence settle budget is raised (30s to 60s) to widen the starvation tolerance, and a convergence-failure message now reports any errors the background delivery pumps swallowed so a genuine stuck state is distinguishable from a starvation timeout. Test-only change; no public-API or wire-format change (#1040).

- **Replication public-API contract suite: the WAL-GC min-cursor probe no longer flakes under CI contention.** `ILatticeWalGc_run_once_min_cursor_is_non_null_after_consumer_reports` polls a far heavier probe than the simple convergence checks the shared 40s ceiling is sized for - each iteration force-deactivates every data leaf, reactivates one with a read (driving a full WAL-replay checkpoint flush that lifts the birth-time block pin) and runs a complete GC pass - so on a contended CI runner a healthy run could exhaust the 40s ceiling. The probe now gets explicit per-call-site headroom instead of inflating the shared ceiling the lightweight convergence probes depend on; a genuinely stuck block-pin stays null and still fails at the larger deadline, so the extra headroom cannot mask a real regression. Test-only change; no public-API or wire-format change (#1041).

- **Replication public-API contract suite: the WAL-GC min-cursor probe flake is a lockstep race, fixed structurally (supersedes the #1041 timeout bump).** The #1041 headroom bump did not work: the same test later blew through the raised 90s ceiling, which falsifies the CI-contention hypothesis - a bigger budget cannot help if the probe condition never becomes true. Empirically the probe is fast (it converges in seconds even under full CPU saturation), so the failure was never slow I/O. The real cause is that `IBPlusLeafGrain.ForceDeactivateAsync` is fire-and-forget (it calls `DeactivateOnIdle`, which only schedules deactivation after the current turn), and the probe read the tree immediately afterwards. When the read won the race it landed on the still-warm leaf, which does no WAL replay and never lifts the birth-time block pin, so `MinCursor` stayed null indefinitely. The fix deactivates the data leaves and then waits for the scheduled deactivation to apply before reading, so the read deterministically drives a cold reactivation, replay, and checkpoint flush; the inflated per-call timeout is reverted to the shared default. Test-only change; no public-API or wire-format change (#1042).

### Added

- **F-140 - Read a key's revision timeline.** A new core read method `ILattice.ScanEntryHistoryAsync(key, fromHlc, toHlc, limit, continuation, ct)` returns a single key's change history as a page of `EntryRevision` records (hybrid-logical-clock stamp, revision kind, origin cluster id, vector clock, and a size-bounded value / delta / metadata preview that mirrors the entry-inspection record). When the F-141 durable history view is enabled for the tree, the primary read is a prefix scan over the view tree's `{sourceKey}/{encodedHlc}` rows - reusing the ordinary entry range-scan machinery, paged with the existing continuation-token mechanism, ordered by encoded clock - so a key's timeline stays readable after the source write-ahead log has been garbage-collected and is reported as clean (`EntryHistorySource.View`, never truncated, bounded only by the configured retention age). For a tree that has not opted into a history view, the method falls back best-effort to the retained source write-ahead-log window for the key's partition above the current garbage-collection trim point, in offset order, and reports truncation honestly (`EntryHistoryPage.Truncated` plus the earliest still-available clock) so a partial window is never mistaken for full history; a delete and a CRDT-delta each map to the right revision kind and payload. The read is side-effect-free and never perturbs the history maintainer or its log pins. New public types `EntryRevision`, `EntryHistoryPage`, and `EntryHistorySource`; see [`docs/lattice/history-views.md`](docs/lattice/history-views.md) (#952).

- **F-141 - Durable per-key history as an opt-in accumulative materialised view.** A new history-view substrate records every revision of every key in a source tree by re-keying each source mutation into an append-only revision row at `{sourceKey}/{encodedHlc}`, maintained on the existing materialised-view subsystem so a key's full timeline survives source WAL garbage collection. Enable it the runtime way - `ILatticeViewFactory.Create(source, name, LatticeHistoryView.Definition(name, services))` - and disable it with `DeleteAsync`; it is off by default with zero cost for trees that do not opt in. An `Accumulative` flag on the view registration suppresses the two rebuilds that would otherwise collapse the timeline (a projection-version change adopts forward and keeps existing rows; an unconstrained range delete records a range-tombstone marker), while an explicit operator rebuild stays the only intentional clear. Per-tree retention is live-tunable through `ILattice.SetHistoryRetentionAsync` / `GetHistoryRetentionAsync`: a `HistoryRetentionMode` of `MetadataOnly` (default - hash and length, no value bytes), `FullValue`, or `Hybrid` for last-writer-wins values (CRDT revisions are always stored delta-only), plus an optional age-bound window stamped onto each row's expiry. New public types `LatticeHistoryView`, `HistoryLatticeViewProjection`, `HistoryRow`, `HistoryRowKind`, `HistoryRetentionMode`, and `HistoryRetentionSettings`; see [`docs/lattice/history-views.md`](docs/lattice/history-views.md) (#953).

- **F-142 - CRDT element-level provenance decoding for every CRDT shape.** A new pluggable decoder turns a CRDT's stored state and/or its author deltas into ordered, element-level member-change events - which element was added or removed, by which replica, in what causal order. `ICrdtProvenanceDecoder` is the per-shape abstraction and `CrdtProvenanceDecoderRegistry` resolves the right decoder by CRDT shape (the same shape tag the State API surfaces on an entry). Every typed CRDT merge mode now has a registered decoder: `OrSetProvenanceDecoder`, `PnCounterProvenanceDecoder`, `VersionVectorProvenanceDecoder`, `MvRegisterProvenanceDecoder`, `OrMapProvenanceDecoder`, `SequenceProvenanceDecoder`, `OrFlagProvenanceDecoder`, and `RwFlagProvenanceDecoder`; the non-CRDT `LwwRegister` shape has no member-level provenance and resolves to nothing (its value-over-time timeline is covered elsewhere). Decoding prefers the author-delta sequence (`CrdtProvenanceDelta`, which preserves operation order and can carry the owning mutation's wall-clock stamp) and falls back to reconstructing provenance from the folded primitive's dots/entries when only the current state is available. Each `CrdtMemberChange` is explicit that a CRDT dot is a causal ordinal (a per-replica counter), not a wall-clock time: a real `HybridLogicalClock` is attached only when the caller supplies the owning mutation's stamp, otherwise events expose causal order only. Per-shape mappings are documented on each decoder (for example: sequence inserts/removes carry node bytes; OR-map surfaces key membership only; the flags carry an empty element because the flag itself is the member; the PN-counter uses the change ordinal to carry a per-replica magnitude rather than a causal counter; the version vector is a causal-frontier snapshot). Concurrent adds from multiple replicas are all represented (no last-writer-wins loss) and a removed-then-re-added element surfaces both events. New public types `CrdtMemberChange`, `CrdtMemberChangeKind`, `CrdtProvenanceDelta`, `ICrdtProvenanceDecoder`, `CrdtProvenanceDecoderRegistry`, `OrSetProvenanceDecoder`, `PnCounterProvenanceDecoder`, `VersionVectorProvenanceDecoder`, `MvRegisterProvenanceDecoder`, `OrMapProvenanceDecoder`, `SequenceProvenanceDecoder`, `OrFlagProvenanceDecoder`, and `RwFlagProvenanceDecoder`; new serializer aliases `ol.cmc` / `ol.cmk`. Core-library addition in `Orleans.Lattice`; no wire-format change to existing types (#954).

- **Optional `LatticeOptions.MaxKeyLength` / `MaxValueSizeBytes` write-size bounds (memory-exhaustion hardening).** Two additive, opt-in options bound the size of a key (character count) and a value or CRDT delta (byte count) accepted by the `ILattice` write surface - `SetAsync` and its TTL overload, `SetIfVersionAsync`, `GetOrSetAsync`, `SetManyAsync`, and the CRDT delta-apply path. When set, an oversized write is rejected with `ArgumentException` at the public boundary before any shard work, so a single misbehaving or hostile authorized writer cannot drive unbounded heap growth and exhaust silo memory. Both default to `null` (unbounded), preserving the historical behaviour; when set they must be at least `1`, enforced by the options validator. No breaking signature change. See [`docs/lattice/configuration.md`](docs/lattice/configuration.md) (#968).

### Changed

- **`MvRegister` merge no longer allocates two transient dot-key `HashSet`s per merge.** `MvRegister.MergeFrom` (the in-place fold behind the static `MvRegister.Merge`, the per-write `MergeDelta` path, and every replication state merge) built one `HashSet<(string, long)>` over each side's live dots purely to answer "is this dot still present on the other side?". A register is single-valued in the steady state and multi-valued only transiently, so both entry lists are tiny; the membership check is now a linear scan over the other side's entries, eliminating both `HashSet` allocations on the hot path. Behaviour is unchanged - the same-dot-on-both-sides survivor rule and pointwise-max context fold are preserved, so the merge stays commutative, associative, and idempotent. Public API and wire format unchanged. Evidence (BenchmarkDotNet `Crdt mvregister merge`, ShortRun + MemoryDiagnoser, two concurrent single-value replicas over an 8-replica shared context): allocated/op ~1168 B -> 768 B (-400 B, ~34%). (#1002)

- **`MvRegister.Values()` no longer builds a 4-stage LINQ pipeline per call.** `MvRegister.Values()` (read on every multi-value register inspection) built an `OrderBy(...).ThenBy(...).Select(...).ToArray()` chain on every call, allocating several iterator and comparer objects plus the result array even for a single-valued register - the steady state. The single-entry case now short-circuits to a one-element array with no sort and no LINQ, and the multi-value case copies the entries out and uses `Array.Sort` with one cached comparer that reproduces the former `(ReplicaId ordinal, Counter)` ordering exactly. Observable output ordering, the public API, and the return type are unchanged. Evidence (BenchmarkDotNet `Crdt mvregister values`, ShortRun + MemoryDiagnoser): single-value allocated/op ~616 B -> 32 B (-95%); 8-value allocated/op ~976 B -> 368 B (-62%). (#1000)

- **`OrSet` no longer allocates a transient `HashSet<OrSetDot>` per key on the merge/remove hot path.** State-level `OrSet.MergeFrom` built one `HashSet` over every per-key dot list, and `OrSet.Remove` built one over the per-element tombstone list, even though an element overwhelmingly carries 1-2 concurrent-add dots; the set construction dominated the actual work. Both paths now take a linear dedup scan while the dot list is small (matching the threshold `LiveDotCount` already used) and only build a `HashSet` once a key genuinely accumulates many concurrent dots, so the O(n+m) protection against quadratic blow-up is retained. Behaviour is unchanged - union of adds and tombstones - so the merge stays commutative, associative, and idempotent. Public API and wire format unchanged. Evidence (BenchmarkDotNet `Crdt orset merge`, ShortRun + MemoryDiagnoser, two 16-element single-dot sets with a half-overlapping range): allocated/op ~6.2 KB -> 4.27 KB (~31%). (#1003)

### Fixed

- **Receiver-side replication shipper no longer re-reads a filtered-only WAL suffix from storage every tick.** Companion to FX-064. On a receiver cluster, a replicated tree's WAL tail is entirely foreign-origin (authored by the peer, applied locally), so the outbound shipper drains it, `ShouldShip` filters every entry out, and the ship buffer ends empty - the pump then returns before `AdvanceCursorAsync`, leaving the durable partition cursor parked behind the foreign suffix. As the peer keeps shipping writes that suffix grows without bound, so each pump tick re-read an ever-larger range from WAL storage (observed live as the EU cluster's Azurite staying ~86-110% CPU while the writer-side US cluster fell to ~6% after FX-064). The serial and bounded-pipelined pump paths now fold the consumed-but-filtered partition cursors past that suffix on a fully-healthy tick (HLC ship cursor untouched - nothing was shipped), so the next tick resumes past it; advancing past foreign entries is safe because origin mismatch is permanent and WAL GC trims on the minimum across all consumers. The fold is allocation-aware: a genuinely idle tail (no entries consumed) returns a cached completed task and never enters the async state machine. `Orleans.Lattice.Replication` fix; no public-API or wire-format change (#1017).

- **FX-064 - Idle WAL tail-polling no longer floods storage with no-op reads.** Every per-partition WAL tailer re-read the durable store on each tick even when caught up: the cross-cluster replication shipper (`WalShardGrain.ReadShippingAsync`, default 10 Hz x 8 partitions) and the materialised-/history-view maintainer drain (`WalLogSubscriber.DrainAsync` -> `IWalShardGrain.ReadAsync`, plus a per-drain `GetTailOffsetAsync` fall-off probe at the view `CoalesceWindow`, default 20 Hz x 8 partitions) each issued an unconditional storage read on every call - so an idle cluster generated a constant stream of empty tail queries against the durable store (observed in the MultiSiteManufacturing sample as ~1300 Azure Table reads/s and ~110% Azurite CPU at rest, the bulk of them empty tail-polls dominated by the view-maintainer drain). The shard grain already tracks the next WAL offset in memory, so a new shared `IsAtOrBeyondTail` guard now returns an empty page directly from that cursor whenever the caller is already at or beyond the tail - covering both `ReadShippingAsync` and `ReadAsync` - and the subscriber drain now skips the storage-backed fall-off probe when an in-memory head check proves the consumer cannot have fallen off, eliminating the round-trips. The hot read methods (`ReadAsync`, `ReadShippingAsync`, `GetNextSequenceAsync`) also return `ValueTask<T>` so the idle fast path completes without a `Task` allocation. Real backlog reads (caller behind the tail) and the commit-driven doorbell wake path are unchanged, so write-propagation latency is unaffected. Core-library fix in `Orleans.Lattice`; no wire-format change; grain-interface signatures widened to `ValueTask<T>` (#1015).

- **FX-062 - Replicated CRDT changes now appear in the receiver's history as member diffs, not a full-value set.** A CRDT mutation (OR-Set tag add/remove, PN-counter, OR-Map, etc.) made on one cluster surfaced on the receiving cluster's entry-history view as a full-value `Set` (origin = source cluster, whole serialized blob tripping the explorer's value-preview cap) instead of a `CrdtDelta` with per-member ADDED/REMOVED changes like a locally-authored write. The per-entry replication applier folded the inbound delta into local state and re-wrote it with a version-checked set, which the history projection classified as a full-value `Set`. The steady-state delta-carrying typed-CRDT and OR-Map applier paths now forward the delta verbatim through the same `CrdtDelta`-recording grain seam the batch path uses (preserving source HLC and origin id), so cross-cluster and local CRDT histories are consistent; bootstrap committed-projection rows (no per-delta shape) keep their full-state set. `Orleans.Lattice.Replication` fix; no public-API or wire-format change (#1005).

- **Cursor pages no longer pre-allocate an unbounded buffer from the caller-supplied `pageSize` (denial-of-service hardening).** The stateful cursor grain behind the public `ILattice.NextKeysAsync` / `NextEntriesAsync` (and the snapshot-isolated variants) sized each page's result buffer directly from the caller's requested `pageSize`. A request with a hostile or buggy `pageSize` (up to `int.MaxValue`) reserved gigabytes of list capacity before a single entry was read, throwing `OutOfMemoryException` and faulting the silo against an arbitrarily small or empty range. The up-front buffer capacity is now clamped to a fixed ceiling; a page is still filled by a streaming scan that stops after `pageSize` items, so paging semantics are unchanged (a legitimately large page still grows on demand and the returned page is still "up to pageSize") while the amplification is removed. Core-library fix in `Orleans.Lattice`; no public-API or wire-format change. (#965)

- **`DeleteRangeStepAsync` no longer pre-allocates an unbounded probe buffer from the caller-supplied `maxToDelete` (denial-of-service hardening; sibling of #965).** The cursor grain behind the public `ILattice.DeleteRangeStepAsync(cursorId, maxToDelete)` sized its per-step probe buffer directly as `new List<string>(maxToDelete + 1)`. The only guard was `ThrowIfNegativeOrZero`, with no upper ceiling - the clamp added in #965 for the `NextKeysAsync` / `NextEntriesAsync` page buffers did not cover this delete-range path. A hostile or buggy `maxToDelete` near `int.MaxValue` reserved a multi-gigabyte list backing array before a single key was read (throwing `OutOfMemoryException` and faulting the silo against an arbitrarily small or empty range), and `int.MaxValue` specifically overflowed the `+ 1` to `int.MinValue`, throwing `ArgumentOutOfRangeException` instead. The up-front capacity is now clamped to the same fixed ceiling via the existing `PageBufferCapacity` helper (clamp applied before the `+ 1`, so the arithmetic can no longer overflow); the probe still streams up to `maxToDelete + 1` keys and the list grows on demand past the ceiling, so step budgeting and delete semantics are unchanged. Core-library fix in `Orleans.Lattice`; no public-API or wire-format change. (#1024)

- **`WalShardGrain.AppendBatchAsync` now bounds the accepted entry count (defence-in-depth).** The batched WAL append pre-allocated per-entry working arrays sized directly to `entries.Count` before doing any work, so a pathologically large batch could reserve arbitrarily large arrays up front (memory-exhaustion risk). The method now rejects a batch whose entry count exceeds a fixed internal ceiling with `ArgumentOutOfRangeException` before any allocation. `IWalShardGrain` is an internal grain reached only via the WAL/replication pipeline, so the ceiling is generous enough that no legitimate coalesced batch reaches it. No public-API or wire-format change (#969).

### Changed

- **Snapshot frozen baselines are seeded in memory and persisted lazily, removing write-amplification on single-page scans.** A snapshot capture previously wrote one durable per-shard baseline row at open and deleted it at close, even for a scan that drained in a single page. The per-shard materialised baseline is now seeded straight into the transient `ISnapshotLeafGrain` in memory at capture; the durable write happens lazily, fanned out across the shards the first time a page reports `HasMore == true`, before the continuation token is returned. A snapshot that drains in one page therefore performs zero durable baseline writes or deletes, while any cursor that survives past page 1 (and can fail over) is still backed by a durable baseline. A seeded leaf evicted before its first page is read fails the next read with `LatticeSnapshotExpiredException` so the caller reopens; a wrong point-in-time view is never returned. Persisted baselines now carry a sliding, throttled time-to-live (new `LatticeOptions.SnapshotBaselineTtl`, default 6 hours) so an orphaned baseline from an interrupted close is reclaimed by a self-clearing reminder while a long-running scan keeps its baseline alive. No public-API or wire-format change. See [`docs/lattice/snapshot-cursors.md`](docs/lattice/snapshot-cursors.md) (#916).

- **F-107 - Replication producer is log-first by default; the commit-time path is reduced to a wake nudge.** The single per-shard write-ahead log written by the leaf commit-log writer is now the one and only source the replication producer ships from. The existing per-`(tree, peer)` `IReplicationShipperGrain` - activated at startup by the replication driver hosted service, kept alive by a keepalive reminder, with a durable per-partition sequence checkpoint persisted across restarts and origin / maintenance / key filtering - tails that leaf WAL directly and is the sole, default, always-on ship driver. The commit-time `IReplogSink` (`ShardedReplogSink`) no longer performs a second, redundant WAL append on the foreground write path: it is reduced to a low-latency nudge that advances the producer-side local vector clock and rings the shipper doorbells so the tailing loop drains immediately instead of waiting for its next timer tick. This removes a synchronous cross-grain WAL round-trip from every replicated commit. A new internal `IWalSubscriber` log-tailing subscriber seam is added, and the materialised-view maintainer's ordinary and aggregation drain loops now run through it instead of carrying their own copy of the tailing mechanics. No public-API or wire-format change. See [`docs/lattice.replication/architecture.md`](docs/lattice.replication/architecture.md) and [`docs/lattice.replication/wal.md`](docs/lattice.replication/wal.md) (#795).

- **Removed the now-unused producer-side local vector clock cache; the commit-time replication nudge is a pure tree-id doorbell.** The producer no longer maintains an in-memory producer-side vector clock mirror at commit time. The shipped causal frontier is sourced entirely from the leaf write-ahead log that the log-tailing shipper reads, so the commit-time mirror it superseded is dead state. The internal `IReplogSink.WriteAsync` is narrowed from `(WalRecord, CancellationToken)` to `(string treeId, CancellationToken)` - it is now purely a wake nudge keyed by the committed tree id, ringing the per-peer shipper doorbells with no record payload. `IReplogSink` is an internal seam, so this is not a public-API or wire-format change, and producer convergence is unaffected because the frontier the shipper sends still comes from the durable leaf WAL. The restore seeder (`IReplicationLocalVcSeeder`) keeps its durable high-water-mark pin and only drops the in-memory prime step that has no remaining consumer (#942).

### Fixed

- **FX-060 - Durable WAL hosts no longer silently launder committed data to empty when the WAL is trimmed past a leaf's durable checkpoint.** A cold leaf activation with an empty per-activation cache and no covering snapshot drove WAL replay with a `-1` "rebuild-the-whole-readable-window" override. That override deliberately suppresses the fall-off-log detector's shared-WAL replay-budget heuristic (the documented sibling-populated-shard false positive), but it also blinded the detector's WAL-trim trigger: a leaf with a real durable checkpoint `N > 0` whose WAL had been trimmed past `N` was read as "nothing to lose", so the leaf silently rebuilt from only the surviving WAL suffix - dropping every trimmed key - then advanced its persisted checkpoint and durable materialiser pin over the lost data, licensing the WAL GC to trim further and laundering the loss across the whole tree (observed live on the MultiSiteManufacturing US cluster, where every tree's durable leaf baselines were emptied while the EU cluster retained its own seeded copy). `ReplayWalSinceCheckpointAsync` now carries a durable-frontier fall-off guard, gated strictly on the cold-reset override: it reads the oldest still-readable WAL offset and throws `LeafProjectionStaleException` when the first offset the leaf still needs (`checkpoint + 1`) has fallen off the log, converting silent permanent loss into a loud, operator-actionable stale projection that drives a rebuild. The benign issue-#919 shape - only the already-applied prefix trimmed with the live tail intact (`tail == checkpoint + 1`) - still replays cleanly. The hazard is not replication-specific: any durable-WAL trim past a leaf's checkpoint (a forward replication consumer, the `WalRetention` TTL ceiling, or a materialised-view cursor) is now contained. This is the containment-and-detection layer; FX-061 ships the root-cause prevention that stops the trim from happening in the first place. Core-library fix in `Orleans.Lattice`; no public-API or wire-format change. (#945, #946).

- **FX-061 - WAL GC no longer trims past a data-holding leaf's durable materialiser frontier before that leaf has registered a blocking pin.** A leaf becomes data-capable the moment it acquires a `TreeId` at one of its two birth seams - `InitializeSiblingAsync` (an adaptive-split sibling) or `SetTreeIdAsync` (a root or bulk-load leaf) - and then accepts committed data via `MergeEntriesAsync` immediately after. `MergeEntriesAsync` persists nothing to the leaf baseline (the WAL is the sole durable commit point) and reports no materialiser pin, so between birth and the leaf's first checkpoint the only durable copy of those keys was the WAL rows, with no pin blocking them. A forward trim driver that advances the WAL floor in that window - the replication shipper, a materialised-view cursor, or the `WalRetention` TTL ceiling - could therefore trim committed-but-un-materialised data straight out of the log, which then fed the FX-060 cold-replay laundering path. The leaf now seeds a durable `HybridLogicalClock.Zero` materialiser block pin atomically at both birth seams, awaited before any data merge, via the new `ILeafCursorReporter.SeedDurableMaterialiserBlockAsync` seam; the `Zero` pin holds the cursor-driven trim floor at the leaf's frontier until the leaf takes its first checkpoint and advances the pin past `Zero`, at which point the block lifts and steady-state trimming is byte-for-byte unchanged. This is the root-cause prevention complementing FX-060's containment, and it is the only protection for a non-replicated durable-WAL host that has no healthy peer to re-bootstrap from. Core-library fix in `Orleans.Lattice`; no public-API or wire-format change. (#947, #949).

### Breaking

- **F-107 - The `orleans.lattice.replication.wal.entries_appended` counter is removed.** It counted the redundant commit-time WAL append that no longer happens; the leaf commit-log writer is the single WAL appender and the log-tailing shipper is the producer. Producer ship-rate remains observable through `orleans.lattice.replication.wal.entries_shipped`. Dashboards or alerts that referenced the growth-rate-vs-ship-rate ratio should track ship-rate (and WAL retention / GC) instead. - **FX-055 - Cross-cluster replication bootstrap no longer loops forever when the sender's snapshot enumerator is reclaimed mid-stream.** The sender-side snapshot export (`LatticeSnapshotProvider`) drove its committed-projection pass through the raw `ILattice.EntriesAsync` grain async-enumerator. ### Fixed

- **FX-054 - CRDT writes are no longer silently lost across a silo restart on a non-replicated tree.** A CRDT write made via `ILattice.ApplyCrdtDeltaAsync` (or any typed-CRDT `Set`) was silently discarded on a cold WAL replay for every tree whose merge-mode resolver does not return the tree's CRDT mode at replay time - every tree on a single-cluster host, and any non-replicated tree on a replicated host. A durable-WAL host (`AddAzureTableWalStorage`) running **without** the replication package therefore never trimmed its WAL, and every **non-replicated** tree in a replicated host was never collected - both grew without bound, and `LatticeOptions.WalRetention` was inert for them. A new per-silo background scheduler runs `ILatticeWalGc.RunOnceAsync` over **every** registered tree (replicated or not) on the new global `LatticeOptions.WalGcInterval` cadence, registered automatically by `AddLatticeWalGc`. It defaults to **1 hour, enabled**, so `LatticeOptions.WalRetention` is effective out of the box; a pass is retention housekeeping, so the coarse default keeps the storage cost low (cost scales with `trees × WalPartitions` per silo). A host that needs a tighter disk bound can lower it; set `WalGcInterval` to `TimeSpan.Zero` (or any non-positive value) to disable the built-in scheduler. It composes with the replication maintenance grain - `RunOnceAsync` and the underlying WAL `TrimAsync` are idempotent, and the pass honours the minimum consumer cursor and the leaf-materialiser checkpoint floor, so a tree collected by both drivers is trimmed safely and it never over-trims. A per-tree GC failure is logged and skipped without stalling the rest of the pass, and a transient registry-enumeration fault is retried on the next tick. The first pass is staggered by a random half-to-one interval offset rather than run at silo start, so it does not add I/O during silo activation and a rolling cluster restart does not align every silo's fan-out into a correlated I/O storm. See [`docs/lattice/configuration.md`](docs/lattice/configuration.md) (#920).

- **FX-052 - Snapshot-isolated scans no longer silently return empty or partial results after a WAL GC trim.** Snapshot-isolated scans (`OpenSnapshotEntryCursorAsync` / `OpenSnapshotKeyCursorAsync`, the read-only state API, and the Explorer Data tab) returned an empty or partial key set on any tree whose committed WAL prefix had been GC-trimmed. The snapshot leaf rebuilt its view by replaying each partition's WAL from offset 0 with no durable checkpoint baseline, but a snapshot reader is an ephemeral reader that registers no WAL retention pin, so `LatticeWalGc` was free to trim the prefix the from-zero replay needed; after a trim the replay read a short or empty slice and served it as the whole history. The live (non-snapshot) path was unaffected because it reconstructs from `checkpoint blob + WAL tail`. Snapshot scans now serve a durable, per-cursor, per-shard frozen baseline captured at open time: the shard root walks each shard's leaf chain, freezes every leaf's warm projection, reads a uniform per-partition `capturedHead`, folds each leaf's own non-overlapping `(frontier, capturedHead]` WAL tail exactly once (so non-idempotent CRDT folds - PN-counters and the like - are never double-counted), unions the leaf projections, and persists the result keyed by `(coordinate, shardIndex)`. The transient snapshot leaf seeds from that baseline through the existing `IsKeyOwned` ownership filter (preserving the FX-050 / FX-051 donor-orphan / virtual-slot exclusion) and does no serve-time WAL replay, so a later GC trim cannot affect it; rebuild-after-eviction reloads the same frozen baseline for a point-in-time view stable across failover. The baseline is deleted on cursor close and on idle-TTL eviction. The `MaxSnapshotReplayEntries` budget gate now bounds the materialised baseline row count. No public-API change; `LatticeSnapshotCoordinate` gains an `[Id(5)] SnapshotBaselineToken` (legacy coordinates default to `Guid.Empty` and fall back to the from-zero replay path). After a full silo/cluster restart that registry is wiped: a forward consumer that persists its own cursor (the replication shipper re-reports its durably-advanced cursor eagerly on activation) could momentarily be the only registered consumer for a tree, while a dormant leaf-materialiser re-registers its pin only lazily on its next activation. The GC then computed its trim floor over the forward consumer alone and trimmed the WAL past the leaf's durable checkpoint, discarding the committed-but-not-yet-checkpointed tail the leaf needed to replay (observed live: a part-label OrSet write and seeded LWW facts were lost across a `docker compose stop/start`, while a non-replicated tree - never GC'd - survived). Each leaf now mirrors its checkpoint frontier into a cluster-wide durable pin grain (one activation per tree, keyed by the tree id, persisted through the configured grain storage); the mirror is fire-and-forget and coalesced off the checkpoint path, and because a too-low durable pin only ever retains more WAL it is always GC-safe. The WAL GC consults the durable pins and lowers its trim floor for any materialiser consumer missing from the in-memory registry (a present consumer keeps its fresher in-memory cursor, so steady-state trimming is unchanged), and a leaf that activated but never checkpointed seeds a durable `Zero` block pin that holds its WAL head until the first checkpoint (the `WalRetention` TTL ceiling still bounds growth). `AddAzureTableWalStorage` now also wires the cursor registry and WAL GC seams (both idempotent) so durable WAL storage never ships without the durable floor. No public-API or wire-format change. See [`docs/lattice/wal.md`](docs/lattice/wal.md) (#919).

- **FX-048 - Concurrent-ingest leaf split no longer crashes the write path with a backward projection-checkpoint advance.** Under sustained concurrent ingest, a B+ leaf split could fault the write path with `ArgumentOutOfRangeException` ("Projection checkpoint must be monotonically non-decreasing"). By completion the captured head was stale (lower than the donor's current checkpoint), and stamping it tripped the monotonic-non-decreasing guard in `SetCheckpointOffsetAsync`. The split-completion advance is only meant to push the donor forward to the split frontier, so it now skips the advance for any partition whose current checkpoint (persisted, maxed with any pending in-memory value) already meets or exceeds the captured head, never asking the guard to move a checkpoint backward. The guard itself is unchanged and still rejects genuine backward moves elsewhere. No public-API or wire-format change (#905).

- **FX-046 - De-flake the cross-cluster atomic-visibility test under CI load.** The replication contract test `SetManyAtomicAsync_visibility_on_remote_site_is_zero_or_all_throughout_convergence` failed the instant its continuous remote-site `GetManyAsync` reader observed a snapshot whose 8 keys did not all carry the same authored round, recording it as a partial-saga visibility violation. Under CI load that occasionally fired on a transient inter-cluster ship/apply window - one key lagged a single round while the receiver was mid-transition between two back-to-back sagas - even though the universe converged a moment later. The reader now settles a multi-round snapshot on a bounded re-read budget before declaring a violation: a transient window resolves to a single round within a read or two and polling resumes, while a genuinely stuck key (or a never-converging saga) persists past the budget and still fails the test with the captured per-key round detail. Test-harness only - no product code change (#901).

- **FX-049 - Public `ILattice` operators now transparently retry transient silo-membership-churn faults, not just cold-start seed timeouts.** A read, write, fan-out, or coordinator call whose target shard activation was hosted on a silo that is restarting, draining, or has just left the cluster surfaced `Orleans.Runtime.SiloUnavailableException` (the activation's host is gone) or an `OrleansMessageRejectionException` (a rejected forward to a deactivating grain) straight to the caller - a membership-convergence artifact that clears the moment the Orleans directory re-places the activation on a live silo. Both retry envelopes that already absorb the cold-start `ShardActivationTimeoutException` - the central per-key `RetryOnStaleRoutingAsync` seam (covering `GetAsync` / `SetAsync` and the other single-key paths, including the four inlined hot-path loops) and the per-call / fan-out `ShardActivationRetry` envelope (covering `CountAsync`, the multi-shard fan-outs, coordinator entry points, sagas, and digests) - now also classify these two churn shapes as transient and reissue them under the same bounded budget and idempotency contract (detection is by type name via the new `ShardActivationRetry.IsTransientSiloChurn`, mirroring the atomic-write saga coordinator's existing deactivation-race detection, because one of the Orleans types is internal). A genuinely unavailable cluster still surfaces the exception once the budget is exhausted. This hardens steady-state operation across secondary-silo restarts and scale-down; the originally-reported symptom was a CI flake where `Chaos_secondary_silo_restart_under_load_preserves_universe` failed its post-window `CountAsync` re-read, whose chaos test additionally gained a bounded post-window settle as defense-in-depth. No public-API or wire-format change (#903).

- **FX-050 - Snapshot-isolated scans no longer surface duplicate keys or stale values after an adaptive shard split.** A snapshot entry / key cursor (`OpenSnapshotEntryCursorAsync` / `OpenSnapshotKeyCursorAsync`, the read-only state API, and the Explorer Data tab) over a tree that had undergone an adaptive shard split returned every moved key twice (adjacent in sort order) and could surface a stale value for a moved key that was updated or deleted after the split. The live scan path was already correct - it reconciles donor `MovedAwaySlots` in its k-way merge and dedups per call - but three defects on the snapshot path remained. First, the snapshot leaf for a donor shard re-materialised its retained orphan copies of moved keys because it filtered replayed mutations by the stamped `ShardIndex` rather than by current slot ownership; the donor and target leaves then each emitted the key. Second, the snapshot fan-out opened against a cached, possibly pre-split routing map, so the pinned map could miss the new target shard. Third, and deepest, a post-split write routed to the donor for an already-moved slot is shadow-forwarded into the target shard's WAL but keeps the donor's source stamp, so the same stamped-`ShardIndex` filter dropped that forwarded record (for example a post-split delete) on the target's snapshot leaf - a cold, checkpoint-free replay - resurrecting the drained pre-forward value. The snapshot coordinate now pins a fresh post-split shard map (`PinnedShardMap`), the cursor resolves each fan-out shard's owned virtual slots under that pinned map and passes them to the snapshot leaf, the leaf resolves per-mutation ownership by the key's virtual slot under the pinned map (keeping shadow-forwarded records so the LWW merge applies them, while dropping donor orphans and sibling-shard multiplexed entries), and the snapshot k-way merge collapses any residual adjacent duplicate as a defensive net. Ownership is resolved point-in-time against the pinned map version so the snapshot stays internally consistent. No public-API or wire-format change. See [`docs/lattice/shard-splitting.md`](docs/lattice/shard-splitting.md) and [`docs/lattice/consistency.md`](docs/lattice/consistency.md) (#907).

## [7.3.0] - 2026-06-20

Minor release across the package family. The headline addition is **asynchronous materialised views** (F-106): a source tree can now project an eventually-consistent, WAL-tailing filter / re-project / aggregation view, maintained in its own tree and read through the ordinary `ILattice` surface - see [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) for the full feature. Supporting the views, a new core mixed atomic set+delete primitive (`SetManyAtomicAsync(upserts, deletes, operationId)`, FX-042) closes the re-key retraction window. On the performance side, lazy post-merge CRDT row materialisation now flattens per-apply allocation from O(state) to O(delta) on both the writerless and durable-writer paths (F-108 / F-109), and the replication receiver folds typed-CRDT delta runs server-side in one batched grain call. The `Microsoft.Orleans.*` family moves to 10.2.0. Stability fixes include removal of the WAL `set-point` phase-one 409 conflict storm and a material reduction of the residual single-account brown-out wedge. See the per-section entries below.

### Added

- **F-122 - Materialised-view source-tree and view-on-view guards.** Two front-door correctness guards close lifecycle gaps in the (unreleased) materialised-view feature. (a) A source tree that still has one or more materialised views can no longer be deleted: `ILattice.DeleteTreeAsync` throws `InvalidOperationException` naming the dependent view(s), so a view can never have its source soft-deleted/purged out from under it (which would freeze the view at stale state, leak the maintainer's source-WAL cursor pin, and fault later rebuilds). The dependent-view lookup is authoritative across the durable runtime-view registry, the startup-declared registrations, and the in-memory catalog, and is resolved through an optional service registered only by `AddLatticeViews`, so a host without views is unaffected. (b) A view can no longer derive from another view: `ILatticeViewFactory.Create` and the startup `AddView` / `AddAggregationView` builders reject a `view-*` source tree with `InvalidOperationException`. No public API or wire change. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#839).

- **FX-042 - Atomic re-key retraction for materialised views via a core mixed set+delete primitive.** A new `ILattice.SetManyAtomicAsync(List<KeyValuePair<string, byte[]>> upserts, IReadOnlyList<string> deletes, string operationId)` overload applies a batch of upserts and deletes all-or-nothing in one visibility flip, so no reader observes a partial set/delete; each delete becomes visible on commit and is dropped on abort, riding the same saga terminal as the upserts. The cross-tree fluent builder gains `LatticeAtomicWriteBuilder.Delete(string key)` and `LatticeTreeBatch` gains an optional `EntryDeletes` channel so a cross-tree atomic batch can carry retractions too. The materialised-view maintainer now flushes a completed atomic batch's upserts and retraction deletes inside this single mixed atomic op on both the single-tree filter/aggregation path and the cross-tree joint-flip path, closing the re-key window: when a source mutation moves a row from view key A to view key B, the upsert at B and the delete at A flip together so a reader never observes both view keys (or neither) at once. No wire-format change (the new per-entry delete channel is optional; an upsert-only batch is byte-identical to before). See [`docs/lattice/atomic-writes.md`](docs/lattice/atomic-writes.md) and [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#803).

- **Batched receiver-side typed-CRDT delta apply.** The replication receiver previously applied each inbound typed-CRDT delta (`OrSet`, `PnCounter`, `MvRegister`, `VersionVector`, flag modes) through a per-entry optimistic read-merge-write loop over the public `ILattice` surface - `GetWithVersionAsync` + `SetIfVersionAsync` per entry, each re-serialising the full O(state) CRDT value client-side and retried under contention - so a run of N CRDT mutations cost O(N) round trips and O(N·state) allocation. The applier's batch path now defers non-prepared CRDT-mode `Set` entries into a single new `IReplicationApplyGrain.ApplyCrdtDeltaManyAsync` grain call that folds every delta server-side inside one non-reentrant grain turn, reusing the same registered `CrdtShape` fold the producer and prepared-commit paths use and stamping each item's source origin / vector-clock / HLC verbatim. Because CRDT folds are commutative, associative, and idempotent, a batch applies in any order and a re-delivered run converges to the same state, so the per-entry concurrency retry is unnecessary. `OrMap` keeps its generic-shaped per-entry seam; prepared/saga entries, null-delta entries, and single-entry runs are routed exactly as before. A grain-seam A/B microbench (`crdt_receiver_apply_per_entry` vs `crdt_receiver_apply_batched`) shows the batched lane cuts per-apply allocation ~78-80% at N≥64 and wall time ~36-46% at N=64/256. Internal-only; no public API or wire change (#802).

- **F-109 - Lazy CRDT post-merge row materialisation on the writerless apply path.** A typed CRDT delta-apply (`ILattice.OrSet(key).AddAsync(...)` and the other value-surface accessors) previously re-serialised the full post-merge state on every apply to populate the in-memory leaf `byte[]` row - an O(state) cost that grows with the accumulated element count even though each apply carries only an O(delta) change. On the writerless apply path (no `ICommitLogWriter` consuming the bytes this apply), the leaf now keeps the typed shadow read-authoritative for the key and produces the canonical row bytes lazily at the first consumer (a `GetAsync` read, snapshot / persist capture, split / projection, replication ship, or any row enumeration), feeding the projection digest from a reused streaming serialiser so the per-apply allocation is O(delta) instead of O(state). The streaming and lazy array serialisers are byte-identical, so a materialised read matches the digest contribution already folded in. Adds a `crdt_apply_growstate` growing-state apply microbench. Internal-only; no public API, wire, or behaviour change (#799).

- **F-108 - Lazy CRDT row materialisation extended to the durable writer path.** The post-merge row deferral shipped on the writerless path now also applies when a commit-log writer is present, so production silos - which always have an `ICommitLogWriter` wired - stop paying the O(state) full-state re-serialisation on every CRDT delta-apply. Because the canonical WAL encoder already strips `WalRecord.Value` for non-prepared CRDT-mode `Set` records, the producer no longer materialises the post-merge state into that slot at all; the persisted and cross-cluster wire bytes are unchanged. The cold-rebuild replay path now folds the typed delta into the prior visible state through the registered `CrdtShape` (mirroring the prepared-commit and cross-cluster receiver folds) rather than reading the stripped value, which also closes a latent gap whereby a non-prepared CRDT key replayed from a durable serialising provider could otherwise rebuild with a null value. A writer-wired `crdt_apply_growstate_writer` microbench confirms the per-apply allocation flattens from O(state) to a flat ~7.7 KB - a 97% reduction at 4096 accumulated OrSet elements - with no regression on the point read / write / apply guard cohorts. Internal-only; no public API or wire change (#800).

- **F-106 (Phase 1) - Asynchronous materialised views.** A source tree can now project an asynchronous, eventually-consistent materialised view maintained by tailing the per-shard write-ahead log. Phase 1 ships a filter / key-preserving re-project view: a built-in `PredicateLatticeViewProjection` keeps the subset of source keys whose value satisfies an `Expression<Func<T, bool>>` filter, optionally transforms the stored value and re-keys the entry, retracts a key that updates out of the predicate, and converges by source hybrid logical clock (last-writer-wins). The view lives in its own `view-{name}` tree read through the ordinary `ILattice` surface, and a view handle (`ILatticeView`) exposes the query surface plus apply-lag observation and an in-place rebuild. Register with `ISiloBuilder.AddLatticeViews(...)` after `AddLattice` (views require a WAL provider, not a replicated cluster; `AddLatticeViews` folds in `AddWalCursorRegistry` so a view can pin the source WAL); declare views at startup or create them at runtime through the injected `ILatticeViewFactory`. The maintainer skips background-maintenance and uncommitted / transactional WAL entries, durably checkpoints its per-partition apply offset, pins the WAL garbage collector to its applied cursor, and rebuilds on a fall-off-log or projection-version change. New public types in the `Orleans.Lattice` namespace: `ILatticeView`, `ILatticeViewFactory`, `ILatticeViewProjection`, `PredicateLatticeViewProjection`, `LatticeViewDefinition`, `LatticeViewOptions`, `ViewWrite`, and `ViewWriteKind`; new silo-builder extensions `AddLatticeViews` and `ConfigureLatticeView` in the core `Orleans.Lattice` package. New `orleans.lattice` meter instruments: `orleans.lattice.view.apply_lag`, `orleans.lattice.view.backlog_depth`, and `orleans.lattice.view.applied`. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 2) - Re-keyed materialised-view deletes, range deletes, and a read-your-writes barrier.** A re-keyed materialised view now retracts correctly: because the built-in `PredicateLatticeViewProjection` key re-map is a pure function of the source key, a value-less delete or tombstone recomputes the same view key the upsert produced and removes it. A source `DeleteRange` is now projected per matched key - exact per-key retraction when the mutation carries `MatchedKeys` (predicate-filtered deletes do, for both key-preserving and re-keyed views), an exact view-side range delete for an unconstrained delete on a key-preserving view, and an in-place rebuild for an unconstrained delete on a re-keyed view. Two distinct source keys re-mapping to one view key (an injectivity violation) are detected within a drain batch, counted on the new `orleans.lattice.view.key_collisions` meter, logged, and resolved by source-HLC last-writer-wins so the view stays well-defined. `ILatticeView` gains an opt-in read-your-writes barrier: `WaitForSourceHeadAsync(timeout, ct)` captures the current source head HLC and blocks until the view has applied up to it, and `WaitForSourceHlcAsync(target, timeout, ct)` blocks until the view's applied position reaches a caller-supplied `HybridLogicalClock` (or throws `TimeoutException`). New public members on `ILatticeView`: `WaitForSourceHlcAsync` and `WaitForSourceHeadAsync`; `ViewWrite` gains range-delete / range-reconcile expression. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 3) - Aggregation materialised views.** A source tree can now project a grouped-reduce materialised view: each source entry is mapped to a group key (a legitimate many-to-one mapping, unlike the injective filter / re-project re-key) and the view materialises one reduced value per group across `count`, `sum`, `min`, `max`, and `set-union`. Declare one with the built-in `AggregationLatticeViewProjection` (a group-key selector, a stable selector-version tag, and the value or member selector the kind needs) registered through `AddAggregationView` or a `LatticeViewDefinition` aggregation overload. The maintainer materialises each group's reduced value under its bare group key, so readers decode it with the new `LatticeAggregationValue` codec and stay oblivious to the internal accumulator layout. Apply is convergent under a single cluster-wide maintainer through a read-before-write retraction: every source key keeps one membership row recording the group and value it last contributed, so an overwrite (including a re-group to a different group) or a delete retracts its prior contribution exactly - `count` / `sum` keep only a per-group running count and sum, while `min` / `max` / `set-union` keep an exact per-group inverse row and re-derive the aggregate from the survivors when the current extremum is deleted. All accumulator, inverse, and membership rows live in the view tree under a reserved NUL (`\u0000`) prefix the view-facing surface skips. A hot group can be sharded with `LatticeViewOptions.AggregationFanout` (default 1) - sub-accumulators hashed on the source key, merged at read - and unbounded-cardinality groups can opt into an approximate bounded top-K / distinct-sample mode with `LatticeViewOptions.AggregationMaxGroupEntries` (a true HyperLogLog estimator for set-union is a later phase). A rebuild resets all aggregation state for the scanned range before re-accumulating. New public types in the `Orleans.Lattice` namespace: `ILatticeAggregationProjection`, `AggregationLatticeViewProjection`, `AggregationKind`, `AggregationContribution`, `AggregationContributionKind`, and `LatticeAggregationValue`; new `LatticeViewRegistrationBuilder.AddAggregationView` overloads in the core `Orleans.Lattice` package, a new `LatticeViewDefinition` aggregation constructor, and the `AggregationFanout` / `AggregationMaxGroupEntries` options. New `orleans.lattice` meter instrument: `orleans.lattice.view.aggregation_applied`. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 4) - Atomic-write visibility for materialised views.** A source `ILattice.SetManyAtomicAsync` batch now becomes visible in a single-tree filter or aggregation view while preserving its all-or-nothing, not-visible-until-committed guarantee: a prepared-but-uncommitted batch never appears, a committed batch appears atomically (no partial-batch is ever observable), and an aborted batch is never surfaced. The maintainer routes prepared WAL entries and per-shard `TxCommit` / `TxAbort` terminals through a staging buffer keyed by `TransactionId`, reassembles the batch via the `AtomicBatchSize` (key count) and `AtomicShardCount` (distinct-shard-terminal) gates, and flips the completed batch through the view tree's atomic primitive with an operation id derived deterministically from the source transaction id so a replay re-attaches to the completed view saga rather than double-applying. Committed batches flow through the same filter / re-key / aggregation projection as ordinary writes. The persisted per-partition resume offset is held back to `min(contiguous-applied offset, lowest-still-staged offset - 1)` so a restart re-reads and re-stages an incomplete batch and can never skip an un-applied prepared entry, and the maintainer pins the source WAL garbage collector at the oldest still-staged prepared entry's HLC (`BlockedAtHlc`), clearing the pin once nothing is staged. Staging is bounded by the new `LatticeViewOptions.MaxStagedTransactions` (default 1024) and `MaxStagedBytes` (default 64 MiB); exceeding either cap, or an un-terminated batch whose pin would sink below the source `WalRetention` ceiling, forces a fall-off-log rebuild from current committed source state. New `orleans.lattice` meter instrument: `orleans.lattice.view.atomic_staging_backstop`. No new public API surface. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 5) - Shadow-swap rebuild, reconcile, and drift digest for materialised views.** A materialised-view rebuild no longer mutates the live view tree in place, so readers never observe a half-built or empty view during a rebuild. The view tree is now generation-addressed (generation 0 keeps the legacy `view-{name}` id for backward compatibility; generation `N > 0` uses `view-{name}#g{N}`); a rebuild builds into the next generation's shadow tree, snapshots each source partition head as the resume floor before scanning, re-projects current source state through the same filter / re-key / aggregation path, and then advances the durable active generation and resume offsets in a **single** state write - an atomic swap from one fully-built tree to the next. A crash before the swap leaves the prior generation serving and reclaims the orphaned shadow on the next attempt; the swapped-out generation is reclaimed after a short grace period. Rebuilt entries now retain their source TTL (previously a rebuild dropped expiries). The `ILatticeView` handle resolves the active generation and caches it for a short TTL, so during the brief post-swap cache-staleness window a reader may serve the prior fully-built generation but never a partial tree. `ILatticeView` gains `ReconcileAsync` (the view anti-entropy: re-derive the expected view from current source state, compare via a content digest, and repair through a shadow-swap rebuild if drifted, returning whether drift was repaired) and `ComputeDigestAsync` (an order-independent content fingerprint over the materialised entries, exposed for divergence detection); reconcile assumes a local source and is a no-op concept for the ship-view topology (a later phase). New public types in the `Orleans.Lattice` namespace: `ViewDigest`; new `ILatticeView` members `ReconcileAsync` and `ComputeDigestAsync`; new `LatticeViewOptions.ReadHandleCacheTtl` (default 1s) and `OldGenerationReclaimGrace` (default 5s). See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 6) - Cross-tree atomic visibility for materialised views.** When a source-side cross-tree atomic write (`IGrainFactory.SetManyAtomicAsync` / `BeginAtomicWrite`) commits across multiple source trees, the views derived from those source trees now flip **jointly, all-or-nothing**: a reader never observes one participating view's slice of the cross-tree batch committed while another participating view's slice is still pre-commit. Each participating view is an ordinary `ILattice` tree, so the view layer reuses the existing cross-tree atomic-write primitive to flip every participating view tree in a single cross-tree saga. When a staged atomic batch completes whose terminals carried a cross-tree operation id, the maintainer does not flip its slice immediately - it computes its slice, resolves its own active-generation view tree id locally, and registers its readiness with a new view-side coordinator keyed by the cross-tree operation id (the analogue of the receiver-side cross-tree barrier). The coordinator freezes its **view wait set** on the first registration - the participant source trees that actually have a configured view (the `participants ∩ present` partial-replication handling that mirrors the receiver) - and, once every present participant view has registered, issues one cross-tree atomic write across the participant view trees so readers observe them flip together. The decision is persisted in two durable steps (flip-intent before the idempotent joint write, applied after) and keyed by a deterministic `mv-xt-{operationId}` so a crash mid-apply is re-driven by a redelivered registration and never exposes a partial set of views. Aggregation views participate too: the aggregation slice is materialised by replaying the batch's contributions through the existing applier over an in-memory buffering store, then contributed as the view's slice. **Liveness:** the coordinator waits a bounded interval (new `LatticeViewOptions.CrossTreeReadinessTimeout`, default 5s) for participant readiness; if a participant view is permanently unavailable it degrades to per-tree-slice atomicity - each present view flips atomically for its own slice - emits a new `orleans.lattice.view.cross_tree_joint_violation` meter instrument, and schedules a reconcile, choosing liveness over an indefinite WAL-pinning stall. New `LatticeViewOptions.CrossTreeReadinessTimeout` (default 5s); new `orleans.lattice` meter instrument `orleans.lattice.view.cross_tree_joint_violation`. No new public API surface. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 7) - Replication modes and lifecycle for materialised views.** A view now declares how its tree is made available across replicating clusters via the new `LatticeViewOptions.ReplicationMode`: the default `LatticeViewReplicationMode.DeriveLocally` runs the maintainer on every cluster and rebuilds the view from the replicated source (the view's data is never replicated - fully backward compatible with every existing deployment), while the opt-in `LatticeViewReplicationMode.ShipView` runs the maintainer only on the producer cluster(s) that host the source locally and replicates the small view tree to thin consumer clusters that want the view but not the full base tree. A new startup hard-fail validator (an `IHostedService` registered by `AddLatticeReplication`, since the inconsistency it guards only arises when replication is configured) refuses to start the silo on the two unsafe misconfigurations: a `DeriveLocally` view whose `view-{name}` tree (or any `view-{name}#g*` generation) is declared in the replication `ReplicatedTrees` map (two writers), and a `ShipView` view whose tree is absent from that map (consumers would never receive it). The maintainer enforces the producer/consumer split at activation - a `ShipView` view whose source WAL is not locally readable suppresses its maintainer entirely (no drain, no WAL pin, no reminder, and `ReconcileAsync` is a producer-only no-op, so drift on a consumer's replicated view tree is repaired by the existing replication anti-entropy) - and a `ShipView` producer rebuilds in place on the stable generation-0 `view-{name}` tree so the replicated tree id never cycles. The new opt-in `LatticeViewOptions.MaxLagBudget` (default 0 = disabled) is the WAL-GC backstop: a view that falls further behind the source than its budget - chronically slow, or a crashed maintainer reactivated on a keepalive tick - is force-evicted (the source WAL cursor is unpinned so a dead view can no longer hold WAL retention) and re-onboarded via a rebuild from current committed source state, which re-pins at the rebuilt head. New public type in the `Orleans.Lattice` namespace: `LatticeViewReplicationMode`; new `LatticeViewOptions.ReplicationMode` and `MaxLagBudget` (with `DefaultMaxLagBudget = 0`). New `orleans.lattice` meter instrument: `orleans.lattice.view.lag_budget_eviction`. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 - Materialised view trees are read-only to direct callers.** A view's `view-{name}` tree (and any `view-{name}#g{N}` generation) is derived state owned by its maintainer, but nothing previously stopped a caller from binding `GetGrain<ILattice>("view-...")` and writing to it directly - which violates the view abstraction and corrupts the drift digest, triggering a spurious rebuild. The public `ILattice` mutating surface now rejects every direct write to a `view-*` tree with `InvalidOperationException`; reads are unaffected, and the maintainer's own writes (and the cross-tree view coordinator's joint flips) carry an ambient capability so they are admitted, as is the replication apply path that delivers a `ShipView` consumer's replicated view tree. `view-` is therefore a reserved tree-name prefix for directly-writable trees. New internal constant `LatticeConstants.ViewTreePrefix`. No new public API surface. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).

Because a view's maintainer is a single grain activation that migrates between silos, the dashboard is a cluster-wide concern: every panel is keyed by view name (and, where deployments span clusters, by cluster) and deliberately offers no per-silo filter. New `LatticeDashboardKind.MaterialisedViews` enum value in the `Orleans.Lattice.Dashboards` namespace; sources the core `orleans.lattice` meter only, so it needs neither the replication package nor the replication meter. See [`docs/lattice.dashboards/metrics-to-panel-map.md`](docs/lattice.dashboards/metrics-to-panel-map.md) (#794).
- **F-106 - Materialised view maintainer obeys source WAL back-pressure.** A view's background maintainer is asynchronous, but on a busy silo its drain still competes with the foreground writer for client-side concurrency (storage connections, threads, the grain scheduler), so a hot source could be slowed by the very view derived from it. The maintainer now samples the source tree's WAL saturation signal at the top of each drain and self-throttles: while the source is `Throttled` it drains a reduced batch (`ThrottledBatchRatio` of `BatchSize`) and defers its next background tick by `ThrottledPauseMs`; while `Saturated` it drips a small `SaturatedBatchSize` batch and defers by `SaturatedPauseMs`. Foreground read-your-writes barriers still make progress (just with a smaller batch); only background ticks are deferred, and the throttle engages only while the source is actually saturated, so a healthy source pays nothing. On by default; opt out per view with `ObeySourceBackpressure = false`. New `LatticeViewOptions` knobs `ObeySourceBackpressure`, `ThrottledBatchRatio`, `ThrottledPauseMs`, `SaturatedBatchSize`, `SaturatedPauseMs` and a new `orleans.lattice.view.source_backpressure` counter (tagged with the observed source regime). See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 follow-on - Typed serialisation-generic projection and read helpers for materialised views.** Several materialised-view surfaces shipped only a `byte[]`-oriented form, forcing callers to hand-roll deserialisation in projection selectors and view reads (for example `groupKeySelector: bytes => JsonLatticeSerializer<User>.Default.Deserialize(bytes)!.Name`). Two additive layers close that gap. On the write side, `AggregationLatticeViewProjection.Create<T>(...)` and `PredicateLatticeViewProjection.Create<T>(...)` take selectors over a typed `T` deserialised through an `ILatticeSerializer<T>` (defaulting to `JsonLatticeSerializer<T>.Default`), so a group-key, value, or predicate selector is written against the domain type rather than raw bytes. On the read side, the new `TypedLatticeViewExtensions` adds `GetAsync<T>` and `EntriesAsync<T>` (deserialising view rows through the same serialiser) plus `GetAggregateDoubleAsync` / `GetAggregateInt64Async` (decoding an aggregation group's reduced value via `LatticeAggregationValue`, returning `null` for an absent group). The existing `byte[]` constructors and reads are retained unchanged for custom wire formats and null-drop semantics. New public type in the `Orleans.Lattice` namespace: `TypedLatticeViewExtensions`. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) and [`docs/lattice/api.md`](docs/lattice/api.md) (#815).
- **FX-043 - Durable runtime-view registration and a view deletion API for materialised views.** A materialised view created at runtime through the injected `ILatticeViewFactory.Create` previously lived only in the in-memory view catalog, so a silo restart silently forgot it and the view stopped being maintained until the caller re-created it. `Create` now persists a durable registration (source tree id, projection CLR type + version, aggregation flag) to a singleton view-registry grain, and on silo start the view activation service re-hydrates each registration - resolving the projection from DI (`GetService` then `ActivatorUtilities.CreateInstance`) - so a runtime view survives a restart whenever its projection type is DI-constructable (a startup-declared view of the same name always takes precedence; the built-in delegate-constructed `PredicateLatticeViewProjection` / `AggregationLatticeViewProjection` are not DI-resolvable and remain startup-declared). The new `ILatticeViewFactory.DeleteAsync(viewName, ct)` tears a view down completely - it unregisters the maintainer reminder, releases the source WAL cursor pin, deletes the backing generations, resets the durable checkpoint, and removes both the catalog entry and the durable registration - and it rejects a startup-declared view, is idempotent, and is a no-op for an unknown view. The teardown recovers the source tree id from the durable registry when the in-memory catalog has no entry (the maintainer can activate fresh on a silo that never saw the `Create`), closing a leak whereby the view's source WAL cursor pin could otherwise be held forever and block source WAL garbage collection. New public member on `ILatticeViewFactory`: `DeleteAsync`. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) and [`docs/lattice/api.md`](docs/lattice/api.md) (#816).
### Changed

- Bump the `Microsoft.Orleans.*` package family from 10.1.0 to 10.2.0 across the solution. Orleans 10.2.0 tightened grain-turn scheduling, which surfaced a latent deadlock in the test-only loopback replication transport used by the public-API contract suite: it ran the destination cluster's applier inline on the sending shipper grain's activation turn, so the destination's grain responses could never be scheduled. The loopback transport now marshals the destination apply onto a neutral thread-pool context, mirroring how a real socket transport decouples send from receive. Production transports (in-process and gRPC) were unaffected (#793, #792).

### Fixed

- **First write to a tree no longer fails when the silo's reminder service is still initializing.** The first `ILattice` write to a tree lazily bootstraps two best-effort background reminders inline on the write path: the tombstone-compaction keepalive (`EnsureCompactionReminderAsync`) and, when auto-split is enabled, the hot-shard monitor (`EnsureMonitorAsync`). Orleans' `LocalReminderService` initializes asynchronously *after* the silo reaches `Active` in membership, so a write issued in that startup window reached `RegisterOrUpdateReminder` while the service was still initializing and surfaced its transient `OrleansException: "Reminder Service is still initializing and it is taking a long time. Please retry again later."` straight out to the caller, failing the user's write. On a loaded CI runner this intermittently failed `Bidirectional_writes_converge_under_lww_register` (the first write after `TestCluster.DeployAsync`, which waits only for membership Active, not reminder-service init). Both bootstraps now recognise that specific transient (via the new internal `ReminderServiceReadiness` classifier, matched by message substring across the inner-exception chain) and defer: they log at debug and leave the per-activation `_ensured` gate unset so a subsequent write re-attempts registration once the service is up - within seconds of silo start. A genuine, unrelated reminder fault still propagates. Internal-only; no public API, wire, or behaviour change.
- **F-106 - Catch-up WAL reads no longer head-of-line-block foreground appends.** Each `(tree, partition)` is served by a single non-reentrant `IWalShardGrain` activation. Its paginating read methods (`ReadAsync`, `ReadShippingAsync`) were not marked `[AlwaysInterleave]`, so a read held the grain's turn for the entire duration of the underlying provider round-trip - an Azure Table page fetch, paginated over the whole backlog - and every concurrent foreground `AppendAsync` queued behind it in the activation inbound queue. Under sustained read load this stalled the foreground write path: the caller-side append-dispatch latency climbed into the seconds while the grain's own in-turn append work stayed in the tens of milliseconds (the wait was the inbound-queue tax, invisible to the grain's self-clock). The materialised-view maintainer is the first sustained driver of this read path (its commit-log reader was previously dormant) and the replication shipper has the same exposure via `ReadShippingAsync`. Both read methods are now `[AlwaysInterleave]`, so catch-up reads interleave with appends instead of serialising ahead of them. This is safe by the same construction that already lets `AppendBatchAsync` interleave: the read path touches only activation-immutable state (the provider, the tree / shard identity, the encoder, the mode resolvers) and committed provider rows, never the append-mutable state, which stays serialised by its existing internal state-gate lock. Internal-only; no public API, wire, or behaviour change. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md) (#794).
- **F-106 (Phase 3) - Aggregation `count` / `sum` views no longer double-count after a mid-drain crash.** The aggregation maintainer applied a `count` / `sum` contribution as a read-modify-write increment of a serialized accumulator row followed by a separate write of the per-source-key membership row. Because WAL delivery is at-least-once and the maintainer checkpoints once per drain batch, a silo crash between the two writes replayed the whole batch and re-applied the increment whose membership write was lost, double-counting (or double-retracting) the group until the next rebuild. The membership row and the affected accumulator slot(s) now flip to their final byte-state together in one all-or-nothing atomic write keyed by a deterministic, rebuild-generation-seeded operation id, so a replay either dedups the saga outright or recomputes a net-zero accumulator delta from the already-advanced membership pointer. An emptied slot or retracted membership row is flipped to a one-byte empty sentinel (the atomic write cannot delete) that the read path treats as absent and the maintainer opportunistically cleans up after materialising; a rebuild bumps the durable generation so re-accumulation mints fresh sagas rather than re-attaching to the retained sagas of the deleted rows. `min` / `max` / `set-union` were already replay-idempotent (their inverse-map mutation is idempotent) and keep the simpler path. See [`docs/lattice/materialised-views.md`](docs/lattice/materialised-views.md).
- **`WalShardGrain` multi-batch flush no longer strands a committed predecessor's acks when a later flush fails.** With `WalMaxPendingBatches > 1`, several flushes for one shard run concurrently against the provider. When a later flush failed, its handler latched the per-grain sticky failure, but the success path of an *earlier* flush that had already committed durably keyed its "apply ack results" decision off that global latch: if the later failure latched the sticky flag in the window between the predecessor's provider call returning and its `TrySetResult`, the predecessor skipped acking and was never faulted either (the failure handler only faults the failed window, later windows, and pending), so its caller's `AppendAsync` task never completed and the shard wedged. Under CI's `--blame-hang` collector this surfaced as a 10-minute inactivity abort rather than an assertion failure, and only under full-suite scheduling pressure (it passed in isolation). The success path now keys off a new per-slot `FaultedByFailure` flag that the failure handler sets only on the failed window and the windows ordered after it; a predecessor that committed durably is never marked and always honours its acks, while later windows whose offset window the post-failure resync rolls back still skip exactly as before. Internal-only; no public API, wire, or behaviour change.
- **`MultiSiloRestartWalDurabilityRegressionTests` no longer flakes on slow CI runners.** The post-restart settle replaced a fixed two-second `Task.Delay` plus single-shot reads (which raised a transient `ShardActivationTimeoutException` when a shard's reactivation on the surviving silo outran the fixed window) with a bounded poll that retries only the transient reactivation exceptions on a generous deadline. A genuinely lost key still returns `null` and is not retried, so the durability assertions retain their full strength. Test-only change.
- **Leaf projection digest no longer overcounts after an out-of-order coalesced publish during a split.** A child's per-write digest publish to its parent is computed and shipped as a separate cross-grain message from the split path's inline publish. Because the leaf mutation surface is `[AlwaysInterleave]`, a coalesced publish that captured a child's *pre-trim* (pre-split) entry count could arrive at the parent fold *after* the split's correct *post-trim* publish, leaving the parent's chained-fold holding a stale-high entry count for a child it still owns - so the aggregate digest overcounted (CI observed 15 entries when only 12 distinct keys were written, intermittently failing `DigestCoalescingWindow_eventually_publishes_aggregate_to_parent` under `--blame-hang` full-suite scheduling pressure). The pre-existing ownership guard only rejected *re-parented* children, not a stale value for a still-owned one. Each publisher (leaf and internal node, push and pull) now stamps a per-activation strictly-increasing `PublishSequence` on its `ChildDigestSnapshot`, seeded from the wall clock so it stays monotonic across reactivations without persisting a counter, and the parent fold drops any snapshot strictly older than the one already folded for that child. A default sequence of 0 (direct unit-test pushes, range/partial digest computations) is unsequenced and always accepted, preserving last-writer-wins for callers that do not stamp one. Wire-compatible (a new optional `[Id(3)]` on `ChildDigestSnapshot`); internal-only, no public API or behaviour change.
- **WAL `set-point` phase-one `409 EntityAlreadyExists` conflict storm removed, and the residual single-account brown-out wedge materially reduced.** Under sustained single-silo `set-point` load against one Azure Tables account, a transient storage blip surfaced a phase-one flush fault to the `WalShardGrain`, which rewound `_nextOffset` to the durable phase-two `TAIL` *without first reconciling* - blind to the phase-one entry rows already durable above the `TAIL`. It then re-coalesced a different batch and re-drove divergent content onto those still-durable offsets, igniting a self-sustaining `409` re-drive storm that collapsed write throughput while reads stayed healthy. Four changes close the storm: (1) an O(1) idempotent phase-one `409` replay proof (a durable prior attempt is recognised and resolved without re-driving, using an `XxHash128` content sentinel rather than a per-row read-back); (2) a provider-level offset-preserving transient phase-one retry that absorbs lost-response replays so the low-load range is solid; (3) the shard-side fix - `WalShardGrain` now `ReconcileAsync`-es (roll-forward contiguous durable orphans / roll-back gapped) **before** reading the tail on a flush failure, exactly as `OnActivateAsync` already did, so recovery resumes from the durable phase-one tail instead of re-driving divergent content; and (4) `AzureTableWalStorageOptions.RetryNetworkTimeout` now **defaults to 10 s** (was unset, i.e. the SDK's unbounded ~100 s) - chosen below the 15 s `WalFlushTimeout` so a transport attempt stuck on a browned-out account surfaces a fault into the reconcile-aware failure handler within the per-flush budget and releases its WAL slot, rather than zombie-ing on while hundreds of abandoned attempts accumulate and self-sustain the brown-out. Set `RetryNetworkTimeout = null` to restore the prior SDK default. **Honest scope:** on the real-Azure P=16 `set-point` ladder these changes eliminate the `409` conflict storm and make the low / mid-load range reliable, but they do **not** fully abolish the wedge - a sufficiently hard single-account Azure Tables brown-out at sustained offered load above the single-account throughput ceiling (measured ~6k entries/s) can still terminally wedge a cohort with real write failures, because the recovery reads target the same browned-out account. The durable remedy for that residual is WAL fan-out across multiple storage accounts (`BENCH_WAL_ACCOUNTS` / `deploy.ps1 -WalAccountCount`), tracked separately. Purely additive on the wire; the only behaviour change is the finite `RetryNetworkTimeout` default (#824).

Minor release across the package family. ### Added

- **F-105 - Couple a typed CRDT mutation into a cross-tree atomic write.** The per-entry CRDT delta carry that the cross-tree atomic-write saga gained for the built-in tag index is now a public, additive builder surface, so any typed CRDT mutation can ride a cross-tree atomic write alongside sibling last-writer-wins writes. Each CRDT value-surface accessor (`OrSet`, `OrFlag`, `RwFlag`, `PnCounter`, `MvRegister`, `Sequence`/RGA, `VersionVector`) gains a `Stage*` counterpart for every live mutator - for example `PnCounterAccessor.StageIncrementAsync(...)`, `OrFlagAccessor.StageEnableAsync(...)`, `OrSetAccessor.StageAddAsync(...)`. A `Stage*` call reads the key's current snapshot once, mints the typed delta exactly once (the same dot-minting logic the live mutator uses), folds it into the snapshot to compute the merged state, and returns a `LatticeStagedCrdtWrite` carrying the key, the merged state, and the typed delta - performing no durable write of its own. Hand the token to the new `LatticeAtomicWriteBuilder.Set(LatticeStagedCrdtWrite)` overload under the matching CRDT-mode tree, and the staged mutation commits all-or-nothing with the rest of the cross-tree batch: the merged state is stored last-writer-wins by HLC and replicates to every peer, so a single authoring cluster's staged CRDT write converges everywhere on its merged value. The delta is minted once and replayed verbatim on crash-recovery, and an aborting saga drops the staged value and delta on every cluster (no byte-inverse compensation). New public type in the `Orleans.Lattice` namespace: `LatticeStagedCrdtWrite`. The prepared/terminal replication path that cross-tree atomic writes ride now carries the staged typed delta and merge mode to the receiver, which folds the delta into its current visible state on the saga's terminal commit, so two clusters writing the same CRDT key concurrently through staged atomic writes converge by the per-replica typed-delta union exactly as the live accessor path does. See [`docs/lattice/atomic-writes.md`](docs/lattice/atomic-writes.md) and [`docs/lattice/api.md`](docs/lattice/api.md) (#780).

- **F-104 - Atomic value-plus-tags writes now honour all-or-nothing coupling under a flag membership mode.** When the built-in tag index is configured for active-active convergence with a flag merge mode (`OrFlag` enable-wins or `RwFlag` remove-wins), `SetValueWithTags(...).Atomic()` previously downgraded silently to eventual coupling: the value was written durably first and the membership rows followed separately as flag enables, because the cross-tree atomic-write saga carried only a single saga-wide author-delta while flag membership needs a distinct typed delta per row. The saga can now carry an optional per-entry author-delta aligned 1:1 with its entries, so an atomic flag-mode value+tags write stages each membership row with its own freshly minted flag-enable delta (storing the merged flag state as the row value) under one cross-tree atomic write: the value and every membership row become visible together, and the merged flag-state row value replicates to every other cluster, carrying its typed flag delta on the prepared/terminal path so the receiver folds the enable into its current visible flag state on the saga's terminal commit. Two clusters enabling membership for the same key concurrently therefore converge by the per-replica flag union through the atomic (prepared) path, not only the eventual accessor path. The enable dots are minted once and persisted on the saga state, so a reminder-driven crash-recovery replay reuses them verbatim without authoring duplicate dots; an aborting saga drops the prepared enable on every cluster exactly as it drops the staged value write, so a flag enable needs no compensating disable. The last-writer-wins (default) membership path and every value-only atomic write are unchanged. See [`docs/lattice/api.md`](docs/lattice/api.md) (#778).

- **F-103 - Background reconciliation coordinator for tag indexes.** Each tag index now self-heals on a configurable background cadence (default hourly) instead of relying on an operator calling `ReconcileAsync`. A per-index coordinator grain - keyed by `{indexName}`, built on the shared crash-/restart-safe coordinator keepalive + phase-timer machinery - registers a recurring schedule reminder the first time a tree is covered by the index (auto-enabled from the tag-write path), and on each firing runs a digest-gated sweep. Because orphan membership rows arise only from key deletions in a covered (subject) tree, and every such deletion folds a tombstone into that tree's `LeafProjectionDigest`, the sweep first probes each covered tree by folding its per-shard leaf-projection digests into a fingerprint and comparing it to the baseline captured at the last successful reconcile: trees whose fingerprint is unchanged are skipped (digest reads only, no scans or writes), and only trees whose digest diverged - or whose digest is unavailable - are deep-scanned and repaired via the existing reconcile path, after which their baseline advances. A clean index therefore incurs only digest-probe cost. Gating is tree-granular (not sub-shard): the replication Merkle-walk machinery that would narrow a dirty tree to a key sub-range lives in the replication package and is not referenced by the core library, so a divergent tree is reconciled in full. Tune per index through `LatticeTagIndexReconciliationOptions` (`Enabled`, `Interval`, `ChunkSize`, `ProbeOnly`), configured globally or per index with `ISiloBuilder.ConfigureLatticeTagIndexReconciliation(...)`; setting `Enabled = false` unregisters any existing schedule. New public type in the `Orleans.Lattice` namespace: `LatticeTagIndexReconciliationOptions`. See [`docs/lattice/api.md`](docs/lattice/api.md) (#770).

- **F-018 - Associate tags with keys and query by tag.** Adds a secondary-index surface that tags the keys of any tree and queries keys back by tag, built entirely on the public `ILattice` surface. Open a tag index through the injected `ILatticeTagIndexFactory` (`tagIndexFactory.Create(tree, indexName)`); membership rows live in a sibling ordinary Lattice tree resolved as `tag-{indexName}`, each keyed `tag \0 treeId \0 key`. Per-key tag CRUD is available through `Key(key)` (`GetAsync` / `SetAsync` replace-diff / `AddAsync` / `RemoveAsync`); query keys with `WithAllTags(...)` (intersection) and `WithAnyTags(...)` (de-duplicated union), each a lazy `IAsyncEnumerable<string>` with `CountAsync`; `TagsAsync()` streams the distinct tags currently in use. `SetValueWithTags(key, value, tags)` writes a value and its tags together - `Eventual` by default (two independent durable writes) or `.Atomic()` (lowered to the existing cross-tree atomic-write saga so the value and its tag rows become visible together). `ReconcileAsync(start?, end?)` idempotently removes membership rows whose key no longer exists in the primary tree. The multi-tree surface (`tagIndex.MultiTree()` or `tagIndexFactory.CreateMultiTree(indexName)`) ranges over every covered tree, yielding `TaggedKey` and supporting `InTree(treeId)` narrowing, with the covered-tree set discovered from an over-approximating, self-healing hint cached on the index tree. This is the conservative complement to `OrFlag` for revocation, kill-switch, and opt-out bits where the safe outcome of a race is the withdrawn state. ### Fixed

- **FX-041 - Cross-cluster staged-CRDT atomic writes now converge by typed-delta fold on the receiver.** A cross-tree atomic write that coupled a typed CRDT mutation (the public `LatticeAtomicWriteBuilder.Set(LatticeStagedCrdtWrite)` surface, or the built-in tag index's per-entry flag-membership carry) rode the two-phase prepared/terminal replication path, which applied the prepared entry's merged-state value last-writer-wins by HLC on the receiver and dropped the staged typed delta. Two clusters writing the same CRDT key concurrently through staged atomic writes therefore reconciled by last-writer-wins of their merged states instead of by the per-replica union, silently degrading convergence (a `+5` on one cluster and a `+3` on another converged to `5` or `3`, not `8`). The prepared receiver path now carries the staged typed delta and merge mode through to the terminal commit and folds the delta into the receiver's current visible state (the primitive's `MergeDelta`) instead of installing the prepared LWW value, so concurrent same-key staged CRDT writes converge by the per-replica typed-delta union on every cluster, identical to the live accessor path - and the tag index's flag-membership active-active convergence now holds through the atomic (prepared) path, not only the eventual path. The fold propagates through every prepared-entry materialization path (WAL replay on activation, shard split/resharding, read snapshots, and bootstrap restore) additively, so legacy persisted/wire state with no staged delta decodes to the unchanged last-writer-wins behaviour. Value-only sagas and single-writer LWW atomic writes are byte-for-byte unchanged. See [`docs/lattice/atomic-writes.md`](docs/lattice/atomic-writes.md) (#782).

- **Causal-apply gate no longer parks a peer write that causally depends on the receiver's own earlier write.** The receiver-side causal-dependency check compares a foreign entry's vector-clock frontier against the receiver's local vector clock, which tracks only *foreign*-applied origins and never advances its own diagonal. A peer entry whose frontier referenced one of the receiver's own writes - for example site C's post-partition write that causally follows site A's pre-partition write, once an A-C partition heals - therefore failed the gate against a perpetually-zero self-component and parked forever, stalling convergence. The gate (and the buffer-drain predicate that retries parked entries) now treat a dependency on the receiver's own cluster id as satisfied, since the receiver durably holds every write it authored. Latent since causal-plus tracking shipped; surfaced by defaulting pre-ship coalescing on (#745), because coalescing collapses the duplicate per-key versions whose redundant re-delivery previously masked the stall. See [`docs/lattice.replication/replication-apply.md`](docs/lattice.replication/replication-apply.md) (#745).

- **FX-040 - Tag index now authors flag-CRDT membership for active-active (multi-writer) convergence.** The built-in tag index previously wrote every membership row as a plain last-writer-wins value write, so the active-active convergence its docs recommended was unachievable - declaring the index tree under a flag merge mode would have faulted on apply because a plain write ships no typed delta. Membership mode and dot-authoring replica id are now sourced from a new injectable replication-configuration seam, `ILatticeReplicationContext`, rather than hand-paired `membershipMode` / `replicaId` parameters that could drift from server config. Tag indexes are opened through a new injected `ILatticeTagIndexFactory` (`Create(tree, indexName)` / `CreateMultiTree(indexName)`, registered by `AddLattice`) - the single entry point, replacing the former `tree.TagIndex(...)` / `grainFactory.MultiTreeTagIndex(...)` extension methods - that captures the seam, so the membership mode and local replica id come from server configuration with no per-call ceremony. The seam reports whether replication is enabled, the local replica id, and the per-index-tree merge mode. The core default reports replication disabled and keeps the original single-writer-optimised LWW path byte-for-byte; `AddLatticeReplication` swaps in a configured implementation sourced from `LatticeReplicationOptions` (`ClusterId` + `ReplicatedTrees`) and registers a startup validator that fails the silo fast when a flag-mode index tree is declared without a configured replica id, instead of faulting on the first write. In a flag mode every index-tree write (membership rows, the key-major mirror, and covered-tree markers) is authored as a flag enable and every removal as a flag disable, so the index ships convergent typed deltas; reads decode the flag state and treat a disabled/tombstoned row as absent in the same scan pass. The background reconciliation coordinator auto-detects the index tree's mode and replica id through the same seam, so its orphan cleanup authors flag disables rather than plain deletes under a flag mode. New public types in the `Orleans.Lattice` namespace: `ILatticeReplicationContext` and `ILatticeTagIndexFactory`. See [`docs/lattice/api.md`](docs/lattice/api.md) (#775).

- **Storage-usage gauges now observe every silo's sink, not just the last-constructed one.** The observable storage gauges (`storage.wal_bytes`, `storage.snapshot_bytes`, `storage.leaf_state_bytes`, `storage.total_bytes`, `storage.policy.over_threshold`) read their series through a process-wide `LatticeStorageUsageMetrics` registration that previously snapshotted only the most-recently-constructed sink instance. In a multi-silo-in-one-process deployment (such as an in-process test cluster) every silo's dependency-injection container builds its own sink instance, so only the last silo to start contributed its trees' series and the others were silently dropped from a scrape. The registration now unions across every live sink instance, and the sink is `IDisposable` so a torn-down silo's instance stops contributing. Single-silo-per-process deployments (the normal production topology) build exactly one instance and are unaffected. The Grafana **Overview** storage panels also stop filtering storage series by `$silo`, so a tree's footprint aggregates across the selected cluster rather than appearing to live on whichever single silo hosts its aggregator.

- **Flaky WAL back-pressure timing tests are now deterministic.** `WalSaturationSignalExtensionsTests` previously asserted near-exact wall-clock elapsed durations (`Stopwatch`) for the Throttled per-call delay, which tripped under full-suite parallel CI load and blocked merges. `WalSaturationSignalExtensions.ApplyBackPressureAsync` now routes its Throttled `Task.Delay` through an injectable `TimeProvider` seam (the public overloads forward `TimeProvider.System`, so production behaviour is byte-for-byte unchanged), and the tests drive a controllable time provider to assert the scheduled delay duration deterministically instead of measuring elapsed wall-clock time. Test-and-internal-seam only; no public API or behaviour change.

- **R-045 - Coalesced per-peer cursor checkpointing now has a time bound.** The replication shipper already amortised its durable per-peer/per-partition resume-cursor write across `LatticeReplicationOptions.ShipCursorWriteInterval` (default 16) successful acks instead of persisting on every batch; it now also flushes the pending cursor whenever `LatticeReplicationOptions.ShipCursorWriteMaxDelay` (new, default 2 s) of wall-clock time has elapsed since the first un-flushed advance - whichever threshold is reached first. The time dimension bounds how stale the durable cursor (and therefore the WAL GC trim frontier) can become on a low-throughput or bursty stream that ships fewer than `ShipCursorWriteInterval` batches and then quiesces, where a pure batch-count rule would otherwise leave the last few advances un-flushed indefinitely. The elapsed check runs both when a new advance is booked and on idle pump ticks (the empty-drain path), so a stream that goes completely silent still checkpoints within the bound; a graceful deactivation continues to flush any pending advance. Crash safety is unchanged: receiver-side apply is HLC-monotonic and dedupes on `(originClusterId, originHlc)`, so any entries re-shipped inside the window are no-op'd at the receiver and no data is lost - lowering the new delay only ever makes the durable cursor fresher. Set `ShipCursorWriteMaxDelay` to `Timeout.InfiniteTimeSpan` to disable the time dimension and coalesce purely by batch count. The new option is validated (`> TimeSpan.Zero` or `Timeout.InfiniteTimeSpan`) by `LatticeReplicationOptionsValidator`. See [`docs/lattice.replication/replication-drivers.md`](docs/lattice.replication/replication-drivers.md#deferred-cursor-persistence) (#462).
- **R-131 - Parallel receiver apply across independent trees.** The replication receiver can now apply independent runs of an inbound batch concurrently instead of strictly serialising every `(treeId, originClusterId)` run, cutting apply latency and the resulting `apply.lag` (which now also drives receiver back-pressure) under multi-tree load. Concurrency is bounded by the new `LatticeReplicationOptions.ApplyMaxParallelRuns` option, and **defaults to `1` (fully-sequential apply, identical to the previous behaviour)** - raise it conservatively, per workload, to let distinct trees apply in parallel. Independence is defined at the tree granularity: runs targeting distinct trees overlap up to the configured cap, while runs that share a tree stay strictly sequential in write-ahead-log order, so every within-run ordering invariant holds unchanged regardless of the configured degree of parallelism - per-origin FIFO, the causal dependency gate and its bounded buffer, per-origin high-water-mark monotonicity, and atomic-batch (saga) apply boundaries. The effective degree of parallelism per batch (the configured value clamped to the number of distinct trees present) is surfaced on the new untagged `LatticeReplicationMetrics.ApplyParallelRuns` histogram (`orleans.lattice.replication.apply.parallel_runs`, unit `{run}`). Purely additive: no wire or serialization change, and a single-tree batch always takes the allocation-free sequential walk. See [`docs/lattice.replication/replication-apply.md`](docs/lattice.replication/replication-apply.md#parallel-apply-across-independent-runs) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md#parallel-apply-degree-applyparallel_runs) (#695).
- **R-127 - Receiver WAL-saturation back-pressure feeds sender backoff.** The replication receiver can now translate the core library's WAL saturation signal into the sender backoff hints it already understands. This behaviour is now **on by default**: `AddLatticeReplication` registers `WalSaturationReceiverFlowControlPolicy` (an `IReceiverFlowControlPolicy`) via `TryAddSingleton`. Hosts opt out by pre-registering `NoOpReceiverFlowControlPolicy` before `AddLatticeReplication`, and tune the mapping with the `ISiloBuilder.AddWalSaturationReceiverFlowControl(...)` extension. On every successful push the policy reads `IWalSaturationSignal.GetCurrentState(treeName)` for the just-applied tree and maps the regime onto the `ReceiverFlowControlHint` stamped on the `ReplicationAck`: `Healthy` yields `ReceiverFlowControlHint.None` (sender resumes at its configured `ShipBatchSize`), `Throttled` yields a reduced batch (a configurable fraction of `ShipBatchSize`) plus a short pause, and `Saturated` yields a minimal drip-feed batch plus a longer pause - so the sender stops piling work onto a writer-side admission gate that is already at its cap and would otherwise fault the apply with `LatticeSaturatedException`. The mapping is tunable per tree through the new public `WalSaturationReceiverFlowControlOptions` (`ThrottledBatchRatio`, `ThrottledPauseMs`, `SaturatedBatchSize`, `SaturatedPauseMs`), with all suggested sizes clamped to `[1, ShipBatchSize]`. The hint rides the existing additive `ReplicationAck.SuggestedBatchSize` / `PauseForMs` slots, so there is no wire or serialization change, and the policy degrades to `ReceiverFlowControlHint.None` when no `IWalSaturationSignal` is registered. New public types: `WalSaturationReceiverFlowControlPolicy`, `WalSaturationReceiverFlowControlOptions`, and the `AddWalSaturationReceiverFlowControl` extension. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#built-in-wal-saturation-policy) (#690).
- **R-128 - Sender-side multi-batch ship pipelining.** The outbound replication shipper can now keep more than one shipped-but-unacknowledged batch in flight per `(tree, peer)` so transport round-trip latency overlaps with draining the next batch, lifting throughput on high-latency links. Opt in by raising the existing `LatticeReplicationOptions.ShipMaxInFlight` above its default of `1`; the default stays strictly serial (ship one batch, await its ack, advance the cursor, ship the next), so behaviour is unchanged until an operator widens the window. The pipeline preserves the per-origin FIFO invariant and advance-strictly-on-ack cursor semantics: acks are consumed in strict FIFO order and the durable per-peer cursor advances past a batch only once that batch and every lower-HLC batch before it have been acknowledged, so a transport failure or ack rejection anywhere in the window leaves the cursor at the last fully-acked frontier with no hole (the next tick re-ships from the durable cursor and the receiver dedupes the overlap). Receiver flow-control composes: when the receiver stamps a `ReplicationAck.SuggestedBatchSize` hint the window collapses back to `1` until the hint clears, throttling batch size and pipeline depth together. The live window depth is surfaced on a new outbound-only observable gauge, `orleans.lattice.replication.peer.ship_in_flight` (new public constant `LatticeReplicationMetrics.ShipInFlightName`), recorded through the new `ReplicationPeerStats.RecordInFlight(tree, peer, depth)` method and readable on the new `ReplicationPeerSnapshot.InFlight` snapshot field. A window greater than `1` issues concurrent `IReplicationTransport.SendAsync` calls for the same pair, so a transport used with pipelining must tolerate concurrent invocation against one pair; The default window of `1` preserves strictly-serial-per-pair behaviour. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#sender-side-pipelining) (#692).
- **R-129 - Wire-version capability advertisement, negotiation telemetry, and floor-guard.** Lays the groundwork for safe rolling upgrades across framing wire versions without yet changing any on-the-wire payload. The receiver now advertises the maximum framing wire version it can decode on a new additive `ReplicationAck.SupportedWireVersion` slot, and an opted-in sender feeds that into the new public `WireVersionNegotiation.Negotiate(localCurrent, minimumSupported, unknownPeerFloor, peerAdvertised)` helper (returning a `WireVersionNegotiationResult`) to compute the negotiated target version - `min(localCurrent, peerAdvertised)` once the peer's capability is known, or a conservative `UnknownPeerWireVersionFloor` until it advertises one. A peer that advertises a version below the configured `MinimumSupportedWireVersion` surfaces the canonical fail-fast hard error (the genuinely-unsupported case). Two new observable gauges - `orleans.lattice.replication.wire_version.negotiated{tree,peer}` and `orleans.lattice.replication.wire_version.downgrade_active{tree,peer}`, backed by the new public `WireVersionNegotiationState` singleton - let operators see when a fleet is running mixed wire versions. **Ships dark / opt-in:** `LatticeReplicationOptions.WireVersionNegotiationEnabled` defaults to `false`. This entry delivers the capability advertisement, negotiation telemetry, and minimum-floor guard only; it does **not** re-encode outbound batches at the negotiated target - the steady-state ship path reuses the bytes the WAL wrote at append time, so an opted-in sender still frames every batch at its current wire version. Actually re-encoding at the negotiated older version (the capability a newer sender needs to ship to a not-yet-upgraded receiver, plus a safe on-by-default posture) is tracked as a follow-up issue (#703). `MinimumSupportedWireVersion` (default `1`) and `UnknownPeerWireVersionFloor` (default current version) are validated by `LatticeReplicationOptionsValidator`. The `SupportedWireVersion` slot is strictly additive on the wire (pre-negotiation receivers omit it and senders ignore it). New public types: `WireVersionNegotiation`, `WireVersionNegotiationResult`, `WireVersionNegotiationState`, `WireVersionNegotiationSnapshot`. See [`docs/lattice.replication/wire-format.md`](docs/lattice.replication/wire-format.md#wire-version-capability-negotiation) (#693).
- **R-105 - Peer digest probe RPC and scheduler (anti-entropy detection).** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. A new per-tree, low-frequency, jittered scheduler reads each shard's local leaf-projection digest via `ILattice.GetLeafProjectionDigestAsync(shardIndex)` and compares it against every peer's digest fetched over a new read-only probe RPC carried on the existing replication push transport, emitting two counters so a dashboard can chart cross-cluster divergence: `orleans.lattice.replication.digest_probe.compared{tree,shard,peer,outcome}` (every comparison) and `orleans.lattice.replication.digest_probe.mismatch{tree,shard,peer}` (only when versions match and digests differ). The probe is strictly read-only - it never mutates data or cursors. Enable it per tree with the new `LatticeReplicationOptions.DigestProbeEnabled` (default `false`); tune the cadence with `DigestProbeInterval` (default 5 minutes, validated `> TimeSpan.Zero`) and `DigestProbeJitter` (default `0.2`, validated `[0, 1]`). It respects the core opt-out: trees with `MaintainProjectionDigest = false` (including the system-tree default) are skipped, and a tree whose registry latch has permanently disabled digesting is skipped for the activation lifetime. When the local and remote digest versions differ, the comparison records `outcome=version_skew` and does **not** raise a mismatch. New public types: `IReplicationDigestProbeTransport`, `DigestProbeRequest`, `DigestProbeResponse`, `DigestProbeOutcome`, and `DigestProbeComparer` in the `Orleans.Lattice.Replication` namespace. The gRPC binding wires the probe RPC over the same channel cache as live push. See [`docs/lattice.replication/anti-entropy-digest-probe.md`](docs/lattice.replication/anti-entropy-digest-probe.md) (#513).

### Changed

- **R-143 - Content-hash payload elision now composes with sender-side multi-batch ship pipelining (deferred half of R-135).** The opt-in content-hash payload-elision round trip previously ran on the strict-serial ship path only: enabling it forced a configured `LatticeReplicationOptions.ShipMaxInFlight > 1` pipelining window to collapse back to one, so dedup silently disabled the R-128 multi-batch throughput benefit. The per-batch manifest exchange now runs inline in the bounded-pipelining drain loop, so elision and pipelining compose - the window no longer collapses when elision is enabled. A batch every entry of which the receiver already holds byte-identical (a fully-elided batch) ships no envelope on the wire; instead it advances the durable per-peer cursor strictly in FIFO order through the same in-flight queue via a synthetic already-completed ack, so per-origin FIFO, causal-dependency gating, atomic-batch boundaries, and advance-strictly-on-ack cursor semantics are preserved across the window. The full-range cursor-advance inputs are captured before the exchange, so the cursor still advances past every originally-drained entry regardless of how many were elided. The synthetic zero-latency ack is excluded from the adaptive batch-size controller (it records no `ship.ack_latency` / `ship.effective_batch_size` sample and never overwrites the receiver-suggested size), so it cannot skew adaptive sizing. Default-off is wire byte-identical to today and rolling-upgrade safe: the manifest exchange remains gated behind the same lazily-learned per-activation peer capability, so an un-bound transport or un-upgraded peer ships the full batch verbatim exactly as before. No new metric and no new public type: the existing `ship.manifest_exchanges` / `ship.elided_payloads` / `ship.elided_payload_bytes` counters remain the observability surface. See [`docs/lattice.replication/transport.md`](docs/lattice.replication/transport.md) (#728).

## [7.0.0] - 2026-06-11

Major release across the package family. Two source-affecting changes set the major digit, both wire-compatible and source-breaking only: Azure Table WAL row-payload compression is now **on by default** (`AzureTableWalStorageOptions.Compression` defaults to `Zstd`), and the twelve public CRDT primitive types moved from the `Orleans.Lattice.Primitives` namespace into the root `Orleans.Lattice` namespace (with `TxStatus` / `TerminalTallyResult` demoted to `internal`). Headline additions: cross-tree (multi-tree) all-or-nothing atomic writes with cross-cluster atomic visibility (F-098); RGA sequence replication for collaborative ordered lists / text via the new `LatticeMergeMode.Sequence` (R-036); WAL compression-savings metrics on the Azure Table provider (F-100); a cluster-internal typed FIFO queue primitive `ILatticeQueue<T>` (F-042); and a WAL phase-one idempotency fix that resolves lost-response Azure Table SDK retries as durable successes instead of failing the batch. See the per-section entries below.

### Added

- **R-036 - RGA sequence replication (delta + dispatch).** Trees configured for the new `LatticeMergeMode.Sequence` mode now replicate collaborative ordered lists / text (an `Orleans.Lattice.Rga` authored through `ILattice.Sequence<T>(key)`) across clusters with full active-active convergence: every site observes an **identical ordered traversal** after concurrent insert / delete bursts, not merely the same set of surviving elements. The producer side captures the dot-explicit structural intent of each edit - `InsertAtAsync` / `InsertAfterAsync` resolve to an inserted node carrying its `(dot, parentDot, value)` and `RemoveAtAsync` / `RemoveAsync` resolve to a tombstoned dot - into a new public `RgaDelta` (with `RgaDeltaNode` inserts and tombstone dots), stamped onto `WalRecord.Delta` and shipped delta-only; the receiver folds it via the new `Rga.MergeDelta(RgaDelta)` operation, which is commutative, associative, and idempotent. `Sequence` is a global closed CRDT shape (`CrdtShape.ForRga`), so no per-tree shape registration is required (unlike `OrMap`). New public types: the `LatticeMergeMode.Sequence` enum member, `RgaDelta` (alias `ol.rgd`), and `RgaDeltaNode` (alias `ol.rgi`). The `RgaAccessor<T>` mutation methods keep their existing signatures but now commit through the typed-delta WAL seam (CAS-free producer-side apply, matching `MvRegisterAccessor` / `OrMapAccessor`). **Back-pressure note:** `Sequence` replicates at operation granularity, so a high-frequency editor against a single sequence key generates one WAL entry per keystroke - apply a producer-side debounce / coalescing policy, or use a coarser-grained LWW / whole-document write for cold sequences. See [`docs/lattice.replication/replication-modes.md`](docs/lattice.replication/replication-modes.md#sequence-mode-back-pressure-hazard) and [`docs/lattice.replication/deltas.md`](docs/lattice.replication/deltas.md) (#456).
- **F-098 - Cross-tree (multi-tree) atomic writes.** New `IGrainFactory.SetManyAtomicAsync(IReadOnlyList<LatticeTreeBatch>, operationId, ct)` extension and a `IGrainFactory.BeginAtomicWrite(operationId)` fluent builder (`LatticeAtomicWriteBuilder`) commit a batch spanning two or more distinct `ILattice` trees all-or-nothing, with the same atomic-visibility guarantee the single-tree `SetManyAtomicAsync` saga gives within a tree - readers on the local cluster and on every replicating cluster observe either every targeted key across every participating tree or none of them, never a partial cross-tree commit. Implemented as a two-level saga: an internal coordinator grain keyed by the caller-supplied `operationId` is the single global decision authority, each participating tree runs the existing per-tree saga in a new prepare-and-pause mode, and each tree's `ITxRegistryGrain` delegates its prepared txid's status resolution to the coordinator until the single global decision lands. New public types `LatticeTreeBatch` (per-tree slice; deliberately not `[Immutable]` so Orleans deep-copies it across the grain-proxy boundary) and the `CrossTreeAtomicWriteOutcome` enum (`Committed` / `PreconditionFailed`). A stable `operationId` is required (no auto-generated overload) and must not contain `/`. Cross-cluster atomic visibility is preserved by a receiver-side barrier: because each participating tree's terminals replicate on their own per-tree WAL feed, the receiver routes cross-tree terminals (stamped with `WalRecord.CrossTreeOperationId` / `CrossTreeParticipants`) through an internal receiver coordinator grain (`ILatticeCrossTreeReceiverGrain`, keyed by `(originClusterId, operationId)`) that holds every participating tree invisible until a terminal has arrived for each tree it expects, then flips them together. The receiver's wait set is scoped to the trees it actually replicates (`LatticeReplicationOptions.ReplicatedTrees`), so a batch spanning a mix of replicated and non-replicated trees stays valid - the barrier completes on the present subset. Purely additive: no change to `SetManyAtomicAsync` or any existing signature, and all new persistent-state slots are forward- and backward-compatible (#671).
- **F-100 - WAL compression-savings metrics on the Azure Table provider.** Each append batch a compressing WAL provider commits now emits per-tree counters on the `orleans.lattice` meter so a dashboard can chart the realised compression savings: `orleans.lattice.storage.wal.uncompressed_bytes` (pre-compression encoded payload bytes) and `orleans.lattice.storage.wal.stored_bytes` (post-compression stored bytes), both in `By` and tagged `tree`, plus `orleans.lattice.storage.wal.compression_skipped` (`{row}`, tagged `tree` and `reason`) attributing every verbatim row to `below_threshold`, `inflation_guard`, or `disabled`. The savings ratio is `1 - stored_bytes / uncompressed_bytes`; the skip-reason breakdown distinguishes a threshold that is set too high (lower `CompressionMinPayloadBytes`) from genuinely incompressible payloads (lowering it would only burn CPU). Exposed as new public constants and `Counter<long>` fields on `LatticeMetrics` (`StorageWalUncompressedBytes(Name)`, `StorageWalStoredBytes(Name)`, `StorageWalCompressionSkipped(Name)`) plus the `ReasonBelowThreshold` / `ReasonInflationGuard` / `ReasonCompressionDisabled` tag constants. Purely additive; emitted once per batch after its phase-1 rows land, so a failed append records nothing. See [`docs/lattice/compression.md`](docs/lattice/compression.md#observability-compression-savings-metrics) (#676).
- **F-075 - Per-row WAL payload compression on the Azure Table provider.** Each WAL entry row's `Payload` column can now be transparently compressed before it is persisted, shrinking the retained on-disk footprint of large mutations. Compression is opt-in per tree via two new `AzureTableWalStorageOptions` knobs: `Compression` (`LatticeCompression`, default `None`) selects the algorithm tag applied to each row, and `CompressionMinPayloadBytes` (`int`, default `256`, validated non-negative) is the encoded-payload threshold below which a row is stored uncompressed even when compression is enabled (`0` compresses every row). The `256` default was chosen empirically for JSON values: an in-process sweep of realistic JSON through the real encode + Zstd-3 path showed compressed payloads never inflate at any size and that the reduction crosses ~25% near 256 encoded bytes, so a higher floor (the `512` the replication framing-tail threshold uses) would leave a band of 25-48%-compressible rows stored verbatim. A compressed row stores `[4-byte little-endian uncompressed length][compressed bytes]` in `Payload` and carries the algorithm tag in a new `Compression` column on `AzureTableWalEntity` (stored as an `int` because Azure Table Storage has no single-byte EDM property type). Reads key on the **row's stored tag, not the reader's option**, so a reader configured with `Compression = None` still inflates compressed rows as long as the matching `ILatticeCompressor` is registered; rows written before the column existed decode the absent property to `0` (`None`) and read back verbatim, so the change is backwards-compatible with no migration. Both encode paths compress (`AppendBatchAsync` and the shipper's pre-encoded `AppendEncodedBatchAsync` fast path) and both read paths inflate (`ReadAsync`, `ReadEncodedAsync`), and the row's recorded `PayloadBytes` now reflects the actually-stored (possibly compressed) size. `AddAzureTableWalStorage` registers a `ZstdLatticeCompressor` fallback (at `LatticeAzureTableServiceCollectionExtensions.DefaultCompressionLevel`, currently `3`) via `TryAddEnumerable` so enabling `Compression = LatticeCompression.Zstd` works with no extra wiring; because registration is additive, a host that has already registered its own Zstd compressor (e.g. for replication) wins the level. The provider gains a compression-aware constructor overload `(IOptions, Serializer<WalRecord>, IWalSaturationSignal?, IEnumerable<ILatticeCompressor>?)` that builds a per-tag dispatch dictionary and fails fast if compression is enabled with no matching compressor registered. See [`docs/lattice/compression.md`](docs/lattice/compression.md#azure-table-wal-row-payload-compression) (#395).
- **F-042 - Cluster-internal FIFO queue primitive `ILatticeQueue<T>`.** A new public typed, single-cluster FIFO queue resolved via `IGrainFactory.GetLatticeQueue<T>(name, serializer?)`, surfacing `EnqueueAsync` (returns a monotonic `long` id), `TryDequeueAsync`, `PeekAsync`, `CountAsync`, and an ascending-id `ListAsync` snapshot, with `LatticeQueueEntry<T>` as the read shape. Each logical queue is one coordinator grain over a reserved `_lattice_queue_{name}` system tree (`LatticeConstants.QueueTreePrefix`, subsumed by the already-reserved `_lattice_` prefix, so no new user-facing tree-name restriction); head/tail/count are served from an in-memory cache, a head-cursor row lets cold start and steady-state dequeue skip already-dequeued ids, and entry ids are recomputed as `max(stored) + 1` on activation. A new optional `LatticeOptions.QueueCapacity` (`null` = unbounded; validated `>= 1` when set) caps a queue with FIFO eviction. Values round-trip through an injectable `ILatticeSerializer<T>` (default `JsonLatticeSerializer<T>.Default`) client-side, so `T` need not be Orleans-serializable. Strictly cluster-internal: not CRDT-replicated and never ships a `LatticeMergeMode`. See [`docs/lattice/queues.md`](docs/lattice/queues.md) (#362).

### Changed

- **Internal-node digest upward-publish reuses a single per-activation deadline timer instead of allocating one per publish.** `BPlusInternalGrain.PublishUpwardAsync` bounded each cross-grain digest publish with a freshly constructed `CancellationTokenSource(timeout)`, which arms a one-shot timer on every publish, at every internal level, on every mutation - the dominant allocation of the bulk-write digest-propagation path (profiled at ~40.7% / ~205 MB of the bulk-write profile). Because upward publishes only run while the activation holds its non-reentrant `_splitGate`, at most one publish is ever in flight per activation, so the grain now arms and recycles a single reusable `CancellationTokenSource` per activation (`CancelAfter` to arm; `TryReset()` to disarm and recycle after each non-fired publish; dropped and re-created only on the rare timeout path). The timeout contract is unchanged in every observable way - the `Timeout.InfiniteTimeSpan` unbounded fast path, the `TimeoutException`-on-park gate-release behaviour, the `orleans.lattice...DigestPublishTimeouts` metric, and the staleness-tolerant re-drive on the next mutation all behave exactly as before. Measured on the microbench tier (BDN dry, `MemoryDiagnoser`, isolated A/B): `microbench_bulk_load_deeper_tree_alloc_b` 145,912 -> 142,464 B/op (-2.36%, deterministic IQR=0), with no change on the shallower bulk-load shapes; the production bulk-write win is larger where the upward-publish path is exercised at depth. No public API or wire-format change.
- **F-042 - The replication dead-letter queue now runs on the shared queue engine.** `ReplicationDeadLetterGrain` was reimplemented on top of the same internal FIFO engine that backs `ILatticeQueue<T>`, consolidating the park/peek/list/remove/evict logic. Its durable on-disk format is preserved byte-for-byte: it keeps its `_lattice_replog_dlq_{treeId}` backing tree, its `e/{19-padded-id}` row keys, and its Orleans binary `Serializer<DeadLetterEntry>` payload, and it does not persist the new head-cursor row, so parked entries written by an earlier version are read back unchanged after upgrade. Public surface, metrics (including `dead_letter.removed{reason=evicted}` on FIFO eviction), and the `EntryKey` / `BackingTreeId` helpers are unchanged (#362).


### Fixed

- **WAL phase-one entry rows are now idempotent under Azure Tables SDK retry.** A phase-one WAL batch is written with non-idempotent `Add` operations, so when the SDK retry pipeline resent a batch whose first attempt had already committed server-side but whose response was lost (a socket / read timeout under CPU or network pressure), the resend collided with the now-durable rows and the service returned `409 EntityAlreadyExists` - which the SDK does not auto-retry. The provider rethrew that 409, failing the whole batch (up to ~4,000 operations on the bench hot path) as a hard write failure even though the data was already durable; because the WAL saturation classifier escalates on the first provider failure, this also flapped the tree into `Saturated` and collapsed write throughput while reads stayed healthy. `AzureTableWalStorageProvider` now catches a phase-one `409`, reads the resident rows back, and - only when every row is byte-identical (same offset, compression tag, and payload bytes) to the batch it tried to write - resolves the conflict as a durable success instead of a failure. A 409 whose resident rows differ, or a row that is absent, is a genuine offset collision and still surfaces loudly as a hard failure (so corruption is never masked); a transient fault during the verification read also surfaces the original 409 rather than the incidental read error. This mirrors the candidate row's long-standing `Upsert(Replace)` idempotency, which the entry rows previously lacked. Proven replays are counted on a new `LatticeMetrics.ProviderIdempotentReplays` counter (`orleans.lattice.provider.idempotent_replays`, `{call}`, tagged `tree` / `shard` / `phase`) - **not** on `provider.retry.exhausted` - so an already-durable write neither fails the caller nor escalates the saturation classifier, and operators get a leading indicator of lost-response retries. The new counter is surfaced on the Commit Path Grafana dashboard's provider-retries panel and documented in [`docs/lattice/metrics.md`](docs/lattice/metrics.md). Purely additive; no wire-format change (#685).

### Breaking

- **F-075 - Azure Table WAL row-payload compression is now ON by default.** `AzureTableWalStorageOptions.Compression` now defaults to `LatticeCompression.Zstd` (was `None`), so WAL rows above `CompressionMinPayloadBytes` (default `256`) are Zstd-compressed unless a host opts out with `Compression = LatticeCompression.None`. This is justified by the measured win - the `EncodeWalBatch_AzureTable_Zstd` microbenchmark shows ~81% fewer allocated bytes (and Gen0/Gen1 -> ~0) when encoding a 99-entry batch of ~4 KB values, while small (sub-threshold) and incompressible payloads see no penalty. A new **inflation guard** in `CompressPayload` makes default-on safe for any payload shape: if the compressed bytes plus the 4-byte length prefix are not smaller than the input (e.g. already-compressed or random binary), the row is stored verbatim with tag `None`, so enabling compression never grows a row. The DI path (`AddAzureTableWalStorage`) auto-registers the `ZstdLatticeCompressor` fallback, so the default works with no extra wiring; the bare `AzureTableWalStorageProvider(options, serializer)` constructor (no compressors) now throws at construction when compression is enabled with no matching compressor registered - set `Compression = None` on that path. Changing the algorithm or Zstd level after rows exist remains safe: reads key on each row's stored tag and the self-describing frame's length prefix, never the reader's configured level. See [`docs/lattice/compression.md`](docs/lattice/compression.md#azure-table-wal-row-payload-compression) (#395).

- **F-078 - Public CRDT primitive types moved from the `Orleans.Lattice.Primitives` namespace into the root `Orleans.Lattice` namespace.** The twelve public CRDT building blocks - `HybridLogicalClock`, `ICrdt<TSelf>`, `MvRegister`, `MvRegisterEntry`, `OrMap<TKey, TValue>`, `OrMapEntry<TValue>`, `OrSet`, `OrSetDot`, `PnCounter`, `Rga`, `RgaNode`, and `VersionVector` - now declare `namespace Orleans.Lattice`, matching the repo convention that the entire public API sits behind a single `using Orleans.Lattice;`. **This is wire-compatible**: every affected type keeps its stable `[Alias(...)]` and the Orleans serializer is CLR-namespace-independent, so persisted WAL rows and the replication wire shape are unchanged. **It is source-breaking** for external host code that imported the old namespace - replace any `using Orleans.Lattice.Primitives;` that resolved one of these types with `using Orleans.Lattice;`. The area-internal helpers (`LwwValue<T>`, `LeafDeliveryCursor`, `SplitState`, `SplitStateExtensions`, `StateDelta`) stay `internal` in `Orleans.Lattice.Primitives` and were never part of the public surface. A type-forwarder shim is not possible for an in-assembly namespace move, so this ships as a single hard flip (#398).
- **F-078 - `TxStatus` and `TerminalTallyResult` are now `internal`.** These two types in `Orleans.Lattice.BPlusTree` were `public` only incidentally: their sole owning interface `ITxRegistryGrain` is already `internal` and no public surface referenced them. They are demoted to `internal` so they no longer leak into the public API; their wire aliases are unchanged (#398).
