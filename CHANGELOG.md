# Changelog

All notable changes to the Orleans.Lattice package family are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

This changelog covers the whole **package family** - every published `Orleans.Lattice` and `Orleans.Lattice.*` package, spanning the core library and its replication, storage, membership, auth, data, backup, caching, schema, scaling, dashboards, MCP, API/gRPC binding, and Explorer companions. Packages ship in lockstep on the major and minor digits; patch digits may advance per-package.

## [Unreleased]

Outstanding work is tracked on [GitHub Issues](https://github.com/NSTA1/Orleans.Lattice/issues), labelled `lattice` or `lattice.replication`. See [`docs/RELEASING.md`](docs/RELEASING.md) for the per-package tag-and-publish protocol.

### Added

- **Orleans.Lattice.Explorer / Orleans.Lattice.Explorer.Entra.Web: graceful re-authentication and cross-instance-durable auth state for multi-replica / failover hosting (opt-in, additive - default behaviour unchanged).** Running the Explorer behind more than one replica could wedge a signed-in operator when a mid-session move landed them on a replica that could neither decrypt their session cookie nor acquire a downstream token. Two complementary opt-in fixes address this. **Graceful re-authentication:** a new `MapLatticeExplorerEntraWebReauth` endpoint issues a forced-interactive OpenID Connect challenge (`prompt=login`) that redeems a fresh authorization code even when a valid session cookie already exists, repopulating the receiving replica's token cache; its caller-supplied return URL is guarded to local paths only (fail-closed open-redirect protection). The console now traps the credential's revoked state and shows a "Your session expired - sign in again" interstitial that navigates to that endpoint, instead of rendering the raw gRPC error inside the circuit. **Cross-instance-durable auth state:** `LatticeExplorerWebOptions` gains opt-in options (`DataProtectionKeyRingBlobUri`, `DataProtectionKeyRingCredential`, `DataProtectionApplicationName`, `ConfigureDataProtection`) to persist the ASP.NET Data Protection key ring to shared Azure Blob Storage so every replica can decrypt one another's session cookie (fail-closed: a blob URI with no credential throws at registration rather than falling back to the ephemeral ring), and the distributed token cache is documented as a first-class estate-global choice. When none of the new options are set, behaviour is exactly as before. ([#1338](https://github.com/NSTA1/Orleans.Lattice/issues/1338))


## [2026-07-24]

Per-package patch activity for 2026-07-24. **`Orleans.Lattice.Replication` advances to 8.0.6** (`lattice.replication-v8.0.6`) and **`Orleans.Lattice` advances to 8.0.2** (`lattice-v8.0.2`); every other package in the family remains at its current version.

### Fixed

- **Orleans.Lattice.Replication: digest anti-entropy re-replay no longer ships CRDT-mode entries with a defaulted merge mode that the receiver rejects (`Orleans.Lattice.Replication` 8.0.6).** The targeted leaf re-replay and its bootstrap-snapshot fallback re-ship WAL-sourced and live-re-derived entries through the typed `ReplicationBatchEnvelope`, which the receiver decodes verbatim. But the canonical WAL codec omits the `WalRecord.Mode` slot whenever it holds the enum default (`LwwRegister`), and the durable read-back has no per-batch framing header to restore it - while bootstrap-fallback entries are re-derived from the live projection with no `Mode` set at all - so every remediation entry surfaced with `Mode = LwwRegister`. For any tree whose fixed merge mode is not `LwwRegister` (every CRDT mode, and the internal `sys-replication-config` OR-Map control tree), the receiver's merge-mode gate rejected a wire mode that disagreed with its locally resolved mode, so automatic anti-entropy could never heal those trees; worse, because per-tree replication enrollment is itself distributed through the `sys-replication-config` OR-Map tree, a cluster that relied on anti-entropy to converge that tree could never learn a peer's enrollment and would then reject the peer's user-tree runs as "not enrolled". The re-replay egress now re-stamps every entry's `Mode` from the tree's resolved merge mode before framing (mirroring the batch-constant `TreeId` re-stamp shipped in 8.0.5 and the ordinary `ChangeFeed` shipper's own mode re-stamp), which is correct because the envelope is strictly per-tree and a tree has exactly one fixed merge mode. ([#1334](https://github.com/NSTA1/Orleans.Lattice/issues/1334))

- **Orleans.Lattice: leaf projection staleness faults now serialise across the grain boundary instead of degrading into an opaque messaging storm (`Orleans.Lattice` 8.0.2).** `LeafProjectionStaleException` is raised from `BPlusLeafGrain` activation (`ReplayWalSinceCheckpointAsync`) when a leaf's durable projection checkpoint has fallen off or diverged from the per-shard WAL and the configured `ProjectionRebuildPolicy` elects to surface the condition rather than auto-recover. Leaf activation is routinely driven across a silo boundary - the data API and the cross-cluster replication digest probe both activate a leaf placed on a peer silo - but the exception carried no `[GenerateSerializer]`/`[Alias]` and no Orleans serialization codec, so when the fault propagated to the cross-silo caller the messaging layer threw `CodecNotFoundException` in `Connection.ProcessOutgoing` instead. A clean, actionable "operator-driven projection rebuild is required" domain error was thereby degraded into a flood of opaque connection and grain-activation failures, surfaced to callers only as a generic internal error that masked the real, recoverable cause. The exception is now `[GenerateSerializer]`-annotated with a stable `[Alias]`, matching its sibling activation-path exceptions (for example `ShardActivationTimeoutException`), so the typed fault round-trips to the caller intact. ([#1336](https://github.com/NSTA1/Orleans.Lattice/issues/1336))

Two new packages debut at 8.0.0: **`Orleans.Lattice.Api.Replication` 8.0.0** (`lattice.api.replication-v8.0.0`) and **`Orleans.Lattice.Api.Replication.Grpc` 8.0.0** (`lattice.api.replication.grpc-v8.0.0`). Existing packages advance: **`Orleans.Lattice` 8.0.1** (`lattice-v8.0.1`), **`Orleans.Lattice.Api.Abstractions` 8.0.1** (`lattice.api.abstractions-v8.0.1`), **`Orleans.Lattice.Api.Mcp` 8.0.3** (through `lattice.api.mcp-v8.0.2` and `-v8.0.3`), **`Orleans.Lattice.Replication.Grpc` 8.0.1** (`lattice.replication.grpc-v8.0.1`), and **`Orleans.Lattice.Replication` 8.0.5** across five changes (`lattice.replication-v8.0.1` through `-v8.0.5`). Every other package in the family remains at its current version. Each entry below names the exact package version that carried it.

### Added

- **Orleans.Lattice.Api.Mcp: opt-in OAuth 2.0 Protected Resource Metadata (RFC 9728) discovery for the MCP endpoint (`Orleans.Lattice.Api.Mcp` 8.0.3).** A remote MCP head was a plain bearer-token resource server: a spec-compliant MCP client that tried to discover the authorization server got a `404` from `/.well-known/oauth-protected-resource` and a bare `WWW-Authenticate: Bearer` challenge with no `resource_metadata` hint, so it could not begin the OAuth sign-in flow and the operator had to paste a pre-acquired token. Set the new `LatticeApiMcpOptions.ProtectedResourceMetadata` (a `LatticeApiMcpProtectedResourceMetadata` carrying the resource identifier, authorization server URLs, and requested scopes) and `MapLatticeMcp` serves an anonymous metadata document at `/.well-known/oauth-protected-resource`, while the binding appends a `resource_metadata` hint to the endpoint's `401` bearer challenge. The challenge augmentation is scheme-agnostic (it wraps whatever bearer challenge the host's authentication handler emits and is scoped to the transport path), so the package takes on no dependency on a specific authentication library, and the metadata endpoint is mapped anonymously so a client can read it precisely because it received a `401`. Leaving the option unset (the default) preserves the previous behaviour exactly. ([#1321](https://github.com/NSTA1/Orleans.Lattice/issues/1321))

- **Runtime per-tree replication configuration: enable or disable cross-cluster replication for a tree at runtime, without a redeploy (`Orleans.Lattice.Api.Replication`, `Orleans.Lattice.Api.Replication.Grpc`, `Orleans.Lattice.Replication`, `Orleans.Lattice.Api.Mcp`, `Orleans.Lattice.Api.Abstractions`).** Replication was previously fixed at boot by the static `LatticeReplicationOptions.ReplicatedTrees` options map; a tree could not be brought into or out of replication on a live cluster. The new `ILatticeReplicationControl` facade (with a gRPC binding and a permission-scoped MCP `lattice_replication_*` tool group) enables a tree under a merge mode chosen at enable-time, disables it without purging data already replicated to peers, and reports each tree's live enabled state, mode, and convergence. The per-tree decision is distributed as a replicated CRDT system tree (`sys-replication-config`), so every enrolled cluster converges on the same configuration with no bespoke handshake; the merge mode is fixed at enable-time (change is disable-then-re-enable, which re-bootstraps), and the commit path fails closed - pausing shipping - when concurrent clusters leave a tree's mode ambiguous. Authoring is gated by the existing fail-closed API access gate; propagation is not re-consented per cluster. The static options map remains as the seed and fallback, so existing static deployments are unaffected. ([#1312](https://github.com/NSTA1/Orleans.Lattice/issues/1312))

### Fixed

- **Orleans.Lattice.Replication: digest anti-entropy re-replay no longer ships tree-less WAL entries that permanently wedge a peer (`Orleans.Lattice.Replication` 8.0.5).** Targeted leaf re-replay and its bootstrap-snapshot fallback re-ship WAL-sourced entries through the typed `ReplicationBatchEnvelope`, which the receiver decodes verbatim - unlike the ordinary shipper's framing path, which strips the batch-constant `TreeId` on encode and re-stamps it from the batch tree name on decode. But the durable WAL read-back does not restore that stripped `TreeId`, so a re-replayed entry reached the peer with an empty `TreeId`. The receiving applier rejects an empty-`TreeId` record and, worse, could not even quarantine it: the per-tree dead-letter and per-origin high-water-mark grains are keyed on the tree id, so parking the poison entry threw on the empty grain key before the entry was dead-lettered or the cursor advanced - turning a single such entry into an unbounded re-ship loop that blocked all convergence for the tree. The re-replay egress now re-stamps every entry's `TreeId` from the batch tree name before framing (mirroring the framing receiver, and correct because the envelope is strictly per-tree), so no tree-less entry is ever shipped. As a defence-in-depth backstop, the dead-letter tracking applier now contains a structurally-invalid empty-`TreeId` failure - recording the dead-letter metric and returning a non-applied result without keying any per-tree grain - instead of crashing the quarantine path. ([#1331](https://github.com/NSTA1/Orleans.Lattice/issues/1331))

- **Orleans.Lattice.Replication: automatic digest anti-entropy now heals below-cursor orphans instead of stranding them (`Orleans.Lattice.Replication` 8.0.4).** When a later write advanced a peer's replication high-water-mark past a gap of older entries that were never shipped, targeted leaf re-replay could not repair them: it re-ships only WAL entries strictly newer than the peer's cursor, so the stranded orphans sit at or below the cursor, are filtered out, and the repair pass reports an empty range. The bootstrap-snapshot fallback - which re-derives the divergent key ranges from the live tree with no cursor filter and re-ships them - previously fired only when the retained WAL had been garbage-collected past the divergence, so a below-cursor gap fell into a blind spot and the drift persisted until an unrelated write happened to re-cover the range. The digest-probe grain now triggers the bootstrap-snapshot fallback on an empty targeted-re-replay range as well as on a trimmed WAL, so a localised divergence the cursor-bounded pass cannot close is always re-derived from the live projection and healed. The fallback stays bounded by the existing per-cycle entry and byte budgets and runs only after the Merkle walk has localised genuine divergence. ([#1330](https://github.com/NSTA1/Orleans.Lattice/issues/1330))

- **Orleans.Lattice.Replication / Orleans.Lattice.Replication.Grpc: automatic digest anti-entropy detection and remediation now runs on deny-by-default (auth-enforced) clusters instead of silently self-blocking (`Orleans.Lattice.Replication` 8.0.3, `Orleans.Lattice.Replication.Grpc` 8.0.1).** The cross-cluster anti-entropy digest chain read a tree's projection digest through the fail-closed data-plane access gate with no ambient principal: the probe grain's own local per-shard read (`ReplicationDigestProbeGrain` via `ILattice.GetLeafProjectionDigestAsync`) and the peer-serving gRPC handlers (`LatticeReplicationGrpcService.ProbeDigest` / `ProbeMerkleWalk` via `GetLeafProjectionDigestAsync` / `GetLeafProjectionDigestForRangeAsync`). On a deny-by-default tree those reads resolved to the anonymous subject and were refused, so the probe skipped every shard, never reached detection, and never localised or remediated drift - disabling self-healing on exactly the secured estates that need it (the engine shipper was unaffected because it reads the WAL through a lower-level, ungated path). Both reads now run under a `LatticeAccessGateContext.EnterSystemOrigin()` scope so the access gate's documented infrastructure bypass applies; the gRPC handlers route through a new internal `ReplicationSystemOriginDigestReader` in the replication package (which already grants IVT to the gRPC binding), so the core package needs no re-release. The system-origin marker is established inside the trust boundary and flows only on in-silo grain calls - the silo-wide capability-stripping call filter strips it from any genuine external client, so it can never be forged from the wire - and the gRPC RPCs remain gated by the replication shared-secret interceptor. ([#1327](https://github.com/NSTA1/Orleans.Lattice/issues/1327))

- **Orleans.Lattice.Replication: a tree whose replication is enabled purely at runtime now ships and converges its writes to peers (`Orleans.Lattice.Replication` 8.0.2).** The replication driver's silo-startup hosted service enrolled its shipper, maintenance, and digest-probe grains only from the static `LatticeReplicationOptions.ReplicatedTrees` options map and returned early when that map was empty. A tree brought into replication at runtime through the `lattice_replication_*` control plane (added in 8.0.6) therefore had its writes captured to the WAL but never shipped, so the data silently diverged across clusters even though the control plane reported the tree as enabled. The driver now enrols from the replicated-tree membership - the union of the static seed map and the runtime-enabled set - and, when the host opts into runtime replication configuration, polls the compiled-config snapshot epoch on a background timer so newly-enabled trees are enrolled live without a restart. A host that uses only the static options map is unaffected: it takes the one-time startup enrolment path and never starts the poll loop. ([#1325](https://github.com/NSTA1/Orleans.Lattice/issues/1325))

### Added

- **Orleans.Lattice.Api.Mcp: a managed-identity-backed administrator credential source for the remote MCP head that self-refreshes its introspection token.** A remote-host MCP server previously needed a static `AdministratorCredential` for permission-scoped discovery; acquired from Entra that token expires after ~1h, silently degrading discovery until the process is restarted. Register `AddLatticeMcpManagedIdentityAdministrator(...)` with an `Azure.Core` `TokenCredential` (for example `ManagedIdentityCredential`) and the silo-audience scope, and the source acquires, caches, and refreshes the token a configurable skew before expiry, failing closed on acquisition failure. It takes precedence over the static `AdministratorCredential`. ([#1304](https://github.com/NSTA1/Orleans.Lattice/issues/1304))

- **`Orleans.Lattice.Explorer.Entra.Web` 8.0.0 - hosted-web Microsoft Entra ID (OpenID Connect) sign-in for the Blazor Server Explorer.** Adds an interactive, browser-based Entra sign-in that wires the ASP.NET Core OpenID Connect flow (authorization code + PKCE, cookie session) through Microsoft.Identity.Web and exchanges the signed-in browser user's session for a downstream State API bearer token, so a hosted Explorer connects to an auth-enabled cluster as that user. It is the web counterpart to the desktop/device-code `Orleans.Lattice.Explorer.Entra`: a remote Blazor Server circuit has no ambient `HttpContext`, so the token acquirer passes the circuit's `ClaimsPrincipal` to Microsoft.Identity.Web explicitly. The package plugs into the core `IExplorerAuthMethod` seam for the `entra` scheme (the released Explorer's sign-in dialog already renders a generic button for it), so there is **no public API change to any released Explorer package**. The auth method and token acquirer are registered scoped for per-circuit credential isolation; by default the registration installs a fail-closed fallback authorization policy and a best-effort auto-sign-in circuit handler that degrades silently to the interactive dialog on any failure. A re-auth-required signal from Microsoft.Identity.Web is translated into a typed `ExplorerWebReauthRequiredException` and latches the credential as revoked rather than serving a stale token. Register with `AddLatticeExplorerEntraWebAuth(...)` and `MapLatticeExplorerEntraWebSignOut(...)`. Part of the broader OpenID Connect work tracked in [#1298](https://github.com/NSTA1/Orleans.Lattice/issues/1298).

- **`Orleans.Lattice.Caching.AzureBlob` 8.0.0 - a durable Azure Blob Storage `IDistributedCache` for the family.** Implements the standard ASP.NET Core `IDistributedCache` abstraction over an Azure Blob Storage container, so a hosted-web component that needs a shared, multi-replica-safe cache - most notably the Microsoft.Identity.Web distributed token cache behind `Orleans.Lattice.Explorer.Entra.Web` - has a durable backend without a dependency on Redis or SQL Server (there is no official Azure Storage `IDistributedCache` adapter). Each entry is a single block blob whose name is the SHA-256 hash of the cache key (optionally under a `KeyPrefix` virtual directory), with absolute and sliding expiry held in blob metadata and enforced lazily on read, so the container self-prunes. Exactly one authentication mode - connection string, service URI with an Azure AD token credential, service URI with a shared-key credential, or a pre-built `BlobServiceClient` - is validated fail-closed at first resolution; the container is created on first use. Expiry arithmetic is pure and `TimeProvider`-injectable. Register with `AddAzureBlobDistributedCache(...)`.

### Changed

- **Orleans.Lattice.Api.Mcp: the `lattice_data_read_range` tool now advertises its range bounds, page size, and continuation token as optional.** They were declared without C# defaults, so the MCP SDK emitted them into the JSON-schema `required` array and a schema-conformant client was forced to send all of them even though the facade treats them as optional. Only `treeId` is required now; omit the rest for a full, unbounded first page. ([#1303](https://github.com/NSTA1/Orleans.Lattice/issues/1303))

### Fixed

- **Orleans.Lattice.Explorer.Entra.Web: hosted-web auto-sign-in now completes on first load instead of leaving the console anonymous (`Orleans.Lattice.Explorer.Entra.Web` 8.0.2).** The auto-sign-in circuit handler runs on `OnConnectionUpAsync`, which fires before the `ConfigurationGate` component initializes the explorer session, so the endpoint configuration (`IExplorerSession.Current`) was still null when the handler probed for the advertised auth scheme. Discovery therefore returned an empty advertisement, the handler concluded the endpoint did not advertise the `entra` scheme, and it left the connection anonymous - the State area listed no trees, the Access area was disabled, and a redundant in-app sign-in button appeared even though the browser was already signed in. The handler now initializes the explorer session itself (idempotently, so the later `ConfigurationGate` initialization is a no-op) before discovery, so `Current` is populated and the advertised `entra` scheme is seen. This is a binary- and wire-compatible change; the handler's constructor gains an `IExplorerSession` dependency resolved from the same per-circuit scope.
- **Orleans.Lattice.Explorer.Web: the credential cookie store no longer throws when a sign-in completes inside a Blazor Server circuit (`Orleans.Lattice.Explorer.Web` 8.0.2).** `CookieCredentialStore` wrote and cleared the credential cookie unconditionally through `IHttpContextAccessor.HttpContext`. Inside a Blazor circuit that accessor resolves the long-lived SignalR request whose response has already started, so writing a response cookie threw `InvalidOperationException: Headers are read-only, response has already started`, which aborted an in-circuit sign-in (for example the Entra auto-sign-in). `SetAsync` and `ClearAsync` now no-op when the response has already started (`HttpResponse.HasStarted`); the credential cookie is best-effort at-rest state and the live connection is driven by the in-memory sign-in, so skipping the write is safe. The explicit `/auth/login` endpoint path, where the response has not started, is unaffected.

- **Orleans.Lattice.Explorer.Entra.Web: the hosted-web Explorer circuit now sees the signed-in Entra user instead of an anonymous principal (`Orleans.Lattice.Explorer.Entra.Web`).** `AddLatticeExplorerEntraWebAuth` now calls `AddCascadingAuthenticationState()`, so the Blazor Server circuit's `AuthenticationStateProvider` reports the OIDC-authenticated browser user rather than an anonymous one. Previously the web host authenticated the browser at the HTTP layer (cookie issued, pages rendered) yet the circuit still observed an anonymous user, so the auto-sign-in handler acquired no State API token and every cluster call was made anonymously - the State area listed zero trees and the Access area was disabled, with nothing logged.
- **Orleans.Lattice.Explorer: an unauthenticated connection is now distinguished from an empty or forbidden one, in the UI and in logs (`Orleans.Lattice.Explorer.Access` / `.UI` / `.Core` and `Orleans.Lattice.Explorer.Entra.Web`).** The auto-sign-in circuit handler now logs a warning when it runs on an anonymous circuit and an informational line when it completes sign-in, so a silent auto-sign-in failure is visible to operators. The Access area's capability probe now separates authentication failures (an unauthenticated rejection, or a denial while not signed in) from genuine authorization denials, and the disabled Access panel shows a distinct "not signed in to the cluster" banner with a sign-in prompt instead of the generic "not permitted" state.
- **Orleans.Lattice.Api.Mcp: MCP tool discovery now keys the caller's subject on the durable `oid` object-id claim instead of `sub`, so Entra delegated (user) callers see the tools their grants allow.** The HTTP credential bridge resolved the caller's principal id from `sub` (mapped to `NameIdentifier`), but for a delegated Entra access token `sub` is a pairwise (user, client-app) identifier that differs from the stable `oid` the silo auth model keys subjects on. Discovery therefore introspected the wrong subject and advertised no tools to a correctly-granted user until rules were redundantly re-authored under the pairwise `sub`. The bridge now prefers `oid` (both the raw claim and its mapped schema URI), falling back to `sub` and then the identity name, so grants authored once by `oid` apply consistently across every client app. ([#1302](https://github.com/NSTA1/Orleans.Lattice/issues/1302))

### Added

- **Dynamic-bearer telemetry backend auth (`Orleans.Lattice.Api.Mcp.Telemetry` 8.0.1) and the new `Orleans.Lattice.Api.Mcp.Telemetry.Azure` 8.0.0 companion package.** The MCP telemetry proxy gains a `DynamicBearer` backend-auth mode and a public `ITelemetryBackendTokenProvider` seam, so it can stamp a rotating bearer token fetched per request instead of a static credential, and fails closed if the mode is selected with no provider registered or the provider returns an empty token. The new companion package supplies a `TokenCredential`-backed provider (`AddAzureTelemetryBackendToken`) that lets the telemetry tools query an Azure Monitor managed-Prometheus workspace with a rotating Entra managed-identity token, keeping the `Azure.Core` dependency out of the cloud-neutral core package. The core additions (an appended `DynamicBearer` enum member and the new interface) are source-, binary-, and wire-compatible ([#1286](https://github.com/NSTA1/Orleans.Lattice/issues/1286)).

- **Secret-less (managed-identity) Microsoft Graph auth for the Entra group resolver (`Orleans.Lattice.Membership.Entra.Graph` 8.0.1).** `LatticeEntraGraphOptions` gains an optional `TokenCredential? Credential` property that selects a secret-less authentication path: when set, `AddEntraGraphGroupResolver` builds the shared app-only Graph client directly from that credential (for example a `DefaultAzureCredential` or `ManagedIdentityCredential` bound to a user-assigned managed identity) via the Graph SDK `GraphServiceClient(TokenCredential, scopes)` constructor, and no client secret is acquired, cached, or refreshed. The confidential-client (client-secret) path is unchanged and remains the default. The two modes are mutually exclusive and validated fail-closed: exactly one must be configured, and supplying both a `Credential` and a `ClientSecret` is rejected as ambiguous. `Microsoft.Graph` already transitively provides `Azure.Core`, so no new dependency is added. This is an additive, opt-in, source-, binary-, and wire-compatible change ([#1291](https://github.com/NSTA1/Orleans.Lattice/issues/1291)).

### Fixed

- **Orleans.Lattice.Explorer: auth-scheme discovery now also carries the transport headers, so sign-in offers the real scheme (for example Entra) instead of degrading to Basic behind an origin-locked proxy (`Orleans.Lattice.Explorer.Core` 8.0.2).** The 8.0.1 fix attached `TransportHeaders` to the shared state client and the four gRPC admin clients, but the auth-scheme probe (`GrpcExplorerAuthSchemeProbe`, which calls the unauthenticated `GetAuthScheme` RPC to learn how an endpoint wants callers to authenticate) opened its own bare gRPC channel and did not apply them. Against an origin-locked endpoint (for example an Azure Front Door origin lock enforced with `X-Azure-FDID`) the probe was therefore rejected at the origin, the caught `RpcException` yielded an empty advertisement, and discovery degraded to the built-in Basic username/password form even though the endpoint actually required Entra. `IExplorerAuthSchemeProbe` gains a transport-header-aware `ProbeAsync` overload (a default interface method that forwards to the existing method, so existing implementations keep compiling), the production probe applies the headers with the same metadata interceptor as the other clients, and `ExplorerAuthSession.DiscoverAsync` threads `ExplorerConfiguration.TransportHeaders` through to it. This is an additive, source-, binary-, and wire-compatible change.

- **Orleans.Lattice.Explorer: the console can now reach a State API that sits behind an origin-locked proxy (`Orleans.Lattice.Explorer.Core` / `.Access` / `.Backup` / `.Schema` 8.0.1).** When the State API origin is fronted by a proxy that only admits requests carrying a fixed routing header - the common case being an Azure Front Door origin lock enforced with `X-Azure-FDID` - the Explorer previously had no way to present that header on its native-gRPC calls, so every call was rejected at the origin and sign-in degraded to the built-in Basic form with an "access denied" banner. `LatticeConnectionSettings` gains an optional `TransportHeaders` dictionary (mapped from a new `ExplorerConfiguration.TransportHeaders`, seedable via the `LATTICE_EXPLORER_TRANSPORT_HEADERS` environment variable) that is attached to every call by all four gRPC admin clients regardless of the authentication mode. Unlike the existing per-sign-in authentication headers, these transport headers survive an interactive sign-in that replaces the credential, and they are never treated as a secret. This is an additive, opt-in, source-, binary-, and wire-compatible change.

### Security

- **Orleans.Lattice.Explorer.Web: the console now emits a `Referrer-Policy: no-referrer` response header.** The Explorer web head's baseline security-header middleware previously omitted `Referrer-Policy`, a member of the documented hardening set. This is a defense-in-depth change - the current console never places tree, key, or subject context in a URL path or query string (that context flows over the SignalR circuit, gRPC request bodies, and in-memory component state), so no existing navigation path leaks it via the `Referer` header. The header keeps that guarantee true for any future route that might embed context in a URL and completes the required hardening set. The middleware now sets `Referrer-Policy: no-referrer` (behind the same "do not clobber an existing value" guard as the other headers) on every response on the Explorer branch, at the root and under a base path. No public API change. (#1283)
- **Orleans.Lattice.Explorer.Web: the console now emits a `Permissions-Policy` response header.** The Explorer web head's baseline security-header middleware previously omitted `Permissions-Policy`, the last member of the documented hardening set. The console uses none of the powerful browser features it names, so the middleware now sends `Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()`, disabling those features for every origin so an injected or compromised script (already constrained by the CSP) cannot request them, and opting the console out of Topics/FLoC cohort computation. This is defense-in-depth hardening, not a fix for an exploitable flaw. Emitted from cached `StringValues` (no per-response allocation) behind the same "do not clobber an existing value" guard as the other headers, on every response on the Explorer branch, at the root and under a base path. No public API change. (#1284)

### Changed

- **Breaking - removed the inert membership user-record CRUD surface.** The
  per-user *record* concept - `MembershipUser` and its
  `ILatticeMembershipDirectory.UpsertUserAsync` / `GetUserAsync` / `ListUsersAsync`
  / `RemoveUserAsync` methods, the `AuthUser` / `AuthUserPage` DTOs and the four
  `ILatticeAuthAdmin` user methods, their `Orleans.Lattice.Api.Auth.Grpc` RPCs
  (`UpsertUser` / `GetUser` / `RemoveUser` / `ListUsers`) and wire types, the four
  `Orleans.Lattice.Api.Mcp` `lattice_auth_*_user` tools, the Explorer Access
  **Users** tab, and the reserved `sys-membership-users` tree (dropped from
  `LatticeSystemTreeNames` and from `ReplicateLatticeSystemTrees` enrolment) - is
  removed. **Why:** these records were **inert for authorization**. The access
  path resolves a subject's groups from its token claims, its asserted groups, and
  the membership *edges* it participates in (`sys-membership-edges`) - never from a
  stored user record - so a `MembershipUser` never affected a single allow/deny
  decision. Its only effect was to introduce a **third, confusing "user" concept**
  alongside the two that carry real weight: the **State-API credential user** (a
  deployment-time credential that gates the read-only State API, provisioned with
  `tools/New-LatticeStateCredential`) and the **static identity-roster user** (an
  entry in an `ILatticeIdentityDirectory` that backs the searchable subject picker
  and friendly-name display). Group membership is still authored through membership
  **edges** (`AddMemberAsync`, unchanged), friendly names still come from the
  identity directory, and `MembershipGroup` and the edge trees are non-inert and
  fully retained. Removing the dead surface eliminates the ambiguity and a
  maintenance burden with no loss of function. This is source- and wire-breaking
  for a consumer that called any of the removed members or persisted to the
  removed tree; migrate group authoring to `AddMemberAsync` and subject
  search/validation to an identity-directory provider.

- **Orleans.Lattice: `MvRegister.MergeDelta` folds a typed delta in place instead of building a throwaway register.** Applying an `MvRegisterDelta` to a live multi-value register previously constructed a transient `MvRegister` (copying the delta's entries into a fresh `List<MvRegisterEntry>` and its context into a fresh `Dictionary`) purely to hand it to `MergeFrom`. Every other CRDT primitive already folds its delta directly, and `MergeDelta` is on the CRDT apply / replication receive hot path, so those three allocations were paid on each delta applied. The fold now applies the delta's entries and context to the receiver directly, keeping the dot-context dominance semantics byte-for-byte identical (verified by an equivalence regression test against the previous `MergeFrom` form). Measured with a new `Crdt mvregister merge delta` microbenchmark (8 disjoint-replica live entries, idempotent same-dots delta): allocated bytes per apply drop from 1768 B to 496 B (about -72%) and the median fold latency from ~820 ns to ~655 ns. No public-API or wire-format change.

- **Extracted the shared API contract into a new `Orleans.Lattice.Api.Abstractions` package.** The four API facades' service interfaces (`ILatticeStateQuery`, `ILatticeStateObserver`, `ILatticeStateMetricsObserver`, `ILatticeDataApi`, `ILatticeAuthAdmin`, `ILatticeBackupControl`) and their request / response models now live in a single, versioned `Orleans.Lattice.Api.Abstractions` package and are `public`, so the gRPC bindings and the `Orleans.Lattice.Api.Mcp` server consume the contract directly instead of through cross-package `InternalsVisibleTo` grants into the facade and core assemblies. The interfaces and models keep their original `Orleans.Lattice.Api.{State,Data,Auth,Backup}` namespaces and their Orleans serialization aliases, so the change is source- and wire-compatible: a consumer that rebuilds against the new packages needs no code change, and persisted or in-flight payloads are unaffected. It is **binary-breaking** for the affected API facade and binding packages, since the moved public types change assembly, so those packages will require a major version bump when they are next released. A new public `LatticeSystemOrigin` seam in the core library gives a co-hosted infrastructure consumer the trusted system-origin scope the MCP server previously reached through an internal-visibility grant. See [`docs/lattice.api.abstractions/README.md`](docs/lattice.api.abstractions/README.md) (#1234).

### Fixed

- **Security hardening across the admin, replication, and telemetry surfaces (pre-v8 remediation).** A coordinated pass closed six verified security gaps found in a pre-release audit, making fail-closed enforcement the default on every affected boundary. Of these, only the replication receiver change is behavioural for an already-released package: a correctly-configured cluster pair (both sides enrolling the same trees with the same mode) is unaffected, but a misconfigured or non-enrolled inbound stream that was previously applied is now rejected; the MCP, telemetry, and Explorer surfaces are unreleased, so their hardening is not a breaking change. See [`docs/lattice.api.mcp/security.md`](docs/lattice.api.mcp/security.md), [`docs/lattice.api.mcp.telemetry/security.md`](docs/lattice.api.mcp.telemetry/security.md), [`docs/lattice.membership/identity-directory-providers.md`](docs/lattice.membership/identity-directory-providers.md), and [`docs/lattice.explorer/running-the-explorer.md`](docs/lattice.explorer/running-the-explorer.md) (#1270).

- **Release engineering: the publish workflow no longer inflates cross-package dependency floors.** `.github/workflows/publish.yml` stamped the release version as a global MSBuild property (`-p:Version` on build, `-p:PackageVersion` on pack), so every ProjectReference'd project in the graph evaluated to the tag version and each packed package emitted its intra-family dependency floors at the tag version instead of the referenced package's real published version. Whenever a referenced package's real version was lower than the tag (the normal case in a per-package patch wave), this silently shipped un-restorable packages - a package requiring, say, `Orleans.Lattice >= 7.9.3` when core was only ever published at 7.9.1. The workflow now trusts each csproj's own `<Version>` as the single source of truth (no global version override), so a packed package's dependency floors resolve to each referenced package's real version; and a new pre-restore guard step reads the packed csproj `<Version>` with `dotnet msbuild -getProperty:Version` and fails the release if it has drifted from the release tag, so a mis-versioned package can no longer be published. CI / release-tooling change only; no library, wire-format, or public-API change.

- **Orleans.Lattice.Api.Backup.Grpc / Orleans.Lattice.Explorer: a restore that fails a precondition now surfaces an actionable reason instead of an opaque internal error.** A restore that could not proceed - most notably a coordinated (replicated-tree) restore whose backup sink is not actually shared across every participating cluster, so a peer cannot resolve the sibling-captured backup and the saga aborts - threw a `LatticeRestoreValidationException` that the gRPC control service mapped to a generic `Internal: "The backup control-API request failed."`, giving the Explorer nothing to show. The service now maps `LatticeRestoreValidationException` to `FailedPrecondition` carrying its (id / tree / byte-count, no-secret) message, and the Explorer's Backups area recognises the unshared-sink signature and renders a friendly "the backup store must be reachable from every cluster" configuration message rather than a raw error. Additionally, the `MultiSiteManufacturing` sample now provisions a dedicated shared Azurite blob account (`azurite-backup`) multi-homed onto both cluster networks and points every silo at it through `Orleans.Lattice.Backup.AzureBlob`, so its coordinated restore actually works under `docker compose` instead of relying on a per-container filesystem path that is not shared; the single-machine `FileSystemBackupSink` path remains the fallback. Explorer and sample changes plus a `FailedPrecondition` mapping in the gRPC binding; no wire-format change to the package family.

- **Orleans.Lattice.Explorer: a replicated CRDT change now renders in entry history as a membership snapshot, not a raw full-value blob.** Follow-up to FX-062. A single CRDT change appeared on the receiving cluster as a `CrdtDelta` member diff, but a later anti-entropy / committed-projection resync still shipped a full-state row (`Set`, value = whole serialized OR-Set/PN-counter/OR-Map, no delta) that recorded as a full-value set and rendered as a raw blob tripping the explorer's value-preview cap - confusing duplicate-looking noise on CRDT trees. The history row already carries the source merge mode, so the explorer now classifies a CRDT-mode `Set` as a membership snapshot (decoded members, visually distinct from an LWW overwrite) rather than a last-writer-wins value diff; LWW sets still render as value diffs. Replication apply correctness and wire format are unchanged - bootstrap full-state stays a correct full-state merge, it just renders nicely. Presentation/classification fix in `Orleans.Lattice.Explorer`; no public-API or wire-format change (#1010).

- **Orleans.Lattice.Explorer web head now enforces antiforgery on the sign-in / sign-out endpoints (login / logout CSRF hardening).** The web head's `/auth/login` and `/auth/logout` form-post endpoints previously called `.DisableAntiforgery()`, justified by `SameSite=Strict` on the credential cookie - but that cookie is not presented on the login POST itself, so it gave no CSRF protection. A cross-site form post could drive a victim's browser to authenticate (or sign out) the Explorer with attacker-chosen credentials, and because the auth session is a process-global singleton this flipped the shared connection's credential for the whole process. Both endpoints now validate a `RequestVerificationToken` (the login and logout forms embed `<AntiforgeryToken />`) and reject a tokenless or mismatched post with `400 Bad Request` before touching the auth session. Explorer-only change; no public-API or wire-format change to the package family. (#966)
