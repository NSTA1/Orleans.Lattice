### Added
- **R-138 - Metrics observability series complete: every Lattice metric is surfaced on a Grafana dashboard.** Umbrella closure for the metrics-observability hardening done while replication was being built out. Both meters (`orleans.lattice` and `orleans.lattice.replication`) now have zero unpaneled live instruments, and the gap can no longer silently reopen: the backlog catch-up charted the previously-unpaneled instruments (35 across both meters), the bundled Grafana dashboards' `docs/lattice.dashboards/metrics-to-panel-map.md` map is accurate, and a forward drift-guard in `DashboardJsonTests` now asserts every live instrument is referenced by at least one panel (the prior guard only checked the inverse direction, so a brand-new instrument with no panel shipped unobservable and passed CI silently). Combined with the standing rule that every metric-adding PR includes its panel + map row + green `DashboardJsonTests` in the same change, metrics observability is now enforced by CI rather than process discipline. Documentation/tracking-only: no library code, behaviour, wire, or serialization change (#712).
- **R-140 - Auto-trained shared compression dictionary from sampled payloads (opt-in, default off).** Adds a runtime alternative to operator-supplied (pre-trained) Zstandard dictionaries: a new core provider samples a bounded reservoir of representative payloads and periodically trains a shared dictionary off the hot path, publishing it under a monotonically increasing dictionary id so the existing dictionary-aware compressor can compress against it. Ships **opt-in and dark** - `CompressionDictionaryTrainingOptions.Enabled` defaults to `false`, and a disabled provider is an allocation-free no-op that emits no telemetry and leaves the wire byte-identical. Every resource is bounded: the reservoir is capped by both sample count and total bytes with a per-sample cap and a configurable sampling rate; the trained dictionary size is capped; training cadence is rate-limited (`MinTrainingInterval`, `MinSamplesToTrain`) with at most one pass in flight; and only a bounded ring of recent dictionary versions is retained. Each successful pass builds the dictionary fully, then atomically rolls over to a new version (monotonic id plus an in-process FNV-1a content hash that dedupes byte-identical re-trains and never travels on the wire); recent prior versions stay resolvable so a frame compressed against a just-superseded version still decompresses, and a consumer lacking a requested id falls back safely through the existing decoder path (no data loss). Register with the new `IServiceCollection.AddLatticeAutoTrainingCompressionDictionary(...)` helper alongside `AddLatticeZstdDictionaryCompressor`. New public types in the `Orleans.Lattice` namespace: `CompressionDictionaryTrainingOptions` and `AutoTrainingCompressionDictionaryProvider`. Five new instruments on the `orleans.lattice` meter, all emitted only while enabled: `compress.dictionary.training_runs` (counter, tag `outcome`), the `compress.dictionary.active_version` and `compress.dictionary.reservoir_fill` observable gauges, and the `compress.dictionary.trained_bytes_in` / `compress.dictionary.trained_bytes_out` byte counters whose out/in ratio is the trained-versus-no-dictionary-baseline compression-ratio delta - with four matching panels on the Overview Grafana dashboard. **Honest scope:** auto-training produces a dictionary locally and does not distribute it to peers; as with operator-supplied dictionaries the trained bytes must be provisioned out-of-band to every peer that needs them (per-peer wire-level capability negotiation remains a documented follow-up). See [`docs/lattice/compression.md`](docs/lattice/compression.md) (#721).
- **R-135 - Content-hash dedup round trip (sender manifest / receiver pull-missing payload elision; opt-in, default off).** Builds on the default-off content-hash re-send-rate measurement to actually *elide* redundant payloads. When enabled, the per-(tree, peer) shipper advertises a per-entry content-hash manifest for the drained batch, the receiver replies with the subset of entries it is actually missing (does not already hold byte-identical content for), and the shipper ships only those payloads - dropping the rest from the wire. The identical-content-newer-HLC case is preserved: a manifest entry whose content the receiver already holds but whose `HybridLogicalClock` is newer (the idempotent re-set of an identical value) advances the receiver's per-origin high-water-mark via a metadata-only apply during the exchange, so the high-water-mark still advances even though the payload is never re-shipped. Opt in per tree with the new `LatticeReplicationOptions.ContentHashDedupElisionEnabled` (default `false`), which additionally requires the existing `ContentHashDedupEnabled` master switch (the options validator rejects enabling elision without it). Default-off is wire byte-identical to today, and the round trip is gated behind a lazily-learned, per-activation peer capability: the exchange seam defaults to a no-op that reports "not supported", so a peer or transport that has not implemented the pull-missing RPC permanently falls back to shipping the full batch verbatim - rolling-upgrade safe. Only value-carrying point-`Set` entries are ever manifested; range deletes, saga terminal marks, prepared atomic-batch entries, and zero-HLC entries always ship verbatim, preserving per-origin FIFO, causal-dependency gating, atomic-batch boundaries, and advance-strictly-on-ack cursor semantics. Elision runs on the strict-serial ship path only (a configured `ShipMaxInFlight > 1` pipelining window collapses to one while elision is enabled). Three new counters on the `orleans.lattice.replication` meter, tagged `tree` and `peer`: `ship.elided_payloads` (constant `ShipElidedPayloadsName`), `ship.elided_payload_bytes` (`By`, `ShipElidedPayloadBytesName`), and `ship.manifest_exchanges` (`ManifestExchangesName`), plus two new Grafana panels on the Replication dashboard. New public types in the `Orleans.Lattice.Replication` namespace: `ContentManifestEntry`, `ContentManifestRequest`, and `ContentManifestResponse`, plus a default-no-op `IReplicationDigestProbeTransport.ExchangeContentManifestAsync` method. **Honest scope:** the manifest engine (build + missing-set + identical-newer-HLC handling), the elision wiring on the shipper serial path, the capability gating, the options/metrics/dashboard surface, and in-process/loopback coverage are complete; wiring the gRPC binding to carry the pull-missing RPC and advance the receiver high-water-mark cross-cluster is a documented follow-up (the default no-op exchange keeps un-bound transports wire-identical to today). See [`docs/lattice.replication/transport.md`](docs/lattice.replication/transport.md) (#705).
- **R-139 - Pre-ship CRDT delta-merge coalescing (opt-in, default off).** The per-(tree, peer) shipper's pre-ship coalescing pass now handles recognised CRDT trees in addition to last-writer-wins trees, completing the CRDT half of pre-ship coalescing. When `LatticeReplicationOptions.PreShipCoalescingEnabled` is on (still **default off**, so wire output is byte-identical when off), a CRDT tree's same-key point-write deltas drained into one batch are folded into a single combined delta - a join over each primitive's semilattice (union for OR-Set adds / removes, pointwise-max for PN-Counter and version-vector components, dot-dominance merge for the multi-value register, grow-only union for the sequence CRDT) - re-encoded onto the kept (highest-HLC) entry, and the earlier same-key entries are elided. Because each combine and the receiver-side apply are both commutative, associative, and idempotent, a coalesced run converges to the **identical** state as shipping every delta individually; unlike the last-writer-wins path it never drops an intermediate delta's contribution. Coalescing stays within a single origin/causal run and never crosses an atomic-batch boundary: range deletes, saga terminal marks, prepared atomic-batch entries, and zero-HLC entries are never candidates. The generic OR-Map mode (whose value CRDT is type-erased on the shipper) and any CRDT entry carrying no typed delta fall back to shipping individually, which is loss-free. A new counter `orleans.lattice.replication.coalesce.deltas_merged` (`{delta}`, tagged `tree`/`peer`, constant `LatticeReplicationMetrics.CoalesceDeltasMergedName`) reports the source deltas folded into a combined delta; the existing `coalesce.entries_elided` / `coalesce.bytes_elided` counters still record the source entries dropped from the wire on the CRDT path. The on-wire entry shape is unchanged (fewer / merged entries of the existing format) - **no wire-version bump**. See [`docs/lattice.replication/deltas.md`](docs/lattice.replication/deltas.md) and [`docs/lattice.replication/replication.md`](docs/lattice.replication/replication.md) (#717).
- **R-134 - Version-adaptive wire-format down-stamping for rolling upgrades (opt-in, default off, default-on flip deferred).** When wire-version negotiation is enabled, the per-(tree, peer) shipper now threads the negotiated effective wire version onto the outbound framing header so a current-build sender can ship a frame a not-yet-upgraded receiver decodes **and** applies, closing the rolling-upgrade stall window for last-writer-wins trees. The new public `WireVersionDownEncoder` (in `Orleans.Lattice.Replication`) is the consumer of the negotiated target: its `MinimumDownEncodableWireVersion` constant, `EnsureDownEncodable(effectiveWireVersion, mode, compression)` precondition check, and `PrepareHeader(in EncodedBatchHeader, effectiveWireVersion)` header-stamper down-stamp the fixed framing header by one version. The mechanism is header-only and exact - no entry segment is re-serialised - because every prior framing version elided a per-entry field rather than adding one (version 4 elided `WalRecord.TreeId`, version 5 hoisted the merge mode into the header and `WalRecord.Mode` carries no wire tag), so the current build's entry segments are already a strict subset of what an older receiver expects; the receiver restores the elided fields from the framing context. A same-version peer stays a true verbatim no-op with zero re-encode cost. A negotiated down-stamp this build cannot produce for the batch's shape - a CRDT-mode tree (whose per-entry merge dispatch depends on the version-5 hoisted header mode an older receiver cannot read) or a compressed framing tail (whose compressor an older receiver is not guaranteed to carry) - fails fast with `NotSupportedException`, the same posture as a below-floor peer. Ships **dark**: `LatticeReplicationOptions.WireVersionNegotiationEnabled` still defaults to `false`, and the **default-on flip is deferred** - the down-stamp is exact only for last-writer-wins, uncompressed trees, and flipping the default safely for a heterogeneous fleet (including CRDT trees and both upgrade directions) needs further stall analysis tracked as follow-up work on the same issue. `UnknownPeerWireVersionFloor` keeps its current-version default so first batches before any ack are unchanged. See [`docs/lattice.replication/wire-format.md`](docs/lattice.replication/wire-format.md) (#703).

The core [`docs/lattice/projection-rebuild.md`](docs/lattice/projection-rebuild.md) digest opt-out section now cross-links the playbook so operators who disable projection-digest maintenance understand they forgo cross-cluster drift detection. Documentation-only: no library code, behaviour, wire, or serialization change (#519).

- **R-108 - Operator opt-in, rate cap, and circuit breaker for automatic anti-entropy remediation.** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. A new master gate `LatticeReplicationOptions.AutoRemediateOnDigestMismatch` (default `false`) governs **all** automatic remediation - both the targeted leaf re-replay repair stage and the GC'd-divergence bootstrap-snapshot fallback. While it is off, drift is still detected and probed exactly as before (the digest probe and the read-only Merkle walk are unaffected) but no automatic re-replay or bootstrap-fallback re-ship is attempted; it is an additional AND-gate in front of the existing per-feature flags (`MerkleWalkEnabled`, `LeafReReplayEnabled`, `BootstrapFallbackEnabled`), which still apply. When remediation is enabled, two guards bound it. First, a per-(tree, peer) rate cap limits remediation re-ship volume to a small fraction of the ordinary ship-batch budget: `RemediationTrafficBudgetFraction` (default `0.01`, i.e. 1% of `ShipBatchSize`, validated to the half-open interval `(0.0, 1.0]`) and `RemediationTrafficWindow` (default 1 minute, validated `> TimeSpan.Zero`) define a deterministic per-(tree, peer) accounting window; once a pair has spent its window budget, further passes are skipped until the window rolls over. Second, a per-(tree, peer) circuit breaker disables remediation after `RemediationFailureThreshold` (default `3`, validated `>= 1`) consecutive failures - a pass that threw or whose re-ship sink reported zero shipped despite candidates selected - and stays open for `RemediationCircuitResetInterval` (default 5 minutes, validated `> TimeSpan.Zero`) before half-opening for one trial pass; a successful pass closes the breaker and any success resets the consecutive-failure count. A new process-wide observable gauge `orleans.lattice.replication.digest_remediation.disabled` (constant `LatticeReplicationMetrics.DigestRemediationDisabledName`) reports value `1` for each currently-disabled `(tree, peer)` tagged `tree`, `peer`, and `reason` (`opt_out`, `budget_exhausted`, or `circuit_open`); a companion counter `orleans.lattice.replication.digest_remediation.skipped` (constant `LatticeReplicationMetrics.DigestRemediationSkippedName`) counts each skipped pass with the same reason tag. New public types: `RemediationGuard` and `RemediationDisabledReason` in the `Orleans.Lattice.Replication` namespace. See [`docs/lattice.replication/anti-entropy-remediation-guards.md`](docs/lattice.replication/anti-entropy-remediation-guards.md) (#516).
- **R-109 - Bootstrap-snapshot fallback for garbage-collected divergence (anti-entropy repair).** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. When [targeted leaf re-replay](docs/lattice.replication/anti-entropy-leaf-rereplay.md) localises a divergence but cannot reach it because the local write-ahead-log has been trimmed past the divergence point (the `leaf_rereplay.skipped{reason=wal_trimmed}` signal), an optional fallback re-derives the committed projection of **only** the divergent leaf range from the live tree (which is immune to WAL trimming) and re-ships those committed entries to the diverged peer through the **same** replication transport ordinary replication uses, so the repair travels the ordinary causal-stable apply path and the receiver dedupes by the verbatim source clock. Snapshot scope is bounded to the leaf ranges the Merkle walk localised, so the repair cost is proportional to the drift, not the whole tree. A new range-scoped `ISnapshotProvider.ExportAsync(treeName, ranges, asOfHlc, ct)` overload is the scoping seam: the default interface implementation filters the whole-tree export client-side by ordinal half-open `[StartKey, EndKey)` range (so existing providers need no change), and a storage-aware provider may override it to push the bound down. Enable it per tree with the new `LatticeReplicationOptions.BootstrapFallbackEnabled` (default `false`); bound the work per pass with `BootstrapFallbackMaxEntries` (default 4096, validated `>= 1`) and `BootstrapFallbackMaxBytes` (default 1 MB, validated `>= 1`). Three new counters on the `orleans.lattice.replication` meter: `bootstrap_fallback.triggered{tree,peer}` (a fallback began), `bootstrap_fallback.entries{tree,peer}` (committed entries re-shipped), and `bootstrap_fallback.skipped{tree,peer,reason}` (skipped without re-shipping, tagged `disabled`, `range_empty`, or `empty`); a `disabled` skip is the operator-only signal that a GC'd divergence was available for the fallback but the host has not opted in. **Honest scope:** the range-scoped export, the committed-projection selection, the cap logic, and the metrics are complete and unit-tested, and the re-ship goes through the live `IReplicationTransport` so it travels the ordinary receiver apply path; cross-cluster push still requires a real push transport (e.g. the gRPC binding), exactly as for leaf re-replay. The fallback re-ships **committed projection rows only** (live values of the divergent range) as last-writer-wins-style sets - prepared-saga snapshot rows are not re-shipped, and per-entry origin is stamped as the local cluster id on the wire, matching the existing whole-tree bootstrap convention; the default `LatticeSnapshotProvider` filters the whole-tree stream client-side rather than pushing the range bound into storage. New public types: `BootstrapFallbackOutcome` and `BootstrapFallbackSkipReason` in the `Orleans.Lattice.Replication` namespace, plus the range-scoped `ISnapshotProvider.ExportAsync` default-method overload and a public `LeafReReplayRange.Contains(string?)` range-membership method. See [`docs/lattice.replication/anti-entropy-bootstrap-fallback.md`](docs/lattice.replication/anti-entropy-bootstrap-fallback.md) (#517).
- **R-107 - Targeted leaf re-replay from WAL (anti-entropy repair stage).** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. When the read-only Merkle walk localises one or more diverging leaves, an optional repair stage re-ships the relevant retained write-ahead-log key ranges to the diverged peer through the **same** TX-aware causal-stable apply pipeline ordinary replication uses, so the repair respects atomic-batch boundaries and the receiver dedupes re-shipped entries by their verbatim source clock (re-sending is idempotent). Producer-side selection uses each localised leaf's `[StartKey, EndKey)` covering range plus the diverged peer's high-water-mark cursor to bound what gets re-sent. Two new counters: `orleans.lattice.replication.leaf_rereplay.entries{tree,peer}` (WAL entries re-shipped) and `orleans.lattice.replication.leaf_rereplay.skipped{tree,peer,reason}` (a pass skipped without re-shipping, tagged `disabled`, `range_empty`, or `wal_trimmed`). A `wal_trimmed` skip is the **operator-only alert**: the local WAL has been garbage-collected past the divergence point so the repair cannot proceed and a bootstrap-snapshot remediation (issue #517) is the follow-up; the feature does **not** attempt repair in that case. Enable it per tree with the new `LatticeReplicationOptions.LeafReReplayEnabled` (default `false`); bound the work per pass with `LeafReReplayMaxEntries` (default 4096, validated `>= 1`) and `LeafReReplayMaxBytes` (default 1 MB, validated `>= 1`), both applied as soft caps that never split an atomic batch. The repair runs only when the digest probe is enabled, a mismatch is found, `MerkleWalkEnabled` is on, the walk localises at least one leaf, and this flag is on. **Honest scope:** the producer-side range selection, WAL read, cap/atomic-batch logic, and metrics are complete and unit-tested, and the re-ship goes through the live `IReplicationTransport` so it travels the ordinary causal-stable apply path at the receiver. The peer high-water-mark cursor is read through a new default-no-op `IReplicationDigestProbeTransport.GetPeerHighWaterMarkAsync` method that returns `HybridLogicalClock.Zero` (the conservative answer that re-ships every in-range retained entry and relies on receiver dedup) until a host supplies a transport that can read the peer's applied watermark; cross-cluster push still requires a real push transport (e.g. the gRPC binding). New public types: `LeafReReplayRange`, `LeafReReplayOutcome`, and `LeafReReplaySkipReason` in the `Orleans.Lattice.Replication` namespace, plus the `IReplicationDigestProbeTransport.GetPeerHighWaterMarkAsync` default method and a new `IReadOnlyList<LeafReReplayRange> MerkleWalkOutcome.LocalisedRanges` member. See [`docs/lattice.replication/anti-entropy-leaf-rereplay.md`](docs/lattice.replication/anti-entropy-leaf-rereplay.md) (#515).
- **R-132 - Shared/trained Zstd dictionary for batch compression (opt-in, default off).** Replication framing can now compress batch tails with a shared Zstandard dictionary, capturing the cross-batch redundancy (repeated key prefixes, identical value schemas, recurring CRDT delta shapes) that defeats per-batch dictionary-less compression on small batches. A new core compression tag, `LatticeCompression.ZstdDictionary` (`0x02`), carries a stable 4-byte dictionary id in the framed tail so the receiver selects the matching dictionary; tags `None` (`0x00`) and `Zstd` (`0x01`) are byte-identical to before and the framing wire version is unchanged (the dictionary id rides the variable tail, not the fixed 32-byte header). Opt in per deployment by setting `LatticeReplicationOptions.FramingCompression = LatticeCompression.ZstdDictionary` together with a non-zero `LatticeReplicationOptions.FramingCompressionDictionaryId`; the default build never requests a dictionary, so its wire bytes are identical to a dictionary-less build. The reserved dictionary id `0` means "no dictionary" and a shipper configured for the dictionary tag with id `0` gracefully degrades to plain `Zstd`. Operator-supplied (pre-trained) dictionaries are the primary path: register the dictionary bytes by stable id with the new `AddLatticeCompressionDictionaries(...)` (or a custom `ILatticeCompressionDictionaryProvider`) and register the dictionary-aware compressor with `AddLatticeZstdDictionaryCompressor(...)`. A silo that cannot resolve the requested dictionary locally degrades the frame to plain `Zstd` rather than emitting an unreadable frame; a receiver that cannot resolve the dictionary id (or the tag) surfaces `NotSupportedException` from the framing decoder and routes through the existing transient-backoff path, rather than silently mis-decoding. The before/after ratio is observable through two new counters tagged by `tree`: `orleans.lattice.replication.compress.dictionary.bytes_in` (`By`, new constant `LatticeReplicationMetrics.CompressDictionaryBytesInName`) and `orleans.lattice.replication.compress.dictionary.bytes_out` (`By`, new constant `LatticeReplicationMetrics.CompressDictionaryBytesOutName`). New public types in `Orleans.Lattice`: `ILatticeCompressionDictionaryProvider`, `OperatorSuppliedCompressionDictionaryProvider`, `ILatticeDictionaryCompressor`, and `ZstdDictionaryLatticeCompressor`. **Honest scope:** operator-supplied (pre-trained) dictionaries are fully shipped; auto-training a dictionary from sampled WAL payloads, and negotiating shared-dictionary capability per peer over the wire-version channel, are documented follow-ups. See [`docs/lattice/compression.md`](docs/lattice/compression.md) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md) (#696).
- **R-106 - Anti-entropy Merkle-walk drift localisation (localise stage).** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. When the digest probe reports a shard-level mismatch, an optional read-only pass walks the shard's internal-node tree top-down by cluster-stable separator-key range, narrowing the divergence toward a single leaf or a small set of leaves and emitting two counters: `orleans.lattice.replication.merkle_walk.localised{tree,depth}` (diverging leaves localised, tagged with the depth reached) and `orleans.lattice.replication.merkle_walk.aborted{reason}` (a capped or non-comparable walk, tagged `depth_cap`, `byte_budget`, `remote_unavailable`, or `version_skew`). Enable it per tree with the new `LatticeReplicationOptions.MerkleWalkEnabled` (default `false`); cap the work per probe with `MerkleWalkMaxDepth` (default 16, validated `>= 1`) and `MerkleWalkMaxBytes` (default 1 MB, validated `>= 1`). The walk runs only when the digest probe is enabled, a mismatch is found, and this flag is on. **Honest scope:** the local descent engine, the key-range probe wire shape, the depth/byte caps, and the metrics are complete and read-only. Obtaining a remote peer's subtree digest for an arbitrary key-range requires a range-fold the current shipping surface does not expose, so the default transport answers every key-range probe as unavailable and the walk aborts `remote_unavailable` until a host supplies a range-answering transport; the cross-cluster remote range-fold (new core surface plus a gRPC binding) is a documented follow-up. New public types: `MerkleWalkProbeRequest`, `MerkleWalkProbeResponse`, `MerkleWalkOutcome`, and `MerkleWalkAbortReason` in the `Orleans.Lattice.Replication` namespace, plus a default no-op `IReplicationDigestProbeTransport.ProbeMerkleWalkAsync` method. See [`docs/lattice.replication/anti-entropy-merkle-walk.md`](docs/lattice.replication/anti-entropy-merkle-walk.md) (#514).

- **R-130 - Pre-ship WAL entry coalescing (opt-in, default off, last-writer-wins trees).** The outbound replication shipper can now collapse redundant per-key versions out of a freshly-drained batch before they cross the cross-cluster link: a hot key rewritten several times within a single ship window no longer ships every intermediate version a last-writer-wins receiver would overwrite anyway. Opt in per tree with the new `LatticeReplicationOptions.PreShipCoalescingEnabled` (default `false`); with the flag off the drain/ship path is byte-identical to before. This is distinct from the content-hash re-send-rate measurement (#461), which only ever measures and never alters the bytes shipped - coalescing actually drops entries from the wire. The pass is scoped, conservatively, to trees whose declared `LatticeMergeMode` is `LwwRegister`: for those the receiver applies each entry last-writer-wins on the value bytes ordered by `(HybridLogicalClock, OriginClusterId)`, so within one drained batch only the highest-HLC version per key survives convergence and the earlier ones are invisible after apply. Because the shipper only ever drains its own cluster's authored writes, every coalescing candidate shares one origin and the drain buffer is already HLC-ascending, so the last occurrence of a key is the highest-HLC one. Every CRDT mode (`OrSet`, `PnCounter`, `VersionVector`, `MvRegister`, `OrMap`, `Sequence`) is left verbatim and never coalesced - the receiver applies each of those by folding the per-entry typed delta into the loaded state, so dropping an intermediate version would lose its contribution rather than merely hide it. Only plain point `Set` / `Delete` writes are eligible: range deletes, saga terminal marks, prepared atomic-batch (saga) entries, tombstone-reap envelopes, and entries carrying `HybridLogicalClock.Zero` are never elided, so atomic-batch boundaries, causal dependencies, per-origin FIFO, and no-cross-origin-reorder all hold unchanged. Every drained entry's per-partition sequence is folded into the resume bookkeeping before the coalescing pass runs, so the cursor still advances past every elided entry and nothing is re-shipped or stranded. The coalesced output is a strict subset of the verbatim batch, so an unmodified receiver decodes and applies it to the identical converged state - purely additive, no wire-format, serialization, `[Id]`, or `[Alias]` change. Two new counters measure the win, both tagged by `tree` and `peer`: `orleans.lattice.replication.coalesce.entries_elided` (`{entry}`, new constant `LatticeReplicationMetrics.CoalesceEntriesElidedName`) and `orleans.lattice.replication.coalesce.bytes_elided` (`By`, new constant `LatticeReplicationMetrics.CoalesceBytesElidedName`). See [`docs/lattice.replication/replication-drivers.md`](docs/lattice.replication/replication-drivers.md#pre-ship-coalescing) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md#pre-ship-coalescing-coalesceentries_elided--coalescebytes_elided) (#694).
- **R-044 - Content-hash payload re-send-rate measurement (opt-in, default off).** The outbound replication shipper can now measure how often it ships a `Set` whose value bytes are byte-identical to the value most recently shipped for the same key - the idempotent-re-write rate that decides whether a sender-manifest / receiver-pull-missing dedup round trip would pay for itself. Opt in with the new `LatticeReplicationOptions.ContentHashDedupEnabled` (default `false`); when off the shipper does no extra work and the wire output is byte-identical to before. When on, the shipper maintains a per-activation, per-key bounded LRU of the last-shipped content hash (FNV-1a 64-bit over the op, key, range end-key, and value bytes), sized by the new `LatticeReplicationOptions.ContentHashDedupCacheSize` (default `4096`, validated `>= 64`), and emits two new observability-only counters as redundant entries drain onto the wire: `orleans.lattice.replication.ship.redundant_payloads` (`{entry}`, new constant `LatticeReplicationMetrics.ShipRedundantPayloadsName`) and `orleans.lattice.replication.ship.redundant_payload_bytes` (`By`, new constant `LatticeReplicationMetrics.ShipRedundantPayloadBytesName`), both tagged by `tree` and `peer`. The measurement never elides, reorders, or alters the bytes shipped: actually skipping a byte-identical re-set carrying a newer HLC would strand the receiver's per-origin high-water mark and change LWW/HLC convergence, so the receiver must consent through a manifest/pull exchange. That exchange requires an additive-but-new request/response shape on the replication transport and is deliberately deferred until wire-version capability negotiation lands, so this change ships the measurement (exactly the signal the feature needs to justify the round trip) with no wire-format, serialization, `[Id]`, or `[Alias]` change. See [`docs/lattice.replication/replication-drivers.md`](docs/lattice.replication/replication-drivers.md#content-hash-dedup-measurement) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md) (#461).
- **R-133 - Sender-side adaptive batch sizing from ack latency / throughput.** The outbound replication shipper can now self-tune its effective per-tick batch size per `(tree, peer)` using an additive-increase / multiplicative-decrease (AIMD) controller driven by measured ack latency and error rate, instead of always shipping at the static `LatticeReplicationOptions.ShipBatchSize`. Opt in with the new `LatticeReplicationOptions.AdaptiveBatchSizingEnabled` flag, which **defaults to `false`**: with the flag off the shipper sizes every batch exactly as it does today (at `ShipBatchSize`, modulated only downward by an active receiver flow-control hint), so steady-state behaviour is byte-identical to the static path until an operator opts in. When enabled, the controller grows the effective size additively toward `ShipBatchSize` while the sliding-window mean ack latency stays at or below `AdaptiveBatchLatencyThreshold`, and backs it off multiplicatively (by `AdaptiveBatchDecreaseFactor`) when ack latency rises above the threshold or a send fails - reacting to back-pressure before the receiver has to raise its WAL-saturation hint. The adaptation only ever operates in the headroom beneath the receiver hint: the effective per-tick cap is `min(adaptive size, receiver-suggested size, ShipBatchSize)`, floored at `1`, so the receiver flow-control hint (`ReplicationAck.SuggestedBatchSize`) remains the hard upper bound and always wins. The adaptation never reorders work, never crosses a batch boundary, and never affects per-origin FIFO or advance-strictly-on-ack cursor semantics; it only shrinks or grows the per-tick entry cap, and composes with `ShipMaxInFlight` pipelining. Four tuning knobs accompany the flag, each validated and XML-documented: `AdaptiveBatchIncrement` (additive step, default `8`), `AdaptiveBatchDecreaseFactor` (multiplicative factor in the open interval `(0,1)`, default `0.5`), `AdaptiveBatchLatencyThreshold` (default `50 ms`), and `AdaptiveBatchWindowLength` (sliding-window length, default `16`). Controller state is in-memory and activation-scoped, so a grain reactivation resets the effective size to `ShipBatchSize` and re-learns from the live link. Two new observability histograms emit once per acknowledged batch regardless of the flag (useful even with static sizing), tagged by tree and peer: `orleans.lattice.replication.ship.effective_batch_size` (unit `{entry}`, new public constant `LatticeReplicationMetrics.ShipEffectiveBatchSizeName`) and `orleans.lattice.replication.ship.ack_latency` (unit `ms`, new public constant `LatticeReplicationMetrics.ShipAckLatencyName`). Purely additive: no wire or serialization change, no new public type, and no behaviour change with the flag at its default. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#sender-side-adaptive-batch-sizing) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md#sender-side-adaptive-batch-sizing-ship-effective_batch_size--ship-ack_latency) (#697).
- **R-045 - Coalesced per-peer cursor checkpointing now has a time bound.** The replication shipper already amortised its durable per-peer/per-partition resume-cursor write across `LatticeReplicationOptions.ShipCursorWriteInterval` (default 16) successful acks instead of persisting on every batch; it now also flushes the pending cursor whenever `LatticeReplicationOptions.ShipCursorWriteMaxDelay` (new, default 2 s) of wall-clock time has elapsed since the first un-flushed advance - whichever threshold is reached first. The time dimension bounds how stale the durable cursor (and therefore the WAL GC trim frontier) can become on a low-throughput or bursty stream that ships fewer than `ShipCursorWriteInterval` batches and then quiesces, where a pure batch-count rule would otherwise leave the last few advances un-flushed indefinitely. The elapsed check runs both when a new advance is booked and on idle pump ticks (the empty-drain path), so a stream that goes completely silent still checkpoints within the bound; a graceful deactivation continues to flush any pending advance. Crash safety is unchanged: receiver-side apply is HLC-monotonic and dedupes on `(originClusterId, originHlc)`, so any entries re-shipped inside the window are no-op'd at the receiver and no data is lost - lowering the new delay only ever makes the durable cursor fresher. Set `ShipCursorWriteMaxDelay` to `Timeout.InfiniteTimeSpan` to disable the time dimension and coalesce purely by batch count. The new option is validated (`> TimeSpan.Zero` or `Timeout.InfiniteTimeSpan`) by `LatticeReplicationOptionsValidator`. See [`docs/lattice.replication/replication-drivers.md`](docs/lattice.replication/replication-drivers.md#deferred-cursor-persistence) (#462).
- **R-131 - Parallel receiver apply across independent trees.** The replication receiver can now apply independent runs of an inbound batch concurrently instead of strictly serialising every `(treeId, originClusterId)` run, cutting apply latency and the resulting `apply.lag` (which now also drives receiver back-pressure) under multi-tree load. Concurrency is bounded by the new `LatticeReplicationOptions.ApplyMaxParallelRuns` option, and **defaults to `1` (fully-sequential apply, identical to the previous behaviour)** - raise it conservatively, per workload, to let distinct trees apply in parallel. Independence is defined at the tree granularity: runs targeting distinct trees overlap up to the configured cap, while runs that share a tree stay strictly sequential in write-ahead-log order, so every within-run ordering invariant holds unchanged regardless of the configured degree of parallelism - per-origin FIFO, the causal dependency gate and its bounded buffer, per-origin high-water-mark monotonicity, and atomic-batch (saga) apply boundaries. The effective degree of parallelism per batch (the configured value clamped to the number of distinct trees present) is surfaced on the new untagged `LatticeReplicationMetrics.ApplyParallelRuns` histogram (`orleans.lattice.replication.apply.parallel_runs`, unit `{run}`). Purely additive: no wire or serialization change, and a single-tree batch always takes the allocation-free sequential walk. See [`docs/lattice.replication/replication-apply.md`](docs/lattice.replication/replication-apply.md#parallel-apply-across-independent-runs) and [`docs/lattice.replication/observability.md`](docs/lattice.replication/observability.md#parallel-apply-degree-applyparallel_runs) (#695).
- **R-127 - Receiver WAL-saturation back-pressure feeds sender backoff.** The replication receiver can now translate the core library's WAL saturation signal into the sender backoff hints it already understands. This behaviour is now **on by default**: `AddLatticeReplication` registers `WalSaturationReceiverFlowControlPolicy` (an `IReceiverFlowControlPolicy`) via `TryAddSingleton`. Hosts opt out by pre-registering `NoOpReceiverFlowControlPolicy` before `AddLatticeReplication`, and tune the mapping with the `ISiloBuilder.AddWalSaturationReceiverFlowControl(...)` extension. On every successful push the policy reads `IWalSaturationSignal.GetCurrentState(treeName)` for the just-applied tree and maps the regime onto the `ReceiverFlowControlHint` stamped on the `ReplicationAck`: `Healthy` yields `ReceiverFlowControlHint.None` (sender resumes at its configured `ShipBatchSize`), `Throttled` yields a reduced batch (a configurable fraction of `ShipBatchSize`) plus a short pause, and `Saturated` yields a minimal drip-feed batch plus a longer pause - so the sender stops piling work onto a writer-side admission gate that is already at its cap and would otherwise fault the apply with `LatticeSaturatedException`. The mapping is tunable per tree through the new public `WalSaturationReceiverFlowControlOptions` (`ThrottledBatchRatio`, `ThrottledPauseMs`, `SaturatedBatchSize`, `SaturatedPauseMs`), with all suggested sizes clamped to `[1, ShipBatchSize]`. The hint rides the existing additive `ReplicationAck.SuggestedBatchSize` / `PauseForMs` slots, so there is no wire or serialization change, and the policy degrades to `ReceiverFlowControlHint.None` when no `IWalSaturationSignal` is registered. New public types: `WalSaturationReceiverFlowControlPolicy`, `WalSaturationReceiverFlowControlOptions`, and the `AddWalSaturationReceiverFlowControl` extension. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#built-in-wal-saturation-policy) (#690).
- **R-128 - Sender-side multi-batch ship pipelining.** The outbound replication shipper can now keep more than one shipped-but-unacknowledged batch in flight per `(tree, peer)` so transport round-trip latency overlaps with draining the next batch, lifting throughput on high-latency links. Opt in by raising the existing `LatticeReplicationOptions.ShipMaxInFlight` above its default of `1`; the default stays strictly serial (ship one batch, await its ack, advance the cursor, ship the next), so behaviour is unchanged until an operator widens the window. The pipeline preserves the per-origin FIFO invariant and advance-strictly-on-ack cursor semantics: acks are consumed in strict FIFO order and the durable per-peer cursor advances past a batch only once that batch and every lower-HLC batch before it have been acknowledged, so a transport failure or ack rejection anywhere in the window leaves the cursor at the last fully-acked frontier with no hole (the next tick re-ships from the durable cursor and the receiver dedupes the overlap). Receiver flow-control composes: when the receiver stamps a `ReplicationAck.SuggestedBatchSize` hint the window collapses back to `1` until the hint clears, throttling batch size and pipeline depth together. The live window depth is surfaced on a new outbound-only observable gauge, `orleans.lattice.replication.peer.ship_in_flight` (new public constant `LatticeReplicationMetrics.ShipInFlightName`), recorded through the new `ReplicationPeerStats.RecordInFlight(tree, peer, depth)` method and readable on the new `ReplicationPeerSnapshot.InFlight` snapshot field. A window greater than `1` issues concurrent `IReplicationTransport.SendAsync` calls for the same pair, so a transport used with pipelining must tolerate concurrent invocation against one pair; The default window of `1` preserves strictly-serial-per-pair behaviour. See [`docs/lattice.replication/receiver-flow-control.md`](docs/lattice.replication/receiver-flow-control.md#sender-side-pipelining) (#692).
- **R-129 - Wire-version capability advertisement, negotiation telemetry, and floor-guard.** Lays the groundwork for safe rolling upgrades across framing wire versions without yet changing any on-the-wire payload. The receiver now advertises the maximum framing wire version it can decode on a new additive `ReplicationAck.SupportedWireVersion` slot, and an opted-in sender feeds that into the new public `WireVersionNegotiation.Negotiate(localCurrent, minimumSupported, unknownPeerFloor, peerAdvertised)` helper (returning a `WireVersionNegotiationResult`) to compute the negotiated target version - `min(localCurrent, peerAdvertised)` once the peer's capability is known, or a conservative `UnknownPeerWireVersionFloor` until it advertises one. A peer that advertises a version below the configured `MinimumSupportedWireVersion` surfaces the canonical fail-fast hard error (the genuinely-unsupported case). Two new observable gauges - `orleans.lattice.replication.wire_version.negotiated{tree,peer}` and `orleans.lattice.replication.wire_version.downgrade_active{tree,peer}`, backed by the new public `WireVersionNegotiationState` singleton - let operators see when a fleet is running mixed wire versions. **Ships dark / opt-in:** `LatticeReplicationOptions.WireVersionNegotiationEnabled` defaults to `false`. This entry delivers the capability advertisement, negotiation telemetry, and minimum-floor guard only; it does **not** re-encode outbound batches at the negotiated target - the steady-state ship path reuses the bytes the WAL wrote at append time, so an opted-in sender still frames every batch at its current wire version. Actually re-encoding at the negotiated older version (the capability a newer sender needs to ship to a not-yet-upgraded receiver, plus a safe on-by-default posture) is tracked as a follow-up issue (#703). `MinimumSupportedWireVersion` (default `1`) and `UnknownPeerWireVersionFloor` (default current version) are validated by `LatticeReplicationOptionsValidator`. The `SupportedWireVersion` slot is strictly additive on the wire (pre-negotiation receivers omit it and senders ignore it). New public types: `WireVersionNegotiation`, `WireVersionNegotiationResult`, `WireVersionNegotiationState`, `WireVersionNegotiationSnapshot`. See [`docs/lattice.replication/wire-format.md`](docs/lattice.replication/wire-format.md#wire-version-capability-negotiation) (#693).
- **R-105 - Peer digest probe RPC and scheduler (anti-entropy detection).** Ships **opt-in and dark** - default off, no behaviour change for an un-opted host. A new per-tree, low-frequency, jittered scheduler reads each shard's local leaf-projection digest via `ILattice.GetLeafProjectionDigestAsync(shardIndex)` and compares it against every peer's digest fetched over a new read-only probe RPC carried on the existing replication push transport, emitting two counters so a dashboard can chart cross-cluster divergence: `orleans.lattice.replication.digest_probe.compared{tree,shard,peer,outcome}` (every comparison) and `orleans.lattice.replication.digest_probe.mismatch{tree,shard,peer}` (only when versions match and digests differ). The probe is strictly read-only - it never mutates data or cursors. Enable it per tree with the new `LatticeReplicationOptions.DigestProbeEnabled` (default `false`); tune the cadence with `DigestProbeInterval` (default 5 minutes, validated `> TimeSpan.Zero`) and `DigestProbeJitter` (default `0.2`, validated `[0, 1]`). It respects the core opt-out: trees with `MaintainProjectionDigest = false` (including the system-tree default) are skipped, and a tree whose registry latch has permanently disabled digesting is skipped for the activation lifetime. When the local and remote digest versions differ, the comparison records `outcome=version_skew` and does **not** raise a mismatch. New public types: `IReplicationDigestProbeTransport`, `DigestProbeRequest`, `DigestProbeResponse`, `DigestProbeOutcome`, and `DigestProbeComparer` in the `Orleans.Lattice.Replication` namespace. The gRPC binding wires the probe RPC over the same channel cache as live push. See [`docs/lattice.replication/anti-entropy-digest-probe.md`](docs/lattice.replication/anti-entropy-digest-probe.md) (#513).

## [7.0.0] - 2026-06-11

Major release across the package family. Two source-affecting changes set the major digit, both wire-compatible and source-breaking only: Azure Table WAL row-payload compression is now **on by default** (`AzureTableWalStorageOptions.Compression` defaults to `Zstd`), and the twelve public CRDT primitive types moved from the `Orleans.Lattice.Primitives` namespace into the root `Orleans.Lattice` namespace (with `TxStatus` / `TerminalTallyResult` demoted to `internal`). Headline additions: cross-tree (multi-tree) all-or-nothing atomic writes with cross-cluster atomic visibility (F-098); RGA sequence replication for collaborative ordered lists / text via the new `LatticeMergeMode.Sequence` (R-036); WAL compression-savings metrics on the Azure Table provider (F-100); a cluster-internal typed FIFO queue primitive `ILatticeQueue<T>` (F-042); and a WAL phase-one idempotency fix that resolves lost-response Azure Table SDK retries as durable successes instead of failing the batch. See the per-section entries below.

### Added

- **R-036 - RGA sequence replication (delta + dispatch).** Trees configured for the new `LatticeMergeMode.Sequence` mode now replicate collaborative ordered lists / text (an `Orleans.Lattice.Rga` authored through `ILattice.Sequence<T>(key)`) across clusters with full active-active convergence: every site observes an **identical ordered traversal** after concurrent insert / delete bursts, not merely the same set of surviving elements. The producer side captures the dot-explicit structural intent of each edit - `InsertAtAsync` / `InsertAfterAsync` resolve to an inserted node carrying its `(dot, parentDot, value)` and `RemoveAtAsync` / `RemoveAsync` resolve to a tombstoned dot - into a new public `RgaDelta` (with `RgaDeltaNode` inserts and tombstone dots), stamped onto `WalRecord.Delta` and shipped delta-only; the receiver folds it via the new `Rga.MergeDelta(RgaDelta)` operation, which is commutative, associative, and idempotent. `Sequence` is a global closed CRDT shape (`CrdtShape.ForRga`), so no per-tree shape registration is required (unlike `OrMap`). New public types: the `LatticeMergeMode.Sequence` enum member, `RgaDelta` (alias `ol.rgd`), and `RgaDeltaNode` (alias `ol.rgi`). The `RgaAccessor<T>` mutation methods keep their existing signatures but now commit through the typed-delta WAL seam (CAS-free producer-side apply, matching `MvRegisterAccessor` / `OrMapAccessor`). **Back-pressure note:** `Sequence` replicates at operation granularity, so a high-frequency editor against a single sequence key generates one WAL entry per keystroke - apply a producer-side debounce / coalescing policy, or use a coarser-grained LWW / whole-document write for cold sequences. See [`docs/lattice.replication/replication-modes.md`](docs/lattice.replication/replication-modes.md#sequence-mode-back-pressure-hazard) and [`docs/lattice.replication/deltas.md`](docs/lattice.replication/deltas.md) (#456).
- **F-098 - Cross-tree (multi-tree) atomic writes.** New `IGrainFactory.SetManyAtomicAsync(IReadOnlyList<LatticeTreeBatch>, operationId, ct)` extension and a `IGrainFactory.BeginAtomicWrite(operationId)` fluent builder (`LatticeAtomicWriteBuilder`) commit a batch spanning two or more distinct `ILattice` trees all-or-nothing, with the same atomic-visibility guarantee the single-tree `SetManyAtomicAsync` saga gives within a tree - readers on the local cluster and on every replicating cluster observe either every targeted key across every participating tree or none of them, never a partial cross-tree commit. Implemented as a two-level saga: an internal coordinator grain keyed by the caller-supplied `operationId` is the single global decision authority, each participating tree runs the existing per-tree saga in a new prepare-and-pause mode, and each tree's `ITxRegistryGrain` delegates its prepared txid's status resolution to the coordinator until the single global decision lands. New public types `LatticeTreeBatch` (per-tree slice; deliberately not `[Immutable]` so Orleans deep-copies it across the grain-proxy boundary) and the `CrossTreeAtomicWriteOutcome` enum (`Committed` / `PreconditionFailed`). A stable `operationId` is required (no auto-generated overload) and must not contain `/`. Cross-cluster atomic visibility is preserved by a receiver-side barrier: because each participating tree's terminals replicate on their own per-tree WAL feed, the receiver routes cross-tree terminals (stamped with `WalRecord.CrossTreeOperationId` / `CrossTreeParticipants`) through an internal receiver coordinator grain (`ILatticeCrossTreeReceiverGrain`, keyed by `(originClusterId, operationId)`) that holds every participating tree invisible until a terminal has arrived for each tree it expects, then flips them together. The receiver's wait set is scoped to the trees it actually replicates (`LatticeReplicationOptions.ReplicatedTrees`), so a batch spanning a mix of replicated and non-replicated trees stays valid - the barrier completes on the present subset. Purely additive: no change to `SetManyAtomicAsync` or any existing signature, and all new persistent-state slots are forward- and backward-compatible (#671).
- **F-100 - WAL compression-savings metrics on the Azure Table provider.** Each append batch a compressing WAL provider commits now emits per-tree counters on the `orleans.lattice` meter so a dashboard can chart the realised compression savings: `orleans.lattice.storage.wal.uncompressed_bytes` (pre-compression encoded payload bytes) and `orleans.lattice.storage.wal.stored_bytes` (post-compression stored bytes), both in `By` and tagged `tree`, plus `orleans.lattice.storage.wal.compression_skipped` (`{row}`, tagged `tree` and `reason`) attributing every verbatim row to `below_threshold`, `inflation_guard`, or `disabled`. The savings ratio is `1 - stored_bytes / uncompressed_bytes`; the skip-reason breakdown distinguishes a threshold that is set too high (lower `CompressionMinPayloadBytes`) from genuinely incompressible payloads (lowering it would only burn CPU). Exposed as new public constants and `Counter<long>` fields on `LatticeMetrics` (`StorageWalUncompressedBytes(Name)`, `StorageWalStoredBytes(Name)`, `StorageWalCompressionSkipped(Name)`) plus the `ReasonBelowThreshold` / `ReasonInflationGuard` / `ReasonCompressionDisabled` tag constants. Purely additive; emitted once per batch after its phase-1 rows land, so a failed append records nothing. See [`docs/lattice/compression.md`](docs/lattice/compression.md#observability-compression-savings-metrics) (#676).
- **F-075 - Per-row WAL payload compression on the Azure Table provider.** Each WAL entry row's `Payload` column can now be transparently compressed before it is persisted, shrinking the retained on-disk footprint of large mutations. Compression is opt-in per tree via two new `AzureTableWalStorageOptions` knobs: `Compression` (`LatticeCompression`, default `None`) selects the algorithm tag applied to each row, and `CompressionMinPayloadBytes` (`int`, default `256`, validated non-negative) is the encoded-payload threshold below which a row is stored uncompressed even when compression is enabled (`0` compresses every row). The `256` default was chosen empirically for JSON values: an in-process sweep of realistic JSON through the real encode + Zstd-3 path showed compressed payloads never inflate at any size and that the reduction crosses ~25% near 256 encoded bytes, so a higher floor (the `512` the replication framing-tail threshold uses) would leave a band of 25-48%-compressible rows stored verbatim. A compressed row stores `[4-byte little-endian uncompressed length][compressed bytes]` in `Payload` and carries the algorithm tag in a new `Compression` column on `AzureTableWalEntity` (stored as an `int` because Azure Table Storage has no single-byte EDM property type). Reads key on the **row's stored tag, not the reader's option**, so a reader configured with `Compression = None` still inflates compressed rows as long as the matching `ILatticeCompressor` is registered; rows written before the column existed decode the absent property to `0` (`None`) and read back verbatim, so the change is backwards-compatible with no migration. Both encode paths compress (`AppendBatchAsync` and the shipper's pre-encoded `AppendEncodedBatchAsync` fast path) and both read paths inflate (`ReadAsync`, `ReadEncodedAsync`), and the row's recorded `PayloadBytes` now reflects the actually-stored (possibly compressed) size. `AddAzureTableWalStorage` registers a `ZstdLatticeCompressor` fallback (at `LatticeAzureTableServiceCollectionExtensions.DefaultCompressionLevel`, currently `3`) via `TryAddEnumerable` so enabling `Compression = LatticeCompression.Zstd` works with no extra wiring; because registration is additive, a host that has already registered its own Zstd compressor (e.g. for replication) wins the level. The provider gains a compression-aware constructor overload `(IOptions, Serializer<WalRecord>, IWalSaturationSignal?, IEnumerable<ILatticeCompressor>?)` that builds a per-tag dispatch dictionary and fails fast if compression is enabled with no matching compressor registered. See [`docs/lattice/compression.md`](docs/lattice/compression.md#azure-table-wal-row-payload-compression) (#395).
- **F-042 - Cluster-internal FIFO queue primitive `ILatticeQueue<T>`.** A new public typed, single-cluster FIFO queue resolved via `IGrainFactory.GetLatticeQueue<T>(name, serializer?)`, surfacing `EnqueueAsync` (returns a monotonic `long` id), `TryDequeueAsync`, `PeekAsync`, `CountAsync`, and an ascending-id `ListAsync` snapshot, with `LatticeQueueEntry<T>` as the read shape. Each logical queue is one coordinator grain over a reserved `_lattice_queue_{name}` system tree (`LatticeConstants.QueueTreePrefix`, subsumed by the already-reserved `_lattice_` prefix, so no new user-facing tree-name restriction); head/tail/count are served from an in-memory cache, a head-cursor row lets cold start and steady-state dequeue skip already-dequeued ids, and entry ids are recomputed as `max(stored) + 1` on activation. A new optional `LatticeOptions.QueueCapacity` (`null` = unbounded; validated `>= 1` when set) caps a queue with FIFO eviction. Values round-trip through an injectable `ILatticeSerializer<T>` (default `JsonLatticeSerializer<T>.Default`) client-side, so `T` need not be Orleans-serializable. Strictly cluster-internal: not CRDT-replicated and never ships a `LatticeMergeMode`. See [`docs/lattice/queues.md`](docs/lattice/queues.md) (#362).

### Changed

- **Internal-node digest upward-publish reuses a single per-activation deadline timer instead of allocating one per publish.** `BPlusInternalGrain.PublishUpwardAsync` bounded each cross-grain digest publish with a freshly constructed `CancellationTokenSource(timeout)`, which arms a one-shot timer on every publish, at every internal level, on every mutation - the dominant allocation of the bulk-write digest-propagation path (profiled at ~40.7% / ~205 MB of the bulk-write profile). Because upward publishes only run while the activation holds its non-reentrant `_splitGate`, at most one publish is ever in flight per activation, so the grain now arms and recycles a single reusable `CancellationTokenSource` per activation (`CancelAfter` to arm; `TryReset()` to disarm and recycle after each non-fired publish; dropped and re-created only on the rare timeout path). The timeout contract is unchanged in every observable way - the `Timeout.InfiniteTimeSpan` unbounded fast path, the `TimeoutException`-on-park gate-release behaviour, the `orleans.lattice...DigestPublishTimeouts` metric, and the staleness-tolerant re-drive on the next mutation all behave exactly as before. Measured on the microbench tier (BDN dry, `MemoryDiagnoser`, isolated A/B): `microbench_bulk_load_deeper_tree_alloc_b` 145,912 -> 142,464 B/op (-2.36%, deterministic IQR=0), with no change on the shallower bulk-load shapes; the production bulk-write win is larger where the upward-publish path is exercised at depth. No public API or wire-format change.
- **F-042 - The replication dead-letter queue now runs on the shared queue engine.** `ReplicationDeadLetterGrain` was reimplemented on top of the same internal FIFO engine that backs `ILatticeQueue<T>`, consolidating the park/peek/list/remove/evict logic. Its durable on-disk format is preserved byte-for-byte: it keeps its `_lattice_replog_dlq_{treeId}` backing tree, its `e/{19-padded-id}` row keys, and its Orleans binary `Serializer<DeadLetterEntry>` payload, and it does not persist the new head-cursor row, so parked entries written by an earlier version are read back unchanged after upgrade. Public surface, metrics (including `dead_letter.removed{reason=evicted}` on FIFO eviction), and the `EntryKey` / `BackingTreeId` helpers are unchanged (#362).


### Fixed

- **WAL phase-one entry rows are now idempotent under Azure Tables SDK retry.** A phase-one WAL batch is written with non-idempotent `Add` operations, so when the SDK retry pipeline resent a batch whose first attempt had already committed server-side but whose response was lost (a socket / read timeout under CPU or network pressure), the resend collided with the now-durable rows and the service returned `409 EntityAlreadyExists` - which the SDK does not auto-retry. The provider rethrew that 409, failing the whole batch (up to ~4,000 operations on the bench hot path) as a hard write failure even though the data was already durable; because the WAL saturation classifier escalates on the first provider failure, this also flapped the tree into `Saturated` and collapsed write throughput while reads stayed healthy. `AzureTableWalStorageProvider` now catches a phase-one `409`, reads the resident rows back, and - only when every row is byte-identical (same offset, compression tag, and payload bytes) to the batch it tried to write - resolves the conflict as a durable success instead of a failure. A 409 whose resident rows differ, or a row that is absent, is a genuine offset collision and still surfaces loudly as a hard failure (so corruption is never masked); a transient fault during the verification read also surfaces the original 409 rather than the incidental read error. This mirrors the candidate row's long-standing `Upsert(Replace)` idempotency, which the entry rows previously lacked. Proven replays are counted on a new `LatticeMetrics.ProviderIdempotentReplays` counter (`orleans.lattice.provider.idempotent_replays`, `{call}`, tagged `tree` / `shard` / `phase`) - **not** on `provider.retry.exhausted` - so an already-durable write neither fails the caller nor escalates the saturation classifier, and operators get a leading indicator of lost-response retries. The new counter is surfaced on the Commit Path Grafana dashboard's provider-retries panel and documented in [`docs/lattice/metrics.md`](docs/lattice/metrics.md). Purely additive; no wire-format change (#685).

### Breaking

- **F-075 - Azure Table WAL row-payload compression is now ON by default.** `AzureTableWalStorageOptions.Compression` now defaults to `LatticeCompression.Zstd` (was `None`), so WAL rows above `CompressionMinPayloadBytes` (default `256`) are Zstd-compressed unless a host opts out with `Compression = LatticeCompression.None`. This is justified by the measured win - the `EncodeWalBatch_AzureTable_Zstd` microbenchmark shows ~81% fewer allocated bytes (and Gen0/Gen1 -> ~0) when encoding a 99-entry batch of ~4 KB values, while small (sub-threshold) and incompressible payloads see no penalty. A new **inflation guard** in `CompressPayload` makes default-on safe for any payload shape: if the compressed bytes plus the 4-byte length prefix are not smaller than the input (e.g. already-compressed or random binary), the row is stored verbatim with tag `None`, so enabling compression never grows a row. The DI path (`AddAzureTableWalStorage`) auto-registers the `ZstdLatticeCompressor` fallback, so the default works with no extra wiring; the bare `AzureTableWalStorageProvider(options, serializer)` constructor (no compressors) now throws at construction when compression is enabled with no matching compressor registered - set `Compression = None` on that path. Changing the algorithm or Zstd level after rows exist remains safe: reads key on each row's stored tag and the self-describing frame's length prefix, never the reader's configured level. See [`docs/lattice/compression.md`](docs/lattice/compression.md#azure-table-wal-row-payload-compression) (#395).

- **F-078 - Public CRDT primitive types moved from the `Orleans.Lattice.Primitives` namespace into the root `Orleans.Lattice` namespace.** The twelve public CRDT building blocks - `HybridLogicalClock`, `ICrdt<TSelf>`, `MvRegister`, `MvRegisterEntry`, `OrMap<TKey, TValue>`, `OrMapEntry<TValue>`, `OrSet`, `OrSetDot`, `PnCounter`, `Rga`, `RgaNode`, and `VersionVector` - now declare `namespace Orleans.Lattice`, matching the repo convention that the entire public API sits behind a single `using Orleans.Lattice;`. **This is wire-compatible**: every affected type keeps its stable `[Alias(...)]` and the Orleans serializer is CLR-namespace-independent, so persisted WAL rows and the replication wire shape are unchanged. **It is source-breaking** for external host code that imported the old namespace - replace any `using Orleans.Lattice.Primitives;` that resolved one of these types with `using Orleans.Lattice;`. The area-internal helpers (`LwwValue<T>`, `LeafDeliveryCursor`, `SplitState`, `SplitStateExtensions`, `StateDelta`) stay `internal` in `Orleans.Lattice.Primitives` and were never part of the public surface. A type-forwarder shim is not possible for an in-assembly namespace move, so this ships as a single hard flip (#398).
- **F-078 - `TxStatus` and `TerminalTallyResult` are now `internal`.** These two types in `Orleans.Lattice.BPlusTree` were `public` only incidentally: their sole owning interface `ITxRegistryGrain` is already `internal` and no public surface referenced them. They are demoted to `internal` so they no longer leak into the public API; their wire aliases are unchanged (#398).

### Added

- **FX-034 - Batch / multi-partition WAL move.** The `ILatticeAdmin` WAL placement surface gains batch overloads of `PlanWalMoveAsync` and `ExecuteWalMoveAsync` that take an `IEnumerable<(int Partition, string TargetProviderKey)>` so an operator can relocate several WAL partitions (or a whole tree) to a different storage backend in one call instead of issuing one move per partition and sequencing them by hand. The batch is **all-or-nothing**: each partition runs the same quiesce-copy-verify phases as a single move (bounded by the new `WalMoveOptions.MaxConcurrentPartitionMoves`, default `1` = sequential), then the durable placement pin flips **once** under a single compare-and-swap that applies every reassignment together, so no intermediate placement is ever observable and every moved partition reaches the same new version. Any per-partition phase failure aborts the whole batch with the pin unflipped, releases every fenced source back to service, and retains the partial target copies for a resumable retry; the batch fails closed (`LatticeWalProviderMissingException`) before touching any log if **any** target key is unresolvable on the serving silo, and rejects an empty batch or a partition named more than once with `ArgumentException`. As with a single move, sources are never trimmed - reclaim each one with `ReclaimMovedWalSourceAsync`. The batch returns the new public `WalMoveBatchPlan` / `WalMoveBatchReceipt` types, each wrapping one per-partition `WalMovePlan` / `WalMoveReceipt` in request order; the single-partition overloads are unchanged. This also corrects the WAL-move quiesce version check, which previously aborted whenever a partition's shard had resolved a *different* placement version than the coordinator expected; because the placement version is global per tree, that spuriously failed any move of a partition after the tree's first move (the global version had advanced while the unmoved partition's shard still lagged). The check now aborts only when a shard is *ahead* of the coordinator. New public types: `WalMoveBatchPlan`, `WalMoveBatchReceipt` (plus `WalMoveOptions.MaxConcurrentPartitionMoves`). See [`docs/lattice/wal-storage-providers.md`](docs/lattice/wal-storage-providers.md#moving-several-partitions-at-once) (FX-034, #633).

The same lifetime-aware pre-check guards the internal shard-root write path and the operator-driven tombstone-compaction pass, so a single `catch (LatticeShuttingDownException)` / `is LatticeShuttingDownException` check now covers every write path rather than only the atomic-write saga that first adopted it. The check is null-tolerant - non-hosted test activations are unaffected. Separately, `AddLattice` now installs an in-library logger filter that demotes the two Orleans transport tear-down `Warning` categories (`Orleans.Messaging` and `Orleans.Runtime.Placement.PlacementService`) to suppressed, but **only** while `ApplicationStopping` is signalled and **only** at the `Warning` level - on a healthy host those warnings are untouched, and `Error`/`Critical` always survive even during shutdown. See [`docs/lattice/api.md`](docs/lattice/api.md) -> "Shutdown back-pressure - `LatticeShuttingDownException`".
- **F-084 - Per-tree pinned WAL storage placement with an `ILatticeAdmin` managed-move surface, for multi-account fan-out beyond the single-account ~22-24 ke/s ceiling.** A tree's WAL partitions can now be spread across several storage backends (for example one Azure Table account each) to exceed any single account's throughput ceiling. Hosts register additional backends in a per-silo provider catalogue with the new `ISiloBuilder.AddLatticeWalStorageProvider(key, factory)` extension; the baseline provider registered through `AddWalStorage` keeps the reserved key `default`. Each tree carries a durable **placement pin** mapping every WAL partition to a catalogue key, defaulting to `default` so existing hosts are unaffected and the resolution path is unchanged. Placement only ever changes through a managed move - never as a side effect of a config edit - via five new methods on the public `ILatticeAdmin` surface: `GetWalPlacementAsync` / `AuditWalPlacementAsync` (inspect the pin and check per-silo resolvability), `PlanWalMoveAsync` (read-only dry run), `ExecuteWalMoveAsync` (quiesce-copy-cutover saga that fences the partition, offset-preservingly copies the retained range to the target, re-converges on in-flight appends, flips the pin under compare-and-swap, then forces the WAL grain to deactivate so its next activation on any silo binds the new provider), and `ReclaimMovedWalSourceAsync` (reclaim the now-redundant source copy once a move is permanent). Moves are non-destructive (`WalMoveReceipt.SourceRetained`) so a move is reverted by simply moving back. A partition pinned to a key a silo did not register **fails closed** (`LatticeWalProviderMissingException`) rather than silently re-routing to the baseline. New public types: `IWalStorageProviderCatalog`, `LatticeWalProviderMissingException`, `WalPlacement`, `WalPartitionPlacement`, `WalPlacementAudit`, `WalMovePlan`, `WalMoveOptions`, `WalMoveReceipt`, `WalMoveOutcome`. Each `ExecuteWalMoveAsync` / `ReclaimMovedWalSourceAsync` call moves a single partition; a batch / whole-tree rebalance API is tracked as the FX-034 follow-up (#633). See [`docs/lattice/wal-storage-providers.md`](docs/lattice/wal-storage-providers.md#multi-account-fan-out-named-providers-and-pinned-placement).
- **`LatticeOptions.WalSaturationFlushLatencyThreshold`** (`TimeSpan?`, default `null` = disabled) and **`LatticeOptions.WalSaturationFlushLatencySampleWindows`** (`int`, default `3`) add a fourth Saturated input to the WAL saturation classifier covering the small-batch blind spot in the existing three inputs (admission depth at cap, dispatch-timeout trips, provider-failure trips). When the threshold is set, the WAL writer increments a per-(tree, shard) trip counter on every provider flush whose wall-clock latency meets or exceeds it; when the classifier observes a non-zero delta in `WalSaturationFlushLatencySampleWindows` sample windows in a row, the tree is upgraded to `Saturated`. Leaving the threshold at its default `null` is a zero-cost no-op: the writer skips the increment and the classifier behaves exactly as before. See `docs/lattice/wal-saturation-signal.md` -> "Flush-latency classifier input" for sizing guidance (FX-036, #635).
- **`AzureTableWalStorageOptions.HonorSaturationSignal`** (`bool`, default `true`) attaches a per-retry `HttpPipelinePolicy` to the Azure SDK pipeline that consults `IWalSaturationSignal.GetAggregateState()` on every retry attempt and, on `Saturated`, stamps the request with a synthetic 503 + `Retry-After: 0` response so the SDK's outer retry policy exits the chain deterministically. The first attempt for any request always reaches the network so the healthy steady state is unaffected; under sustained saturation the policy prevents in-flight retries from occupying WAL slots for the rest of their retry budget while the writer has already concluded the storage tier is shedding load. Set to `false` to restore the historical unguarded SDK retry behaviour. See `docs/lattice/wal-storage-providers.md` -> "Honoring the WAL saturation signal in the SDK retry loop" (FX-035, #634).
- **`AzureTableWalStorageOptions.SaturationShortCircuitCooldown`** (`TimeSpan`, default `2 s`) is the sticky-window duration the saturation-aware retry policy keeps short-circuiting SDK retries for after the last observation of `Saturated`. Closes the timing gap between the silo's saturation sampler (default 200 ms tick - the effective lifetime of any single `Saturated` observation under a transient burst regime) and the Azure SDK's exponential retry spacing (default 800 ms - 3.2 s between attempts): without the cooldown, the SDK retry that fires 800 ms after the `Saturated` observation almost always lands in a `Throttled` or `Healthy` window and passes through to the network, burning storage-side capacity the classifier just told us is exhausted. Set to `TimeSpan.Zero` to disable the sticky window and consult only the present aggregate state (FX-035, #634).
- **`orleans.lattice.provider.retry.short_circuited`** counter (tagged `status`) increments once per Azure SDK retry abandoned by the new saturation-aware retry policy. Tag value `503` matches the synthetic-response status so operators can dashboard the policy's hit rate per silo and prove whether it ever fired (FX-035, #634).
- **`LatticeSaturatedException`** (public, sealed, derives from `InvalidOperationException`, alias `ol.lsa`, carries originating `TreeId`) thrown by the WAL writer admission gate and the atomic-write saga coordinator when the per-tree saturation signal stays `Saturated` past the caller's configured wait budget. Distinct from `LatticeShuttingDownException` (which is one-way): saturation is recoverable, so the caller contract is to back off and retry the same lattice activation once the per-tree signal returns to `Healthy`. See `docs/lattice/api.md` -> "Saturation back-pressure" and `docs/lattice/wal-saturation-signal.md` -> "Library-side consumers" for the full surface (FX-033, #629).
- **`LatticeOptions.WalAdmissionSaturationWaitBudget`** (`TimeSpan`, default `5 s`) bounds the wall-clock budget the WAL writer admission gate (`PartitionTracker.AcquireAsync`) spends parked on `IWalSaturationSignal.WaitForHealthyAsync` before refusing a dispatch with `LatticeSaturatedException`. Set to `TimeSpan.Zero` to disable the gate (historical pre-admission-gate behaviour); set to `Timeout.InfiniteTimeSpan` to wait forever on recovery (FX-033, #629).
- **`orleans.lattice.wal.writer.append.admission_saturation_refusals`** counter (tagged `tree`, `partition`) counts writer-side admission dispatches refused with `LatticeSaturatedException`. Distinct from the dispatch-timeout counter (`admission_timeouts`) and the drain-release counter (`drain.releases`) so operators can dashboard the steady-state saturation-budget refusal rate separately from per-call deadlines and host-shutdown drains (FX-033, #629).

New public types: `LatticePredicateNode`, `LatticePredicateNodeKind`, `LatticeConstant`, `LatticeConstantKind`, `LatticeComparisonOperator`, `LatticeBooleanOperator`, `LatticeStringMethod`, `LatticePredicateContext`, `LatticePredicateTranslator`, `ILatticePredicateSerializer`, and `AtomicWriteOutcome`. Predicate evaluation is allocation-conscious on the read path (ordinal span-based property lookups, short-circuit matching). See [`docs/lattice/atomic-writes.md`](docs/lattice/atomic-writes.md) for the guarded-write surface (P-000 umbrella #555).

### Changed

- **Closed-shape CRDT value (de)serialization is now System.Text.Json source-generated, cutting reflection off the delta-apply hot path.** The `OrSet`, `PnCounter`, `VersionVector`, and `MvRegister` state and delta shapes resolved by `CrdtShapeRegistry` previously (de)serialized through the reflection-based `JsonLatticeSerializer<T>`, so every `ApplyCrdtDeltaAsync` paid per-call System.Text.Json metadata resolution to decode the incoming delta and re-encode the post-merge state. Those four closed shapes now route through a new source-generated `JsonSerializerContext`, while the generic `OrMap<TKey, TValue>` shape - open over host-supplied pairs the generator cannot enumerate - stays on the reflection serializer. The emitted JSON is byte-identical to the legacy path (same property discovery, no naming policy, default options), so persisted `byte[]` rows and the replication wire shape are unchanged; a conformance suite asserts byte-equality and cross-lane round-trips for every shape. Measured on the microbench tier (BDN `InProcessEmitToolchain`, `MemoryDiagnoser`): `microbench_point_apply_crdt_delta_alloc_b` 2,400 -> 2,144 B/op (-10.7%) with mean latency -22%. No public API change (#652).
- **WAL writer admission gate consults the per-tree saturation signal before each acquire.** Pre-FX-033 the admission semaphore was signal-blind: under the storage-account 409-Conflict regime the classifier raised `Saturated` many times before the first observable failure, but every new dispatch still admitted into the semaphore and parked at the cap for the full `WalAppendDispatchTimeout` (default 30 s) before surfacing as a generic `TimeoutException`. The new gate parks the caller on `WaitForHealthyAsync` up to `WalAdmissionSaturationWaitBudget` (default 5 s) before refusing fast with `LatticeSaturatedException`, so callers observe the back-pressure in budget time instead of waiting out the dispatch deadline. Borderline-recovery races are suppressed by a single re-read after budget expiry; caller-supplied cancellation surfaces as `OperationCanceledException` (FX-033, #629).
- **Atomic-write saga `QuiesceOnSaturatedAsync` budget raised from a fixed 5 s to `min(MaxSagaQuiesceWait = 30 s, perTree.WalAppendDispatchTimeout)`.** Pre-FX-033 the 5 s budget was too short to span the typical 409-Conflict burst recovery window (1-10 s) and the saga's fall-through to `SetManyAsync` then amplified the regime by re-dispatching the same RowKeys into a still-throttled storage account. On budget exhaustion with the tree still `Saturated`, the saga now refuses fast with `LatticeSaturatedException`, preserves its persisted state at `Execute` with the current `NextIndex` (mirroring the existing `LatticeShuttingDownException` fast-path), and lets the caller's next idempotent retry on the same `operationId` resume once the signal returns to `Healthy`. The saga also walks `AggregateException` chains so a writer-side `LatticeSaturatedException` bubbling through `SetManyAsync`'s leaf fan-out surfaces typed with the writer-side tree-id attribution preserved (FX-033, #629).
- **`benchmark/azure-throughput/Silo/Program.cs` TCP ingest now applies back-pressure on both the read and the channel-write side of the loop.** Pre-FX-033 the reader gated only `ReadLineAsync`, so a `Healthy -> Saturated` transition between sampler ticks (default 200 ms) let the reader queue thousands of lines into the bounded channel before the next sampler tick parked the reader. A second `ApplyBackPressureAsync` call immediately before `channel.Writer.WriteAsync` converts the channel from a burst absorber into a flow-control fence; under `Healthy` the overhead is two concurrent-dictionary reads (sub-microsecond), under `Saturated` the writer side parks on `WaitForHealthyAsync` before the line crosses into the drain pipeline. The producer is unchanged - back-pressure still propagates via the kernel TCP window (FX-033, #629).
- **`benchmark/azure-throughput/scripts/run-cohort.ps1` verdict classifier tightened against two false-positive regimes observed on single-account perf reports.** (a) Read-only workloads (`get-point`, `get-many`) no longer downgrade to `WEDGE` on the trailing zero-rate `drainTailSamples` rule: read paths have no WAL backlog to drain, so a few trailing zero-rate samples post-producer-shutdown are normal FINAL-emission bookkeeping lag rather than the WAL-drain-wedge phenotype the rule was tuned for. The drain-tail length still surfaces in the verdict reasons for diagnostic completeness. (b) `ReminderService has been stopped` exception lines are subtracted from the exception tally before the `DEGRADED` rule fires - they're a benign shutdown-race between an in-flight write's post-commit reminder-refresh and `ReminderService.Stop`, which the saga's retry chain recovers from cleanly (the cohort's `FINAL failed=` count is unaffected). The count of excluded benign lines is still surfaced in the verdict reasons (FX-035, #634).
- **Live cohort verification (D4as_v5, 4k:5 / 45s, n=3 per write workload, single Azure Tables Standard account).** Post-FX-033 cohort run produced **15/15 HEALTHY** with **zero `failed=N`** across every workload (`get-point`, `set-point`, `get-many`, `set-many`, `set-many-atomic`), eliminating the pre-FX-033 wedge phenotype (`6/15` wedged, `121,060` failed entries cumulative, two `set-many-atomic` cohorts SIGKILL'd without FINAL). Headline per-mode deltas vs the pre-FX-033 triage cohort: `set-many` steady-state throughput +10% (11,692 -> 12,812 e/s) with per-call p99 -86% (7,034 -> 1,010 ms); `set-point` throughput +29% (3,253 -> 4,210 e/s) with p99 -34%; `set-many-atomic` throughput -14% (4,617 -> 3,984 e/s) - the latter is the correct trade-off of honest back-pressure on the saga vs the pre-FX-033 amplification of the 409-Conflict burst via retried RowKeys. Full per-cohort table and observations in [`benchmark/azure-throughput/throughput.md`](benchmark/azure-throughput/throughput.md) §34.5-34.6 (FX-033, #629).
- **Predicate push-down evaluation resolves top-level-member predicates with a zero-allocation `Utf8JsonReader` fast path instead of `JsonDocument.Parse`, cutting per-candidate-row allocation on every predicated scan / read / cursor / conditional-mutation path.** `LatticePredicateEvaluator.Matches` previously materialized a `JsonDocument` per candidate value before folding the predicate IR; that document object (its metadata database is pool-rented, but the wrapper and per-parse state are not) cost ~72 B per row evaluated. When the predicate references at least one member and every member path is a single top-level property name (the common shape - `Age >= 18`, `Name.StartsWith("A") && Active`, etc.), the evaluator now folds the tree against a forward-only `Utf8JsonReader` (a `ref struct`, no heap), resolving each member by an ordinal-first / case-insensitive-fallback forward scan that exactly mirrors the slow path's `JsonElement.TryGetProperty` semantics. A single zero-allocation validation pass preserves the "must be well-formed JSON, else no match" contract even when the tree short-circuits before reading past a malformed region, so behaviour is byte-for-byte identical (the full lambda-vs-evaluator oracle and the case-insensitive / missing-member / non-JSON / null cases all pass unchanged). Nested (`a.b`) member paths and constant-only predicates keep the `JsonDocument` slow path, whose random-access model resolves dotted paths without re-scanning. Measured on the new `microbench_predicate_key_scan` instrument (BDN `InProcessEmitToolchain`, `MemoryDiagnoser`, 1,000-row JSON-seeded scan, n=3 cohorts): `microbench_predicate_key_scan_alloc_b` **98,928 -> 26,928 B/op (-72.8%, deterministic, IQR=0 across n=3)** - the residual is fixed async-enumerable iteration overhead; the JsonDocument-per-row cost is eliminated. The change is confined to the predicate evaluator (reached only by predicate-bearing operations), so non-predicate microbenchmarks are structurally unaffected. Size-and-engine change only; the predicate allowlist, null-aware equality / ordering, string-method, and strictly-subtractive contracts are unchanged. Follow-up to the issue #652 design-lead #2 (predicate `Utf8JsonReader` fast path).
- **The shard-root batched-write shadow-forward loop is skipped entirely when no adaptive split or moved-away slot is active, cutting `SetMany` bulk-write allocation roughly in half.** After every batched local leaf apply, `ShardRootGrain.SetManyLocalOnlyAsync` fed all N input keys through a per-entry `ForwardLocalWriteToShadowIfNeededAsync` loop so writes for slots that have moved to a sibling shard reach the destination. In the dominant single-silo, no-resize steady state every per-entry call resolves to a null target and returns synchronously, but the `async Task` wrapper still drove the whole loop and boxed a per-entry async state machine (~120 B/key). The wrapper now checks the exact guard the per-entry helper depends on - `SplitInProgress is null && MovedAwaySlots.Count == 0` - once up front and returns `Task.CompletedTask`, skipping the loop and its async machinery; the slow path is unchanged when a split or moved slot is active. The steady-state caller already resumed synchronously here, so the yield behaviour is preserved. Measured on the microbench tier (BDN `InProcessEmitToolchain`, `MemoryDiagnoser`, n=3 cohorts): `microbench_set_many_4_shards_alloc_b` 238,456 -> 118,456 B/op (deterministic across n=3, **-50.3%**); the `point_write_alloc_b` control (single-key `SetAsync`, which calls the per-entry helper directly and is untouched) held at 840 B/op exactly. 461 split / resize / shadow-forward / migration / set-many tests pass.

### Fixed

- **`set-many-atomic` Azure-throughput cohorts no longer WEDGE on shutdown (no FINAL line).** In `benchmark/azure-throughput/Silo/Program.cs` the FX-032 in-flight-tail quiesce awaited `IWalSaturationSignal.WaitForHealthyAsync` for up to `InFlightTailQuiesceBudget = 30 s` - exactly equal to the `lattice-silo.service` systemd `TimeoutStopSec=30 s`. When the tree was still `Saturated` at the producer-stop boundary (the normal case for the slow saga path), the quiesce consumed the entire stop window and systemd SIGKILL'd the silo before the FINAL line could be emitted, surfacing as a `WEDGE` verdict in 2/3 `set-many-atomic` cohorts of a live perf run. Bench-infrastructure only; no product/library code change (FX-038, #641).
- **De-flaked the digest-coalescing cluster integration test under CI load.** The shared `LatticeDigestSettleHelpers` convergence-poll budget was a hard-coded 2 s, which a saturated CI runner could overrun before the coalescing-window publish converged, surfacing as a spurious `TimeoutException`. A genuine non-convergence still fails the test promptly. Test-harness only - no product code change (FX-037, #639).

### Added

- **Byte-accurate storage usage and advisory WAL byte-pressure retention.** You can now query the retained storage footprint of a tree (WAL, snapshot, and leaf-state bytes) via `ILattice.GetStorageUsageAsync`, and roll the figures up across every registered tree in the cluster via the new `ILatticeAdmin.GetTotalStorageUsageAsync`. The same totals are exposed as OpenTelemetry observable gauges (`orleans.lattice.storage.wal_bytes`, `storage.snapshot_bytes`, `storage.leaf_state_bytes`, `storage.total_bytes`) plus a `storage.policy.over_threshold` 0/1 gauge, with two new counters (`storage.policy.trim_triggered`, `storage.policy.bytes_reclaimed`) and four new panels on the bundled Grafana overview dashboard. A new advisory `LatticeOptions.WalMaxRetainedBytes` ceiling lets the WAL garbage collector prioritise byte-pressure trims without ever crossing the safe consumer frontier - an over-threshold tree held up by a lagging consumer is surfaced for diagnosis rather than silently growing unbounded. The storage gauges populate **automatically** on every silo via a background poller (`LatticeOptions.StorageUsagePollInterval`, default 15 s) - you no longer have to call the storage-usage API to make the dashboards light up - and stay correct across a multi-silo cluster: each tree is counted on exactly one silo and a series expires from a silo's sink when the tree's aggregator migrates away, so a cross-silo sum never double-counts. Set `StorageUsagePollInterval` to `TimeSpan.Zero` to opt out. The advisory policy uses a hysteresis band so a tree hovering near the ceiling is not trimmed on every garbage-collection pass: byte pressure arms when retained WAL crosses `WalMaxRetainedBytes` and disarms once a trim drives retained bytes at or below `WalMaxRetainedBytes * WalBytePressureReclaimTarget` (default `0.8`), and growth that stays inside that band does not re-trigger until the ceiling is crossed again.
- **WAL writer now back-pressures honestly instead of silently absorbing into an unbounded queue when the shard cannot drain (G-026).** The shard-side `WalMaxPendingBatches` ceiling (default 8) historically bounded `WalShardGrain._inFlight` only; the writer-side per-`(tree, partition)` `WalCommitLogWriter.PartitionTracker` was unbounded, so a saturating offered rate stacked up to 18+ pending dispatches per partition (observed in the 2026-06-03 wedge cohort) with no caller-visible signal until the silo wedged. A per-partition admission semaphore, sized at `WalMaxPendingBatches` and bounded by the existing `WalAppendDispatchTimeout`, now caps writer-side depth symmetrically. When the shard cannot drain, callers receive a typed `TimeoutException` naming the admission deadline in bounded time instead of parking forever. Two new instruments make the new regime observable: `orleans.lattice.wal.writer.append.admission_timeouts` (the counter that increments when a dispatch is refused at the deadline) and `orleans.lattice.wal.writer.append.admission_wait` (the histogram that surfaces back-pressure as honest tail-latency well before any hard timeout fires). Set `WalMaxPendingBatches=0` to opt out and restore the historical unbounded-writer shape for rollback / parity testing.
- **Writer-layer per-partition pending-append dispatch is now observable, so the upstream variant of the WAL wedge is attributable without source-walking (G-025).**
- **Per-shard WAL flush lifecycle and reshard activity are now observable, so the residual phase-1/activation WAL wedge can be attributed without source-walking (G-024).**

### Changed

- **`WalCommitLogWriter` internal awaits no longer silently drop the grain context (FX-024).** The singleton writer helper is invoked from grain turns (the leaf grain's foreground commit path, the shard-root saga terminal path); the historical `.ConfigureAwait(false)` on every internal await silently dropped the caller's grain scheduler on resume, making the resume-context of each await unclear and leaving the helper one bug-fix away from breaking the single-threaded-turn invariant for any state added later. Only the four deliberate outbound `IWalShardGrain` dispatch awaits keep `.ConfigureAwait(false)`, because their catch must land off a possibly-wedged grain context so the writer-side wedge-attribution counter and log line still fire. An audit test pins the count at exactly four going forward. No behavioural change for callers.

### Fixed

- **Every public `ILattice` operator that drives the shard-root activation-readiness seed now transparently absorbs cold-start seed timeouts, not just `ReshardAsync` (FX-027).** Extends the FX-026 typed-exception envelope across the rest of the operator surface: per-key read / write / version-check / CRDT-delta / get-or-set / delete paths (via the central `RetryOnStaleRoutingAsync` helper, which now catches `ShardActivationTimeoutException` alongside the existing stale-routing exceptions), multi-shard fan-outs (per-shard wraps inside `GetManyAsync`, `SetManyAsync`, `DeleteRangeAsync`, `CountAsync`, the scan first-page init in `KeysAsync` / `EntriesAsync`, the cursor WAL-head snapshot fan-out, and `GetMaterialiserLagAsync` so a single shard's seed-timeout retries only that shard and not every sibling), per-tree coordinator entry points (`DeleteTreeAsync` / `RecoverTreeAsync` / `PurgeTreeAsync` / `ResizeAsync` / `UndoResizeAsync` / `SnapshotAsync` / `MergeAsync` / `BulkLoadAsync` / `CompactShardAsync` / `RebuildLeafProjectionAsync`), the saga path (`SetManyAtomicAsync` both overloads via `IAtomicWriteGrain`), the digest fast path (`GetLeafProjectionDigestAsync`), and the warmup probe (per-shard wrap inside `WarmUpAsync`'s shard probe). Adds a generic `ShardActivationRetry.RunAsync<T>` overload for fan-outs that produce per-shard values. Replication-apply call sites remain out of scope because the receiver-side `ReplicationApplier` already has its own retry / dead-letter envelope.
- **`ILattice.ReshardAsync` transparently absorbs cold-start activation-seed timeouts instead of surfacing them to callers (FX-026).** The G-019 shard-root activation-readiness seed deadline (`LatticeOptions.ActivationReadyTimeout`, default 15 s) is by design retriable - every cross-grain step in the seed is idempotent on retry, with the timeout existing only to release the activation gate so a retry can take the seed - but `ReshardAsync` was surfacing the bare `TimeoutException` to the caller on the first parked seed, breaking any operator that calls reshard during host startup (e.g. a startup-reshard pattern that pins a tree at N shards from day one). The seed now throws a typed `ShardActivationTimeoutException` (publicly visible, derived from `TimeoutException`, with `TreeId` / `ShardIndex` / `TimeoutSeconds` slots for attribution), and `ReshardAsync` internally retries up to three times with linear 1 s / 2 s backoff before propagating; worst-case caller-visible wall is ~48 s on defaults, well under the Orleans response deadline. - **`docs/lattice/configuration.md` Options Reference table now lists every `LatticeOptions` property.**

Equal-count requests now return success and leave the shard map / manifest version unchanged; only `n < currentCount` (a genuine shrink) continues to throw, since shrink is still unsupported.
- **Storage-usage gauges no longer activate idle leaves to compute their footprint (FX-025).** The cluster-wide storage-usage poller previously fanned out through the per-tree storage-usage aggregator, which in turn activated every leaf and snapshot grain in the tree to sample their byte sizes - defeating the cold-tree assumption that idle trees stay quiescent. The poller now drives `ILatticeAdmin.PollWalUsageAsync` against a new per-tree `ILatticeWalUsage` aggregator that touches only `IWalShardGrain` activations, never a leaf, internal node, snapshot storage, or shard-root grain. Leaf-state and snapshot bytes are now incrementally tracked at the source (`LeafEntryCache.StateBytes` maintained on every store / remove / clear; `LeafSnapshotBlob.SnapshotBytes` precomputed at save time) and pushed to the owning shard root on every digest-publish commit boundary, so `ShardRootGrain.GetStorageUsageAsync` becomes a constant-time read off activation-scoped running totals. - **First-activation shard seed no longer wedges the write pipeline when a registry or root-leaf RPC parks (G-019).** The one-time activation-readiness seed a shard root runs the first time a brand-new or freshly-reactivated shard prepares for an operation (the defensive state re-read, the tree-registry registration, the deterministic root-leaf init pair, and the initial shard-state write) runs while the shard-root init gate is held. During a startup reshard or membership change Orleans can park one of those cross-grain awaits - the target registry or leaf activation is not yet visible - leaving the seed neither completing nor faulting, pinning the gate, stalling every interleaved read/write turn, and wedging the whole write pipeline with no fault and no activation recycle until the caller-side response deadline expires. The seed is now bounded by a new `LatticeOptions.ActivationReadyTimeout` deadline (default 15 s): a parked seed is abandoned and the operation retried against refreshed routing once the reshard settles, with every seed step idempotent on retry so no data is lost or double-registered. A new `orleans.lattice.shard_root.activation_ready.timeouts` counter surfaces the condition. Set `ActivationReadyTimeout` to `InfiniteTimeSpan` to restore the historical unbounded await.
- **Shard projection-digest entry counts stay exact across internal-node splits (FX-022).**
- **`GetManyAsync` now returns an all-or-nothing snapshot across a mid-saga reshard (G-020).**
- **WAL flush deadline now recovers even when a storage-provider hang ignores cancellation (G-019).** The `LatticeOptions.WalFlushTimeout` deadline previously only fired if the provider observed the deadline's cancellation token; a provider call that hangs in a non-cancellable wait - a half-activated partition from a placement/reshard race, or an SDK retry loop that swallows cancellation - left the grain awaiting forever even after the deadline elapsed, so the in-flight slot never drained and the shard's append pipeline stayed wedged at `WalMaxPendingBatches`. The grain now also bounds its own wait on the provider task, so the deadline recovers the shard regardless of whether the provider honours cancellation. This closes the residual real-Azure saturation-rung wedge that survived the initial v6.1.3 fix.
- **Reshard swap-phase writes no longer wedge the pipeline when a cross-shard forward parks (G-021).** During an online reshard the destination shard's ownership changes, and Orleans can reject an outbound shard-to-shard write forward and leave the caller-side await neither completing nor faulting; the forwarding turn then never returned, the per-shard write fan-out saturated at its in-flight limit, and the whole write pipeline stalled with no fault and no activation recycle. Outbound shard forwards (the online-resize shadow forward and the adaptive-split migration forward) are now bounded by a new `LatticeOptions.ShardForwardTimeout` deadline (default 15 s): a parked forward is abandoned and the write retried against refreshed routing, while data convergence stays guaranteed by the split coordinator's authoritative leaf-chain drain. A new `orleans.lattice.shard_root.forward.timeouts` counter and a CommitPath dashboard panel surface the condition. Set `ShardForwardTimeout` to `InfiniteTimeSpan` to restore the historical unbounded await.
- **Internal-node digest upward publishes no longer wedge a B+ tree branch when a parent parks mid-mutation (G-022).** When an internal node folded a child's projection digest and republished the aggregate to its own parent, that cross-grain publish ran under the node's non-reentrant split gate with no ceiling; a parent that was itself mid-mutation could leave the publish neither completing nor faulting, holding the split gate and wedging every subsequent mutating turn on that activation. The upward publish is now bounded by a new `LatticeOptions.DigestPublishTimeout` deadline (default 15 s): a parked publish is abandoned and the turn faults with a `TimeoutException` so the split gate releases, and the staleness-tolerant digest re-converges on the next mutation's publish. A new `orleans.lattice.internal.digest_publish.timeouts` counter surfaces the condition. Set `DigestPublishTimeout` to `InfiniteTimeSpan` to restore the historical unbounded await.
- **Residual phase-1/activation WAL wedge is now bounded and attributable per `(tree, shard)` (G-023).** Despite the activation-readiness seed deadline (G-019) and the WAL flush deadline (G-019), a residual bimodal wedge survived at the Azure-Tables WAL saturation rung where every shipped deadline read zero yet `inFlight` stayed pinned at `WalMaxPendingBatches`. The wedge mechanism lives upstream of the existing deadlines and could not be attributed without source-walked instrumentation. The change ships a coordinated diagnostic pack: the writer's outbound `IWalShardGrain.AppendBatchAsync` / `AppendAsync` RPC is now bounded by a new `LatticeOptions.WalAppendDispatchTimeout` deadline (default 30 s) - converting a 180-second blind hang on the Orleans response timeout into a structured `TimeoutException` with per-shard counter attribution via `orleans.lattice.wal.append_dispatch.timeouts` - while the per-shard `WalShardGrain.FlushAsync` preflight region (the synchronous setup and initial scheduler yield that precede the provider-call deadline) is now bounded by a new `LatticeOptions.WalFlushPreflightTimeout` deadline (default 5 s), so a paused activation scheduler that never resumes the post-yield continuation is caught and the slot drains, rather than pinning `_inFlight` with no deadline armed; the trip is attributed via `orleans.lattice.wal.flush.preflight.timeouts`. A new `orleans.lattice.wal.shard.deactivate.in_flight` histogram observes `_inFlight.Count` at every `OnDeactivateAsync`, so a deactivation with non-zero in-flight count immediately followed by a preflight timeout on a successor activation directly attributes the mid-call deactivation orphan hypothesis. Each deadline can be set to `InfiniteTimeSpan` to restore the historical unbounded await.

Panel #11 retitled to "Per-peer last outbound ship (seconds ago)" with `direction="outbound"` matcher; consecutive-errors panel breaks down by `direction`; new panel #20 "Per-peer last inbound apply (seconds ago)" mirrors the outbound view filtered by `direction="inbound"`.
- Multi-partition WAL replay on leaf activation. The silo-wide default for `LatticeOptions.WalPartitions` flips from `1` to `8`; existing trees pin the value in force at first WAL write into the tree registry, so the default change is non-breaking for already-registered trees. New trees pick up the new default and have every leaf's activation-time materialiser fan out across `[0, WalPartitions)` partitions with a two-pass replay (per-partition Set/Delete absorption with TxCommit / TxAbort / DeleteRange deferred until every partition's pending-tx record is populated, then drained) and a post-pass per-partition checkpoint reconciliation that advances each partition's `ProjectionCheckpointOffsetsByPartition` to the highest applied offset once the saga-prepare clamp lifts. The snapshot cursor and the operator projection-admin paths fan out alongside: `LatticeSnapshotCoordinate` gains an additive `[Id(3)] PerShardPerPartitionWalOffsets` slot (legacy scalar preserved via max-of-partitions), `ISnapshotLeafGrain.OpenAsync` takes per-partition captured offsets and the materialiser filters by shard index to prevent sibling-shard data absorption, and `IShardRootGrain.SnapshotWalHeadAsync` returns `long[]` (per-partition heads) with `GetShardMaterialiserLagAsync` summing per-partition lags. New wire-additive `LeafNodeState.ProjectionCheckpointOffsetsByPartition` slot persists per-partition checkpoints; per-partition cursor consumer ids (`_lattice_materialiser_{treeId}_{leafGrainId}_{partition}`) let the per-shard WAL GC trim each partition under its own slowest consumer. New `LatticeOptions.WalPartitions >= 1` option validator. **`LatticeReplicationOptions.DefaultReplogPartitions` flips from `1` to `8`** in lockstep so the replication shipper reads every partition the commit-log writer fanned across (without alignment the shipper would miss 7/8 of writes).
- Per-tree `WalPartitions` pin on `TreeRegistryEntry` (additive `[Id(9)] int?`). Stamped at first `ILatticeRegistry.RegisterAsync` from the silo's then-current `LatticeOptions.WalPartitions` value; never mutated thereafter. `LatticeOptionsResolver` reads the pin in preference to the live `IOptionsMonitor<LatticeOptions>` value, so the resolved `WalPartitions` seen by every grain is tree-immutable for the lifetime of the tree - the foreground commit-log writer and the activation-time materialiser always agree on the partition fan-out shape regardless of what the silo's currently-configured value is. System trees bypass the registry and hardcode `WalPartitions = LatticeConstants.DefaultSystemTreeWalPartitions` (`1`) so they stay on the single-partition shape regardless of the silo-wide user-tree default.
- **Expanded chaos-test coverage.** Twelve new chaos fixtures across the four test projects pin previously-unverified invariants: range-delete exclusivity under concurrent writers, `SetIfVersionAsync` (CAS) linearisable winners under contention, `ScanAsync` cooperative cancellation, two-silo restart under load (currently `[Ignore]`'d pending a grain-type-discrimination fix tracked on GitHub Issues), producer-side WAL trim cannot prune un-acked entries, per-peer liveness probe + receiver-side inbound-error counters under partition-and-heal, OR-Map convergence (currently `[Ignore]`'d pending a chaos-pump dedupe gap), tombstone-reap envelopes never crossing the producer boundary under compaction+shipping churn, gRPC transport convergence under transient channel faults, and Azurite-backed WAL append/trim under concurrent load with storage faults. New `ProductionShipperFixture` provides a real `AddLatticeReplication` + in-process loopback transport harness with partition / heal / batch-observation / receiver-fault-injection hooks. The `IsTransient` predicates used to classify retry-eligible exceptions on chaos hot paths now cover the documented exhaustion classes (CAS-budget exhaustion, stale routing) that production callers already absorb.

### Breaking

- **Doubled series on `peer.last_contact_seconds` and `peer.consecutive_errors`.** Hosts that opt into both directions see two series per `(tree, peer)` pair (one outbound, one inbound). Dashboards that previously matched these gauges without filtering by `direction` must add `direction="outbound"` to preserve the pre-bidirectional shape, or accept the doubled series. Metric names and units are unchanged. `peer.entries_behind` / `peer.bytes_behind` are unaffected.

## [6.0.1] - 2026-05-29

Minor release. **Backwards-compatible at the wire level.** Defaults flips on three configuration knobs lift the out-of-the-box throughput at the Azure-Tables operating point measured by the post-v6.0.0 throughput campaign; hosts that depend on the pre-v6.0.1 behaviour opt out explicitly per knob. One previously-deferred `Orleans.Lattice.Dashboards` rebuild surfaces 34 instruments that shipped without any operator-visible panel on v6.0.0.

### Changed - configuration defaults (opt-out)

- **`LatticeOptions.WalMaxPendingBatches`: `1` -> `8`.** The per-shard WAL grain's in-flight-batch cap. Raises the pipeline depth between the producer and the storage provider's flush envelope; pairs with the `PhaseTwoCoalescingWindow` flip so the worker's 49-row coalescing window has enough arrivals to engage. Hosts that depend on strict-serial-per-shard append shape opt out by setting `WalMaxPendingBatches = 1` explicitly.
- **`LatticeOptions.DigestCoalescingWindowMs`: `0` -> `5` ms.** The leaf-side projection-digest publish window. Defers the cross-grain `OnChildDigestPublishedAsync` hop behind a one-shot grain timer; mutations arriving within the window collapse into one publish. The running `ProjectionHash` on persisted state still advances per-mutation, so cold-reactivation replay is bit-identical to the synchronous shape. Hosts that depend on the read-after-write digest invariant opt out by setting `DigestCoalescingWindowMs = 0`.
- **`AzureTableWalStorageOptions.PhaseTwoCoalescingWindow`: `TimeSpan.Zero` -> `5 ms`.** The worker's first-arrival hold window before a phase-2 commit fires. Lets the worker coalesce multiple commits into one Azure-Tables transaction when arrivals overlap; pairs with `PipelinePhaseTwoCommits` and `WalMaxPendingBatches` so the upstream pipeline actually produces overlapping arrivals. Hosts that depend on commit-on-first-arrival opt out by setting `PhaseTwoCoalescingWindow = TimeSpan.Zero`.
- **`AzureTableWalStorageOptions.PipelinePhaseTwoCommits`: `false` -> `true`.** Returns the caller as soon as the *previous* batch's phase-2 commit lands; the current batch's phase-2 runs asynchronously through the same per-shard worker. Phases 0 and 1 remain synchronous and durable, so the activation-time reconciler contract is unchanged - the only observable change is that a phase-2 failure surfaces on the *next* `AppendBatchAsync` rather than the failing one. Hosts that need failure-on-the-failing-call semantics (or that run against a single-writer backend like Azurite where overlapping writes contend rather than overlap) opt out by setting `PipelinePhaseTwoCommits = false`.

**Multi-partition WAL replay shipped on `[Unreleased]`.** `LatticeOptions.WalPartitions` now defaults to `8` (the throughput-campaign sweet spot) and `LatticeReplicationOptions.DefaultReplogPartitions` follows in lockstep. The activation-time WAL replay loop on `BPlusLeafGrain` fans across every configured partition (two-pass replay with post-pass per-partition checkpoint reconciliation), the snapshot cursor and projection-admin paths fan out alongside, and the tree-registry pin keeps every grain agreeing on the partition fan-out shape for the lifetime of the tree.

### Added - operator-visible surface

- **34 new metrics surfaced in `Orleans.Lattice.Dashboards`.** The `CommitPath` dashboard gained 13 panels (SetAsync / SetManyAsync envelope p50/p95, per-stage sub-attribution for both, ShardRoot per-step, WAL append decomposition + batch shape + back-pressure, storage-provider phase-2 + retries, `leaf.commit.in_flight`, `WarmUpAsync`, digest-coalescing efficacy). The `AtomicWrites` dashboard gained 4 panels (per-phase saga durations, broadcast sub-attribution, per-key work vs serial-gap wait, fan-out size distribution). All 34 referenced metrics resolve via the existing drift-guard test.
- **`orleans.lattice.leaf.digest.publishes` counter** tagged `tree` + `path` (`coalesced_scheduled` / `coalesced_skipped` / `coalesced_fired` / `inline` / `deactivation_flush`). Closes the behavioural-attribution gap for the `DigestCoalescingWindowMs` flip - operators can now confirm the coalescing path is actually firing on Azure rather than silently regressing to the pre-c2-xxix resolver-drop shape.
- **`AzureTableWalStorageOptions.DefaultPhaseTwoCoalescingWindow`** and **`DefaultPipelinePhaseTwoCommits`** static-readonly fields so hosts can reference the shipping defaults symbolically. Each is pinned by a dedicated unit test (`PhaseTwoCoalescingWindow_defaults_to_five_ms`, `PipelinePhaseTwoCommits_default_value_is_true`).

### Added - WAL throughput

- **`AzureTableWalStorageOptions.EliminateCandidateRowOnHotPath`** - opt-in WAL throughput optimisation that skips the phase-0 candidate-row write on every `AppendBatchAsync` and shrinks the phase-2 transaction by one action. Off by default; orphan recovery is preserved by an additional batch-partition scan above `TAIL` in `ReconcileAsync`. See `docs/lattice/wal-storage-providers.md` for the downgrade-safety note.

### Added - benchmark harness

- **`benchmark/azure-throughput/`** - real-Azure Storage WAL throughput harness (two-container ACI deployment) brought into the benchmark family. Exposes `BENCH_WAL_ELIMINATE_CANDIDATE_ROW`, `BENCH_WAL_PARTITIONS`, `BENCH_WAL_MAX_PENDING_BATCHES`, `BENCH_WAL_PHASE2_COALESCING_WINDOW_MS`, `BENCH_FLUSH_CONCURRENCY`, `BENCH_SHARD_COUNT`, `BENCH_FLUSH_MS`, `BENCH_DIGEST_COALESCING_WINDOW_MS`, and `BENCH_RESPONSE_TIMEOUT_SEC` so the same single-silo harness can A/B every defaults-flip candidate against a real Azure Tables account. The bundled ladder driver and Phase-A attribution reporter were brought into this branch alongside the harness.

### Changed - documentation

- **`docs/lattice/wal-storage-providers.md`** updated for both Azure-Tables default flips: the `PipelinePhaseTwoCommits` section is now framed as "as of v6.0.1 the default is `true`" with the opt-out conditions enumerated, and the comparison table relabels "Default" / "Pipelined" as "Pre-v6.0.1 / opt-out (`= false`)" / "v6.0.1 default / pipelined (`= true`)".
- **`docs/lattice/metrics.md`** documents the new `orleans.lattice.leaf.digest.publishes` counter including the c2-xxix regression signature it catches, and the expanded scope of the `CommitPath` and `AtomicWrites` dashboards.

The captured-and-base-passed double-use is replaced with a single `GrainContext.ActivationServices` call. No behavioural change; warning count drops from 1 to 0.

## [6.0.0] - 2026-05-22

Major release. **Not backwards-compatible.** The on-wire WAL format, the persisted leaf state shape, the replication transport contract, and the public API surface have all changed since the v5.0.x line. There is no in-place upgrade from any v5.x deployment - tenants must drain and reseed Azure Table WAL storage, and every cross-cluster replication peer must be on v6.0.0 before traffic resumes. The historical v5.0.0 / v5.0.1 / v5.1.0 NuGet tags shipped only the F-052 operator-tooling slice on top of the v4.1.1 baseline; everything else listed below is new since that line.

### Breaking - on-wire and persisted format

- **`WalRecord.Value` dropped from CRDT-mode WAL and wire payloads (R-119).** CRDT entries now carry only the typed delta; the full-state serialisation is no longer emitted on the producer side. LWW entries are unaffected in shape. v5.x receivers do not understand the new shape - cross-cluster peers must be upgraded in lockstep.
- **Typed-delta wire collapse and OR-Map replication (R-035).** Replication envelopes carry the typed delta directly rather than the fold-then-reserialise round trip the v5.x line used.
- **Per-row WAL payload trims (R-114, R-115, R-116, R-117).** `TreeId`, `Mode`, `ShardIndex`, and the per-entry origin envelope are stripped from the on-wire bytes; the receiver reconstructs them from the envelope context. The on-disk WAL rows are not readable by a v5.x reader.
- **One-encode commit-to-wire end-to-end (R-114 stage 5, folding R-115).** The producer-side encode happens once and the same bytes flow from leaf-commit through WAL append to replication ship.
- **Azure Table WAL wire format harmonised with the in-memory baseline (R-079).** The on-disk row layout under `WalEntry` is the canonical shape; existing Azure Table data must be drained or migrated before upgrading.
- **Framing-tail compression for replication envelopes (R-043)** with a reusable `ILatticeCompressor` core seam. Compression negotiation is required between v6 peers.

### Breaking - persisted leaf state shape

- **Delta-only producer-side CRDT state model (R-120).** The leaf-as-`byte[]` model is replaced with a leaf-as-delta-journal-plus-cache model. The persisted `LeafNodeState.Entries` and `LeafNodeState.LiveCount` slots are gone; the runtime-owned `LeafEntryCache` is rebuilt from the WAL on every activation. Existing v5.x persisted leaf state is not loadable - tenants must reseed via WAL replay against a clean leaf state row.
- **Leaf snapshot safety net.** New `ILeafSnapshotStorageGrain` captures a point-in-time projection when a leaf's `ProjectionCheckpointOffset` approaches WAL retention; reactivation prefers the snapshot over from-scratch replay when the snapshot offset is strictly newer than the persisted checkpoint.

### Breaking - public API surface

- **`IReplicationTransport` typed-envelope shape (R-047).** The transport contract exchanges typed envelopes, not opaque `byte[]`. Hosts implementing a custom transport must migrate to the typed seam.
- **`ITypedReplicationTransport` is the canonical transport contract.** Receiver-side per-entry shard RPCs collapse into batched `ApplyMergeManyAsync`.
- **`IReplicationTopology` widened to govern doorbell and fall-off probes (R-113).** Topology providers now answer both routing and fall-off-probe authority questions.
- **Zero-copy WAL provider contract via `IWalMutationEncoder` (R-076).** `IWalStorageProvider` implementations receive a writer rather than an allocated byte array; existing providers must migrate.
- **`ILattice.ApplyCrdtDeltaAsync(string, LatticeMergeMode, byte[], CancellationToken)`** added for hosts that pre-compute typed deltas off-grain and want to commit them through the same producer-side path. The producer-side delta-apply seam is the new authoritative write path.
- **Per-tree OR-Map shape registration** via `ISiloBuilder.AddOrMapShape<TKey, TValue>(string)`; closed-shape modes resolve through the registry's global fallback.

### Added - CRDT primitives

- **MV-Register primitive and accessor (F-039)** with receiver-side replication dispatch (R-034).
- **OR-Map CRDT primitive and accessor (F-040)** - observed-remove map with recursive CRDT-value merge.
- **RGA sequence primitive and accessor (F-041)** - Replicated Growable Array for collaborative ordered lists and text.

### Added - replication and transport

- **Receiver-side flow control (R-062)** - back-pressure policy hook on the apply side.
- **Back-pressure `IHealthCheck` for the replication shipper (R-065)**.
- **Observable replication topology with runtime peer changes (R-066)** - topology can be updated without a restart.

### Added - storage and WAL

- **Pipelined phase-2 commit on the Azure Table WAL provider (F-070)**.
- **Batch WAL append on the leaf write path (F-069)**.
- **Pre-built `TableServiceClient` slot on `AzureTableWalStorageOptions` (R-112)** - hosts can hand a pre-configured client to the provider.

### Added - compaction

- **Compaction policy controls and telemetry (F-071)**.
- **Configurable compaction tick cadence (F-072)**.
- **Intra-shard leaf-walk batching for tombstone compaction (F-073)**.
- **Shard-root dirty-leaf tracking for compaction (F-074)**.

### Added - tuning and release infrastructure

- **`LatticeOptions.LeafSnapshotMargin`** (default `0.30`) and **`LatticeOptions.LeafSnapshotReClassifyEveryNCheckpoints`** (default `64`) to tune the snapshot-on-fall-off trigger.
- **`CHANGELOG.md`** - canonical per-version release notes for the package family, governed by [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) discipline going forward.
- **`docs/RELEASING.md`** - per-package tag-and-publish protocol documenting the release-engineering contract the publish workflow expects (tag shapes, per-package push order, accidental-bulk-push recovery, historical-tag backfill guidance).

### Changed

- **Exact byte accounting in WAL pending-batch sizing (R-075)**.
- **Trim-aware WAL live-entry accounting (R-077)**.
- **Multi-batch in-flight WAL flush concurrency (R-074)**.
- **Dead shipper-side encode eliminated on typed transports (R-078)** - the typed transport never re-encodes a payload the producer already emitted.
- **Package family realigned on a single major version.** `Orleans.Lattice.Replication`, `Orleans.Lattice.Replication.Grpc`, `Orleans.Lattice.Storage.AzureTable`, and `Orleans.Lattice.Dashboards` move from `5.0.1` to `6.0.0` in lockstep with the core package.

### Fixed

- **Post-restart projection drop.** The runtime-owned `LeafEntryCache` is rebuilt from the WAL on every activation. The persisted `ProjectionCheckpointOffset` survives across activations, so trusting it after a cold start would cause WAL replay to read only `(checkpoint, head]` and silently drop every offset `<= checkpoint` from the rebuilt cache. Activation now computes a local replay-start override when no snapshot rehydrated and the cache is empty, so the replay covers the entire readable window. The persisted slot is never mutated by activation; the override is local to the replay loop only, preserving the public empty-tree digest contract.
- **`LwwValue.Merge` tie-break instability on equal HLC.** Concurrent writes with identical HLC timestamps no longer hash-order non-deterministically; ties are broken by `(OriginClusterId, payload bytes)` lexicographic order for byte-exact convergence across replicas.
- **Bounded retry on `StaleShardRoutingException`** across the public `ILattice` surface. Reshards and merges no longer surface a transient routing exception to user code; the public surface retries with a small bounded budget and only surfaces if the budget is exhausted.

### Migration notes

- **There is no in-place upgrade from v5.x.** The persisted leaf state shape, the WAL on-disk format, the WAL on-wire format, and the replication transport envelope shape have all changed.
- **Coordinated upgrade required across replication peers.** A v6.0.0 producer cannot ship to a v5.x receiver and a v5.x producer cannot ship to a v6.0.0 receiver. Schedule a maintenance window, drain replication queues, upgrade all peers in lockstep, then resume.
- **Azure Table WAL tenants must drain or reseed.** Existing rows under the configured `WalEntry` table are not readable by the v6 reader. The recommended path is to quiesce writes, drain replication, drop the WAL table, and let v6 reseed from leaf snapshots.
- The migration guide (core roadmap **F-021**) tracks the full upgrade runbook.
