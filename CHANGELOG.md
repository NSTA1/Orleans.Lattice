## [Unreleased]

Outstanding work is tracked on [GitHub Issues](https://github.com/NSTA1/Orleans.Lattice/issues), labelled `lattice` or `lattice.replication`. See [`docs/RELEASING.md`](docs/RELEASING.md) for the per-package tag-and-publish protocol.

### Security

- **Orleans.Lattice.Explorer.Web: the console now emits a `Referrer-Policy: no-referrer` response header.** The Explorer web head's baseline security-header middleware previously omitted `Referrer-Policy`, a member of the documented hardening set. Without it, a browser navigating from an authenticated console page to a foreign origin could leak the full request URL - which can carry tree, key, or subject context in its path or query - in the `Referer` header. The middleware now sets `Referrer-Policy: no-referrer` (behind the same "do not clobber an existing value" guard as the other headers) on every response on the Explorer branch, at the root and under a base path. No public API change.

## [8.0.0] - 2026-07-20

Coordinated family major release - every package in the family advances in lockstep to `8.0.0`. Alongside a wave of incremental improvements and a pre-release security-hardening pass, this release publishes several major new capabilities for the first time:

- **Explorer web console (`Orleans.Lattice.Explorer.Web`, plus the shared `Orleans.Lattice.Explorer.Core` / `.UI` / `.Backup` / `.Access` / `.Schema` / `.Entra` libraries).** An opt-in, embeddable, auth-aware web console for a running cluster: a tree browser plus fail-closed **Backups**, **Access** (groups, membership, and access-control policy), and **Schema** admin areas, sign-in against an auth-enabled State API, per-key live history, and a searchable identity-directory subject picker.
- **Model Context Protocol server (`Orleans.Lattice.Api.Mcp`) and its telemetry companion (`Orleans.Lattice.Api.Mcp.Telemetry`).** Exposes the cluster's state, data, backup, and auth facades - and read-only OpenTelemetry metrics - to an AI agent or MCP-aware tool as fail-closed, permission-scoped tools over streamable HTTP.
- **Schema control API (`Orleans.Lattice.Api.Schema` and its gRPC binding `Orleans.Lattice.Api.Schema.Grpc`).** A transport-agnostic facade for per-tree write-validation policy, envelope versioning, dead-letter inspection, remediation, and a read-only compliance audit.
- **Shared API contract (`Orleans.Lattice.Api.Abstractions`).** The API facades' service interfaces and their request/response DTOs are now a single, public, versioned package that the gRPC bindings and the MCP server consume directly.
- **Provider-agnostic identity-directory validation** across the membership and Explorer Access surfaces, with a zero-dependency in-process static roster and a Microsoft Graph (Entra) provider.

This release carries **breaking changes** - review the sections below and each affected package before upgrading:

- The API facade interfaces and DTOs moved into `Orleans.Lattice.Api.Abstractions` (binary-breaking for the API facade and gRPC binding packages; source- and wire-compatible once rebuilt).
- The inert membership user-record CRUD surface (`MembershipUser` and its directory/admin/gRPC/MCP surface, and the `sys-membership-users` tree) was removed (source- and wire-breaking for a consumer that used it; migrate group authoring to `AddMemberAsync` and subject search to an identity-directory provider).
- The replication receiver now rejects inbound writes for trees not enrolled for replication locally and dead-letters wire-merge-mode mismatches (behavioural for an already-deployed cluster; a correctly configured, symmetrically enrolled cluster pair is unaffected).

### Added

- **Explorer Access: the membership UI reflects the cluster's group-merge mode.** The `Orleans.Lattice.Explorer` Access area now reads whether locally-defined group membership is effective for authorization from the server (a new `LocalMembershipEffective` flag on `AccessModelDescriptor`, derived from `LatticeMembershipOptions.GroupMergeMode`) and adapts accordingly. Under a `TokenOnly` merge mode - where group membership is resolved solely from the identity-provider token - the group-create and member add/remove controls are disabled with an explanatory banner while staying read-only viewable, so an operator is not misled into editing inert membership; the Policies and Explain tabs stay fully live in every mode. `Union` and `DirectoryOnly` are unaffected. The gating is advisory: the server remains the fail-closed enforcement point. See [`docs/lattice.explorer/managing-access.md`](docs/lattice.explorer/managing-access.md) (#1260).

- **Explorer Access: provider-agnostic identity-directory validation and a searchable subject picker.** The `Orleans.Lattice.Explorer` Access area now validates every subject against a configured identity source instead of trusting a free-typed id. A new provider-agnostic identity-directory seam (`ILatticeIdentityDirectory` in `Orleans.Lattice.Membership`) backs a searchable, paged subject typeahead across users and groups everywhere the area picks a subject, and a fail-closed create form that blocks an unknown or wrong-kind principal and shows each provider's guidance on what a valid id looks like; a real-time access-state banner reports the cluster's authentication mode and warns when authorization rules are recorded but not enforced. The library ships two providers - a zero-dependency in-process static roster (`AddStaticIdentityDirectory`) and a Microsoft Graph-backed Entra provider (`Orleans.Lattice.Membership.Entra.Graph`, app-only, `User.Read.All` / `Group.Read.All`) - or a host plugs in its own; when no directory is configured the area degrades to unvalidated free-text and says so. Directory-search latency and hit / miss counts are published on the `orleans.lattice.membership` meter with bundled Grafana panels, and the Explorer sample gains a config-gated dual-mode (static by default, opt-in Entra) walkthrough. See [`docs/lattice.membership/identity-directory-providers.md`](docs/lattice.membership/identity-directory-providers.md) and [`docs/lattice.explorer/managing-access.md`](docs/lattice.explorer/managing-access.md) (#1244).

- **Orleans.Lattice.Explorer: an installable, opt-in web console with access-control and schema administration.** The Explorer web head is now published as an embeddable hosting library, `Orleans.Lattice.Explorer.Web`: a consumer adds it with `AddLatticeExplorerWeb(...)` and mounts it with `MapLatticeExplorer(...)` to host the read-only console inside their own ASP.NET app (at the root or a subpath), and the standalone web head runs on the same code path so the two cannot drift. The shared explorer libraries (`Orleans.Lattice.Explorer.Core`, `.UI`, `.Backup`, `.Access`, `.Schema`) ship as packages for the first time. The console gains two new capability-gated, fail-closed admin areas alongside Explore and Backups: an **Access** area to manage groups, membership, and access-control policy and explain effective permissions over the existing auth gRPC API, and a **Schema** area to manage per-tree write-validation policy, schema versions, dead letters, and a read-only compliance audit. The Schema area is backed by a new transport-agnostic schema control facade, `Orleans.Lattice.Api.Schema`, its code-first gRPC binding `Orleans.Lattice.Api.Schema.Grpc`, and a new compliance-audit scan in `Orleans.Lattice.Schema`. Because the console reaches a cluster only as a gRPC client, run it as an isolated head so its Blazor Server session-affinity requirement does not tax cluster scaling. See [`docs/lattice.explorer/running-the-explorer.md`](docs/lattice.explorer/running-the-explorer.md), [`docs/lattice.explorer/managing-access.md`](docs/lattice.explorer/managing-access.md), [`docs/lattice.explorer/managing-schema.md`](docs/lattice.explorer/managing-schema.md), and [`docs/lattice.api.schema/README.md`](docs/lattice.api.schema/README.md) (#1104, #1207, #1237, #873).

- **F-184 - Orleans.Lattice.Api.Mcp.Telemetry: read-only cluster telemetry over MCP.** A new opt-in companion package to `Orleans.Lattice.Api.Mcp` that exposes the cluster's OpenTelemetry metrics to an AI agent or MCP-aware tool as four read-only Model Context Protocol tools - instant query, range query, metric-name discovery, and metric metadata - backed by a Prometheus/PromQL HTTP proxy. The surface enforces a **dual-credential trust boundary**: the tools are unlocked only by a new cluster-wide `LatticeOperation.Telemetry` authorization grant (deliberately distinct from the data-plane operation set and never implied by it), the Prometheus backend credential is configured on the host and never exposed to the agent, and reads are constrained by an optional exact-or-wildcard metric allow-list and query time-range guardrails, with every backend failure mapped to a clean fail result rather than an unhandled error. Register it with `AddTelemetryTools` alongside the MCP server; it advertises the `telemetry` tool group only to callers holding the cluster-wide grant and stays inert until registered. See [`docs/lattice.api.mcp.telemetry/README.md`](docs/lattice.api.mcp.telemetry/README.md) (#1233).

- **F-182 - Orleans.Lattice.Api.Mcp: a Model Context Protocol server over the API facades.** A new `Orleans.Lattice.Api.Mcp` package exposes the cluster's four transport-agnostic API facades - state (read-only introspection), data (key/value reads and opt-in writes), backup (inspect and opt-in control), and auth (policy and membership introspection and opt-in administration) - as Model Context Protocol (MCP) tools an AI agent or MCP-aware tool can discover and call over streamable HTTP, built on the official `ModelContextProtocol` C# SDK. The surface is **fail-closed and permission-scoped**: an unauthenticated session is offered nothing, and an authenticated caller is advertised only the tool groups its effective authorization grants allow, with every tool call running the adapted facade under the caller's own credential so the facade's access gate authorizes the real caller. Each facade group is opt-in (`AddStateTools` / `AddDataTools` / `AddBackupTools` / `AddAuthTools`), mutating verbs are gated behind an explicit enable flag and carry a destructive hint, and the server runs either co-hosted on a silo (`AddLatticeMcp` + `MapLatticeMcp`) or as a standalone remote host that reaches the cluster over the existing gRPC API bindings (`AddLatticeMcpRemote`). See [`docs/lattice.api.mcp/README.md`](docs/lattice.api.mcp/README.md) (#1142).

- **Runtime backup scheduling from the Explorer creation form.** The backup creation form in the `Orleans.Lattice.Explorer` **Backups** area gains a *Schedule recurring* option: tick it and pick an interval in hours and minutes, and clicking **Backup** both captures immediately and registers a recurring backup of the selected tree, following the chosen full / incremental kind. This is backed by a new runtime scheduling path through the whole stack: `ILatticeBackupScheduler.ScheduleRecurringBackupAsync` and `ILatticeBackupSchedulerGrain.ScheduleRecurringAsync` register (or update) a durable Orleans reminder at a caller-supplied interval - overriding the startup-configured cadence for that kind and surviving silo restarts - clamped up to the scheduler minimum; a new `LatticeBackupControl.ScheduleBackupAsync` facade operation authorizes the scope with the same fail-closed grant as a capture; and a new `ScheduleBackup` gRPC RPC (with `BackupScheduleRequestMessage` / `BackupScheduleResponse` wire records, a `LatticeBackupApiOperation.ScheduleBackup` operation, and interceptor mapping) exposes it over the wire. The new `LatticeBackupScheduleRequest` record carries the scope, kind, and interval; scheduling targets a single tree, so it is unavailable for a multi-tree backup set. See [`docs/lattice.explorer/managing-backups.md`](docs/lattice.explorer/managing-backups.md).

- **F-180 - Orleans.Lattice.Explorer: backup and restore management area.** The Explorer gains a top-level area switcher above the per-tree detail tabs, with the existing tree browser as the **Explore** area and a new **Backups** area for backup and restore management. The area switcher is a registration seam - a future area joins it with a single entry - and it is capability-aware: an area or action the connected user cannot use renders disabled (greyed out) rather than hidden. Inside the Backups area the user can list the backups visible to them (scope, full / incremental kind, and creation time), capture a full or incremental backup of a scope, restore a backup into a target tree, and delete a backup; each control enables or disables per scope from an advisory capability report gathered once after sign-in and refreshed on an auth change. To power the grey-out, `Orleans.Lattice.Api.Backup` and its gRPC binding gain a **read-only capability probe** (`ProbeCapabilities`) that runs the same fail-closed access gate every operation uses and reports the caller's allowed-operation set for a scope with no side effects. The grey-out is advisory only: the server remains the fail-closed enforcement point, every real action is still authorized on the server when it runs, and a server denial surfaces as a clean "not permitted" affordance rather than an unhandled error. See [`docs/lattice.explorer/managing-backups.md`](docs/lattice.explorer/managing-backups.md) (#1131).

- **Chaos coverage for derived-state, routing, and cross-cluster recovery across a physical-identity swap.** Five new `[Category("Chaos")]` suites harden the restore-style cutover paths (a logical tree repointed to a freshly minted physical identity under its registry alias) under sustained load and fault injection, complementing the deterministic single-swap regressions that landed with the heal fixes. `ShippingRecoveryAcrossIdentitySwapChaosTests` (Orleans.Lattice.Replication) cycles the inter-site edge through partition and heal across single and repeated cutovers and asserts every peer re-resolves onto the new physical WAL and converges on the post-swap key set, with keys authored only into the abandoned identity while partitioned never reaching a receiver. `DerivedStateRecoveryAcrossIdentitySwapChaosTests` (Orleans.Lattice.Replication) drives a folded view through repeated cutovers with backlog accreting between drains and asserts the maintainer rebuilds-and-rebinds so dropped keys are retracted and only the final identity survives. `BackupRestoreReconcileChaosTests` (Orleans.Lattice.Backup) drives a real shadow-cutover restore under a large tagged working set with a concurrent reader, and repeated restores to earlier point-in-times, asserting the restore-fired tag-index reconcile narrows membership to exactly each restored subject. `ShadowCutoverRoutingSelfHealChaosTests` (Orleans.Lattice.Backup) warms many stateless-worker routing activations against a tree's pre-cutover identity under sustained concurrent reads, cuts over to a restored shadow, and asserts every activation self-heals onto the restored snapshot with no read ever surfacing the internal staleness signal and none left permanently stale - across repeated cutovers to successively earlier point-in-times. `CrossTreeAtomicWriteAcrossCutoverChaosTests` (Orleans.Lattice.Backup) fires a sustained stream of cross-tree atomic writes while one participant is repeatedly cut over underneath the saga, asserting the saga's deadline-bounded retry loops absorb the staleness signal (never leaking it) and that a fresh all-or-nothing batch still commits atomically on both trees afterward. No product code change: the suites confirm the shipped heal, reconcile, and self-heal retry paths hold under duress. See [`docs/lattice/chaos-tests.md`](docs/lattice/chaos-tests.md) and [`docs/lattice.replication/chaos-tests.md`](docs/lattice.replication/chaos-tests.md) (#1167).

- **F-164 - the state-explorer connects to an auth-enabled State API.** Teaches `Orleans.Lattice.Explorer` to authenticate against a State API that requires it, discovering the required sign-in mechanism from the server rather than being pre-configured for one. The server advertises its scheme through a new **unauthenticated** `GetAuthScheme` RPC (the single exemption in the gRPC auth interceptor; every data / catalog method stays enforced) that returns only public OIDC discovery parameters (authority, tenant, client id, audience) and is empty by default. The Explorer models sign-in as an extensible `IExplorerAuthMethod` provider seam: the built-in username/password (Basic) method is regression-safe (it still persists to the credential store exactly as before), while token-based schemes are resolved by matching the advertised scheme against registered providers and presenting the correct login challenge; an optional `Orleans.Lattice.Explorer.Entra` package plugs in Microsoft Entra interactive sign-in without the core taking a dependency on it. **Token lifecycle is managed transparently and correctly**: `ExplorerAccessTokenSource` refreshes proactively ahead of expiry (a clock-skew margin driven by an injected `TimeProvider`), collapses concurrent refreshes to a single in-flight call (a semaphore plus a generation counter so a racing caller adopts the winner's token instead of re-fetching), and latches a revoked refresh so a dead token is never retried in a loop; a mid-session auth failure triggers exactly one silent refresh-then-retry before the connection re-challenges the user. **Access tokens are never persisted** - only Basic username/password touches the credential store; every token scheme clears it and holds credentials in memory only, and the challenge runs before any session state is mutated so a cancelled or invalid login leaves the session untouched. The whole surface is opt-in: an Explorer pointed at an unauthenticated endpoint behaves exactly as before. See [`docs/lattice.explorer/connecting-to-an-auth-enabled-state-api.md`](docs/lattice.explorer/connecting-to-an-auth-enabled-state-api.md) (#1102).

- **F-144 - Orleans.Lattice.Explorer: History tab (per-key revision timeline, retention-mode aware).** A new History tab in the explorer detail panel renders a selected key's change-history timeline over the F-143 `GetEntryHistoryAsync` State API endpoint, for both CRDT and plain last-writer-wins keys. It reuses the Data tab's key selection (drill into a key in the Data tab, then switch to History, or type a key directly) and shows the active retention mode for the key as a badge. Each revision row carries its relative and absolute hybrid-logical-clock timestamp, originating replica / cluster id, and operation kind (set / delete / crdt-merge / range-delete), and renders adaptively to the per-row retention shape: a full-value (or value-retaining hybrid) LWW revision shows the JSON-aware value preview plus a line diff against the previous retained value; a metadata-only revision shows the value hash and length with an explicit "values not retained - metadata only" affordance and no diff; a CRDT revision shows decoded element-level member add / remove events with their originating replica rather than a raw blob. An inline divider marks a retention-configuration transition between adjacent revisions (for example `retention changed: full-value -> metadata-only`), derived purely from the per-row retention descriptors with no extra backend call. The page surfaces a prominent "history truncated by retention" banner only for the trimmed write-ahead-log fallback, a subtler bounded-by-age hint for the durable history view, and a WAL-window-fallback hint when no history view is enabled; a newest-first toggle and a "load more revisions" continuation page the timeline. New explorer types `IHistoryReader` / `HistoryReader`, `HistoryTimeline`, `HistoryPage`, `HistoryRevisionRow`, `HistoryMemberChange`, `HistoryValueDiff`, `HistoryDiffLine`, `RetentionTransition`, and the render-branch enums `HistoryRowRenderMode` / `HistoryDiffLineKind`, plus the `History` detail tab and the `AddExplorerHistory` registration (#956).

- **F-145 - Orleans.Lattice.Explorer: live follow mode for the History tab.** With a key open, the History tab now keeps its timeline live: it subscribes to the forward change feed (`ObserveChangesAsync`) scoped to the tree, filters client-side to the followed key, and appends each new mutation to the timeline in real time without a manual refresh, so the user watches history grow. A visible "Live" indicator with a pause / resume control sits above the timeline; while paused, incoming changes are buffered (and shown as a count) and flushed on resume so none is lost. A live-appended row is a lightweight metadata-only marker - it carries only the notification's kind, hybrid-logical-clock timestamp, and origin, with no value preview, line diff, or CRDT member list - clearly flagged as the live tail pending a durable backfill; the timeline never re-fetches per notification. Rows are de-duplicated against the already-loaded page by hybrid-logical-clock (the identifier both a loaded revision and a live notification carry), so the retrospective page and the live tail never double-count where they overlap. The subscription is torn down on key change and tab dispose (no leaked stream or background task). The live feed only carries changes emitted while the tab is open: it extends the timeline forward from "now" and is not a substitute for durable history retention of past changes. New explorer types `IHistoryLiveFollower` / `HistoryLiveFollower` and `HistoryLiveTail`, plus the `HistoryRowRenderMode.LiveTail` render branch and the live follow wiring on the `History` detail tab (#957).

- **Orleans.Lattice.Explorer: the Data tab's selected-entry detail now updates live.** With a key selected in the Explorer **Data** tab, its value / decoded CRDT current-state panel now refreshes automatically as the underlying entry is mutated, instead of staying frozen at the value read when the key was first opened. The detail subscribes to the forward state-API change feed (`ObserveChangesAsync`) scoped to the tree, filters client-side to the selected key (an exact match, or a range delete whose swept range covers it), and on a match debounces a silent re-read (`GetEntryAsync`) that swaps the displayed value and decoded CRDT members with no spinner - so a CRDT key's members appear and disappear in step with the writes. A connection-state-mirrored "Live" indicator sits in the detail header and a non-fatal "Live updates stopped" note surfaces a dropped subscription, mirroring the History tab. The subscription is torn down on key change and tab dispose (no leaked stream or refresh loop), and the live wiring degrades gracefully when the change-feed services are not registered. The live feed only carries changes emitted while the tab is open. New explorer types `IEntryLiveFollower` / `EntryLiveFollower` and the `EntryChangeSignal` value type (#1018).

### Changed

- **Breaking - removed the inert membership user-record CRUD surface.** The
  per-user *record* concept - `MembershipUser` and its
  `ILatticeMembershipDirectory.UpsertUserAsync` / `GetUserAsync` / `ListUsersAsync`
  / `RemoveUserAsync` methods, the `AuthUser` / `AuthUserPage` DTOs and the four
  `ILatticeAuthAdmin` user methods, their `Orleans.Lattice.Api.Auth.Grpc` RPCs
  (`UpsertUser` / `GetUser` / `RemoveUser` / `ListUsers`) and wire types, the four
  `Orleans.Lattice.Api.Mcp` `lattice_auth_*_user` tools, the Explorer Access
  **Users** tab, and the reserved `sys-membership-users` tree (dropped from
  `LatticeSystemTreeNames` and from `ReplicateLatticeSystemTrees` enrolment) - is
  removed. **Why:** these records were **inert for authorization**. The access
  path resolves a subject's groups from its token claims, its asserted groups, and
  the membership *edges* it participates in (`sys-membership-edges`) - never from a
  stored user record - so a `MembershipUser` never affected a single allow/deny
  decision. Its only effect was to introduce a **third, confusing "user" concept**
  alongside the two that carry real weight: the **State-API credential user** (a
  deployment-time credential that gates the read-only State API, provisioned with
  `tools/New-LatticeStateCredential`) and the **static identity-roster user** (an
  entry in an `ILatticeIdentityDirectory` that backs the searchable subject picker
  and friendly-name display). Group membership is still authored through membership
  **edges** (`AddMemberAsync`, unchanged), friendly names still come from the
  identity directory, and `MembershipGroup` and the edge trees are non-inert and
  fully retained. Removing the dead surface eliminates the ambiguity and a
  maintenance burden with no loss of function. This is source- and wire-breaking
  for a consumer that called any of the removed members or persisted to the
  removed tree; migrate group authoring to `AddMemberAsync` and subject
  search/validation to an identity-directory provider.

- **Orleans.Lattice: `MvRegister.MergeDelta` folds a typed delta in place instead of building a throwaway register.** Applying an `MvRegisterDelta` to a live multi-value register previously constructed a transient `MvRegister` (copying the delta's entries into a fresh `List<MvRegisterEntry>` and its context into a fresh `Dictionary`) purely to hand it to `MergeFrom`. Every other CRDT primitive already folds its delta directly, and `MergeDelta` is on the CRDT apply / replication receive hot path, so those three allocations were paid on each delta applied. The fold now applies the delta's entries and context to the receiver directly, keeping the dot-context dominance semantics byte-for-byte identical (verified by an equivalence regression test against the previous `MergeFrom` form). Measured with a new `Crdt mvregister merge delta` microbenchmark (8 disjoint-replica live entries, idempotent same-dots delta): allocated bytes per apply drop from 1768 B to 496 B (about -72%) and the median fold latency from ~820 ns to ~655 ns. No public-API or wire-format change.

- **Extracted the shared API contract into a new `Orleans.Lattice.Api.Abstractions` package.** The four API facades' service interfaces (`ILatticeStateQuery`, `ILatticeStateObserver`, `ILatticeStateMetricsObserver`, `ILatticeDataApi`, `ILatticeAuthAdmin`, `ILatticeBackupControl`) and their request / response models now live in a single, versioned `Orleans.Lattice.Api.Abstractions` package and are `public`, so the gRPC bindings and the `Orleans.Lattice.Api.Mcp` server consume the contract directly instead of through cross-package `InternalsVisibleTo` grants into the facade and core assemblies. The interfaces and models keep their original `Orleans.Lattice.Api.{State,Data,Auth,Backup}` namespaces and their Orleans serialization aliases, so the change is source- and wire-compatible: a consumer that rebuilds against the new packages needs no code change, and persisted or in-flight payloads are unaffected. It is **binary-breaking** for the affected API facade and binding packages, since the moved public types change assembly, so those packages will require a major version bump when they are next released. A new public `LatticeSystemOrigin` seam in the core library gives a co-hosted infrastructure consumer the trusted system-origin scope the MCP server previously reached through an internal-visibility grant. See [`docs/lattice.api.abstractions/README.md`](docs/lattice.api.abstractions/README.md) (#1234).

### Fixed

- **Security hardening across the admin, replication, and telemetry surfaces (pre-v8 remediation).** A coordinated pass closed six verified security gaps found in a pre-release audit, making fail-closed enforcement the default on every affected boundary. The `Orleans.Lattice.Api.Mcp` tool authorizer is now consulted at both tool advertisement and tool invocation through one lock-step gate, so tools stay denied until a host explicitly opts in an authorizer (secure by default). The `Orleans.Lattice.Api.Mcp.Telemetry` metric-name allow-list rejects any unparseable, negated, or non-exact `__name__` matcher instead of letting it bypass the list. The `Orleans.Lattice.Replication` receiver drops inbound batches for trees not enrolled for replication locally and dead-letters batches whose wire merge-mode disagrees with the locally-resolved mode, re-resolving the mode locally rather than trusting the wire header. The `Orleans.Lattice.Membership` / `Orleans.Lattice.Api.Auth` administrative create paths validate a supplied principal against the identity directory when `ValidationRequired` is set and a real provider is active, rejecting an unknown or wrong-kind id fail-closed via the new public `LatticeDirectoryValidationException`. The `Orleans.Lattice.Explorer` web console isolates each operator's auth session and cluster connection to its own Blazor circuit - completing the login/logout CSRF hardening, which had noted the process-global session as an outstanding risk - and emits anti-clickjacking security response headers (Content-Security-Policy `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`) on every response. Of these, only the replication receiver change is behavioural for an already-released package: a correctly-configured cluster pair (both sides enrolling the same trees with the same mode) is unaffected, but a misconfigured or non-enrolled inbound stream that was previously applied is now rejected; the MCP, telemetry, and Explorer surfaces are unreleased, so their hardening is not a breaking change. See [`docs/lattice.api.mcp/security.md`](docs/lattice.api.mcp/security.md), [`docs/lattice.api.mcp.telemetry/security.md`](docs/lattice.api.mcp.telemetry/security.md), [`docs/lattice.membership/identity-directory-providers.md`](docs/lattice.membership/identity-directory-providers.md), and [`docs/lattice.explorer/running-the-explorer.md`](docs/lattice.explorer/running-the-explorer.md) (#1270).

- **Release engineering: the publish workflow no longer inflates cross-package dependency floors.** `.github/workflows/publish.yml` stamped the release version as a global MSBuild property (`-p:Version` on build, `-p:PackageVersion` on pack), so every ProjectReference'd project in the graph evaluated to the tag version and each packed package emitted its intra-family dependency floors at the tag version instead of the referenced package's real published version. Whenever a referenced package's real version was lower than the tag (the normal case in a per-package patch wave), this silently shipped un-restorable packages - a package requiring, say, `Orleans.Lattice >= 7.9.3` when core was only ever published at 7.9.1. The workflow now trusts each csproj's own `<Version>` as the single source of truth (no global version override), so a packed package's dependency floors resolve to each referenced package's real version; and a new pre-restore guard step reads the packed csproj `<Version>` with `dotnet msbuild -getProperty:Version` and fails the release if it has drifted from the release tag, so a mis-versioned package can no longer be published. CI / release-tooling change only; no library, wire-format, or public-API change.

- **Orleans.Lattice.Api.Backup.Grpc / Orleans.Lattice.Explorer: a restore that fails a precondition now surfaces an actionable reason instead of an opaque internal error.** A restore that could not proceed - most notably a coordinated (replicated-tree) restore whose backup sink is not actually shared across every participating cluster, so a peer cannot resolve the sibling-captured backup and the saga aborts - threw a `LatticeRestoreValidationException` that the gRPC control service mapped to a generic `Internal: "The backup control-API request failed."`, giving the Explorer nothing to show. The service now maps `LatticeRestoreValidationException` to `FailedPrecondition` carrying its (id / tree / byte-count, no-secret) message, and the Explorer's Backups area recognises the unshared-sink signature and renders a friendly "the backup store must be reachable from every cluster" configuration message rather than a raw error. Additionally, the `MultiSiteManufacturing` sample now provisions a dedicated shared Azurite blob account (`azurite-backup`) multi-homed onto both cluster networks and points every silo at it through `Orleans.Lattice.Backup.AzureBlob`, so its coordinated restore actually works under `docker compose` instead of relying on a per-container filesystem path that is not shared; the single-machine `FileSystemBackupSink` path remains the fallback. Explorer and sample changes plus a `FailedPrecondition` mapping in the gRPC binding; no wire-format change to the package family.

- **Orleans.Lattice.Explorer: a replicated CRDT change now renders in entry history as a membership snapshot, not a raw full-value blob.** Follow-up to FX-062. A single CRDT change appeared on the receiving cluster as a `CrdtDelta` member diff, but a later anti-entropy / committed-projection resync still shipped a full-state row (`Set`, value = whole serialized OR-Set/PN-counter/OR-Map, no delta) that recorded as a full-value set and rendered as a raw blob tripping the explorer's value-preview cap - confusing duplicate-looking noise on CRDT trees. The history row already carries the source merge mode, so the explorer now classifies a CRDT-mode `Set` as a membership snapshot (decoded members, visually distinct from an LWW overwrite) rather than a last-writer-wins value diff; LWW sets still render as value diffs. Replication apply correctness and wire format are unchanged - bootstrap full-state stays a correct full-state merge, it just renders nicely. Presentation/classification fix in `Orleans.Lattice.Explorer`; no public-API or wire-format change (#1010).

- **Orleans.Lattice.Explorer web head now enforces antiforgery on the sign-in / sign-out endpoints (login / logout CSRF hardening).** The web head's `/auth/login` and `/auth/logout` form-post endpoints previously called `.DisableAntiforgery()`, justified by `SameSite=Strict` on the credential cookie - but that cookie is not presented on the login POST itself, so it gave no CSRF protection. A cross-site form post could drive a victim's browser to authenticate (or sign out) the Explorer with attacker-chosen credentials, and because the auth session is a process-global singleton this flipped the shared connection's credential for the whole process. Both endpoints now validate a `RequestVerificationToken` (the login and logout forms embed `<AntiforgeryToken />`) and reject a tokenless or mismatched post with `400 Bad Request` before touching the auth session. Explorer-only change; no public-API or wire-format change to the package family. (#966)
