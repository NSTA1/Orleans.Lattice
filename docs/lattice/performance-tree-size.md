# Performance: tree size

This page shows how point-read latency changes as one tree grows, and how many
keys a tree can hold before its P95 read latency degrades against the same
cluster's small-tree baseline. The
tables are regenerated by `benchmark/tree-size-report.ps1` on the Layer 3
multi-silo rig (Azure Container Apps). The producer runs in its own container
as an Orleans client, separate from the silos, so every latency below is what
a client sees, network hop included.

The other performance pages read a small keyspace that sizes with the offered
load. Here the keyspace is the whole tree: one tree is grown in segments,
and after each segment the cluster reads uniformly over every key it holds.
The design ladder runs to 30 million keys. The run published here is the
100 k-key validation of the method; the larger rungs are being re-run, see
[Where the ladder stops](#where-the-ladder-stops).

See also [Performance: single silo](performance-single-silo.md),
[Performance: multi-silo scaling](performance-multi-silo.md) and
[how Layer 3 is measured](performance-methodology-layer3.md).

## The short answer

At 100 k keys a warm cluster serves uniform point reads at about 1.1 ms P50
and 3.75 ms P95 on one silo, and about 2.9 ms P50 and 8.55 ms P95 on four.
Three independent runs per silo count read every seeded key back with no
missing or wrong values.

That size is the baseline every larger size is graded against, so this run
does not yet locate a knee: it validates the seed, the read check and the
grading before the larger rungs are spent. Earlier attempts at 1 M and 3 M
keys found correctness and recovery defects instead of a knee; see
[Where the ladder stops](#where-the-ladder-stops).

## How it is measured

- **One tree, grown in place, per silo count.** Each silo count runs one
  producer execution against fresh storage. It grows one tree rung by rung,
  bulk-appending only the keys each rung adds
  (`ILattice.BulkAppendChunkAsync`, 16,384 keys per chunk, 245-byte values),
  so reaching 30 M keys costs one 30 M-key seed rather than 44 M.
- **Reads run on the warm cluster that seeded the tree.** After each rung's
  seed lands, the same silos are read for 60 s. The tree is not reopened by a
  new cluster between rungs: a bulk-loaded tree opened by freshly started
  silos replays its write-ahead log leaf by leaf before it can serve, so a
  cold cluster measures recovery, not reads. Cold-start latency is listed
  below as a separate measurement.
- **Uniform reads over the whole tree.** The producer reads with
  `ILattice.GetAsync`, striding over every seeded key, at
  1,000 vehicles x 5 Hz per silo (5,000 reads/s per silo offered).
- **Latency is measured by the client.** Each read is timed in the producer.
  The tables report the quantiles of the steady window (t >= 15 s), taken as
  the upper edge of a fixed histogram bucket, so a figure is an upper bound
  on the true quantile.
- **Degradation is relative to the small tree.** Each silo count's
  smallest consistent size is its baseline. A larger size is degraded when
  its median P95 is at least 1.5 times the baseline's (`-KneeFactor`) and
  its fastest repeat is slower than the baseline's slowest, so the two
  bands do not overlap. The knee is the first degraded size. A fixed budget
  is not used: at single-digit milliseconds it would grade the client round
  trip, not the tree.
- **Every read is checked.** The seed writes a value derived from each key's
  index, so the producer compares every value it reads with the one seeded. A
  wrong or missing value grades the size `INCONSISTENT`, whatever its
  latency. It is the only hard failure, and an inconsistent size is never a
  baseline.
- **Repeats bound the variance.** With repeats, each size reports the median
  P95 with its range across runs in square brackets. A spread above 30% of
  the median that is also wider than 3 ms is flagged `(wide)`. The flag is
  advisory: at a few milliseconds one slow run moves the spread by more than
  30%, so it never fails a size on its own.

## Where the ladder stops

Earlier attempts at larger sizes stopped on defects rather than on read
latency. The fixes are in place and the 300 k, 1 M, 3 M, 10 M and 30 M rungs
will be re-run against them.

- **Bulk-loaded leaves carried no checkpoint ([#6152](https://github.com/NSTA1/Orleans.Lattice/issues/6152)).** A leaf filled by
  `BulkAppendChunkAsync` wrote its entries to the write-ahead log but never
  persisted a grain-state checkpoint, so every reactivation replayed its log
  before it could answer. At 3 M keys reads queued behind that replay and
  the read phase froze; an earlier 10 M attempt failed at about 7.4 M keys
  with `LatticeSaturatedException` from the same backlog.
- **Seed throughput fell as the tree grew ([#6153](https://github.com/NSTA1/Orleans.Lattice/issues/6153)).** The storage
  account's transaction rate fell from about 229,000 to about 80,000 per
  minute over a 3 M seed, so a 30 M seed would have run for many hours.
- **A retried seed chunk could lose keys.** A chunk whose first attempt
  failed part-way, under storage saturation, could be laid out again on retry
  with leaf ranges that excluded some of its keys. A 3 M run read back about
  one leaf's worth of keys per affected shard as missing. Retries now keep
  the first attempt's layout, and the read check exists to catch this class
  of defect.

## What these numbers do not tell you

- **Cold start.** Every read runs on silos that already hold the tree. How
  long a freshly started cluster takes to serve a large bulk-loaded tree is
  governed by write-ahead-log replay and is a separate measurement.
- **Mixed read and write load.** The ladder reads only. Writes during the
  ladder would add splits and WAL traffic; that is a separate measurement.
- **Skewed reads.** Every key is read equally often. A workload whose hot set
  is much smaller than the tree reads more like a smaller tree.
- **Organically grown trees.** A bulk-appended tree has full leaves. A tree
  grown by ordinary writes has leaves about half full, so it has about twice
  as many leaf grains for the same key count.
- **Other value sizes, larger silos and other storage accounts.** Values are
  245 bytes, Container Apps caps a replica at 8 GiB, and every cohort shares
  one Azure Storage account.

## Re-running it

```powershell
./benchmark/azure-throughput/scripts/deploy-aca.ps1 -NamePrefix <prefix>
./benchmark/tree-size-report.ps1 -NamePrefix <prefix>
az group delete --name rg-<prefix> --yes --no-wait
```

`-Resume` picks up an interrupted sweep from its saved state, `-DryRun`
re-renders this page from that state, and `-Sizes`, `-SiloAxisSizes` and
`-SiloCounts` change the grid, and `-Repeats` runs each ladder several times.
`-KneeFactor` sets the ratio to the baseline at which a size degrades, and
`-SpreadGatePct` and `-SpreadFloorMs` set the spread above which a size is
flagged `(wide)`. With `-DryRun` these grading options regrade the saved
results without re-running anything. `-DegradeP95Ms` and `-DegradeFactor` are
retired and ignored. See
[the rig's README](../../benchmark/azure-throughput/README.md#tree-size-sweep)
for every option.
