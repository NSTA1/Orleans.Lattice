# Performance: tree size

This page shows how point-read latency changes as one tree grows, and how many
keys a tree can hold before its P95 read latency leaves a fixed budget. The
tables are regenerated by `benchmark/tree-size-report.ps1` on the Layer 3
multi-silo rig (Azure Container Apps). The producer runs in its own container
as an Orleans client, separate from the silos, so every latency below is what
a client sees, network hop included.

The other performance pages read a small keyspace that sizes with the offered
load. Here the keyspace is the whole tree: one tree is grown in segments to
30 million keys, and after each segment the cluster reads uniformly over every
key it holds.

See also [Performance: single silo](performance-single-silo.md),
[Performance: multi-silo scaling](performance-multi-silo.md) and
[how Layer 3 is measured](performance-methodology-layer3.md).

## How it is measured

- **One tree, grown in place, per silo count.** Each silo count runs one
  producer execution against fresh storage. It grows one tree rung by rung,
  bulk-appending only the keys each rung adds
  (`ILattice.BulkAppendChunkAsync`, 16,384 keys per chunk, 245-byte values),
  so reaching 30 M keys costs one 30 M-key seed rather than 44 M.
- **Reads run on the warm cluster that seeded the tree.** After each rung's
  seed lands, the same silos are read for 60 s. The tree is not reopened by a
  new cluster between rungs: a bulk-loaded tree opened by freshly started
  silos replays its write-ahead log leaf by leaf before it can serve, so a
  cold cluster measures recovery, not reads. Cold-start latency is listed
  below as a separate measurement.
- **Uniform reads over the whole tree.** The producer reads with
  `ILattice.GetAsync`, striding over every seeded key, at
  1,000 vehicles x 5 Hz per silo (5,000 reads/s per silo offered).
- **Latency is measured by the client.** Each read is timed in the producer.
  The tables report the quantiles of the steady window (t >= 15 s), taken as
  the upper edge of a fixed histogram bucket, so a figure is an upper bound
  on the true quantile.
- **The budget is absolute.** A size is within budget when its P95 is at or
  below 5 ms, roughly one Azure Tables round trip.

## What these numbers do not tell you

- **Cold start.** Every read runs on silos that already hold the tree. How
  long a freshly started cluster takes to serve a large bulk-loaded tree is
  governed by write-ahead-log replay and is a separate measurement.
- **Mixed read and write load.** The ladder reads only. Writes during the
  ladder would add splits and WAL traffic; that is a separate measurement.
- **Skewed reads.** Every key is read equally often. A workload whose hot set
  is much smaller than the tree reads more like a smaller tree.
- **Organically grown trees.** A bulk-appended tree has full leaves. A tree
  grown by ordinary writes has leaves about half full, so it has about twice
  as many leaf grains for the same key count.
- **Other value sizes, larger silos and other storage accounts.** Values are
  245 bytes, Container Apps caps a replica at 8 GiB, and every cohort shares
  one Azure Storage account.

## Re-running it

```powershell
./benchmark/azure-throughput/scripts/deploy-aca.ps1 -NamePrefix <prefix>
./benchmark/tree-size-report.ps1 -NamePrefix <prefix>
az group delete --name rg-<prefix> --yes --no-wait
```

`-Resume` picks up an interrupted sweep from its saved state, `-DryRun`
re-renders this page from that state, and `-Sizes`, `-SiloAxisSizes` and
`-SiloCounts` change the grid. See
[the rig's README](../../benchmark/azure-throughput/README.md#tree-size-sweep)
for every option.
